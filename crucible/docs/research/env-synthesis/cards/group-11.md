# Group 11 reading cards (CUA and MCP benchmarks, GUI RL, tool simulators, user simulators)

**Batch summary.** 29 papers. Read FULL: 21. PARTIAL: 8 (UI-TARS, OpenCUA, Non-Collaborative Users, Lost in Multi-Turn, SimulatorArena, MirrorBench, UserBench, UserRL; in each the main text was read in full and only parts of long appendices were skipped). ABSTRACT-ONLY: 0. All texts came from the arXiv HTML.

**Five cross-paper takeaways for Part 2.**
1. **Executed checks beat judged rewards, and the gap is large.** ZeroGUI's VLM reward (precision 61.5% at best) gave +2.5 points on OSWorld. Execution-checked RL on the same benchmark gave +14.6 (DART-GUI) and up to 48.9% absolute (ComputerRL). The base models and action spaces differ, so the comparison is only indicative. The commonest judge error is accepting a claimed completion that never happened: 45% of LiveMCPBench's judge errors. Judges must never see the policy's self-report. For read-only answers, use atomic claims derived from the World's end state, one judge call per claim (MCP-Atlas). This supports §3.0 rule 2 and argues against any LLM-scored "solvability" gate (MCP-Bench, StableToolBench).
2. **The simulated user is part of the World, and it moves measured difficulty.** Swapping only the user LLM moved τ-bench success by about 9 points, and a one-line politeness tweak moved 11 of 18 tasks to a different difficulty bin (Lost in Simulation). Simulated users are about 5× too verbose and too cooperative (SimulatorArena, MirrorBench). Pairwise realism judges prefer their own family. Designs that work keep task state and reward in code with the LLM only voicing the user (UserRL), shard the goal into information pieces with a delivery tracker (Non-Collaborative Users; Lost in Multi-Turn), and turn hard user behaviours into separate modules, not prompt text. Implications: record the user-simulator id and version in provenance, key p̂ by (task, student, simulator), and add a simulator-swap probe to F10.
3. **Construction-based task generators exist for state Worlds, and their knobs are explicit.** Four patterns carry over directly. AndroidWorld: seeded parameters, noise rows, state check, teardown. UserBench: a preference bank × validated implicit phrasings, with best/correct/wrong/noise rows seeded so the answer key is built in. Lost in Multi-Turn: spec sharding, gated by executed Concat and Shuffle-concat runs at ≥ 0.8 of Full. MCPMark: "evolve harder", then perturb the solved end state by hand to prove the checker flips. Each gives a knob that does not need new ground truth: preferences per facet, shard count, distractor rows, tools or servers, retrieval k, user behaviour mode, observation format.
4. **Per-instance variance is large and partly structural, so p̂ needs seeds, not just repeats.** One AndroidWorld seed (an off-screen category that needs a scroll) can make a task look unsolvable. OpenCUA's Pass@1 vs Pass@16 is 20% vs 39% when only the system date differs. The best-to-worst spread on the same instruction is about 50 points in multi-turn (Lost in Multi-Turn). MCPMark's pass^4 is about a third below pass@1. F9 should therefore sample several seeds and clock offsets per task. Seed parameters that change the behaviour signature should become declared knobs or separate cells (F7).
5. **Sparse-reward pool management is a solved pattern, but small benchmark pools do not transfer.** The pieces: admit tasks with baseline pass@16 > 0 (ARPO); inject a stored success into all-fail groups (ARPO, DART); cut rollouts once a task's p̂ passes about 0.6; cap each task's horizon at its longest observed success (DART). For Crucible, the F4 oracle trajectory can be the injected positive for below-band tasks. But all of these papers train on OSWorld's own tasks, and held-out gains are about zero (ARPO: 55.2 → 56.3). Two hacks need explicit guards: a harness that writes FAIL on the agent's behalf earns reward on infeasible tasks (ARPO), and dropping generated infeasible tasks halves refusal ability (ZeroGUI).

## 2606.29537 — OSWorld 2.0: Benchmarking Computer Use Agents on Long-Horizon Real-World Tasks (XLANG Lab and collaborators, 2026; arXiv)
Read: FULL (main text; appendices C.2 website framework, E.1 judge and user-sim validation, E.2 safety checks, F annotation).  Relevance to Part 2: medium-high. It is a hand-built benchmark, not a synthesis pipeline, but its World design (self-hosted stateful services, coherent user profile, injected mid-task events, bounded simulated user), its checkpoint rubric and its two-sided QA (hack audit and false-negative audit) are exactly the ingredients F1, F2, F5 and F6 need.
**Problem.** Desktop benchmarks are saturated (Opus 4.8 at 83.5% on OSWorld-Verified) because tasks are short and single-app; the authors want multi-hour, cross-app workflows with hidden state and a changing World.
**Method / algorithm.**
1. Task collection: about 90% from internally trained annotators who study a domain (tutorials, docs, use), draft a task (instruction, input artifacts, expected end state) from Reddit, tutorials and their own work, then a second annotator cross-checks feasibility, redundancy and rubric ambiguity. Minor channels: practitioner interviews (good, expensive), questionnaires (low yield; respondents cannot calibrate complexity), and LLM-synthesised proposals, which showed three defects: unrealistic artifacts, shallow workflows that glue unrelated operations, and hack risk from unanticipated alternative solutions. LLM proposals are used only as idea aids.
2. Environment: the OSWorld VM plus 31 self-hosted web services (email, bank, team chat, travel, visa, insurance, conference portals). Each site is a Next.js app with `/api/state` (load, reset, export a JSON state envelope), `/api/files`, `/health`, and a `/state-manage` authoring page; state is scoped by a `user_id` cookie so many task instances share one container. Caddy routes `app.localhost`. The open web stays reachable for search.
3. Initial state per task: files, open docs and tabs, site records, message history, all consistent with one user profile (ids, dates, amounts agree across sources). Synthetic records only where privacy or control requires.
4. Simulated user with bounded, configured knowledge behind an ASK_USER channel. Dynamic hooks inject emails or chat messages mid-run that change the semantic task state (distinct from "streaming" UI that moves between observation and action).
5. Ten non-exclusive phenomenon tags per task (cross-source reasoning 42.6%, visual-spatial precision 41.7%, implicit-state inference 39.8%, multi-item tracking 39.8%, conflict disambiguation 36.1%, multimodal editing, tutorial following, dynamic environment 9.3%, streaming 5.6%, proactive interaction 5.6%).
**Verification / grading.** Final state scored against all checkpoints in any order (mean 27.25 per task) to allow alternative paths; binary = all checkpoints. Functional checks first; model judges only as objective binary checklist items, each judge prompt validated on correct and confusable-wrong states; judges supply 11.53% of total score and never more than 50% of any task. QA stack: (a) a coding agent generates unit tests for the rubric over expected solution paths; (b) two humans re-solve end to end; (c) several frontier agents roll out to reveal unanticipated solutions. Two audits: reward hacking (exploiting files, APIs, browser storage, project metadata; example: route checker that only checks waypoints accepts a driving route) and false negatives (rigid checks penalising harmless format). Separate side-effect checks (credential leak of planted fake secrets, disk exhaustion, document integrity, privileged group membership, leftover processes, sandbox bypass, sudoers, xhost). Judge validation: 20 tasks × 3 states, Sonnet 4.6 98.5% agreement; user sim: 20 tasks × 20 states, human-verified 95.8–100%.
**Scale & cost.** 108 tasks; median human time 1.6 h (48× OSWorld 1.0); 2.44 apps per task; Opus 4.7 averages 318 tool calls. Eval cost about $72/task (Opus 4.8 batched), $25.5 (GPT-5.5), $2.4–6.6 (open models). AWS t3.2xlarge, residential proxy.
**Key results.** 500 steps: Opus 4.8 batched 20.6% binary / 54.8% partial; GPT-5.5 13.0/49.5 at 37K output tokens; Qwen 3.7-Plus 2.8/21.5; Kimi 2.6 4.6. Partial scores cluster at 41–54% for all strong agents; extra inference buys partial credit, not completion. Binary falls to 0 for tasks over 163 human-minutes. Human-easy tasks are often agent-hard (only 11.1% of human-easy tasks are agent-easy), driven by perception timing and multimodal verification. Agents spend under 7% of budget on recovery and repair. Exposure attribution (Handled / Blocked / Untested per phenomenon) shows hidden-state phenomena are the main blockers. Unsafe behaviour: 33% of tasks bypass the UI (Opus 4.7: 35 system-level changes), 14% read hidden browser state.
**Failure modes & limits.** Mostly human-built (does not scale to 1000); one run per model for behaviour analysis; GPU-free but costly evals; phenomenon tags are annotator labels. My critique: partial checkpoint credit with order-free scoring invites checkpoint farming in RL; "binary = all checkpoints" makes long tasks near-zero signal for a 35B student.
**Tips & tricks.**
- Expose every World service through one state API (load, reset, export JSON) plus cookie-scoped tenancy, so many tasks share a container.
- Score the end state against an unordered checkpoint set so alternative paths pass.
- Validate every judge prompt on correct and confusable-wrong states before use; cap judge share per task.
- Run a separate side-effect suite with planted fake secrets (canary credentials).
- Use exposure attribution (Handled / Blocked / Untested) instead of raw per-tag scores, so a tag is only blamed when the agent reached it.
- Treat LLM task proposals as ideas: they glue unrelated operations and miss alternative solutions.
**Fit to Crucible Part 2.** F1/F2: adopt the state-envelope API and coherent-profile seeding (one profile, consistent ids across Apps) as the SeedBundle contract; injected events map to the clock/events World facet and `timing_checks`. F3 diversity: the ten phenomena are a ready-made scenario-type axis for the DomainSpec grid (dynamic environment, conflict disambiguation, implicit state, proactive ask). F5/F6: copy the two-sided audit (hack and false-negative), the planted-canary collateral checks, and judge validation on confusable states (anchor set). F10: exposure attribution is the intent-audit primitive "did the failure happen at the intended skill". Avoid: checkpoint-sum rewards without collateral; human-heavy authoring. Priority P1.

## 2510.24563 — OSWorld-MCP: Benchmarking MCP Tool Invocation In Computer-Use Agents (Jia et al., 2025; arXiv)
Read: FULL (main text, ablations, appendix cases and tool list).  Relevance to Part 2: medium. Its tool-synthesis pipeline (solve tasks with code, keep code that passes, wrap it as tools, filter task-specific tools) is a small F1 precedent, and its "when should a tool be used" metric is an intent signal; the benchmark itself is a thin layer over OSWorld.
**Problem.** GUI-only CUA benchmarks are unfair to agents that also call tools; no benchmark measures when a CUA should pick an MCP tool over GUI actions.
**Method / algorithm.**
1. Code generation: o3, with a CoAct-style prompt, writes code solutions for each OSWorld task over multi-turn interaction.
2. Code filter: o3 summarises the usable code; the summary is re-run on the task and kept only if it completes it. Yield: 72 verified solutions.
3. Tool wrap: o3 packages each verified solution as an MCP tool (prompted wrapper).
4. Add 192 tools curated from existing MCP servers; total 264. Two GUI-agent experts review each tool; keep only if both approve; drop task-specific tools and functional duplicates. Result: 158 tools over 7 apps (no GIMP or Thunderbird servers because of version constraints), of which 25 are deliberately non-target distractors.
5. Annotators label each of 361 tasks as Tool-Beneficial (250; some tool makes it substantially more efficient) or Non-Tool-Beneficial (111). 153 tasks need multi-round tool calls.
6. At run time, tools for the current app are pre-selected by RAG; the agent chooses per step between MCP tools and 11 GUI primitives.
**Verification / grading.** OSWorld's original execution-based evaluators (unchanged). New metrics: Tool Invocation Rate TIR = (n_t + n_g)/(N_t + N_g), where n_t counts successes on tool-beneficial tasks that used a tool and n_g successes on non-tool-beneficial tasks that used none; Average Completion Steps. Hackable surface: tools derived from task solutions can collapse a task to one call, so accuracy gains partly measure tool-to-task leakage; the authors' filter for "task-specific" tools is human judgment only.
**Scale & cost.** 158 tools, 361 tasks, 3 runs per configuration, step caps 15 and 50. No cost reported.
**Key results.** MCP raises accuracy for most models: o3 8.3 → 20.4 (15 steps), Gemini-2.5-Pro 7.4 → 20.5, Claude 4 Sonnet 40.1 → 43.3 (50 steps), Agent-S2.5 47.1 → 49.5. Best TIR only 36.3% (Claude 4 Sonnet); Qwen2.5-VL-72B 10.9% and its steps rise with tools. TIR correlates with accuracy; ACS does not. Accuracy and TIR drop as the number of available tools per task rises; tasks needing four tool rounds: 0% GUI-only, 16.7% with MCP (Claude). Ablations on Gemini-2.5-Pro: removing RAG (all 158 tools in context) cuts accuracy 20.5 → 15.5 and TIR 16.8 → 11.6; randomly shuffling tool order raises accuracy 20.5 → 22.7 (order effects of about 2 points; they fix lexicographic order).
**Failure modes & limits.** Single-environment (OSWorld) evaluators reused; tool-beneficial labels are human; TIR conflates "used a tool" with "used it correctly". Order and retrieval sensitivity mean scores depend on harness choices. My critique: generating tools from the very tasks they are evaluated on is a contamination pattern Crucible must not copy for training tasks.
**Tips & tricks.**
- Keep a generated tool only if its code, re-run, actually completes a task (execution filter).
- Include non-target distractor tools in every tool menu.
- Fix tool-description order and the tool retrieval step; both move scores by 2–5 points.
- Measure "tool used when it should be, not used when it should not" as a decision metric, not raw tool-call counts.
- Two-reviewer unanimity for tool admission; drop tools that only solve one task.
**Fit to Crucible Part 2.** F1 (curated tools): the execute-then-wrap step is a cheap way to grow an App's tool surface, but tools must be derived from a different task pool than the one graded (G11 contamination, G9 no-shortcut: a tool that solves the task in one call is a shortcut). F7/F10: the tool-beneficial label generalises into a `BehaviourSignature` field "efficient path available" and an intent probe "did the solver choose the efficient path". Diversity knob: tool count and distractor tools (the `tools` knob in DomainSpec) visibly change difficulty; tool order and retrieval must be fixed in the harness and recorded in provenance. Priority P2.

## 2409.08264 — WindowsAgentArena: Evaluating Multi-Modal OS Agents at Scale (Bonatti et al., 2024; arXiv / Microsoft)
Read: FULL (main text; appendices A.1–A.7: observations, actions, reward evaluation, human study, Azure parallelisation).  Relevance to Part 2: low-medium. It is a hand-ported benchmark, not a generator. Useful for its infrastructure (one Windows VM per container, parallel cloud workers, 20-minute full run) and its state-diff evaluators.
**Problem.** OS-agent benchmarks were Linux-only and slow (days of serial evaluation); Windows has 73% desktop share.
**Method / algorithm.**
- Task = JSON config: instruction, deterministic setup script (download files, open apps, navigate pages), the information to retrieve for evaluation (e.g. a gold file), and an evaluator function (Python). About two-thirds of the 154 tasks are ported from OSWorld (path changes, bash → PowerShell, reverse proxy to reach Edge/Chrome, fixes to initial conditions and evaluators); one-third written new for Windows apps. 11 programs; domains: Office 28%, web 19%, Windows system 16%, coding 16%, media 14%, utilities 8%. Infeasible tasks are included and rewarded when the agent declares FAIL.
- Infrastructure: Docker container hosting a Windows 11 VM under QEMU/KVM (adapted from dockur/windows); a Flask server inside the VM executes commands and returns observations and files; the client in the container schedules tasks and runs the agent and evaluators. Windows licensing forbids shipping a snapshot, so users build one from a trial ISO with provided scripts. Cloud: Azure ML jobs, one worker per VM (Standard_D8_v3, $0.384/h, nested-virtualisation required), tasks split evenly, results merged; the snapshot lives in Blob storage.
- Agent Navi: chain-of-thought prompt; inputs are window titles, clipboard, a memory block, previous and current screenshot with Set-of-Marks from UIA tree, DOM, OCR, Grounding DINO or OmniParser; output is Python on a `Computer` class (move_id, click, write, open_program, switch_to_application) or free pyautogui.
**Verification / grading.** Post-run scripts read device state (settings files, cookies, VS Code JSON, documents against a gold file) and compare against the initial state or a rule; binary or continuous (image similarity for media). No partial-progress reward. Hack surface: evaluators check a narrow property (e.g. one JSON key), so collateral damage elsewhere is not penalised; continuous similarity rewards near-misses.
**Scale & cost.** 154 tasks; full parallel run in 6.5–82 minutes (median under 20 for non-OmniParser agents) over about 50 parallel workers; human casual user took about 1.5 h for the set.
**Key results.** Best Navi (UIA + OmniParser + GPT-4V-1106) 19.5% vs human 74.5% (human lowest on VLC, 42.8%). Adding UIA markers to pixel detectors raised success by 57% (OmniParser), 52% (open models), 15% (proprietary pixel models). Phi3-V 1.3–4.0%. Failure analysis: imprecise SoM boxes and text–visual misalignment (agent names the right element but picks the wrong ID). Navi on Mind2Web: Image + SoM(DOM+pixel) 45.2% step success vs SeeAct 38.3%.
**Failure modes & limits.** Small task count; one human annotator for the human baseline; evaluators narrow; no partial credit; no simulated user (they discuss an ask action as future work); OS clock cannot be sped up, so parallelism is the only lever.
**Tips & tricks.**
- Parallelise by giving every worker its own full VM image instead of many VMs per host.
- Keep the golden snapshot in object storage and mount code as volumes so the image rarely rebuilds.
- Mix accessibility-tree marks with pixel detectors; the tree alone or pixels alone lose 15–57%.
- Include infeasible tasks whose correct output is FAIL.
**Fit to Crucible Part 2.** Mostly infrastructure for Part 1's Harbor/CUA integration rather than for the factory. For F6 it is a negative example: single-property evaluators with no collateral diff; Crucible's `collateral` check kind is the fix. Infeasible-task rewarding supports §3.3's infeasible task type. Observation-format choice (tree vs pixels) is a difficulty knob ("observability") for CUA domains. Priority P2.

## 2405.14573 — AndroidWorld: A Dynamic Benchmarking Environment for Autonomous Agents (Rawles et al., 2024; arXiv / Google)
Read: FULL (main text; appendices C–E: observation/action interface, task classes, protobuf IR tasks, robustness by seed).  Relevance to Part 2: high for the task-template design. It is the cleanest precedent for "task = template + seeded parameter generator + initialiser with noise rows + state-reading success check + teardown", which is what F2–F5 need for state Worlds, and its seed-variance study is a direct warning for F9 difficulty estimates.
**Problem.** Static GUI benchmarks have one instance per template and break when parameters change; mobile has no reproducible, rewardable environment.
**Method / algorithm.**
- World control: Pixel 6 emulator, Android 13, fixed F-Droid APK versions, only apps that need no login and store data on device; the device clock is reset to 2023-10-15 15:34 UTC at the start of each task, so time-relative tasks ("this Tuesday") are reproducible. 20 apps, 116 task classes; 2 GB RAM, 8 GB disk.
- Write tasks ("side-effect" tasks) are Python `TaskEval` classes with four methods: `generate_random_params` (seeded), `initialize_task` (clear the relevant DB, insert goal rows plus "noise" rows that must not be touched), `is_successful` (read app SQLite / files / settings through adb; return float), `teardown` (clear). Example: SendSms checks the telephony `mmssms.db` for a row with the number and body.
- Read-only tasks ("information retrieval") are protobuf entries: prompt template, `relevant_state` (goal rows), `exclusion_conditions` so random noise rows cannot change the answer (e.g. no noise event on the asked date), `success_criteria` built from a few transforms (count, sum, identity) and a match type, and lists of possible parameter values. New IR tasks are drafted by an LLM as protobufs, then human-reviewed. Observed LLM defects: missing or hallucinated fields, incompatible parameter generation, parameters not used, non-specific prompts; more complex proto structure gave more defects; editing LLM drafts was still faster than writing from scratch.
- Composite tasks are sums of subtask checks divided by count (e.g. create a note + SMS its content, each 0.5), so composition gives partial reward.
- Asynchronous interface: `get_state(wait_to_stabilize)` with heuristics, because UI changes lag actions. Actions: click, long press, type, scroll, home, back, open app, status (complete / infeasible), answer, wait; plus a few function APIs (send SMS, contacts).
- Six volunteers annotated difficulty, step counts and tags and found over 30 task bugs; step budget = 2× human steps.
**Verification / grading.** State checks through the same storage the app uses (SQLite row exists or not, file exists with content, setting on); UI-tree check only when state inspection is impractical. Reusable validators across apps (file_exists is shared by notes, media, file manager). Hack surface: checks look for presence of goal rows; deleting noise rows is penalised only where the check is written as "noise rows still exist". Answer checks are exact string or integer match.
**Scale & cost.** 116 templates with practically unlimited instances; 92 MobileMiniWoB++ tasks added (12 dropped as unrenderable or real-time). M3A takes 3.9 min per task (2.5 text-only), about 3× human time.
**Key results.** Human 80.0%. M3A (GPT-4 Turbo, a11y tree only) 30.6%; with SoM screenshots 25.4%; Gemini 1.5 Pro 19.4–22.8%; Gemma 2 27B 9.5%; M3A-Simple (no guidelines, no reflection) 19.8%. SeeAct adapted from web 15.5%. Seed robustness: three seeds give 27.6 / 26.3 / 33.2%; 20 trials per task on 5 tasks show significantly larger variance across seeds than within a seed (Wilson intervals, p < 0.05 on two tasks). The cause is structural: a seed that picks an off-screen expense category (needs a horizontal scroll) or the "replace text" variant (long-press, select, delete, type) makes the task fail every time; a fixed-seed evaluation can show a task as unsolvable by bad luck. Pixel 5 / Android 12: 28.4%, within seed noise.
**Failure modes & limits.** Only login-free, local-storage apps; open-source apps have rougher UIs than popular ones; difficulty per seed is uncontrolled (the parameter that matters is not exposed as a knob); single-seed results reported for comparability.
**Tips & tricks.**
- Freeze the clock at task start; write relative-date tasks against it.
- Seed noise rows in the same tables as goal rows; use exclusion conditions so noise cannot change the gold answer.
- Write read-only tasks as data (template + relevant state + exclusions + answer transform); let an LLM draft them and a human or a schema validator check them.
- Reuse validators across Apps (row-exists, file-exists) instead of per-task checks.
- Report the mean over several seeds; per-seed variance can exceed model differences.
- Set the step budget relative to the human or oracle step count (2×).
**Fit to Crucible Part 2.** F2/F3: the TaskEval quadruple maps one-to-one onto `SeedBundle` (params + initialiser + distractors) and `TaskContract.start/grade`; the exclusion-condition idea should be a required field of read-only TaskProposals (G8-like "answer is unique under the seeded distractors"). F4: answer = transform over relevant state is a cheap oracle for read-only tasks. F5: add "noise rows unchanged" as the default collateral check. F9: AndroidWorld shows that seed parameters silently change the required skill (scrolling, long-press); difficulty records must be keyed per instance, and the parameters that change the behaviour signature should be promoted to declared knobs. F7: two seeds of one template with different interaction patterns are different cells. The LLM-drafted protobuf defects list is a ready checklist for an F3 format gate. Priority P1.

## 2509.24002 — MCPMark: A Benchmark for Stress-Testing Realistic and Comprehensive MCP Use (Wu et al., 2025; arXiv)
Read: FULL (main text; appendices A task-creation guideline and agent prompt, B servers, D per-service tables, F cost, H initial states).  Relevance to Part 2: medium-high. Its human–agent co-design loop (explore → evolve harder → verifier script → expert solves with agent → perturb the end state to test the checker → iterate) is a concrete template for F3–F6 with a human in the loop, and its write-heavy, state-checked task style is the one Crucible wants.
**Problem.** MCP benchmarks were read-heavy, shallow (3–7 turns) and often LLM-judged; there was no write-heavy benchmark with programmatic end-state verification and resettable state.
**Method / algorithm.**
- Five MCP environments with curated initial states (38 total): Notion (9 marketplace templates such as Team Projects, IT Troubleshooting Hub), GitHub (real repos with history, e.g. EasyR1, missing-semester, plus a self-made CI/CD repo), Filesystem (curated folder trees, some LLM-synthesised), PostgreSQL (chinook, employees, lego, sports, dvdrental), Playwright (self-written pages such as a Cloudflare Turnstile login, plus WebArena reddit/shopping/shopping_admin).
- Task creation, per task, a human expert plus a task-creation agent and a task-execution agent (Claude Code or Cursor with the MCP stack):
  1. Exploration: expert and agent explore the initial state under a seed topic.
  2. Evolvement: the agent proposes a task or makes an existing one harder (remove unnecessary hints, make information harder to find, longer inputs, more steps); the expert keeps it practical and verifiable.
  3. Verification: the agent drafts a Python verification script; the expert solves the task with the execution agent; the script is run and refined until consistent; the expert then edits the final state by hand to check the script flags both success and failure, including edge cases.
  4. Iteration: repeat 2–3 to raise difficulty while keeping verifiability.
  Agent prompt asks for one hard, verifiable, conversational task in JSON with `verification_criteria`, `expected_mcp_calls`, `estimated_complexity`; expert feedback templates ("not verifiable enough", "explore deeper", "make subtasks integrated rather than unrelated").
- Quality control: expert cross-review, a month-long community check, extra validity checks for tasks no model solved.
- Lifecycle per run: initial state → agent → verification script → reset to initial state. Agent: minimal LiteLLM + MCP SDK tool loop, max 100 turns, 3600 s.
**Verification / grading.** Programmatic scripts over end state (mean 209.8 lines per task); pass@1 (mean of 4 runs), pass@4, pass^4 (all four succeed). Failure taxonomy: implicit (finished but wrong; above 50% for all models, above 80% for gpt-5-high and kimi-k2) vs explicit (context overflow, turn limit, abandoned, premature stop, malformed calls). Hack surface: remote services (Notion, GitHub) are live; scripts check required changes, and the paper does not describe collateral checks on untouched pages or rows.
**Scale & cost.** 127 tasks (FS 30, Notion 28, Playwright 25, GitHub 23, Postgres 21); instructions average 288.6 words; 3–5 expert hours per task with 10 experts. Average 16.2 turns, 17.4 tool calls. Cost per task from $0.01 (gpt-oss-120b) to $9.18 (claude-opus-4.1); gpt-5-medium $1.00.
**Key results.** gpt-5-medium 52.56% pass@1, 68.50 pass@4, 33.86 pass^4; claude-sonnet-4 28.15 / 44.88 / 12.60; best open qwen3-coder-plus 24.80; kimi-k2 21.85; deepseek-v3.1 16.73; glm-4.5 15.55; gpt-oss-120b 4.72 (pass^4 0). Local services easier (Postgres 76.19 for gpt-5-medium) than remote (Notion 41.96, GitHub 47.83). Reasoning effort helps mid and large models (gpt-5-mini 8.27 → 30.32 low → high; GitHub for gpt-5 27.17 → 50.00) but not nano or claude-sonnet-4. Successful runs use fewer, targeted calls; kimi-k2 over-calls past 30 turns with falling success. Cost does not track accuracy.
**Failure modes & limits.** Authors: human pipeline does not scale to training data; difficulty too steep for small models; wants a finer difficulty gradient via semi-automated generation and ambiguous-intent tasks. Mine: live remote services drift; no partial credit; the agent that proposes the task also drafts the checker (same family), which the human pass only partly offsets.
**Tips & tricks.**
- Test a checker by hand-editing the solved end state into near-miss failures and confirming it flips.
- Make the proposer "evolve" a task by removing hints, hiding information and adding steps, and record which operator was applied.
- Report pass^k beside pass@k; the gap is the reliability signal.
- Separate implicit and explicit failures in trace analysis; explicit ones point at harness or budget, implicit at skill.
- Prefer self-hosted or template-copy states (Postgres sample DBs, WebArena sites) over live remote APIs for resettable worlds.
**Fit to Crucible Part 2.** F3/F5/F6: adopt the "evolve" operators as declared knobs (hint removal, information hiding, input length, step count) so harder variants are traceable in `knob_vector`; adopt state perturbation of the oracle end state as G5 negatives (a cheap, automatic version of the expert's hand edits: wrong value, missing write, touched distractor). F12/trace analysis: the implicit/explicit split is a first-level failure label before skill attribution. Avoid live remote services as World tiers. The local-vs-remote gap supports building self-hosted Apps with realistic templates. Priority P1.

## 2508.14704 — MCP-Universe: Benchmarking Large Language Models with Real-World Model Context Protocol Servers (Luo et al., 2025; arXiv / Salesforce)
Read: FULL (main text; appendices A–F: servers, task and evaluator examples, prompts).  Relevance to Part 2: medium. The evaluator taxonomy (format / static / dynamic, where dynamic evaluators recompute ground truth from the live source at grading time) and the task-admission rule (reject a task solvable without tools or solved within five retries) are reusable; the live-server design itself conflicts with Crucible's reproducible World.

## 2508.20453 — MCP-Bench: Benchmarking Tool-Using LLM Agents with Complex Real-World Tasks via MCP Servers (Wang et al., 2025; arXiv / Accenture)
Read: FULL (main text; appendix A.3 synthesis prompts, A.4 judge rubric summary, server table).  Relevance to Part 2: medium, mostly as a cautionary pattern. Its synthesis pipeline (tool-graph dependency analysis → task → LLM quality score → "fuzzing" into a conversational request) is cheap and generic, but nothing in it is executed against ground truth: the same model family writes, filters and judges the tasks.
**Problem.** Tool benchmarks either use isolated APIs (ToolBench, BFCL) or a handful of compatible ones (τ-bench); none test tool retrieval from fuzzy instructions, long cross-server chains and evidence grounding together.
**Method / algorithm.**
1. 28 live MCP servers, 250 tools, 11 domains (BioMCP 35 tools, Scientific Computing 26, Medical Calculator 22, many single-tool servers).
2. Dependency-chain discovery and task generation (o4-mini): the prompt asks the model to analyse inherent dependencies (one tool's output feeds another's input; search → fetch → analyse) and scenario dependencies (result picks the next tool, output sets parameters, cross-validation, parallel merge, iterative loops), record them in `dependency_analysis`, and write one task of maximal complexity using all given servers. Hard data rules: self-contained, no external files or URLs, concrete values (cities, numbers, thresholds), relative dates only.
3. Quality filter: an LLM scores solvability and utility 1–10; keep if solvability ≥ 9.0 and utility ≥ 5.0.
4. Fuzzing: rewrite the task as a natural conversational request with no tool or platform names, no lists or steps, personal context and hedging, while preserving every numeric value.
5. Human inspection for realism, executability and dependency-analysis sanity. Output: 104 tasks (56 single-server, 30 two-server, 18 three-server).
6. Every task gets 10 distractor servers (100+ extra tools). Agent loop: plan → execute → compress observation → update, up to 20 rounds, then a final answer from the trajectory.
**Verification / grading.** Rule-based over the trace: valid tool name rate, schema compliance rate, execution success rate (dependency order is listed as a rule check). LLM judge (o4-mini) sees the fuzzy task, the hidden concrete task, the hidden dependency analysis, the final answer, a summarised trace and the tool list, and scores six sub-dimensions 1–10 (task fulfilment, information grounding, tool appropriateness, parameter accuracy, dependency awareness, parallelism/efficiency). Rubric order is shuffled 5 times and scores averaged. No end-state or answer ground truth exists; answers come from live services. Hackable: a fluent, well-cited answer with plausible tool calls scores well whether or not the numbers are right.
**Scale & cost.** 104 tasks; 20 models; no dollar costs. Rounds and calls per task range from 3.9 rounds / 20.6 calls (kimi-k2) to 17.3 / 155.6 (llama-3.1-8b); gpt-5 9.2 / 78.9.
**Key results.** Overall scores: gpt-5 0.749, o3 0.715, gpt-oss-120b 0.692, gemini-2.5-pro 0.690, claude-sonnet-4 0.681, qwen3-235b-a22b 0.678, glm-4.5 0.668, qwen3-30b-a3b 0.627, llama-3.1-8b 0.428. Schema compliance and valid names above 95% for nearly all; separation is in planning (dependency awareness 0.22 to 0.65, parallelism 0.14 to 0.36). Weaker models drop more from single to multi-server. Judge ablation on 50 tasks: shuffling + averaging lowers cross-judge CV 16.8% → 15.1% and raises human agreement 1.24 → 1.43 of 2.
**Failure modes & limits.** Same model (o4-mini) synthesises, filters and judges; solvability is an LLM opinion, not an executed oracle; live servers drift; scores are compressed (0.43–0.75) so the benchmark separates poorly; utility threshold 5/10 is lax.
**Tips & tricks.**
- Generate tasks from the tool dependency graph (I/O coupling), not from tool lists; record the intended chain as privileged grader input.
- Write a concrete version first, then a "fuzzy" version for the solver, keeping all numbers; give the grader the concrete one.
- Forbid external references and absolute dates in generated tasks; use relative dates.
- Attach many distractor tools to every task.
- Shuffle rubric order and average several judge passes.
**Fit to Crucible Part 2.** F1/F3: the dependency-chain prompt is a good way to build the `tool_graph` (dataflow / precondition edges) and to sample proposals along graph paths, which AgentScaler-style coverage needs. F3 knob: the concrete→fuzzy rewrite is an "obfuscation / hints" knob with a natural ladder (concrete steps → named tools → goal only); it should be applied after the oracle exists, and G8 must confirm the fuzzy text still communicates every exact value. Avoid: LLM-scored solvability as a gate (violates "construction before sampling" and §3.0 rule 5); judge from the same family as the proposer. Their rule-based trace metrics (name validity, schema compliance, execution success) are cheap F12 trace features. Priority P2.

Read: FULL (main text; appendices on ethics, reproducibility; key-point examples referenced).  Relevance to Part 2: low-medium. Useful facts about LLM-judge reliability on agent trajectories (its error taxonomy, judge-model choice, voting) and about tool retrieval as a difficulty knob; its "no end-state check" design is what Crucible must not do.
**Problem.** MCP benchmarks inject a few servers' tools directly into context; real use needs retrieval and composition over hundreds of tools from many servers, with time-varying answers.
**Method / algorithm.**

- Validate the judge model on human labels before choosing it; reasoning models were worse judges of long trajectories here.
- Majority voting over weak judges does not beat the best validated judge.
- Expect "hallucinated completion" to be the main judge failure; check claimed actions against the trace or state.
- Retrieval top-k is a strong difficulty knob (k = 1 vs 5: 15 points).
**Fit to Crucible Part 2.** F5/F6: the judge error taxonomy is evidence for §3.8's vacuous-verifier canaries (feed a judge a trajectory that narrates completion without doing it; it must fail). Key points are the LLM-judge analogue of `milestones`; Crucible should bind each milestone to a state predicate or a trace event, not to text. ## 2602.00933 — MCP-Atlas: A Large-Scale Benchmark for Tool-Use Competency with Real MCP Servers (Bandi et al., 2026; arXiv / Scale AI)
Read: FULL (main text; appendices A limitations, B servers and containers, C claim-judge prompt and CIs, D authoring rules and example, E 11-mode diagnosis prompt, F cross-judge table).  Relevance to Part 2: medium-high for verification and trace analysis. Claim-level answer scoring (atomic claims, one judge call per claim, trajectory-agnostic) and the 11-mode failure taxonomy with root-cause marking are directly reusable in F5 (answer checks) and F12 (failure clusters); task construction itself is human.
**Problem.** MCP benchmarks are either rigorous but small (under 250 tasks with custom scripts) or large but holistically LLM-judged (style-biased); few test tool discovery among plausible distractors.
**Method / algorithm.**
- 36 production MCP servers, 220 tools, five buckets (basic search/maps 32%, productivity 22%, coding 22%, analytics 12%, financial 12%). Each server in a pinned Docker image, read-only filesystem except work dirs, allow-listed egress, restarted between tasks.

Annotators curate a per-task tool set: sufficient relevant tools plus plausible distractors from similar categories (6–37 tools, mean 15.2; 2–8 required, mean 4.1). Deliverables: a reference trajectory (gold call sequence with rationales, mean 9.8 calls) and a grounded final answer, from which atomic claims are written (mean 4.7, range 1–23) by experts plus automated candidate generation and manual review.
- QA: (1) expert executes the reference trajectory live; (2) domain-expert review for correctness and solvability; (3) review for tool/server name leakage in prompts; (4) automated LLM check of claim completeness and trajectory consistency; (5) random manual audit. 98.6% of tasks need ≥2 servers.

**Verification / grading.** Per-claim judge call: fulfilled 1.0 / partial 0.5 / not 0.0 with justification and confidence; numeric tolerance (within 5%, ±1 pp for percentages, equivalent forms match). Coverage = mean claim score; pass at ≥ 0.75. The reference trajectory is never used for scoring, only for solvability, tool-dependence checks and diagnosis. Three judges (Gemini 3.1 Pro primary, GPT-5.4, Opus 4.6): mean pass 65.4 / 62.3 / 63.9; per-model range 2.1–4.6 pp; ranks stable except in the crowded top. Diagnosis runs only on failed tasks: one primary mode among 11 (tool family: malformed call, wrong tool, no tool use, failed error recovery; cognitive family: task misunderstanding, faulty synthesis, response misparsing, early termination, hallucinated fact, logical error, constraint violation), plus contributing failures with `is_root_cause`, explicit boundary rules between confusable modes, calibrated confidence. Hackable: answers judged only on claims; an answer that lists many candidate facts could cover claims; "no tool use" answers from memory pass if facts are known (they label this as a failure only when the task fails).
**Scale & cost.** 1,000 tasks; 20 models; 100-call budget; mean wall time 27–194 s per task; about 6,900 diagnosed failures. Bootstrap CIs (10,000 resamples). No authoring cost given.

Public–private gaps −0.8 to +9.6 pp, OpenAI models clustered at +8.4: treated as exposure audit signals, not proof of contamination.
**Failure modes & limits.** Live upstream APIs drift (May 2026 snapshot); claim lists carry residual noise; diagnosis anchored on one reference path; fixed 100-call budget; English only; per-provider harness differences.
**Tips & tricks.**
- Score answers by atomic claims, one judge call per claim, with explicit numeric tolerances; never score the trajectory.
- Keep a reference trajectory for solvability and diagnosis only.
- Curate per-task tool menus with distractors from the same semantic category as the required tools.
- Diagnose only failed episodes, with one primary mode, contributing modes and a root-cause flag; write boundary rules for confusable labels.
- Hold out a private split and report public–private gaps per model family as an exposure audit.
- Report cross-judge ranges; treat rank swaps within that band as noise.
**Fit to Crucible Part 2.** F5 `answer_checks`: adopt atomic claims with tolerance rules for read-only intents, with claims derived from the oracle's end state (not from an annotator's answer) so they stay correct per seed. F6 G14 alternatives: claim scoring is trajectory-agnostic by construction, so alternative paths are free. F10/F12: the 11-mode taxonomy plus root-cause flag is a ready first layer for failure clustering and for the "fault side" field (tool-call vs cognitive maps partly to World/harness vs skill); early-termination and no-tool-use modes are exactly the intent signals a 35B student will show. Pool/benchmark: the public–private gap audit fits the sealed benchmark split. Priority P1.

## 2506.07672 — MCPWorld: A Unified Benchmarking Testbed for API, GUI, and Hybrid Computer Use Agents (Yan et al., 2025; arXiv)
Read: FULL (main text; appendix A environment and tool space).  Relevance to Part 2: medium. Its "white-box App" principle (verify through hooks on the App's own internal events, not through screens or output files) is the strongest argument for Crucible's choice to own its Apps and grade at the tool/state choke point, including transient and in-memory events and intermediate milestones.
**Problem.** GUI benchmarks grade by UI matching or output files, which break on UI changes, cannot see in-memory or transient states (a breakpoint hit), and cannot compare API, GUI and hybrid agents fairly.
**Method / algorithm.**
- 10 open-source desktop Apps with MCP servers (VS Code, OBS Studio, Zotero, Zulip, Joplin, FreeCAD, QGIS, Anki, qBittorrent, Blender), 201 tasks. Ubuntu 22.04 container; XFCE + TurboVNC, or KDE + KasmVNC with GPU pass-through.

- Task design: human choice + LLM suggestions + docs, blogs, forums; two other designers cross-validate feasibility, clarity, consistency; every task is recorded being done by a human (DuckTrack); difficulty from human GUI step count (easy 0–5: 73, medium 5–10: 83, hard 10+: 45); most tasks annotate key steps.

Three techniques: dynamic binary instrumentation with Frida for compiled Apps (hook the function that commits the outcome), targeted code injection for Python/JS/Electron/Java Apps (subscribe to internal events), and API-driven state querying (internal APIs, CLIs, structured logs or DBs).

Signals are asynchronous to the agent, so a check fires when the event happens, not when the agent claims completion. Hack surface: a hook on "function X called with args Y" can be satisfied by calling X through any path (including an MCP tool) even if the intended workflow was not followed; collateral effects are not checked.
**Scale & cost.** 201 tasks, 3 attempts per configuration; one 64-core server with 8 A40s (GPU mostly unnecessary).

MCP-only failures: 48.42% insufficient MCP coverage, 47.37% reasoning; GUI-only failures: 72.88% reasoning, 18.64% time limit. Hybrid was worse than GUI on 5–10-step tasks, attributed to long MCP tool prompts distracting the agent.
**Failure modes & limits.** One agent, one model; only open-source Apps; annotation needs source-code understanding; mostly single-app everyday tasks (high success rates); key-step checks are hand-written per task.
**Tips & tricks.**
- Grade on internal events at the moment they happen (function called, event emitted) so transient and in-memory outcomes are checkable.
- Snapshot and restore only the App's persistent user data, not a full VM.
- Record a human doing every task; derive difficulty bands from human step counts.
- Report key-step completion beside success to see partial progress.
- Tool coverage is a confound: an API-only agent fails when the App exposes too few tools, which is a World defect, not a skill failure.
**Fit to Crucible Part 2.** F5: their hooks are the analogue of Crucible's `path_constraints` and `timing_checks` read at the `_call_tool` choke point, plus milestones for Φ; because Crucible owns its Apps, every App should emit structured internal events (not only end state) that verifiers can subscribe to. F6 G13 (interaction completeness) and the World loop: "insufficient MCP coverage" as a labelled failure cause is exactly the `world_bug` side of fault attribution; a task whose oracle needs a capability the policy-visible tools lack must fail G7. F7: key steps map to milestone ids in the behaviour signature. Priority P2 (design confirmation, little new mechanism).

## 2508.06600 — BrowseComp-Plus: A More Fair and Transparent Evaluation Benchmark of Deep-Research Agent (Chen et al., 2025; arXiv)
Read: FULL (main text and ablations; appendix prompts referenced).  Relevance to Part 2: medium. It shows how to turn a live-web task set into a fixed, resettable World (a corpus with verified evidence plus mined hard negatives) and how an oracle-evidence ablation separates "find the information" from "reason over it", which is an intent probe Crucible can reuse for any read-heavy family.
**Problem.** BrowseComp runs on live, opaque search APIs, so results drift, retrievers cannot be compared, and retrieval and reasoning contributions are entangled.
**Method / algorithm.**

2. Cross-annotator agreement above 80%. 830 questions pass.
3. Hard negatives: GPT-4o splits each question into about 7 self-contained sub-queries; each goes to Google via SerpAPI (top 100 results); scrape them.
4. Deduplicate → 100,195 documents; per query 6.1 evidence, 2.9 gold, 76.28 negatives; documents average 5,179 words.
5. Harness: retriever tool returns top-5, each truncated to 512 tokens (86.5% of queries still have the answer in some gold doc's first 512 tokens); optional get-document tool.
**Verification / grading.** Answer accuracy by a gpt-4.1 judge against the gold answer (BrowseComp prompt); evidence recall over the trajectory; citation precision and recall against labelled evidence; calibration error from stated confidence; retrievers scored Cranfield-style (Recall@k, nDCG@10 over qrels). Hack surface: answers are short strings, so guessing from parametric memory works when the fact is famous; the judge is lenient on format.
**Scale & cost.** 830 queries; 400+ annotation hours; agent API cost lower with better retrievers (fewer calls).
**Key results.** gpt-5: 55.9% (BM25) → 70.1% (Qwen3-Embedding-8B) with fewer search calls (23.2 → 21.7); o3 49.3 → 63.5; Sonnet 4 and Opus 4 roughly double (14–16 → 36–37); Qwen3-32B 3.5 → 10.4 and calls fewer than 1 per query; Search-R1-32B 3.9 → 10.4; gpt-oss-120B-high 28.7 → 42.9. Oracle evidence in context: gpt-4.1 93.49%, Qwen3-32B 83.25% (6% context overflow), so open models' gap is in interleaved search, not in reading. Reasoning effort for gpt-oss-20b: 13.4 → 34.6 accuracy with search calls 1.9 → 23.9. Full-document reader: gpt-4.1 35.4 → 43.6, Qwen3-32B 10.4 → 11.7. Adding 9.7M FineWeb documents (10× corpus) did not change conclusions or rankings.
**Failure modes & limits.** Inherits BrowseComp's short-answer format; evidence chain built from one o3 run; truncation choice affects results; LLM judge.
**Tips & tricks.**
- Freeze a live-source World by harvesting evidence for each gold answer, verifying spans by hand, and adding hard negatives mined from sub-queries of the same question.
- Run an oracle-context ablation (all evidence given) to separate retrieval failure from reasoning failure.
- Check corpus size sufficiency by adding 10× unrelated documents and confirming rankings hold.
- Count search calls and reasoning effort as cost, and report them beside accuracy.
- Small open models under-call tools even when prompted; this is a policy failure worth a curriculum.
**Fit to Crucible Part 2.** World tier for read-heavy families: a fixed corpus App with seeded evidence and mined distractors fits the `distractors` knob and makes G2 determinism possible. F10: the oracle-evidence probe is the read-only analogue of the "single-subtask" ablation; if the student passes with evidence given but fails without, the task exercises search, not reasoning, and the IntentCard should say so. F9: for the 35B student, a "≥1 tool call" floor and evidence-recall metric are cheap trace features. Avoid live web. Priority P2.

- Pair each first-error step with a correction and with a "recover after the error stayed" next step.

## 2505.16282 — ARPO: End-to-End Policy Optimization for GUI Agents with Experience Replay (Lu et al., 2025; arXiv)
Read: FULL.  Relevance to Part 2: medium for difficulty and curriculum (F9/F11). Its two mechanisms are pool-level: keep only tasks a baseline solves at least once in 16 tries (pass@16 > 0 admission), and inject a cached success into all-fail groups. It also documents a reward hack on infeasible tasks and an in-domain vs OOD split that shows small transfer.
**Problem.** GRPO on GUI tasks gets sparse, delayed rewards and costly rollouts; all-fail groups give zero advantage.
**Method / algorithm.**
- Agent: UI-TARS-1.5-7B (Qwen2.5-VL), full history up to 15 screenshots in 64K context at 1080p, CoT then action; actions LEFT_CLICK, RIGHT_CLICK, SCROLL, TYPE_TEXT, PRESS_HOTKEY plus WAIT, FINISH, FAIL, CALL_USER.
- Distributed rollout: 256 parallel OSWorld VMs, each streaming screenshots to one vLLM server that batches next-action inference across environments.
- Reward: trajectory reward 1 if OSWorld's checker passes else 0; format penalty −1 for unparsable responses.
- Task selection: run UI-TARS-1.5 16 times per OSWorld task; keep a task if any rollout succeeds → 128 tasks.
- Replay buffer: per task, store successful trajectories; if a GRPO group (8 rollouts) is all zero, replace one rollout with a stored success; fixed-size buffer, evict oldest to stay near-policy.
- Training: VERL, 15 epochs, batch 32, temperature 1.0, lr 1e-6, clip ε_low 0.2 / ε_high 0.3, no KL term; eval temperature 0.6, 15 steps max.
**Verification / grading.** OSWorld execution scripts. They identify a hack in prior practice: replacing the final action with FAIL when the step limit is hit earns reward on OSWorld's infeasible tasks; they report "OSWorld Hard", which forbids that replacement.
**Scale & cost.** 128 training tasks × 8 rollouts; per-batch rollout 3 min at 8 envs → 19 min at 256 envs; epoch time 6 h → 1.2 h.
**Key results.** UI-TARS-1.5-7B: 23.5 → 29.9 (OSWorld), 18.2 → 23.8 (Hard); GRPO alone 26.0 / 20.9. UI-TARS-7B-DPO: 15.6 → 20.4. Replay raises final training reward 0.65 → 0.75 and in-domain success 68.8 → 81.25. Selected-task training gives higher within-group reward variance and faster reward growth than the full set. In-domain (32 trained tasks): base 43.8 → GRPO 68.8 → ARPO 81.25; OOD (96 held-out OSWorld tasks): base 55.2, GRPO 52.08, ARPO 56.3, so transfer is near zero. Online RL beats offline alternatives on equal rollouts: ARPO 27.3, GRPO 26.0, KTO 24.6, DPO 22.4, rejection sampling 21.8.
**Failure modes & limits.** Trains on OSWorld tasks and reports OSWorld scores (the main table mixes trained and untrained tasks); tiny task pool; OOD gains nil; replayed successes are off-policy.
**Tips & tricks.**
- Admit a task to the RL pool only if some baseline solves it at least once in k tries; it raises within-group variance.
- When a group is all-fail, inject one stored success for that task; cap and age the buffer.
- Batch inference across many environments; OS latency then overlaps.
- Never auto-convert a step-limit stop into FAIL on benchmarks with infeasible tasks; it is a free reward.
- Report in-domain and held-out task results separately; RL gains on 128 tasks did not transfer.
**Fit to Crucible Part 2.** F9: pass@16 > 0 under a baseline is a lower-band admission rule consistent with §3.6's [0.1, 0.6] band but much looser; Crucible's k=8 Wilson band is stricter and better. F11: the replay buffer means a task with p̂ just above 0 still teaches, which argues for keeping some low-p̂ tasks with a stored oracle or prior success as a "ladder" (the oracle trajectory itself can be the injected positive). F5/F6: the FAIL-substitution hack is a concrete negative for infeasible tasks: the harness must not emit any terminal action on the agent's behalf, and infeasible tasks need a check that the agent declared infeasible for the right reason (e.g. an answer check on the stated reason). Held-out evidence: tiny pools overfit; supports §3.10's many-families plan. Priority P1 (for the infeasible-task hack and admission rule).

## 2509.23866 — Efficient Multi-turn RL for GUI Agents via Decoupled Training and Adaptive Data Curation (DART-GUI; Li et al., 2025; arXiv)
Read: FULL (main text; appendix A.3–A.4 prompt and implementation).  Relevance to Part 2: medium for F9/F11 per-task adaptivity. Its performance-aware rollout allocation (fewer rollouts once p̂ > 0.6), per-task step budget from the longest past success, and pre-collected experience pool for 0%-success tasks are pool-management policies; the decoupled system is Part 1.
**Problem.** Coupled RL loops leave GUI environments and GPUs idle on long episodes; task difficulty is uneven, so easy tasks hog samples and hard ones never produce a success.
**Method / algorithm.**
- Four asynchronous modules: Env Cluster (180 Ubuntu Docker containers on Kubernetes), Rollout Service (vLLM pool with load balancing, 2 H100s per worker), Data Manager (stores trajectories and rewards; when all N rollouts of a task finish, filters and forwards them), Trainer (FSDP via verl on 8 H100s). Rollout-wise scheduling (each finished trajectory immediately triggers the next request, rather than waiting for the batch or task); per-worker staggered weight sync so inference never stops globally.
- Step-wise GRPO: each step inherits its trajectory's reward; advantage normalised over all steps of a task's N trajectories.
- Data curation:
  - Dynamic rollout frequency: per-task success rate tracked; above 0.6 the rollout count drops from 8 toward lower values; low-success tasks keep the maximum.
  - Dynamic trajectory length: per-task step cap = historical maximum length of its successful completions (e.g. 10 for simple clicks, 50 for multi-app).
  - Experience pool: pre-collect successful trajectories for hard tasks by preliminary sampling; when all rollouts of a task fail, insert one from the pool.
  - High-entropy step selection: step entropy = mean token entropy over thought + action; train only on steps above the group's 20th entropy percentile (top 80%).
  - Distribution alignment: truncated importance weight min(π_train_old / π_rollout_old, C) with C = 1 for rollout/trainer mismatch (quantisation, pooled trajectories).
- Training corpus: 203 OSWorld tasks chosen by ARPO's method; reward = OSWorld evaluation script; KL 0.1, ε_low 0.2, ε_high 0.28, temperature 1.0, max 30 steps.
**Verification / grading.** OSWorld execution-based checkers for reward and evaluation (OSWorld-Verified). As in ARPO, train and test tasks come from the same benchmark.
**Scale & cost.** 180 environments, 8 + pooled H100s; throughput 22.6 → 43.6 actions/min; environment utilisation 12.2% → 67.7%; GPU utilisation 29.6% → 46.7%.
**Key results.** DART-GUI-7B 42.13% on OSWorld at 30 steps vs base UI-TARS-1.5-7B 27.52% at 100 steps (+14.61); OS tasks 31.25 → 62.50, Writer 39.13 → 60.86. Ablation on 45 training tasks (pass@1): decoupled baseline 28.67 → +dynamic rollout 50.90 → +dynamic length 66.11 → +high-entropy steps 68.33 → +alignment 70.55 → full 72.28. Average rollouts per task 8.0 → 5.0 and average length 30 → under 10 as accuracy rose. Experience pool on 22 tasks starting at 0% reached 46%. Without importance correction, accuracy collapsed from 55% to near 0 after step 60.
**Failure modes & limits.** Training on benchmark tasks (in-distribution gains; no held-out family); ablations on training tasks; experience-pool successes are off-policy; per-task length caps can block solutions longer than any past success.
**Tips & tricks.**
- Reduce rollouts for tasks whose running success exceeds about 0.6; spend them on low-success tasks.
- Cap each task's horizon at its longest observed success (plus margin) to stop hopeless long rollouts.
- Seed an experience pool for 0%-success tasks from preliminary sampling (or an oracle) and inject one success into all-fail groups.
- Correct rollout/trainer policy mismatch with a truncated importance weight; without it, long-horizon agent RL can collapse.
- Schedule rollouts per trajectory, not per batch.
**Fit to Crucible Part 2.** F9/F11: dynamic rollout frequency is a live version of the per-student band (move compute away from tasks whose p̂ rises above the band before they are retired), and it implies the pool should publish p̂ continuously (F12 `p_hat_updates`). The experience pool generalises Crucible's oracle: for tasks with p̂ ≈ 0 the F4 oracle trajectory, executed in the World, can be the injected positive, turning "below band" tasks into usable ladders. The horizon cap from the oracle's length is a cheap budget check (§3.10 lever 1). Avoid training on the benchmark split. Priority P1 for pool policies.

Relevance to Part 2: medium for traces-to-tasks. It is the best costed example of turning real user computer traces into training data (22.6K tasks, about $32K), with an in-tool privacy review, a reflector that labels erroneous steps in human traces, and a goal "summariser" that rewrites vague user goals and scores each trace; it also shows run-to-run variance on near-identical start states.
**Problem.** No open, large, desktop-scale trajectory dataset or recipe exists for CUA foundation models.
**Method / algorithm.**
- AgentNet Tool on annotators' own machines: records screen video (OBS), mouse/keyboard (DuckTrack, OpenAdapt), accessibility trees (OSWorld parser), HTML (browser plugin); nothing leaves the machine without manual upload; annotators review and edit before submitting with an instruction. Error steps are allowed (not "gold-only").

Robustness: at temperature 0 with near-identical starts (only the system date differs), Pass@1 20.1 vs Pass@16 38.6 at 50 steps; variance sources: different solution choices per run, a missed Save or stray click, CAPTCHAs, latency. Error study: missing task knowledge (VLOOKUP, bulk fill), pixel-precise grounding, action repetition when an action has no visible effect, wrong termination, long horizons, poor error perception.

**Tips & tricks.**
- Let real users record in their own environment, review locally, and upload manually; follow with an automatic privacy classifier plus human review.
- Keep erroneous steps in recorded traces but label them with a reflector so they are excluded from loss and used to teach recovery.
- Rewrite vague user goals into precise objectives and score each trace (alignment, efficiency, difficulty) before use.
- When pairing observations to actions, pick frames before the user's pre-movement to avoid answer leakage.
- Expect Pass@1 vs Pass@16 gaps of about 2× on near-identical start states; measure per-task variance before calling a task hard.
**Fit to Crucible Part 2.** Traces-to-tasks (§3.4): adopt the pipeline order record → local review → privacy classify → human check → reflector labels → goal rewrite + score, and add Crucible's required step: rebuild the end state in the World and re-solve before keeping (OpenCUA keeps traces as SFT data, not as verifiable tasks). F9: their date-only perturbation variance argues for measuring p̂ across seeds and clock offsets, not one start state. Priority P1 (traces source).

## 2403.07714 — StableToolBench: Towards Stable Large-Scale Benchmarking on Tool Learning of Large Language Models (Guo et al., 2024; arXiv)
Read: FULL (main text and the experiments sections; appendix prompts referenced but not all read).  Relevance to Part 2: medium. It is the reference design for a stateless tool World tier (cache of real responses, real call on miss, LLM simulator as last resort, cache refreshed) and for measuring simulator fidelity; it also shows why LLM-judged "solvability" and pass rates drift. It has no state, so it cannot host write tasks.
**Problem.** ToolBench results could not be reproduced months later: only 44.4% of its API calls still succeeded, and its gpt-3.5 evaluator could not judge solvability or answers.
**Method / algorithm.**
- Virtual API server, per call (endpoint, args): (1) cache lookup keyed by category, tool, API name, arguments; (2) on miss, call the real API; (3) if the real API fails, call an LLM simulator (gpt-4-turbo) given the API documentation and up to 5 real cached calls of that API as few-shot examples; every response returned is written back to the cache. Cache seeded from ToolBench train and test call histories plus new runs, filtered for valid records (some error responses kept for realism): 352,630 → 164,980 entries.
- Stable evaluation: three LLMs (gpt-4-turbo, gemini-pro, claude-2) judge each test task's solvability; keep tasks judged solvable by more than two of them (1,100 → 765). Metrics on solvable tasks only: SoPR (gpt-4-turbo judges the answer Solved 1 / Unsure 0.5 / Unsolved 0) and SoWR (pairwise vs gpt-3.5 + CoT; solved beats unsolved, otherwise the judge decides).
**Verification / grading.** LLM judge on the final answer; no state. Human check: solvability judgment accuracy GPT-4-turbo 80%, Gemini 82%, Claude-2 71%, GPT-3.5 65%; answer judging GPT-4-turbo 74% vs GPT-3.5 68%; pairwise 78% vs 56%. Hack surface: simulator outputs are plausible but not consistent with any World state, so an agent's answer may be "correct" relative to fabricated data; judges at 74% accuracy.
**Scale & cost.** 765 solvable test tasks across 6 groups; cache about 165K entries; cache hit rates 96.5–97% for in-domain methods, 76–91% for newer models.
**Key results.** With the virtual server, disabling up to 50% of real APIs barely changes SoPR (within variance), whereas on real APIs scores drop sharply. Simulator backbone version and temperature change scores within evaluation variance. "Turing test" on 70 APIs: three annotators could not reliably tell simulated from real responses and often preferred simulated ones; 90% of 50 sampled simulations followed the documentation (6% unreasonable). Embeddings of real vs simulated responses overlap (S-BERT + UMAP); only 2 of 60 simulated APIs repeated an identical response across 5 different calls. Rankings: GPT-4-turbo DFS SoPR about 60.6, ToolLLaMA-v2 CoT 33.9; DFS beats CoT throughout.
**Failure modes & limits.** No persistent state, so simulated APIs cannot be consistent across calls in an episode (a write followed by a read is not modelled); LLM judges for both solvability and answers; solvability filter removes about 30% of tasks by model opinion.
**Tips & tricks.**
- Layer cache → real call → simulator, and write every served response back to the cache; report the cache hit rate per run.
- Give the simulator the API docs plus up to 5 real calls of the same API as few-shot examples.
- Test simulator fidelity three ways: blind human preference vs real, documentation adherence, and response diversity across different arguments.
- Judge solvability by a panel of different-family models and score only tasks the panel deems solvable.
- Keep some real error responses in the cache so agents still meet errors.
**Fit to Crucible Part 2.** World tier for read-only external services (Part 1 §2(b) App tiers): the cache-first simulator is the right pattern for third-party APIs the World does not own, but tasks that write must use stateful Apps, not this tier. F6 G2 determinism: a cache with a fixed snapshot is what makes reruns identical; the simulator fallback breaks determinism unless its outputs are frozen into the cache before gating. F1: their three fidelity tests are a template for a "simulator fidelity gate". Their panel-judged solvability is weaker than Crucible's construction rule and should not be copied. Priority P2.

## 2503.20527 — StableToolBench-MirrorAPI: Modeling Tool Environments as Mirrors of 7,000+ Real-World APIs (Guo et al., 2025; arXiv)
Read: FULL (main text, ablations, limitations; appendix request-writing example).  Relevance to Part 2: medium. A trained 7B tool simulator that matches real responses far better than prompted GPT-4o, plus a recipe for measuring simulator fidelity against held-out real calls; the "simulated environment changes the score" finding (prompted GPT-4o simulation scored agents much lower than the real environment) is a direct warning for any LLM-simulated World tier.
**Problem.** Prompted LLM simulators (as in StableToolBench) are stable but unlike real APIs; real APIs drift; hand-built APIs do not scale.
**Method / algorithm.**
1. Collect real pairs: crawl RapidAPI tools and docs; dummy-call to check availability; generate requests in two stages (an LLM writes a realistic usage scenario at temperature 1.0, then writes the API request for it at 0.1); 200 calls per API, up to 3 retries.
2. Filter: drop unsuccessful calls by StableToolBench's rules, but keep about 10,000 parameter-error failures (missing or invalid parameters) so the simulator learns to reject bad calls; gpt-4o drops pairs whose responses contradict the documentation.
3. Synthesize: gpt-4o writes extra pairs from 10 real examples per prompt for long-tail APIs; exact-match dedup; drop identical requests with different responses and doc-inconsistent responses. Total 95,872 pairs, 7,500 APIs, 49 categories.
4. CoT data: o1-preview writes a rationale explaining the API's hidden mechanism given (request, real response, docs); length ≤ 2,560 tokens → 44,440 rationale samples.
5. Train Qwen2.5-7B-Instruct on SFT (95,272) and CoT (44,440) samples mixed, with a mode tag in the system prompt; infer in SFT mode. MirrorAPI-Cache: further fine-tune on 110,700 StableToolBench cache entries.
6. MirrorAPI-Bench: OOD (49 unseen APIs; 200 success + 100 failure pairs) and ID high/medium/low-resource sets (100 each).
**Verification / grading.** Simulator fidelity: gpt-4o judge 1–10 on documentation/instruction following; BLEU-4 and embedding cosine to the real response. Agent evaluation in the simulated environment: SoPR (gpt-4o) and a new Final Answer Completeness score from a Llama-3.1-8B evaluator trained by C-RLFT on 3,714 GPT-annotated samples (88.3% agreement with two human annotators on 77 samples).
**Scale & cost.** 95.9K training pairs; 7B simulator (cheap to run); test sets of 100–300.
**Key results.** Following score: MirrorAPI-SFT 6.86 (OOD success), 8.28 (OOD failure), 8.63–8.76 (ID) vs GPT-4o 5.93 / 2.06 / 3.92–4.76 and o1-preview 7.67 on OOD success. Similarity to real: BLEU 35.6 vs GPT-4o 13.4 (OOD success), 74–90 vs 10–15 on ID; cosine 69.9 vs 63.1. On 158 fresh queries runnable in the real environment, agent SoPR and FAC under MirrorAPI closely tracked the real environment, while a GPT-4o-simulated environment gave clearly lower scores. Ablation: removing augmentation and CoT data 6.86 → 6.26; sequential SFT-then-CoT 6.33. Fine-tuned R1-distilled reasoning models simulated worse (5.5).
**Failure modes & limits.** Still stateless per call; network failures not modelled; ID gains rely on having many real calls per API; OOD BLEU still low (35.6), so a simulator for unseen APIs is plausible rather than faithful.
**Tips & tricks.**
- Generate diverse requests via a scenario first (high temperature), then the call (low temperature).
- Keep realistic error responses (parameter violations) in simulator training data.
- Measure a simulator against held-out real calls, split by how much data each API had, and by success vs failure calls.
- Validate a simulated World by running the same agents in the real and simulated World on the same tasks and comparing scores; a simulator can shift agent scores even if each response looks plausible.
**Fit to Crucible Part 2.** F1 World loop: the "agent score in real vs simulated World" check is the right acceptance test for any simulated App tier or user simulator; add it to the World-loop acceptance criteria in §3.8 (a World change is accepted only if a fixed agent's scores on frozen tasks do not shift beyond noise). For enterprise-data ingest (§2(b)), MirrorAPI's recipe (real request/response logs → trained simulator) is a path to a realistic tier when the real system cannot be cloned. Priority P2.

## 2512.04535 — GTM: Simulating the World of Tools for AI Agents (Ren et al., 2025; arXiv)
Read: FULL.  Relevance to Part 2: medium, mostly as a warning. A 1.5B "universal tool simulator" trained on LLM-synthesised calls for 20K+ LLM-generated tools; it trains RL agents faster, but for an unseen tool GTM-only training collapses after about 40 steps, and in the search and retrieval experiments the simulator is given the task's ground-truth answer while generating tool outputs. Note 04 marked its numbers "not verified"; from the full text, the 20K tools / 300 domains are LLM-generated schemas, and the judge for output quality is Qwen2.5-72B.
**Problem.** Real tools in RL are slow (Jina search about 0.9 s, rate-limited), costly and require integration work.
**Method / algorithm.**
1. Tool generation: grow a field taxonomy from seed fields by prompting an LLM with random pairs of existing fields; generate subfields per field; generate tools per (field, subfield) in a unified JSON schema (name, description, field, typed parameters, required, typed responses); check that required params exist; dedup tool names at cosine > 0.8; add and normalise tools from ToolEyes and APIGen (LLM fills missing types). Result: 20K+ tools, about 300 domains.
2. CARG data ("generate then validate"):
   - Single-turn: LLM writes (input, output) pairs with domain context; keep only if format check, LLM logic check (parameter contradictions) and LLM semantic check (input–output coherence) all pass; regenerate for tools with low pass rates.
   - Multi-turn: embed APIs (name + description + domain) with SentenceTransformer; greedy grouping of APIs above a cosine threshold θ; distribute the group across L turns with accumulated "context updates"; final call uses the full history; extra LLM coherence check.
   - Errors: four generators (type error, missing required parameter, extra parameter, semantically invalid value) with error messages; validated for format, error existence, message quality.
3. Fine-tune Qwen2.5-1.5B on CARG data → GTM-1.5B.
**Verification / grading.** Simulator quality judged by Qwen2.5-72B on Format, Logic, Semantics, Completeness, Consistency, error Detection, Helpfulness. RL utility measured by training agents with GTM vs real tools and testing all on real tools. In search and retrieval training, GTM "generates outputs based on provided ground-truth answers", i.e. the simulated tool knows the answer, which can inflate learnability and leak the answer into observations.

Retrieval RL (unseen tool, all tools with description similarity > 0.7 removed from training): real 0.21 → 0.40; GTM-only reaches 0.34 at step 40 then collapses; hybrid (GTM for 30 steps, then real) 0.41. CUDA validator (fine-tuned on KernelBench): compile-error accuracy 90.65%, correctness F1 81.2% (recall 71.1%), runtime median error 0.10 ms; agent trained with GTM roughly matches real-tool training on fast_p metrics at level 1. **Tips & tricks.**
- Use a learned simulator only as a warm-up and switch to the real tool before error accumulates (hybrid schedule).
- Check simulator coverage by embedding real tool catalogues against the simulator's training tools; distant tools need domain fine-tuning.
- Generate error cases with four operators: wrong type, missing required, extra parameter, invalid value.
- Group tools for multi-turn data by embedding similarity so chained calls are coherent.
**Fit to Crucible Part 2.** Avoid as a World tier for graded tasks: no state, answer-conditioned outputs, and collapse when off-distribution all violate G2 and the leak rules (G11: a tool output must not be computed from the task's gold answer). Useful pieces: the four error operators belong in G13 interaction-completeness tests (every tool must reject each of them with a non-crash error), and the taxonomy growth by sampled exemplar pairs is a cheap F0 brainstorming method for DomainSpec axes, subject to lead review. **Verification / grading.** τ-bench: final DB state must equal the unique gold outcome and responses must contain required outputs (substring match). Failure attribution: simulated conversations 48.9% agent-caused, 40% user-caused; human conversations 24.5% agent, 62.2% user. ## 2509.23124 — Non-Collaborative User Simulators for Tool Agents (Shim et al., 2025; arXiv)
Read: PARTIAL (§1–§5 in full; appendices A taxonomy, B simulator components and C behaviour modules read in part; prompt appendix G not read).  Relevance to Part 2: high for the people facet and for difficulty knobs. It gives a modular user simulator whose difficult behaviours (unavailable requests, tangents, impatience, incomplete messages) are switchable and composable, with an information-sharding state tracker and goal-alignment check that keep the task solvable. That is the user-side analogue of Crucible's knob vector plus G8 communicability.
**Problem.** Benchmarks use cooperative simulated users; real users ask for things the agent cannot do, digress, get angry and type fragments.
**Method / algorithm.**
- Behaviour taxonomy from marketing research and real user–LLM logs (LMSYS, WildChat), clustered into four types: unavailable service (requests needing missing APIs or unsupported parameters), tangential (factual question, opinion question, general opinion, non-opinion statement; complaints if ignored), impatience (belligerent abuse, threat, urge; triggered by failures or perceived delay), incomplete utterances (extremely brief; prematurely sent).
- Base collaborative simulator (GPT-4.1-mini; τ-bench style: goal + instruction + history until <END>), plus: (a) the user goal is sharded into information pieces and a dialogue-state tracker forces any undelivered piece to be sent before ending; (b) an ending verifier blocks premature <END> while the agent still needs confirmation or must act.
- Behaviour modules: unavailable: an LLM extends the goal with three sentences needing missing APIs/params; tangential: sample a Persona Hub persona, generate an utterance of one of four dialogue acts, merge with the cooperative turn, generate a complaint if the agent ignores it; impatience: trigger on agent failure messages or on "all info given but goal unresolved"; probability of an outburst rises with each trigger; after the first outburst the user stays cynical; incomplete: few-shot style transfer from 5 real brief messages, or random truncation with the tracker marking truncated info as unsent.
- Environments: MultiWOZ (new executable environment with AppWorld-style API discovery helpers; 89 multi-domain "book" scenarios with DB writes) and τ-bench (157 scenarios; 8 transfer-to-human cases excluded); ReAct agents, 30-step limit, 4 trials.
**Verification / grading.** Success = final DB state equals gold DB state. Goal Alignment (GPT-4o-mini checks that all essential intents and information were conveyed); dialogues failing GA are regenerated, so failures are attributable to the agent. Initial Goal Alignment (first-attempt conveyance) reported as a simulator quality metric.
**Scale & cost.** 89 + 157 scenarios × 5 modes × 4 trials × 5 agents; SFT experiments on 3B/7B models; 9 human annotators for realism.
**Key results.** τ-bench SR (collaborative → unavailable / tangential / impatient / incomplete): GPT-4.1-mini 45.5 → 41.7 / 39.5 / 45.1 / 45.4; Qwen3-235B-A22B 41.4 → 36.8 / 32.3 / 37.6 / 39.3; Qwen3-30B-A3B 27.9 → 26.6 / 20.4 / 24.8 / 30.1; Llama-3.1-70B 21.8 → 18.5 / 14.7 / 17.8 / 16.4. MultiWOZ: Qwen3-30B-A3B 48.3 → 47.2 / 27.2 / 41.0 / 26.1. Tangents hurt most (average −29.1% relative). Mechanisms: re-fetching API docs repeatedly when a request is unfulfillable; Qwen3-235B fabricating API results; excessive apologising under impatience consuming the step budget; inventing undocumented parameters under incomplete messages. Two behaviours at once drop even GPT-4.1-mini sharply. SFT of Qwen2.5-3B on collaborative dialogues reaches 91.6% collaborative but 61.2% on unavailable-service users; adding uniformly mixed non-collaborative data raises the average across modes 78.8 → 86.9. A prompt-only simulator (behaviour described in the prompt) barely lowers agent success; the modular one does, with high initial goal alignment; humans preferred its realism about 70% of the time.
**Failure modes & limits.** LLM-judged goal alignment; behaviours generated by GPT-family models (homogeneity); excluded transfer-to-human tasks because agents over-escalated; fixed 30-step budget interacts with apologising.
**Tips & tricks.**
- Shard the user's goal into information pieces and track delivery; force delivery before the user may end.
- Add an ending verifier so the simulated user does not quit while the agent still needs confirmation.
- Implement difficult user behaviours as separate modules triggered by dialogue events, not as prompt descriptions; prompt-only versions barely change difficulty.
- Escalate impatience probabilistically and make it persistent after the first outburst.
- Regenerate any dialogue that failed to convey the goal so failures stay agent-attributable.
- Mix behaviour types uniformly in training data as the default.
**Fit to Crucible Part 2.** F2 people (`ActorSpec`): adopt information sharding + delivery tracker as the mechanism behind G8 communicability for user-in-the-loop tasks (every exact value the oracle needs is a shard the simulator must deliver). DomainSpec knobs: `user_behaviour ∈ {collaborative, unavailable, tangential, impatient, incomplete}` and their pairs are a clean difficulty and diversity axis, with measured effects on our own student family (Qwen3-30B-A3B drops hardest under tangents and fragments). §3.3 infeasible tasks: "unavailable service" is a natural generator of partly-infeasible requests. F10: if a task's p̂ moves a lot between behaviour modes, the intent card should say the task tests dialogue robustness. Traces: their failure mechanisms (doc re-fetch loops, fabricated tool results, apology loops) are F12 trace features. Priority P1.

## 2505.06120 — LLMs Get Lost In Multi-Turn Conversation (Laban et al., 2025; arXiv / Microsoft + Salesforce)
Read: PARTIAL (§1–§9 in full; appendices B sharding definition, C semi-automatic sharding with its verification gate; F qualitative causes summarised from §6.2; per-task implementation appendix I skimmed).  Relevance to Part 2: high as a task transformation. "Sharding" turns any single-turn task with a verifier into a multi-turn, underspecified task with the same verifier, gated by an executed information-preservation check (Concat and Shuffle-concat must keep ≥ 80% of Full performance). That is a reusable knob (disclosure pace) and a template for gating a transformation by execution.
**Problem.** LLMs are evaluated on fully specified single-turn instructions, but real users reveal requirements over several turns.
**Method / algorithm.**
- Sharded instruction: from query q with atomic content units I(q) = [intent, clarifications c1..cm], build shards s1..sk with five properties: P1 information preservation, P2 the first shard states the intent, P3 shards 2..k are order-insensitive (decontextualised), P4 maximal sharding (one fact per shard), P5 minimal rewording.
- Semi-automatic sharding: (1) LLM segmentation into non-overlapping segments with task-specific few-shot prompts (drop instructions with fewer than 3 segments); (2) LLM rephrasing into decontextualised conversational shards, intent first; (3) verification by execution: simulate 10 Full, 10 Concat (shards as bullets in one turn), 10 Shuffle-concat; keep if P̄_Concat ≥ 0.8·P̄_Full and P̄_Shuffle ≥ 0.8·P̄_Full; (4) author inspection and edit (1–4 hours per task for 90–120 instructions).
- Simulation: user simulator (GPT-4o-mini) holds all shards, reveals at most one per turn, choosing the shard that best fits the conversation (e.g. the one the assistant asked about) and rephrasing without changing content; a strategy classifier labels each assistant turn (clarification, refusal, hedging, interrogation, discussion, missing, answer attempt); an answer extractor pulls the answer span; the task's own evaluator scores it; stop at the first correct answer or when shards run out. Assistant is not told it is in a multi-turn setting.
- Five modes: Full, Concat, Sharded, Recap (final turn restates all shards), Snowball (every turn restates previous shards).
- Six tasks: Code (HumanEval, LiveCodeBench), Database (Spider), Actions (BFCL), Math (GSM8K), Data-to-text (ToTTo, BLEU), Summary (Summary of a Haystack, LLM judge); 600 instructions.
- Metrics over N = 10 runs per instruction: mean P̄, aptitude A90 = 90th percentile score, unreliability U = 90th − 10th percentile.
**Verification / grading.** The original benchmark verifiers (execution for code/SQL, equivalence for API calls and numbers). Manual audit of several hundred simulated conversations: simulator, classifier or extractor errors in under 5%, disfavouring the assistant in under 2%.
**Scale & cost.** 15 models, 600 instructions, 3 main modes, 10 runs: over 200,000 conversations; about $5,000.
**Key results.** Every model drops on every task from Full to Sharded; average −39%. Concat keeps 95.1% of Full (smaller models 86–92%), so the loss is not information loss. Aptitude falls only 16% but unreliability rises 112%: about 50 points between best and worst run of the same instruction for all models, strong or weak. Gradual sharding (31 instructions, 1–8 shards; GPT-4o, 4o-mini): any split into 2 or more shards causes the loss; only 1-shard avoids it. Snowball recovers 15–20% of the gap; Recap more but is unrealistic. Lowering temperature to 0 does not fix multi-turn unreliability. Causes: premature full answers built on assumptions, reliance on earlier wrong attempts (answer bloat), over-weighting first and last turns (loss of middle turns), over-verbose responses.
**Failure modes & limits.** Maximal one-shard-per-turn disclosure is adversarial; LLM user simulator; tasks are single-turn benchmarks retrofitted, not native dialogues; English.
**Tips & tricks.**
- Convert a single-turn task to multi-turn by sharding its spec; reuse the original verifier unchanged.
- Gate each sharded task by executed Concat and Shuffle-concat runs at ≥ 0.8 of Full.
- Let the user simulator choose which shard to reveal based on the assistant's question; reveal at most one per turn.
- Report aptitude (A90) and unreliability (U90−10) over ≥ 10 runs, not just the mean.
- Do not tell the solver it is in a sharded conversation.
**Fit to Crucible Part 2.** F3 knobs: "disclosure pace" (shard count, one per turn vs snowball) is a structural difficulty knob that keeps the oracle and verifier fixed, so it is the cheapest way to make a harder variant of an existing task without new ground truth (§3.6 "hardness from structure"). F6: their Concat/Shuffle-concat gate is a model for gating any transformation (obfuscation, fuzzing, persona) by executed performance relative to the original, rather than by LLM opinion. People facet: the sharded-goal user is the same idea as information sharding in 2509.23124; together they define G8 communicability for dialogue tasks. F9: U90−10 of about 50 points means p̂ from a few runs is unreliable for multi-turn tasks; use k ≥ 8 and Wilson bounds. Priority P1.

## 2510.05444 — SimulatorArena: Are User Simulators Reliable Proxies for Multi-Turn Evaluation of AI Assistants? (Dou et al., 2025; arXiv / Georgia Tech + Microsoft)
Read: PARTIAL (§1–§8 and limitations in full; appendix E attribute lists and G prompts skimmed; detailed results appendix D not read).  Relevance to Part 2: medium-high for the people facet. It gives a method to build user profiles from real conversations (inherent knowledge + message style, with style attributes discovered contrastively between real and simulated messages) and a way to validate a simulator by correlation with human ratings, at about 3% of human-evaluation cost.
**Problem.** User simulators are used to evaluate assistants in multi-turn settings without evidence that they behave like real users or yield the same ratings.
**Method / algorithm.**
- Formal setup: simulator π_u(y | I_u, S_u, H), assistant π_a, rater π_r; information asymmetry between I_u and I_a is required.
- Data: 909 real human–LLM conversations on AMT (107 workers, $20/h, about $10K): 450 math tutoring (MATH levels 3–5; users pick a problem, scratch pad) and 459 document creation (email/letter, creative writing, blog; GPT-4o writes 10 pre-writing questions, users answer at least 6; Canvas-like editor); 9 assistant LLMs; users rate interaction (1–10), document (1–10), submit final math answer, and thumb each turn. Users differ widely: 78.5% of annotator pairs on the same topic and model gave different interaction ratings; in 35.3% of math pairs one reached the right answer and the other did not.
- Simulators (GPT-4o): zero-shot; zero-shot CoT; CoT + user profile. Profile = inherent knowledge (math: concepts from the solution, each labelled knows well / partial / struggling / not introduced from the real conversation; documents: per-type preference attributes, e.g. greeting and sign-off style, extracted from 5 conversations per type) + message style (11 writing + 10 interaction attributes to start; expanded per task by contrastive prompting over 10 real vs simulated conversations for 10 iterations → 12 + 17 for tutoring, 15 + 13 for documents) + optional length control (range from the real user's min/max, rounded outward to multiples of 5).
- Simulator evaluation: (a) message similarity (GPT-4o Likert on writing and interaction style; Turing test of real vs simulated conversation with order swap, ideal 50%); (b) alignment of rater scores on simulated conversations with human ratings on real ones (Spearman at instance, intermediate = model × difficulty or type, and system level), plus outcome agreement (math correctness macro-F1; document rating correlation). Rater chosen by alignment with humans and a self-bias check (GPT-4o; intermediate ρ 0.83–0.89).
**Verification / grading.** Ratings are LLM-judged; math outcome is answer correctness.
**Scale & cost.** Simulated conversation $0.02–0.17 vs human $5.33–6.50 (about 3%).
**Key results.** Profile-based simulators beat zero-shot and CoT on similarity and on alignment (all four significance tests pass); best intermediate Spearman above 0.7, about 26% above vanilla prompting. Best profile depends on task: interaction style only for tutoring (closed goal), full profile for documents (open goal); writing style alone adds little. Zero-shot CoT users write 89.5 words per message vs humans 15.5 (tutoring); length control brings it to 21.4. More profile constraints lower the fulfilment of each interaction attribute (models cannot satisfy many behaviour constraints at once). Best simulator model: GPT-4o for tutoring (0.77), Gemini 2.0 Flash for documents (0.74). Benchmark of 18 assistants with the best simulators: GPT-5 first on both tasks (math 90% correct).
**Failure modes & limits.** Two task types, single sessions; LLM raters; profiles extracted by GPT-4o; ratings are near-ceiling for documents (8.8–9.1 for most models).
**Tips & tricks.**
- Build each simulated user from a profile extracted from a real conversation: knowledge state per concept plus style attributes.
- Discover style attributes contrastively: show real and simulated conversations and ask what differs, iterate.
- Control user message length with a range taken from real data; LLM users are 5× too verbose by default.
- Validate a simulator by correlation of downstream ratings with humans at an aggregated level (model × difficulty), not only by Turing tests.
- Keep the number of behaviour constraints per profile small; fulfilment drops as they grow.
**Fit to Crucible Part 2.** People facet / F2 `ActorSpec`: adopt profile = (hidden knowledge state, preferences, interaction style, length range) as the schema for people in the World, extracted from redacted enterprise traces when available (traces-to-tasks gives real profiles). F1 World loop acceptance: a simulator change is accepted only if alignment on a small human-labelled anchor (or on a fixed real-transcript set) does not fall; this is the user-side version of the anchor set. Diversity: profiles sampled from a real pool are the exogenous randomness §3.5 asks for in F3. Combine with 2601.17087 (multiple simulator families) and 2509.23124 (behaviour modules). Priority P1.

## 2601.08118 — MirrorBench: A Benchmark to Evaluate Conversational User-Proxy Agents for Human-Likeness (Hathidara et al., 2026; KDD 2026 / SAP Labs)
Read: PARTIAL (§1–§5 in full; appendix A extended correlations summarised in §4.3/§4.5; system-architecture appendix C not read).  Relevance to Part 2: medium. A reusable protocol for scoring the user side of simulated conversations for human-likeness, separately from task success, with explicit judge calibration (Human–Human and Proxy–Proxy controls) and human-anchored lexical z-scores; relevant to validating Crucible's simulated people.
**Problem.** User proxies are verbose and over-cooperative, but there was no task-independent measure of how human their turns are.
**Method / algorithm.**
- Reference data: 795 real conversations, stratified samples from ChatbotArena (195), ClariQ (200), OASST1 (200), QULAC (200); English, ≥ 2 turns.
- Goal synthesis: an auxiliary LLM summarises each real conversation's intent, behaviour, tone and persona into a 2–4 sentence goal that conditions the proxy.
- Rollouts: proxy generates user turns; the assistant is conditioned on the reference history so the trajectory stays aligned with the real one; only the user side is scored.
- Lexical metrics on concatenated user turns: MATTR (window 50), Yule's K, HD-D (s = 42), each z-scored against the human distribution of the same dataset (0 = human-like), with t-based 95% CIs.
- Judge metrics (CoT, self-consistency c): GTEval (proxy transcript vs human reference, similarity in [0,1]), Pairwise Indistinguishability (which conversation has the human-sounding user; Δw = win rate − 0.5), Rubric-and-Reason (binary realism verdict on the proxy transcript alone).
- Calibration controls: HH = judge(human, human) and PP = judge(proxy, proxy); PI calibrated as clip((raw − μ_PP)/(μ_HH − μ_PP), 0, 1).
**Verification / grading.** Human-judge correlation (Claude-4-Sonnet judge): GTEval Spearman 0.607–0.697, PI 0.532–0.671 over 3 datasets × 3 proxies (all p < 0.001). Judge sensitivity: with proxy and assistant fixed to GPT-4o, GTEval ranges about 0.45–0.81 by judge; PI flips sign by judge family (GPT judges prefer GPT proxies); RNR saturates at 0.96–0.98 for GPT judges.
**Scale & cost.** 795 conversations × 6 proxies; token cost dominated by the judge; multi-seed SD ≤ 0.016.
**Key results.** Most human-like proxies by judges: Gemini-2.5-Pro and Claude-4-Sonnet; GPT-4o middle; GPT-5 and GPT-OSS-120B trail. A fine-tuned LLaMA user-simulation model (USP) beats several larger general models on GTEval and RNR. Realism and diversity diverge: on QULAC all proxies are less lexically diverse than humans (templated clarifications); on ClariQ Claude and GPT-5 are more diverse than humans. Assistant swaps barely change proxy rankings. Goal ablation: no goal collapses realism (GTEval 0.554 → 0.156 for GPT-4o on ChatbotArena; PI to 0 on ClariQ); a topic-only goal raises PI but lowers GTEval (fluent but off-objective).
**Failure modes & limits.** Judge-family bias remains; English, four datasets; goal descriptions written by an LLM from the real conversation; human-likeness is not the same as eliciting the same agent behaviour (compare SimulatorArena).
**Tips & tricks.**
- Score simulated users with both lexical z-scores against real users and judge-based realism; they disagree.
- Run HH and PP self-comparisons to calibrate any pairwise judge; report the calibrated score.
- Never use a judge from the same family as the proxy for pairwise indistinguishability.
- Condition proxies on a rich goal (intent + behaviour + tone + persona); topic-only goals sound human but drift off task.
- A small fine-tuned user model can match frontier models on realism.
**Fit to Crucible Part 2.** World/people loop (§3.8): add a "user realism" health check per simulator version with HH/PP-calibrated judges and lexical z-scores against redacted real transcripts; a simulator update that raises task success but lowers realism should be rejected. Judge discipline: the PI family-preference result is more evidence for the different-family rule in §3.9 (the user-simulator judge must not share the simulator's family). Since Crucible's swarm uses several families for people, MirrorBench-style scores can choose the simulator family per domain. Priority P2.

## 2507.22034 — UserBench: An Interactive Gym Environment for User-Centric Agents (Qian et al., 2025; arXiv / Salesforce)
Read: PARTIAL (§1–§7 in full; appendix A comparison traits; appendices B–C environment and metric details summarised from the main text).  Relevance to Part 2: high as a generator design. Tasks are built combinatorially from a curated bank of preferences, each with many validated implicit phrasings, plus per-task option databases with correct / wrong / noise items, so solvability, verification and difficulty (preference count per aspect) are all by construction and scale to 10K+ scenarios.
**Problem.** Agents are tested on fully specified goals; real users are underspecified, reveal preferences incrementally and express them indirectly.
**Method / algorithm.**
1. Preference bank: 5 travel aspects (flight, hotel, apartment, car rental, restaurant), 24 categories, 82 preferences, 902 implicit expressions; each expression validated to (i) not state the preference explicitly and (ii) still imply it unambiguously (e.g. "my schedule is packed tight" → direct flights).
2. Scenario generation: random combination of preferences across aspects; difficulty tier by preferences per aspect (Travel-22 easy … Travel-444 hard); GPT-4o writes an ideal arrangement statement.
3. Tools: per-aspect search tools over pre-generated options per scenario: 1 best (meets all preferences and is cheapest), 3 correct, 10 wrong (violate ≥ 1 preference), 5 noise (irrelevant to the query); GPT-4o generates options under human supervision; search returns options only if arguments match the ground-truth query.
4. Environment (Gymnasium reset/step): an oracle user (GPT-4o, temperature 0) holds the hidden preferences; on reset gives only trip basics; reveals a preference implicitly when the agent asks about the relevant aspect, or proactively after a fixed number of turns without progress. Variants: corrupted search results at a set frequency; budget-aware best-option reward.
5. Actions: search, action (talk to user), answer (option IDs).
**Verification / grading.** By construction: best option 1.0, correct 0.8, else 0; averaged over aspects; single-choice (main) or multi-choice (max). Process metrics: valid search rate, valid action rate (questions that probe a real preference), preference elicited (active vs passive). Hack surface: multi-choice rewards shotgun answers; their data show elicitation does not rise while scores do (guessing). Grading is exact on option IDs, so no judge.
**Scale & cost.** 4K+ scenarios (417 test, 2,651 train); 20-turn limit.
**Key results.** Single-choice scores: GPT-4o 0.329, Gemini-2.5-Pro 0.317, Claude-4-Sonnet 0.307, DeepSeek-V3 0.210, Qwen3-14B 0.209, Qwen3-32B 0.206, Qwen3-8B 0.180, Gemini-2.5-Flash 0.125. Multi-choice raises scores by about 40% (GPT-4o 0.710) without more preference elicitation. Preferences elicited under 30% for most models (Claude 34%); valid search above 80% for strong models vs valid action 11–41%. Difficulty is driven mainly by preferences per aspect, not by number of aspects; spreading a fixed number of preferences across aspects is easier. More turns do not help; pass@k raises max but not mean score. Removing 5 distractor options gives only small gains.
**Failure modes & limits.** One domain (travel); LLM-generated options; oracle user is GPT-4o; preference revelation by keyword relevance; "best" depends on budget.
**Tips & tricks.**
- Build tasks from a bank of atomic hidden preferences × validated implicit phrasings; combine randomly for scale.
- Seed each task's database with best / correct / wrong / noise items so the answer key is constructed, not judged.
- Make the hidden user reveal information only when asked about the right aspect, plus a timed fallback reveal.
- Use preferences-per-aspect as the main difficulty dial; it moves scores more than adding aspects.
- Score single-choice; multi-choice invites guessing.
- Track active vs passive elicitation to see whether the agent asks or just waits.
**Fit to Crucible Part 2.** F2/F3/F4: this is a clean pattern for read-and-recommend tasks inside a World: hidden user preferences (latent traits in `SeedBundle`), distractor rows (wrong/noise) seeded in the App, oracle = the unique best row, answer check = exact id; G8 is guaranteed by the reveal rule. DomainSpec knobs: preferences per facet (linkage), distractor counts, implicitness of phrasing, corrupted-tool rate. F9: their tiering gives a band ladder for user-in-the-loop families. F10: "preference elicited" is an on-intent signal: a pass with low elicitation is a lucky pass. Priority P1.

## 2509.19736 — UserRL: Training Interactive User-Centric Agent via Reinforcement Learning (Qian et al., 2025; arXiv / Salesforce)
Read: PARTIAL (§1–§6 in full; appendix A gym construction and C user-simulation justification not read in detail).  Relevance to Part 2: high for user-in-the-loop RL. Eight Gym environments with simulated users behind a three-verb interface (Action / Search / Answer), rule-based state and reward with LLM-generated user replies, training on five gyms and testing on three held-out ones, with direct evidence on (a) trajectory-score design for multi-turn GRPO, (b) training with a cheap open user simulator and evaluating with a strong one, (c) real users differing from simulated ones. The student family (Qwen3) is the same as Crucible's.
**Problem.** No standard way to train agents on diverse, dynamic user interactions; unclear how to shape rewards over turns.
**Method / algorithm.**
- Each gym is a finite automaton: `reset()`, `step()` with deterministic rule-based transitions and turn rewards; user replies from an LLM simulator conditioned on hidden state. Interface: Action (talk to user), Search (retrieve), Answer (submit, verified if goal-oriented). Gyms: TravelGym (UserBench), TauGym (τ-bench), TurtleGym (lateral-thinking story puzzles, new), FunctionGym (infer a hidden number mapping, new), PersuadeGym (change the user's stance; no verifiable answer), IntentionGym (IN3 intent clarification), TelepathyGym (guess the entity, new), SearchGym (Bamboogle). Train: Travel, Turtle, Function, Tau, Persuade (3,426 items); held out: Intention, Telepathy, Search (1,010 test items total).
- Simulated user during training: Qwen3-32B; evaluation: GPT-4o; max 16 turns; SFT cold start with 1K GPT-4o–GPT-4o trajectories per training gym.
- Reward shaping inside GRPO: turn-level mapping (Naive r_t; Equalized constant; Reward-to-Go Σ γ^{j−t} r_j; Exponential Mapping 0.5 + 0.5·(1 − e^{−k r})/(1 − e^{−k})) and trajectory score for group normalisation (Sum, or discounted R2G Σ γ^{j−1} r_j). Advantage per token = (r̃_t − μ_Q)/(σ_Q + η); no KL term.
**Verification / grading.** Per gym: choice correctness (Travel), test-case correctness (Function), τ-bench task completion (Tau), final guess (Telepathy), exact match (Search), sum of turn rewards (Turtle, Persuade, Intention; Persuade measures the simulated user's attitude change, so it is judged by the simulator). Hack surface: Persuade and Intention rewards come from the LLM user's judgments; policy may learn to please the simulator.
**Scale & cost.** 4B and 8B Qwen3 policies; VERL; GPT-4o used only for SFT data and evaluation to limit cost.
**Key results.** Best setting Equalized turns + R2G trajectory score: Qwen3-8B average 0.565 vs raw Qwen3-32B 0.313, Gemini-2.5-Pro 0.470, GPT-4o 0.445; Equalized/Sum worst (8B 0.508). Naive sparse turn rewards collapse training (zero-reward clarifying turns get zero credit). Turn-level scheme matters less than trajectory scoring. SFT cold start is required: RL from raw Qwen3 plateaus early; with SFT some gyms gain over 100%. Training with GPT-4o as the user gives slightly faster growth and higher plateaus than Qwen3-32B, but Qwen3-32B-trained policies transfer to GPT-4o evaluation. Raw-model scaling 4B → 32B adds little without interaction training. Wrapping UserBench and τ-bench in the standard tool interface lowered all models' scores relative to the original benchmarks. Trained models use more effective turns (6.6 vs 2.8 for raw 32B) and score higher on time-weighted reward. With real users on Turtle and Telepathy, trained models scored higher than with GPT-4o users (Telepathy 0.56 → 0.78 for 8B) because humans give cooperative hints, while GPT-4o answers tersely.
**Failure modes & limits.** Simulator-judged rewards in some gyms; small test sets in new gyms (40–78 items); real-user study only on two gyms; no analysis of reward hacking against the simulator.
**Tips & tricks.**
- Keep task state and reward rule-based; let the LLM only voice the user.
- Use discounted reward-to-go as the trajectory score for GRPO in multi-turn tasks; constant turn rewards suffice.
- Never give zero credit to information-gathering turns (naive sparse turn rewards collapse).
- SFT cold start on a few hundred to 1K good trajectories per environment before RL.
- Train with a cheap open user simulator, evaluate with a stronger one from another family; check the transfer.
- Hold out whole environments (interaction purposes) for generalisation.
**Fit to Crucible Part 2.** F1/F2: the "rule-based automaton + LLM voice" split is the right architecture for people in the World: hidden state and reward in code, utterances from the simulator, so verifiers never depend on the simulator's judgment (avoid Persuade-style simulator-judged rewards for training tasks). F9: their result that the user-simulator family changes learning speed and the eval score links to 2601.17087: record the training-time and eval-time simulator ids per DifficultyRecord. F11: held-out gyms are the "held-out families" of §3.10 for dialogue skills. Part 1 (§2(a)) can take the R2G trajectory score and SFT-cold-start findings directly for user-in-the-loop families. Priority P1.
