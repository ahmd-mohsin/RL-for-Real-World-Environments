# Group 02 cards: environment and task synthesis, verifier testing, self-improving loops

**Papers: 29. Read FULL: 27. PARTIAL: 2 (OfficeTown 2610.23194, ProgAgent 2610.14774; bodies in full, some appendices only by heading). ABSTRACT-ONLY: 0.** All full texts came from arXiv HTML. Where a FULL card says "skimmed", it refers to example listings, prompt dumps, trajectory transcripts or supplementary per-family result grids (VHD-Play H.2), never to method sections or the main results.

**Five cross-paper takeaways for Part 2**

1. **Build first, run the reference during generation, and let execution decide which side to repair.** Running the reference solution inside the build session is the largest single yield lever: valid environments rise from 19.5% to 84.8% (GPT-5.6-sol) and from 19.4% to 73.0% (DeepSeek-V4-Flash) (AutoEnvScaling 2610.14163). A failed check should repair the task or the solution, not discard it. Repaired tasks are mostly the hard ones: 75–83% of GRADUS's round-2 and round-3 recoveries are medium-hard or hard (2610.27781). RST runs 15 rounds of this at 498–572 accepted tasks per 1,000 attempts and about $0.05 a task (2608.05466). The LLM may diagnose but must never certify. When an LLM wrote the verifier from the agent's view, 88% of GRPO groups were wasted and the student did not beat its base (Tev 2610.18868). → F1–F6 run as agentic sessions with host-side gates, and every repair round is attributed to a side.
2. **Verifier testing needs more than an oracle check plus a no-op check.** A solution-pass filter alone selects lenient verifiers, and only must-fail negatives removed the false positives (SCA 2506.01716). The strongest gate set in the batch is Tev's eight gates: 14 generic gaming probes, a reward-causality test (mutate each cause), two independently written solvers that must agree, grader and solver code with disjoint import closures, metamorphic cases and stale-output counterfactuals. Three cheap checks are new to us. Perturbed hidden copies of the World stop hard-coded answers: without them accuracy fell to 16.8, against 46.1 with them and 28.1 untrained (EnvLunch 2610.33817). Realisation checks catch decisions whose downstream effects were only partly applied (Interlock 2610.19686). A six-category exploit taxonomy with log-based detectors and four hardening toggles cut exploits by 87.7% at no cost to task success (RHB 2605.02964). → Proposed new gates: G15 exploit probes, G16 reward causality, G17 solver agreement. Also new negative classes for constant answers and partial propagation, and a realisation check kind in F5.
3. **G8 communicability is the most common silent defect, and the batch gives concrete static tests for it.** Examples: test literals that the instruction never states (SETA's all-fail case, 2607.10891). RST's rule that every reward-changing condition must be stated or discoverable. ClawLoop's **answer contract**, which names each hidden rule (filter, rounding, tie-break, join key) without giving values (2610.14118). The external-vs-internal parameter split (EnvFactory 2605.18703; EnvCraft 2609.05576). The rule that a supervised action is valid only if its arguments trace to learner-visible evidence (Trajectory2Gym 2610.33568). The recoverability audit from observed files alone (Data World 2610.21656). Review of failing tests for unstated assumptions (WebUniverse 2610.33149). → G8 becomes a deterministic pre-rollout gate over three things: oracle argument provenance, verifier assertions checked against the instruction and World, and hidden decision rules checked against a declared contract.
4. **Coverage must be enforced at corpus level, with structure, not by prompt variety.** In GRADUS, removing the global (policy, outcome) ledger was the largest ablation (telecom 0.75 → 0.54). Tev requires a strength-2 covering array over 19 axes. Trajectory2Gym counts support per realised capability path and synthesises toward deficits; random subsampling misses rare paths. RST enforces caps per parent, per family and per cohort, plus a lineage-recoverability gate. Composed multi-App tasks beat single-App tasks at equal data (CompoWorld 2609.33665: AutomationBench 12.83 → 33.33). Breadth of domains or families helps at a fixed trajectory count (Interlock 16 → 128 domains; WebUniverse's text + vision mix, where vision-only data hurt functional skill). AZR's dynamic K references were worth about 5 math points. → The F3 prompt gets a coverage ledger. F11 enforces a covering array and caps. F7 measures cell membership from realised paths.
5. **Structural hardness is cheap to produce and easy to mislabel, so it must be paired with intent probes and re-measurement.** RES drops frontier pass rates from about 85% to 6–29% with inherited access transformations; independent single transformations barely changed difficulty (93.3% vs 6.7% pass) (2610.16397). RST and ProgAgent produce hardness mainly through length and data volume. The interface changes what a task measures: under DTC, pass@8 falls from 0.95 to 0.42 as the World grows, while under PTC it stays above 0.87 (ProgAgent). Revealing all parameters still left the model at 0.231 against 0.962 written-out (VHD-Play 2609.27321). Pass-rate-conditioned mutation operators miss their declared direction 23–40% of the time (SETA). A self-directed difficulty controller overshot (ClawLoop). An untrained shared proposer decayed from 86.8% to 22.4% valid and training collapsed (AutoEnvScaling). → Every knob move needs re-measurement per student. F10 adds a budget-2× probe, a direct-access or written-out probe, and an interface probe. For tasks where the 35B's p is below about 0.05, use a verified progress potential reward (Tev PPRS): at 27B, terminal-only reward could not complete one optimiser step.

## 2410.12952 — Facilitating Multi-turn Function Calling for LLMs via Compositional Instruction Tuning (BUTTON) (Chen et al., 2024; ICLR 2025 per arXiv v2, venue line not in text)
Read: FULL (body; appendices A prompts, B data, C metrics/implementation/ablation prompts; C.4 parallel-call cases skimmed).  Relevance to Part 2: medium-low. It is an SFT data pipeline with LLM-simulated tools and no verifier, so it fails our "execution decides" rule; its value is the bottom-up composition recipe (atomic task → composed task → tools derived from the sub-task breakdown), which is a clean pattern for F3/F4 compositional hardness.

**Problem.** Function-calling data was mostly single-turn; real queries need decomposition and planning over several calls, and no source pairs compositional instructions with matching functions and labelled multi-turn trajectories.

**Method / algorithm.** "Bottom-Up Then Top-dOwN", every step run by GPT-4o (2024-05-13).
1. *Scenario collection.* Extract a ≤10-word scenario ("booking flights") from each conversation of glaive-function-calling-v2 and ToolLLaMA; dedup by sentence-embedding similarity above a threshold (value n/r); expand by asking the LLM to alter the action or subject of a scenario.
2. *Atomic task.* One prompt turns a scenario into a single-step task: realistic, self-contained (all needed values given, no clarification possible), function-agnostic (no tool names, no hints), ≤30 words.
3. *Composition.* Two heuristics only: **sequential** (add a subsequent task that consumes the first task's output) and **parallel-then-sequential** (add an independent parallel task, then a subsequent task needing both outputs). Few-shot examples in the prompts. The sub-task set S_i is kept as privileged metadata.
4. *Filter.* An LLM judge checks whether the sub-tasks suffice to complete the composed task (yes/no after reasoning); failures dropped. Yield n/r.
5. *Function generation from the breakdown.* Functions are written after the task, per sub-task: descriptive, general (get_weather(city), not get_weather_in_london), granular, and output-to-input consistent across sequential calls. A sub-task needing only logic/comparison/arithmetic gets zero functions. Schema: name, description, parameters, required, responses.
6. *Top-down trajectory.* Three LLM agents: a user (knows the task, withholds solution steps), an assistant (sees tools, the task and the sub-task breakdown; ReAct-style observation/thought/call; plans in turn 1; calls final_answer), and one tool agent per function that role-plays execution from the definition, told it "never makes errors". The breakdown is removed from the final data.
7. *Parallel-call control.* For tasks whose sub-tasks can run in parallel, 50% of trajectories are generated under a "one call at a time" system prompt and labelled with it; the rest use the "parallel allowed" prompt.
8. Mix 8,000 BUTTONInstruct samples with 100k OpenHermes-2.5 samples; full-parameter SFT (lr 2e-5 cosine, batch 64, 5 epochs for 7–8B, 2 for 70–72B, 8,192 tokens, loss on assistant turns, 32×H800).

**Verification / grading.** None during synthesis beyond the composition filter: tools are simulated, so trajectories are never checked against state. Evaluation uses GTA (229 queries, 14 real tools) and Tool-Query (60 tasks, real APIs, subgoal labels); they relaxed Tool-Query exact match to "answer substring present", which is itself hackable by verbose answers.

**Scale & cost.** 8K trajectories; token or $ cost n/r.

**Key results.** GTA end-to-end answer accuracy: Llama3-8B 1.4 → 30.5; Qwen2-7B 13.1 → 27.3; Qwen2-72B 27.3 → 45.7 (GPT-4o 46.0). Tool-Query success: Llama3-8B 5.0 → 35.0; Llama3-70B 31.7 → 58.3; Qwen2-72B 41.7 → 58.3 (GPT-4o 40.0). Grounding accuracy was already ≈95% before tuning; the gain is in planning (process and success). Ablation (Tool-Query, Llama3-8B/70B): replacing bottom-up with a monolithic "write a complex task" prompt, or the multi-agent rollout with one monolithic prompt, cost on average 15.0% relative success and 7.5% relative process rate; the small model lost more (16.1% vs 6.4%). Data 2k → 8k raised success 21.7 → 35.0, with larger gains on hard items. Disabling parallel calls: success 35.0 → 28.3.

**Failure modes & limits.** Authors: no verification step; quality rests on prompts. Mine: simulated tools that never fail teach no error recovery and no stateful consistency; the assistant sees the gold breakdown, so trajectories are "privileged demonstrations" that can encode leaks; only two composition shapes (depth ≤ 3); the evaluation sets are tiny (60 and 209 items) with no variance reported.

**Tips & tricks.**
- Compose from atomic, self-contained sub-tasks; keep the breakdown as privileged metadata, never in the instruction.
- Derive tools from the breakdown, with a "general, not task-named" rule, to avoid one tool per task.
- Allow zero-tool sub-tasks (reasoning steps) so plans mix computation and calls.
- Filter composed tasks by checking that the sub-tasks jointly entail them.
- Toggle behavioural knobs (parallel calls) by system prompt and generate matched data for both settings.

**Fit to Crucible Part 2.** F3/F4 and §3.6 "hardness from structure": the sequential and parallel-then-sequential operators are a cheap, typed composition knob (depth, width) over verified sub-tasks, but in Crucible each sub-task must first have its own executed oracle, so the composition is a program join, and the joined oracle must re-run (G2/G3). Adopt the "privileged breakdown" field into `TaskProposal.privileged_notes` and use it for the F10 single-subtask ablation. Avoid simulated tools and a privileged assistant as a ground-truth source. Priority P2 (pattern only).

## 2506.01716 — Self-Challenging Language Model Agents (Zhou et al., 2025; venue n/r, UC Berkeley + FAIR at Meta)
Read: FULL (body, appendices A–H incl. challenger prompts, compute and hyperparameters; Figure 4 values are only in the figure, not in the text).  Relevance to Part 2: high. Code-as-Task (instruction + verifier + example solution + failure cases, all executed) is the minimal version of our F4–F6 spine; its ablation is the cleanest published evidence that a solution check alone inflates false positives and that negatives remove them.

**Problem.** Training tool-use agents with RL needs many feasible, verifiable, non-trivial tasks; human annotation does not scale, and LLM proposers without grounding produce ambiguous or impossible tasks.

**Method / algorithm.** One model plays two roles.
1. *Challenger* (π_task): an agent that first calls the environment's tools (up to 15 steps; the web prompt asks for about 10 exploratory exchanges) to read hidden state (users, orders, reservations), then emits a **CaT**:
   - instruction (natural language; for τ-bench it is a user-simulator script with persona and hidden goal);
   - `evaluate()`: Python that queries the DB (τ-bench) or string-matches an expected output (M3ToolEval);
   - an example solution (tool-call code);
   - ≥3 failure cases: near-miss solutions (wrong item id, wrong payment method, cancel instead of update).
   Prompts insist: never invent ids not seen through tools, run the solution and check before answering, be different from the examples. After generation, ids the solver should discover (the order number) are redacted from the instruction.
2. *Automatic checker*: reset the hidden DB, then check (a) all code runs, (b) solution passes `evaluate`, (c) every failure case fails. On failure the traceback goes back to the challenger to revise.
3. *Executor* (π_exec): trained on kept tasks. Self-improvement uses the same Llama-3.1-8B for challenger, executor and (in τ-bench) the user simulator, with one-step REINFORCE on 0/1 reward (≡ rejection fine-tuning on successes). Distillation samples Llama-3.1-70B trajectories on the tasks and SFTs the 8B on all of them, failures included.
4. Hyperparameters: RFT lr 1e-5, 6 epochs; PPO/GRPO lr 1e-6, 32 tasks × 8 rollouts per iteration, KL 0.001, clip 0.1, 16k context.

**Verification / grading.** Executed verifier on end state or answer. The three-way check is a gold-sanity plus negative-kill test. Remaining hole: under-specified instructions (false negatives) such as "return one of my latest orders", which execution cannot detect. They also found 40% of τ-bench Airline test tasks pass with no action and removed them, a null-agent defect in the benchmark itself.

**Scale & cost.** 800 synthetic tasks and 12k rollouts per setting. Filter survival with Llama-3.1-8B as challenger: runnable verifier 47.7%; + solution passes 9.5%; + all failure cases fail **5.2%**. Compute (8×A100-hours): challenge generation 8 (Calculation, Web) to 32 (Retail, Airline); rollouts 24; RFT 3; eval 0.5–2.

**Key results.** Average pass@1 over four environments: Llama-3.1-8B 12.0 → 23.5 self-improving (PAE baseline 12.9); distillation 32.2 (PAE 30.1). PAE's ungrounded tasks drove Airline pass@4 to 0. Calculation: RFT/DPO 20.3 → 31.8, online PPO/GRPO 43.2, but GRPO collapsed to 0 late without careful tuning. Human audit of 50 Retail rollouts per variant (200 trajectories, 8 human-hours): adding the solution check cut false negatives but *raised* false positives, because lenient verifiers pass the solution filter and the filter amplifies them (some passed with no action at all); adding failure cases removed all false positives; false negatives from missing information remained. Filtering narrowed the difficulty distribution (solution length) for the 8B challenger but not for the 70B. Scaling: 200 or 400 tasks with more rollouts per task improved train but not test; only 800 tasks gave steady test gains. Joint training over all four environments gave no gain over per-environment models (23.0 vs 23.5); gains are environment-specific. A gap remains to 800 human-curated oracle tasks under PPO.

**Failure modes & limits.** Authors: under-specification FNs; environment-specific gains; weak models are prompt-sensitive. Mine: the challenger writes its own negatives, so they are near-misses it can imagine, not adversarial; there is no side-effect negative and no collateral check, so "did the right thing plus extra damage" passes; τ-bench user simulated by the 8B itself at train time; no difficulty targeting beyond the filter.

**Tips & tricks.**
- Require the proposer to explore the World through the same tools before proposing; ban ids not observed.
- Reset the World before checking each proposal; send the traceback back for revision.
- A solution-pass filter alone selects for lenient verifiers: always pair it with must-fail negatives.
- Redact discoverable identifiers from the instruction after construction.
- Run a null agent on every benchmark task; drop tasks that pass with no action.
- Prefer more tasks over more rollouts per task for generalisation.

**Fit to Crucible Part 2.** Direct evidence for G3 (solvable), G4 (null agent), G5 (negatives fail) and the F5 `NegativeSet`. Adopt the revise-on-traceback loop for F4/F5 repair rounds. Adapt: negatives must come from our mutation operators and a different-family builder, plus a side-effect class (§3.3), rather than from the proposer. The residual under-specification FN maps onto G8 communicability and the F10 null-instruction probe; SCA shows execution alone cannot catch it, so G8 must be a separate check (every value the oracle uses is visible in the start state or the user's known info). The "tasks not trajectories" scaling result supports the many-families plan in §3.10. Priority P0 (it is already the model for G3–G5; make the side-effect class and G8 explicit).

## 2505.03335 — Absolute Zero: Reinforced Self-play Reasoning with Zero Data (Zhao et al., 2025; venue n/r, ICML-style preprint, Tsinghua/BIGAI/Penn State)
Read: FULL (body; appendices A–D incl. hyperparameters, validation code, complexity/diversity metrics, failed alternatives; prompt figures are images, not in the text).  Relevance to Part 2: medium. It is single-turn code reasoning, not agentic environments, but it is the canonical "learnability-rewarded proposer + executor as ground truth" design, and its ablations (dynamic references, determinism check, failed composition curriculum) transfer directly to F3, G2 and the task loop.

**Problem.** "Zero" RLVR still needs human-curated question–answer sets; can one model generate its own learnable, verifiable curriculum and improve general reasoning from it?

**Method / algorithm.** One LLM π_θ with two roles and three task types over triplets (program p, input i, output o = p(i)):
- *Deduction*: proposer emits (p, i); executor computes o; solver predicts o from (p, i).
- *Abduction*: proposer emits (p, i); solver predicts an input given (p, o); checked by p(i_π) = o (non-bijective programs allowed).
- *Induction*: proposer takes a program from the deduction/abduction buffers and emits N inputs plus a natural-language message m; solver sees half the I/O pairs and m and must write a program passing the hidden half (discourages if-else lookup tables).
Loop (Algorithm 1), per iteration:
1. *Seed.* Buffers start from B×S (S = 4) triplets generated by the base model from a single identity-function "zero triplet"; no model updates during seeding.
2. *Propose.* For deduction/abduction, condition on K = 6 uniformly sampled past triplets and ask for a *different* one; for induction, sample a program and generate inputs + message.
3. *Validate and construct* (the gate): (a) integrity: runs without error and returns something; (b) safety: forbidden modules list (os.sys, sys, shutil, subprocess, threading, random, datetime, time, hashlib, etc.); (c) **determinism**: run twice (j = 2), outputs must be equal. Only valid proposals count as correctly formatted.
4. *Fill.* If fewer than B valid proposals, top up from the buffer of past validated triplets. Every valid triplet enters the buffer whatever its reward.
5. *Solve and reward.* Solver reward r_solve = 1 if the answer is value-equal to gold. Proposer reward is a learnability score from G = 8 solver Monte Carlo rollouts: r_propose = 0 if the mean solve rate r̄ = 0, else 1 − r̄ (so the easiest solvable tasks earn least, unsolvable tasks earn nothing). Format penalty: −0.5 well-formatted but wrong, −1 format error.
6. *Update* with Task-Relative REINFORCE++: advantages normalised separately for each of the six (task type × role) groups, PPO clip objective, no KL, entropy 0.001, lr 1e-6, batch 64×6, 500 steps, veRL, 3–5 days on A800 clusters.

**Verification / grading.** Python execution is the only judge; gold answers are produced by running the proposer's program. Known leaks they chose to keep: global variables and comments in programs can reveal answers; removing them *lowered* performance (the solver used them as hints, and the proposer was not told about the post-processing).

**Scale & cost.** "Unlimited" tasks; max 16,384 programs in a buffer; 500 steps; GPU-hours n/r beyond "3–5 days".

**Key results.** Qwen2.5-7B-Coder: overall average 40.2 → 50.4 (code 56.6 → 61.6; math 23.9 → 39.1), beating zero-style models trained on 2k–484k curated pairs by 1.8 points average. Gains grow with scale: Coder 3B/7B/14B +5.7/+10.2/+13.2. Llama-3.1-8B only +3.2 (below SimpleRL). Ablations on 7B base (overall avg): deduction only 43.3; without induction 43.8; **fixed prompt instead of K dynamic references 43.8 (math −5.3, code −0.8)**; solver-only training (proposer prompted but not trained) 45.4; full 46.8. Seeding from LeetCode raised early coding scores but plateaued at the same level, and math was lower than self-generated seeds. Proposed-program complexity and AST-edit diversity rose during training without being rewarded.

**Failure modes & limits.** Authors: safety-concerning CoT from Llama ("uh-oh moment"); deterministic programs only. Failed alternatives worth knowing: an error-type prediction task gave nothing; a **composition curriculum f(g(x)) collapsed** to f returning g(x) unchanged; explicit complexity and diversity rewards gave no measurable gain; recency-weighted reference sampling risked collapse; multiplicative reward aggregation was less stable than additive. My critique: the learnability reward favours tasks the *current* solver rarely solves, which also rewards near-impossible-but-lucky tasks (r̄ = 1/8 gets 0.875); no external audit of label correctness beyond execution, which is sound here only because the executor is the ground truth.

**Tips & tricks.**
- Determinism gate: run the oracle twice and compare outputs before admitting a task.
- Condition proposals on K sampled existing tasks and ask for a different one; it was worth about 5 math points.
- Normalise advantages per (task type, role) in multi-task self-play.
- Top up a short batch from the validated buffer so training batch size stays fixed.
- A composition operator needs an executed check that the composite differs from its parts, or it degenerates.
- Seeding from an external dataset helps early but does not raise the ceiling.

**Fit to Crucible Part 2.** G2 determinism (already cited) and F3's "K nearest tasks as do-not-repeat references" (already cited in §3.5) both come from here; keep them. The learnability reward 1 − r̄ with zero at r̄ = 0 is a usable F11 archive score for self-play sources; prefer a band-centred score (§3.6) since 1 − r̄ peaks near the "rarely solved" edge. The f(g(x)) = g(x) collapse is a direct warning for §3.6 "hardness from structure": F7 must verify that a composed task's behaviour signature differs from its parents', which the plan already demands for variants; apply it to compositions too. AZR's comment/global-variable leakage shows that leak rules (G11) can conflict with learning signal; measure before stripping. Priority P1 for the self-play source (later), P0 for the two already-adopted mechanisms.

## 2609.33665 — Compositional Environment Scaling for General Agents (CompoWorld) (AllSpark Team: Yang, Xu et al., 2026; venue n/r)
Read: FULL (body; appendices A gradient analysis, B world-model scope, C calendar mock; D trajectory skimmed).  Relevance to Part 2: high. It trains *our student* (Qwen3.6-35B-A3B) with a swarm-style synthesis model (GLM-5.3), and shows that composing reusable verified services into cross-service tasks beats single-service tasks at equal data, which bears on F1 (App library), F3 (walk-based proposal), §3.6 knobs and the reward shape.

**Problem.** Environment-scaling work generates tasks inside one environment; real workflows move information and state across several services, and single-environment training does not teach that.

**Method / algorithm.**
1. *Service library (F1-like).* Crawl public MCP specs, keep self-contained apps, normalise to function-calling schemas. A coding agent (pi harness, sandboxed; GLM-5.3) infers entities, writes a **Pydantic state model** (unknown fields and invalid updates rejected), implements every tool as a state transition returning unified JSON `{success, data | error{code,message}}`, and writes its own tests (normal use + error handling), repairing until they pass. **A separate agent session writes adversarial, boundary tests from the spec only**; tools failing them are quarantined from the deterministic set.
2. *Selective world model.* Tools that cannot be implemented locally (external systems, model inference) are served by an LLM that predicts (s′, o); the update is instantiated through the same Pydantic models so state stays type-valid. Share: 7.1% of tools, about 10% of samples touch one.
3. *Composition.* Product environment E_C over K services: joint state is the tuple of service states; namespaced actions; an action changes only its own service. Sample K = 5 services plus **5 distractor services** for tool discovery. Draw a *walk* of length L ∈ [7, 12] over them with constraints: covers every chosen service, no consecutive repeats, L > K so at least one revisit, where a revisit is meant to force re-reading a value made stale by an intervening step. Each edge means the next service's input can only come from the previous service's observation. The walk records service-level dependencies, not a tool sequence.
4. *Agentic task authoring* (bounded revision loop): explore (call the services), design (scenario from the walk, a validated s0, instruction u, a rubric of objective criteria), **probe** (the author solves the task by actually executing the walk; the end joint state becomes the reference goal g), translate each rubric criterion into an executable final-state check v, require v(g) = 1 and that every tool the task uses was exercised by the probe, then submit. v checks task-relevant conditions only, so alternative paths can pass.
5. *Agent interface.* Four meta-tools: list_services, list_tools, describe_tool, call_tool.
6. *Training.* SFT on 3K successful DeepSeek-V4-Flash trajectories (3 epochs, batch 32, lr 1e-4), then GRPO on 1K tasks (N = 8, clip 0.20/0.28, lr 1e-5, no KL or entropy). **Completion-Focused Rubric Reward**: per group, criterion pass rate p_j; weight w_j = λ + (1 − p_j), λ = 0.01; R_i = Σ w_j b_ij / Σ w_j, so R = 1 only when all pass and rarely satisfied criteria dominate the advantage. The gradient analysis shows each criterion's coefficient is proportional to its completion gap; a criterion every rollout fails still gives zero signal.

**Verification / grading.** Executable final-state checks from a rubric, accepted on the author's own probe. No negatives, no collateral check, no independent second solver: the author writes the task, solves it and writes the checks, so a check that is too lenient (or one that only passes the author's path) is not detected. World-model tools make some observations unverifiable.

**Scale & cost.** 448 services, 10,130 tools; software/DevOps 22% of services, productivity 12%, no domain above a quarter. Candidate compositions C(448,5) ≈ 1.47×10^11. 3K SFT trajectories, 1K RL tasks, 150 RL steps. Yields per stage, tokens and $ n/r.

**Key results.** Qwen3.6-35B-A3B, eight benchmarks, average +9.17: AutomationBench pass 10.33 → 32.33 (GPT-5.4 27.67, Opus 4.6 25.50, DeepSeek-V4-Flash 36.33); SkillsBench +15.19; VitaBench +10.50; VitaBench 2.0 only +1.62; τ³-Banking 10.65 → 16.49. The 397B (Qwen3.5-397B-A17B) baseline scores 5.50 on AutomationBench, below the 35B. **Composed vs single environments at 1K SFT trajectories and equal environment count**: τ³-Banking 9.62 → 17.53, AutomationBench 12.83 → 33.33; single-environment SFT slightly *hurt* τ³-Banking and DeepPlanning versus the base. SFT size: gains at 100 examples; AutomationBench 33.33 at 1K vs 32.67 at 3K; SkillsBench peaks at 1K (45.13) and falls to 40.91 at 3K. Reweighting vs uniform rubric: eval score about 0.76 vs 0.67 at step 140. RL added only 1.2 points over SFT on average and lowered τ³-Banking; most of the gain is SFT.

**Failure modes & limits.** Authors: finite tests cannot capture real business rules; environment quality judged mainly by downstream gains plus spot checks; simulation errors propagate inside affected workflows; uniform rubric scores saturate after SFT while full completion stays low. Mine: no per-stage yields or quarantine rates; benchmark-level judges are a Qwen model; "revisit forces stale re-read" is asserted, not verified; no intent or shortcut checks; the more-data plateau (SkillsBench drop at 3K) hints at distribution narrowing.

**Tips & tricks.**
- Give each App a typed state model that rejects unknown fields; make every tool return one JSON envelope with explicit error codes.
- After the builder's own tests pass, run a *separate* session that writes adversarial tests from the spec; quarantine failures.
- Add distractor Apps to every task so tool discovery is part of the skill.
- Use walk length L (with forced revisits) as the main difficulty knob, separate from service count K.
- Weight rubric criteria by group failure rate (w = λ + 1 − p) so RL does not stall on saturated partial credit.
- Keep simulated tools to a small, measured share and report it.

**Fit to Crucible Part 2.** F1: adopt the typed-state + unified envelope + independent adversarial tester pattern; it matches our blind tool tester role and the G13 interaction-completeness gate. F3/§3.6: add `walk_length`, `services`, `distractor_apps` and `revisits` to the DomainSpec knob schema, and record the walk in `BehaviourSignature.cross_app_flows` so F7 can confirm the claimed cross-App dependency was actually exercised. F4: the "probe" is our oracle-by-construction; add G2 determinism and G5 negatives, which CompoWorld lacks (side-effect negatives especially, since multi-App tasks have many orthogonal rows to damage). F5/reward: the completion-focused weighting is a cheap drop-in for multi-criterion `Grade` components; keep the binary all-pass as the keep-rule metric. The composed-beats-single result supports making "cross-App" an axis of the coverage grid. ## 2605.18703 — EnvFactory: Scaling Tool-Use Agents via Executable Environments Synthesis and Robust RL (Xu et al., 2026; venue n/r, HKUST-GZ + Huawei)
Read: FULL (body; appendices B–I incl. compute/token table, algorithms, EnvGen tester/reviser prompts, ToolGraph and QueryGen prompts).  Relevance to Part 2: medium-high. It gives a concrete F1 build-test-revise loop with a three-layer tool test, a dependency-resolving tool-chain sampler for F3, and an "external vs internal parameter" split that is exactly the G8 communicability rule; its reward (trajectory match + state) and its reviser's freedom to blame the test are things to avoid.

**Problem.** Agentic RL for tool use lacks stable stateful environments (real APIs are slow and costly, simulators hallucinate, synthetic ones are stateless or need pre-collected docs) and its synthetic queries are over-specified "instruction lists", not natural intents.

**Method / algorithm.**
1. *EnvGen (F1).* (a) A Search Agent inspects the current pool for coverage gaps, searches the web for real API docs and usage examples, and writes environment metadata (description, tool definitions, schemas). (b) A Code Agent (Kimi-K2-Thinking) writes a Pydantic DB schema with load/save serialisation (session isolation, reproducibility) and Python tools wrapped as an MCP server, with `load_scenario` and `save_scenario` tools. (c) A Test Agent writes test scenarios at four complexity levels (simple 1–2 entities; medium 3–5 with edge values; complex 5–10 with relations; boundary: empty collections pass, extreme values, invalid inputs must raise a validation error, each tagged `expected_behavior`), then validates in three layers: L1 load the scenario (blocking), L2 2–3 cases per tool (valid, boundary, error), L3 save and compare the state with original + expected modifications. (d) A reviser classifies errors (Pydantic, load/save, tool logic, state, schema mismatch), fixes CRITICAL first, and **may declare a failure a "scenario problem"** (bad test) instead of a code bug. Loop until all pass or the revision budget ends. Success 92.9% per environment, 192K prompt + 31K completion tokens, about 3 min.
2. *Tool graph.* Nodes are tools and their parameters. Edge v_i → v_j if any output-parameter embedding of v_i (BAAI/bge-m3) has cosine similarity above a threshold (value n/r) with an input parameter of v_j. Then an LLM per environment adds missing logical edges (parameter-less tools like delete_all_notes would be isolated) and prunes spurious ones.
3. *Topology-aware sampling (F3).* An LLM labels each input parameter **external** (a user can supply it: city, name) or **internal** (system state: hotel_id). A tool may join the chain only when every required input is optional, external, or produced by an already-sampled tool; otherwise SamplePriors recursively walks inverse edges to add a producer (depth ≤ 3; with probability 0.1 it adds a producer even when not needed, for diversity). Then BFS forward to 1..k outgoing neighbours for branching (non-linear chains).
4. *QueryGen.* Plan a persona and scenario from the chain; build a DB state that fits the schema; split the chain into turns of 1–5 tools. Per turn: decompose into subgoals, articulate a request, then apply four refinements: implicit reference (replace ids by context), action compression (drop inferable steps), ambiguity introduction, goal expansion (related secondary goal). The simulated user knows only external parameters and executes "user tools" (login, reset_password, physical actions) when instructed. Generate k candidate trajectories with an agent in the sandbox; pick the best by DB-state change (selection procedure partly LLM-based, details thin); strip redundant calls; mask arguments that do not affect correctness.
5. *Training.* SFT (Qwen3-30B-A3B-Thinking trajectories, failed calls removed), then GRPO (DeepSeek-V3.2 trajectories; lr 1e-6, 8 rollouts, batch 256, 16k tokens, 10 epochs, each turn a sample). Reward R = α·R_traj + (1 − α)·R_state − γ·P_length.

**Verification / grading.** Tools: three-layer executed tests against saved state. Tasks: the reference trajectory and its end DB state; reward mixes trajectory match (penalises valid alternative paths, rewards imitation) and state equality. No negatives or hack tests.

**Scale & cost.** 85 environments, 842 tools, 7 domains; 1,622 SFT + 953 RL conversations (4.82 turns, 3.29 steps per turn). Trajectory synthesis about 1.2 min per conversation asynchronously; SFT trajectories 85.4% success, RL 88.2%; 1,000 trajectories about 20 GPU-hours on 2×80GB. SFT 10 GPU-h, RL 20 GPU-h on 8×80GB (Qwen3-4B).

**Key results.** Qwen3-4B overall 24.09 → 30.77 (EnvScaler 29.56 with 191 envs/11,572 tasks; AWM 25.47 with 526 envs); BFCL multi-turn 33.50 → 48.50; Qwen3-8B MCP-Atlas pass 5.15 → 13.75. 50 → 75 → 85 environments: rising with diminishing returns. Refinement vs none at 250 SFT trajectories: +0.4 to +1.0 overall on BFCL categories (small). α sweep: α = 0.5 best (41.38); α = 0 (state only) and α = 1 (trajectory only) both worse. Direct RL without SFT gains less and is less stable.

**Failure modes & limits.** Authors: stateful MCP needs one connection per session, a throughput bottleneck. Mine: the reviser can relabel failures as test defects with no independent check, which is exactly how a builder games its own tests; the expected state in L3 is judged by the tester LLM, not frozen; "external vs internal" is an LLM label, not verified; trajectory-match reward teaches imitation of one path; MCP-Atlas evaluated on 291/500 tasks; baselines are released checkpoints at different scales; refinement gains are within noise.

**Tips & tricks.**
- Give every App `load_scenario`/`save_scenario` so tests and graders can snapshot and diff state.
- Write tool tests at four complexity tiers and tag each with expected pass vs expected validation error.
- Make scenario loading a blocking first test layer.
- Label every tool parameter external (user-known) or internal (must be read from the World); constrain the simulated user to external values.
- Resolve producers recursively before adding a consumer to a sampled chain.
- Mask arguments that do not affect correctness (limit, page size) before grading.

**Fit to Crucible Part 2.** F1: adopt the layered test (load → per-tool cases → save-and-diff) and the four tiers for the blind tester; **reject the reviser's "scenario problem" escape** unless a different-family checker approves it, as §3.9 already requires ("debugger cannot edit expected states"); freeze expected digests at write time. F3/F4: the external/internal labelling is a cheap, typed implementation of **G8 communicability**: store it in `ToolSpec` (per-parameter `provenance: external|internal`) and have G8 check that every external value the oracle uses appears in the instruction or the user's known info, and every internal value is produced by an earlier oracle call. The recursive producer sampler is a good F3 seed generator for `knob: linkage`. Argument masking maps onto column policies (exempt). Avoid trajectory-match reward; our state checks + path constraints cover it. Priority P1.

## 2609.05576 — EnvCraft: Synthesizing Executable Environments in Agentic RL for Claw-like Agent (Zeng et al., 2026; venue n/r, HIT SCIR/PKU/Huawei/Tsinghua)
Read: FULL (body; appendices B taxonomy and archetypes skimmed, C prompts/constraints/cross-artifact rules, D hyperparameters, reward handling, quality rubric, calibration, ablation).  Relevance to Part 2: high for F1 engineering contracts and F5/F6 consistency rules; medium for method, because tasks have **no executed oracle**: solvability rests on an LLM rubric plus a frontier pass rate > 0, which our rule 3 (construction before sampling) forbids.

**Problem.** "Claw-like" agents (OpenClaw-style harnesses with bash, files, databases, long loops) need stateful workspace environments, but synthetic environments so far are tool-call endpoints only.

**Method / algorithm.**
1. *Scenarios.* 41 general tool-use + 42 Claw-specific scenarios (12 + 13 coarse categories) from the OpenClaw community and prior benchmarks; an LLM expands each into an environment spec (entities, state attributes, business rules) and a tool spec (schemas, return formats, read-only vs write side-effect flags).
2. *Archetype-guided generation.* Nine interaction archetypes (transactional workspace, cross-tool pipeline, dynamic human–agent interaction, asynchronous event triggering, constraint-guided state machine, multi-resource temporal scheduling, bilateral matching, distributed workflow orchestration, fault-tolerant stream processing), each a template with a reference implementation. Pick up to two by keyword overlap with the spec as in-context anchors; generate one executable environment class. Claw environments also get a built-in bash tool and co-generated "skills" (markdown workflow guides).
3. *Engineering contract* (Table 15, enforced at generation): every public function returns a dict and maps failures to structured errors; no mutable module globals; data directory immutable during rollouts; atomic writes (temp + os.replace); bounded-timeout file locks; **timestamps computed from base_time and action_index, wall clock forbidden**; session bound only through trainer-injected env vars (no --session-id flag the agent could spoof); hidden trainer commands excluded from agent help; the evaluator is deterministic and side-effect free; full state retrieval and deterministic scenario loading for snapshot/restore. Error taxonomy: infrastructure errors are generic (no internal paths), domain errors name the entity, field, current state or valid alternative so the agent can self-correct; "stale information" emits a warning and the evaluator applies a penalty.
4. *Environment audit.* AST static checks against the schema rules, then dynamic tests from S0 (tool validity, transitions, edge-case exceptions); failures go to an LLM self-heal loop. 324 raw → 139 kept (42.9%; general 34.5%, Claw 57.0%).
5. *Tool chains.* Bi-level graph: intra-environment tool graph (static analysis + LLM pre/post-conditions, weighted edges) and an environment graph (LLM edges by domain and data flow). Weighted random walks; cross-environment tasks chain 2–5 environments. **Every chain must end in a write tool** so a state check exists.
6. *Task synthesis.* (a) Classify each parameter user-specified vs tool-derived; write the instruction stating user-specified values and referring to tool-derived ones only abstractly (non-speculability). (b) Decompose into a multi-turn user sequence conditioned on one of the 5 most similar PersonaHub personas per environment (500 total). (c) In **one response**, generate the initial workspace (required entities plus distractors: dirty data, near-duplicates, outdated versions, decoys, odd formats, but exactly one correct answer) and a deterministic stdlib-only verifier that writes a weighted itemised score; unexpected fields or fabricated entities get large penalties; no LLM judge, no network.
7. *Cross-artifact invariants* (C.6): path consistency (request paths = verifier paths), data consistency (every expected value derivable from the built files), objective consistency (verifier checks only what the request implies), answer uniqueness, information separation, code-only evaluation.
8. *Data audit.* DeepSeek-V4-Pro scores each candidate 0–3 on solvability, verifier integrity, and consistency; keep only s_sol = 3, s_val = 3, s_con ≥ 2, sum ≥ 8. Then Qwen3.5-27B runs 8 rollouts (T 0.7, 32 turns, 300 s); keep 0 < p < 1. Verifier crashes or timeouts are data defects, not agent failures: removed from calibration, up to 2 automatic verifier repairs, else discard. 35,464 → 19,777 (55.8%; general 64.7%, Claw 41.2%).
9. *RL.* GRPO, G = 8, lr 1e-6, KL 0.02, 1 epoch, 32k generation, 32 turns, 64 Ascend 910B NPUs. Binary reward for Tool tasks, graded [0,1] for Claw tasks; recoverable tool errors stay in the trajectory; verifier errors give reward 0.

**Verification / grading.** Deterministic itemised verifiers over the workspace. Weak points: the verifier is generated with the task by the same model; no reference solution is run; the LLM rubric judges verifier completeness; the p > 0 filter on a 27B model is the only solvability evidence, and it admits tasks a lucky or hacking rollout passed.

**Scale & cost.** 139 environments, 19,777 tasks. Tokens and $ n/r. Two-stage curriculum: 115 steps on 8k Tool samples, then 30 steps on 2k Claw samples.

**Key results.** Qwen3-8B: PinchBench 12.94 → 24.85, Claw-Eval 44.06 → 55.42, with 35% fewer tokens per task; general Tool data alone gave only +1.57/+1.74; Tool-then-Claw ≈ Claw only. Qwen3-32B +6.59/+2.43; Qwen3.5-9B +4.85/+4.08. BFCL-v3 multi-turn: Qwen3-8B 39.25 → 46.25; τ²-bench gains small (27.09 → 29.80). Rubric means: filtered 1.38 vs retained 2.97. Ablation: adding the built-in bash tool to Claw environments 14.96 → 24.02 on PinchBench (skills co-synthesis effect truncated in the text). General BFCL ability retained after Claw training (59.5 → 60.0).

**Failure modes & limits.** Authors: few. Mine: no oracle execution (solvability by judge + sampling); the 0 < p < 1 filter is tuned to a 27B, not to the trainee; verifier and workspace from one generation risk shared blind spots; LLM judge (DeepSeek) scores verifier integrity, but "verifier complete, no false-positive paths" is exactly what a judge cannot certify; τ² gains near noise.

**Tips & tricks.**
- Forbid wall-clock time in Apps; derive timestamps from a base time and the action index for determinism.
- Bind sessions through trainer-injected env vars, never an agent-visible argument.
- Hide trainer/admin commands from agent-facing help.
- Split errors into generic infrastructure errors and informative domain errors.
- Force every sampled chain to end in a write so state verification is possible.
- Generate instruction, start state and verifier in one response, then check cross-artifact invariants (paths, derivability, objective, uniqueness, separation).
- Treat verifier crashes as data defects with bounded repair, not as agent failures.
- Seed distractors deliberately (near-duplicates, stale versions, decoys) under an answer-uniqueness constraint.

**Fit to Crucible Part 2.** F1: copy Table 15 into the App contract (wall-clock ban maps onto our clock injection; session binding onto custody; snapshot/restore onto `StateAdapter`), and the error taxonomy into ToolSpec conventions. F2: the distractor menu is a ready `distractors` knob palette. F3/G8: the user-specified vs tool-derived split is the same rule as EnvFactory's; implement once. F5/F6: the six cross-artifact invariants are a cheap deterministic pre-gate before G3; add "answer uniqueness" to G14 (alternatives) reasoning. Avoid their solvability proof: keep F4's executed oracle and use frontier sampling only as audit. "Chain ends in a write" should not be a rule for us: read-only answer tasks and infeasible tasks are required types (§3.3). Priority P0 for the App contract items, P1 for the invariants.

**Problem.** Terminal tasks have no natural grounding signal like PRs; synthesising environment, instruction and verifier together is hard, and source-driven pools have skewed difficulty and tech-stack distributions.

**Method / algorithm.**
1. *Sources (SETA-Synth).* Stack Overflow, Unix & Linux StackExchange (also Ask Ubuntu in examples), Kaggle notebooks, NL2Bash; filtered by votes and accepted-answer status.

4. *Execution checks.* No-op: the tests run with no agent action must pass zero tests. Oracle: solve.sh must pass all tests. Self-review removes tests that enforce unstated conventions.

The worked example: five GPT-5.4 rollouts all failed the same two tests because the test demanded four JSON literals the instruction never stated, and all five rollouts chose differently; oracle and test shared the hidden assumption, so no-op/oracle could not catch it.

The evolve agent reads the full task, plans it as a DAG of steps, researches docs, writes a draft spec per variant or a FILTERED file, and the variant passes the same build, no-op, oracle and self-review gates, then is re-measured on the training model.

Reward = fraction of tests passed + a bonus if all pass (0.2 in the main text, +0.5 in the appendix table; the text is inconsistent). Qwen3-8B non-thinking (thinking overflowed context), AReal on one 8×H200 node, 16 trajectories per task, 30 agent iterations, lr 1.7e-5, clip 0.4, no KL; 560 environments subsampled after dropping those too hard for the base model. DeepSeek-V4-Flash trained with Miles on 64 H200s.

**Verification / grading.** Unit tests on end state; no-op and oracle checks; self-review; judge for all-fail tasks. The judge only audits r = 0 tasks, so leaks or lenient tests on solved tasks are not checked, and partial-credit reward makes a lenient test worth reward.

**Scale & cost.** 4,567 tasks (3,255 synthesised + 1,312 evolved), 14 categories (sysadmin 35.8%, ML 12.2%, data processing 10.5%, SWE 7.8%). Evolution pairs: 505 decrease, 143 increase, 553 change-context. Per-stage yields and $ n/r. All builds by Claude Opus 4.6.

**Key results.** Qwen3-8B TB 2.0: 3.1 → 10.7 ± 1.3 mean (best run 12%); TB 1.0 7.8 → 17.8. DeepSeek-V4-Flash TB 2.0 pass@1 40 → 43 ± 2.5, pass@5 54 → 58. Transfer (pass@4): CompileBench 6.7 → 40% (15 tasks), CRUST-Bench 15 → 24%, QuixBugs 7.5 → 15%. Partial reward raised the share of tasks with within-group variance from 49% to 86%. Evolution moved Qwen3-8B median pass rate 6% → 38% under decrease (77% of pairs moved in the declared direction) and 83% → 69% under increase (60% moved as declared). Change-context: 46.1% crossed a category; of the rest 91.3% rotated at least one technology. SFT on 1,112 Kimi-K2.5 successes: TB 2.0 pass@16 2.25 → 15.7.

**Failure modes & limits.** Authors: two model families only; terminal only. Mine: the evolution operators miss their declared direction 23–40% of the time, so re-measurement is essential; difficulty is measured on the trainee, which couples the pool to one student; the builder is a frontier model of one family that also writes tests and oracle; the 94 design flaws are a lower bound (only r = 0 tasks were audited); CompileBench has 15 tasks.

**Tips & tricks.**
- Keep per-source adapter prompts separate from one base task-design prompt.
- Split every spec into an agent-visible brief and builder-only notes.
- Run a no-op test (zero passing tests) and an oracle test (all pass) on every build.
- Send all-fail tasks to a judge that sees per-test failure frequencies; identical failures across rollouts on one literal point to an unstated convention.
- Choose the mutation by measured pass rate: harder above 0.5, context shift in (0, 0.5], easier at 0 with partial progress.
- Forbid "more of the same" and artificial constraints as hardness; require each variant to be harder along a different dimension.
- Re-measure every variant; the declared direction fails often.

**Fit to Crucible Part 2.** F5/F6: no-op = G4, oracle = G3 (already planned). The A.3 failure is a **G8 communicability** case for patch/file tasks: every literal a test asserts must appear in the instruction or be derivable from the start state; make G8 a static check over test assertions, not only over oracle tool arguments, and run it before any rollout. Plans that are cosmetic, add checks unrelated to the workflow, or hide required information only in tests are rejected.

Near-duplicate-of-seed check.

Failure classes: zero reward, build failure, timeout, runtime error, excessive output, unknown. **Bounded repair** (≤2 rounds) restricted to the six files, conditioned on the contract and logs; repair may not weaken semantic checks, remove shortcut protection or expose private requirements; re-preflight and re-run after each repair.

**Verification / grading.** Oracle validity + contract validity + shortcut-rejection checks inside the verifier. Instruction audit metrics over rounds: "hidden-check protection" 38.2% → 63.5%, short-instruction risk 41.6% → 7.5%, private-test references 0.1%, literal leakage 0%, median requirement coverage 0.42 → 0.57, weakly grounded tasks 32.8% → 1.2%. DeepSeek-V4-Pro pass@4 90% → 2.5%, partial credit 0.970 → 0.170; near-miss failures (≥75% checks) 86.4% → 1.2%. Strictest-criterion pass: DeepSeek-V4-Pro 72% → 4%, GPT-5.6-sol 72.2% → 7%. ## 2610.04906 — Scaling Verifiable Environments for Long-horizon Work Agents (WorkForge) (Zhang et al., 2026; venue n/r, Tencent LLM Dept + Fudan)
Read: FULL (body; appendices A–E incl. pseudocode, SFT/eval setup, GDPval subset, verifier ablation, worked finance example).  Relevance to Part 2: medium-high. It is the clearest recipe for **knowledge-work tasks over real files**, with verification anchored to checked "workspace facts", and it trains a Qwen3.5-35B-A3B base (our student's family). But it is SFT only, its semantic criteria are LLM-judged, and there is no oracle execution or negative testing.

**Problem.** Work agents need long-horizon environments with realistic, heterogeneous files and trustworthy verification; synthetic workspaces are toy-like (few files, evidence concentrated), and rubric criteria not grounded in observable facts produce hallucinated requirements.

**Method / algorithm.**
1. *Scene Blueprints (human).* Domain experts distil workflows into b = (workflow + context, expected deliverable, required sources + dependencies, domain-specific decisions). Number of blueprints and expert effort n/r.
2. *Environment mapping.* An acquisition agent searches, reads pages, downloads and previews public resources (e.g. a Kaggle mirror of the Kenneth French data library) and maps each blueprint to K distinct resource pools; each workspace keeps one pool with its original file organisation (one-to-many blueprint → workspaces).
3. *Environment profiling.* An agent explores the workspace and writes a profile: summary of domain, file roles, potential task directions; **workspace facts** (checkable statements with computation references, e.g. "Emerging five-factor data start at 198907"); artifact schemas and statistics.
4. *Task design.* From blueprint + profile, generate the visible instruction and a **hidden solution plan**; regenerate if paths are invalid or components unsupported.
5. *Fact verification.* Check the key factual claims of the plan against the workspace and record the evidence (the worked example shows a corrected fact: an assumed shared 1990 start was wrong for one region). Build an atomic rubric from facts + task constraints, split into programmatic criteria (file validity, value-in-context checks with expected value and context keywords) and semantic criteria judged by an LLM on 0–10 with per-criterion guides. Average 21.9 criteria per task (example: 8 programmatic + 15 semantic).
6. *Trajectories.* GLM-5.3 solves tasks in Claude Code and OpenClaw harnesses; scores S_prog (fraction of checks) and S_sem (mean of s/10) kept separately; trajectories selected by threshold for SFT.
7. *Training.* Full-parameter SFT, 5 epochs, batch 64, 256K context, lr 1e-5 cosine.

**Verification / grading.** Programmatic checks on artifacts + LLM-judged semantic criteria, both anchored to profiled facts. Hack surface: value-in-context checks with keywords can be satisfied by listing values; semantic criteria inherit judge leniency; no check against unrequested changes; authors note verifiers ignore intermediate behaviour and have limited expert calibration.

**Scale & cost.** 16,665 tasks, 40 domains (top 4 = 31.9%, top 10 = 56.9%), 60 file types, 42.3 files and 279 KB per workspace; trajectories average 31.8 steps, 33.8 tool calls, 76,485 tokens. Real vs LLM-synthesised workspaces from the same blueprint: 5.4× more files, 2.4× more file types, 279 vs 21.5 KB. Cost n/r.

**Key results.** Qwen3.5-35B-A3B-Base: GDPval 45.5 → 73.6, APEX 5.0 → 21.3, ALE 11.4 → 28.7 (pass@1 3.8 → 12.4), ClawEval 35.4 → 53.3, WildClaw 18.6 → 29.9. Qwen3.5-27B: GDPval 79.4 → 82.4 (Qwen3.5-397B: 79.7). Data volume 1K → 16K: ALE +13.0, WildClaw +8.4, monotone. Trajectory length (1K each): 41–60-turn trajectories beat 0–20-turn by +4.2 ALE, +5.0 WildClaw. **Selection-signal ablation (1K trajectories, threshold 0.7):** LLM-only ALE 15.62, programmatic-only 14.89, hybrid 22.11 (pass@1 4.8/4.8/11.4). Harness-specific transfer: Claude Code-trained beats OpenClaw-trained on ALE under Claude Code (24.2 vs 16.1), the reverse on WildClaw (+6.2). Behaviour: 5.3× more external domains visited, evidence retrieval 5.9% → 16.2% of calls, post-error reasoning 144 → 614 chars.

**Failure modes & limits.** Authors: needs expert workflows and public resources (weak for proprietary domains); reliability rests on profiling completeness; deliverable-only verification. Mine: SFT distillation from GLM-5.3, so gains partly reflect the teacher; no RL; GDPval uses 201/220 tasks and the official rubric score; semantic judge identity n/r; no measure of verifier precision; facts are profiled by the same pipeline that writes the task.

**Tips & tricks.**
- Profile the workspace into checkable facts first, then let tasks and checks reference fact ids.
- Verify the hidden plan's factual claims against the files and record corrections.
- Keep programmatic and semantic scores separate; select on their mean, not either alone.
- One blueprint → many workspaces from distinct real resource pools: cheap breadth at fixed intent.
- Retrieve real files rather than synthesising them when exploration is the skill.
- Match training and evaluation harnesses, or train on both.

**Fit to Crucible Part 2.** F2 (state seeding) and the enterprise ingest path: "profile then anchor" is the right order for document/file Worlds; add a `WorkspaceFacts` record to `SeedBundle` (fact id, statement, computation reference, evidence path) and require every answer/state check to cite a fact id (a traceability gate under G8/G11). The blueprint → many pools mapping is a natural `FamilySpec` (one family = blueprint × skill leaf; instances = resource pools), which fits §3.10's "many families, few instances". Avoid LLM-judged semantic criteria as reward unless a frozen anchor set calibrates the judge (§3.8); for F10, WorkForge's hybrid-beats-either result supports keeping both signals for trajectory selection and SFT, not for RL reward. Harness-specific transfer is a measurement caveat for our benchmark protocol (§2(e)). Priority P1.

## 2610.14163 — AutoEnvScaling: Automating the Data Flywheel with Terminal Agents (Yu et al., 2026; venue n/r, Northeastern/Microsoft/Stanford/UW/UNC)
Read: FULL (body; appendices A–I incl. HiL-Bench task, cross-domain admission, proposer skills, reference-execution ablation, training/calibration settings, cold-start controls, labelling protocol).  Relevance to Part 2: **very high**. It trains our exact student (Qwen3.5/3.6-35B-A3B), compares prompt vs feedback vs agent-in-sandbox generation across eight proposers (including two of our swarm families), defines a proposer reward from admission gates, and shows what breaks when a shared policy's proposer is not trained. It is the strongest evidence for running F1–F5 as agentic sessions (our `factory/machine.py` / RLM builder) rather than prompt pipelines.

**Problem.** Environment supply grows at researcher speed and goes stale as the agent improves; pipeline synthesis fixes the generation procedure in advance.

**Method / algorithm.**
1. *Environment design as a terminal task.* A proposer agent runs in a sandbox (coding harness: Codex, Claude Code or Pi; child containers to build and test; restricted web with benchmark pages blocked). Workspace: past solver rollouts with verifier output, past environments, Harbor create-task skill, an AutoEnvScaling overlay skill, and the proposer's own memory and tools (persist across rounds). **The proposer can edit its memory and tools but not the instructions or admission checks, which run outside the sandbox.**
2. *Assignments.* Each episode names a parent environment, the solver's pass rate on it and its most common failure. The proposer reads trajectories and verifier stdout, then builds a simpler variant (if the solver keeps failing) or a harder one (longer horizon or an added skill). The overlay skill says the primary objective is **reward spread** (std across attempts), mean only secondary; adapt an exemplar toward an unseen weakness; never manufacture spread through randomness, flaky timing, underspecification or nondeterminism; gate milestones so partial credit is not an identical additive checklist.
3. *Validation (host side).* Build; reference solution must score 1.0; empty solution must score < 0.5 (do-nothing check); 13-gram overlap with held-out benchmarks flags contamination; `harbor check` reviews the task against the Terminal-Bench rubric, graded by the proposer's own model (acknowledged weak: shared mistakes between solution and tests, shortcut-rewarding tests).
4. *Calibration.* 4 solver rollouts (expand to 8 if the mean is within 0.15 of a band edge); keep if mean ∈ [0.25, 0.75] and std ≥ 0.1. Tasks below the band get one diagnostic rollout with reference-solution hints to guide revision. ≤2 revisions per assignment. The pool (256 active tasks) is re-reviewed every 16 solver updates; tasks leaving the band are replaced from new rollouts.
5. *Rewards.* Solver: fraction of tests passed. Proposer: −1 if validation fails, −0.25 if valid but out of band, +1 if admitted.
6. *Proposer improvement.* Closed models: harness optimisation between rounds (it merged validation steps into a script, cached useful GitHub tasks and Docker images as a skill). Open models: one shared policy trained on both roles with DPPO, separate advantage baselines (proposer groups of 128 trajectories per assignment, mean-centred, no std division; solver groups per environment), drop zero-variance groups, proposer trained every k = 16 solver updates, lr 1e-6, no KL/entropy, 4–8 B200s; unfinished terminal trajectories carried across updates with live sandbox state.
7. *Cold start for the self-proposer.* Base Qwen3.6-35B-A3B made valid environments 32.3% of the time; SFT on 600 proposer trajectories (Claude Opus 5, DeepSeek-V4-Flash, Kimi-K3) raised it to 86.8% (paired 60-assignment control: 33.3% → 76.7%) with no detectable change in solving (TB2.1 40.0 → 41.1, CI [−4.9, 7.4]).

**Verification / grading.** Oracle = 1, no-op < 0.5, same-model rubric review, calibration. Authors state plainly that passing validation does not prove correctness and call for testing against partial, incorrect and alternative solutions and isolated evaluation services.

**Scale & cost.** Valid-environment rate, prompt → prompt+feedback → AutoEnvScaling: DeepSeek-V4-Flash 3.5% → 12.1% → 89.0% (cost per valid env $0.08 → $0.02); GPT-5.6-sol 41.1 → 65.5 → 86.3% ($0.59); Claude Opus 5 74.6 → 89.5 → 94.0% ($1.18, more expensive than prompt); Gemini-3.8-Flash 64.8%. **Reference-execution self-check ablation**: disabled vs enabled, GPT-5.6-sol 19.5 → 84.8%, DeepSeek-V4-Flash 19.4 → 73.0%, Claude Opus 5 52.0 → 94.0%. Cross-domain admission (oracle full reward, no-op zero, reset reproduces state): 1,061/1,489 runs (71.3%); terminal/SWE/GPU 87–100%, browser 26–81%, computer use 40–79%, professional workflows 33–62%, mean 1.2–2.8 rounds.

**Key results.** Matched training steps, TB2.1 avg@5: Qwen3.5-35B-A3B 26.7 → Tmax 34.6/35.5 → AutoEnvScaling 38.9 (GPT-5.6-sol) / 39.3 (Opus 5); **without solver trajectories in the workspace 35.3/32.6** (feedback is worth 3.6–6.7 points). Qwen3.5-9B 19.1 → 33.5/36.6 (Tmax 27.2/29.2). Self-proposer Qwen3.6-35B-A3B: TB2.1 41.1 → 53.3 (+12.2; Tmax +6.1 less), TB4.0 1.6 → 3.2. 3.1× more usable (non-zero-variance) groups than Tmax; 42% less rollout-collection time per step. **Without proposer training (shared weights, solver-only updates) the proposer's valid rate fell 86.8% → 22.4% by step 160 and training collapsed**; with it, 79.6% dip then 94.7%. HiL-Bench (ask for missing info): 500 generated underspecified tasks with a withheld-details registry; Qwen3.6-35B-A3B success 6.8% (official 100 tasks) → 33.9%, Ask-F1 29.6 → 55.3, beating Opus 5 (7.5%, 14.4).

**Failure modes & limits.** Authors: gains not shown beyond the runs; TB4.0 low; validation ≠ correctness; cross-domain environments not yet trained on. Mine: the rubric reviewer is the proposer's own model; the calibration band is measured on the current solver only (pool tied to one student, re-reviewed every 16 updates); partial-credit tests invite lenient checks; the self-proposer's admission gate is the only thing between it and reward hacking of its own curriculum, and the paper shows that gate degrading fast when untrained; harness differences (Pi vs Terminus-2) shift absolute scores a lot.

**Tips & tricks.**
- Let builders execute the reference solution during generation; it is the single largest yield lever.
- Run admission checks outside the builder's sandbox; let the builder edit its own memory/tools, never the checks.
- Feed the builder real solver trajectories and verifier stdout, keyed to the parent environment.
- Target reward spread (std ≥ 0.1) as well as a mean band; expand rollouts near band edges.
- Give below-band tasks one hinted diagnostic rollout before revising.
- Reward builders −1 / −0.25 / +1 for invalid / out-of-band / admitted.
- If one policy plays both roles, train the proposer role too, or its validity decays and RL collapses.
- Cold-start a weak proposer with a few hundred good proposer trajectories.
- Block benchmark pages from builder web access and run 13-gram decontamination.

**Fit to Crucible Part 2.** F1–F5: strong support for making each build stage an agentic session with execution (our machine/RLM sessions) and for keeping the gates host-side (rule 5, "gate code hidden from improvers"). F9: adopt the mean band + std ≥ 0.1 + adaptive k (4 → 8 near edges) as a concrete sequential rule (§3.6 proposes k = 4 first; this is the published variant). F12 → F3: the "assignment" object (parent task, student pass rate, modal failure, trajectories) is exactly the missing consumer of `factory/failures.py` BuilderIntents (§3.4 item 6); define `Assignment{parent_ref, student_id, p_hat, failure_cluster, trace_refs}` as F3's input for traces-to-tasks. ## 2610.16523 — eau: Environment-Agent-User Co-evolution for Training User-Centric Agents (EAU) (Cai, Zhang et al., 2026; venue n/r, Alberta/NUS/Kuaishou)
Read: FULL (body; appendices A intervention interfaces and run records, B benchmarks, C hyperparameters, D notes).  Relevance to Part 2: high for the **World loop and the trace-diagnosis role** (its run records are a catalogue of simulator and environment defects found from training traces), medium as a method to adopt now: it hot-swaps rewards and simulator rules during RL, which §3.8 rightly defers (P2).

**Problem.** In multi-turn user-centric RL, the reward depends on a stochastic user simulator and an environment that may have broken tools, unreachable states or wrong verifiers; reward shaping cannot fix a simulator that leaks the answer or a counter that deadlocks episodes.

**Method / algorithm.**
1. *Meta-agent.* Claude Code (Opus 5) or Codex with filesystem access to source code, training logs and rollouts; it reads logs at a fixed interval, diagnoses whether a bad trajectory comes from the policy, the user simulator, the environment or the RL config, consults and updates an **experience pool** (a directory of notes persisted across runs), and edits a declared list of knobs (it may extend the list). It uses **training-side feedback only**; evaluation sets, simulator config, limits and scoring are never touched.
2. *Symbolic user.* Explicit rules mapping parsed agent outputs to user replies (what to reveal and when), with knobs: facts_per_reply, match_threshold, volunteer_interval, max_reveals, reveal_return_shape. Mixed with the LLM user (CoSER, a fine-tuned Llama-3.1-8B; GPT-4o-mini at evaluation) via ε-symbolic sampling: symbolic with probability ε, else LLM.
3. *Environment knobs.* Intermediate reward rules (added or revised), episode length (max_steps), min_questions, per-gym reward scales and clips, predicate weights; gym-specific noise/wrong-choice counts and failure intervals.
4. *Agent knobs.* Entropy and KL coefficients. Algorithm fixed: PPO with a critic and GAE computed over action tokens only (observation tokens excluded so turn advantages are not diluted).
5. *Write checks* (the "integrity gate"): declared ranges per knob; per-write change caps (entropy ≤ 0.004 per write); **difficulty-increasing updates require recent training success ≥ 0.80** (four max_steps increases were rejected before qualifying).
6. *Timescales.* Intra-run hot swaps, and inter-run restarts (up to 5 runs per experiment including proactive restarts) when a fix needs an offline patch; resumption from checkpoints.

**Verification / grading.** Benchmark rewards (hidden unit tests in ColBench; state match + information conveyed in τ²). Integrity of changes rests on range checks only; the authors state these "do not guarantee behavioral correctness".

**Scale & cost.** 3 benchmarks, Qwen3-4B and Qwen2.5-7B; 624-step runs on ColBench; 4 GPUs per node; meta-agent inference cost and total compute n/r (they state limits are not a matched compute budget).

**Key results.** Overall (UserGym + ColBench): Qwen3-4B 0.627 vs InfoPO 0.545 (+15.0%) and PPO 0.462; Qwen2.5-7B 0.615 vs 0.544. ColBench success 0.439 → 0.600 (Qwen3-4B). τ²-bench (Qwen3-4B) average 18.5 (PPO) → 21.5. A generic meta-agent ("improve RL training", no symbolic user or intervention skill) gave mixed results (UserGym 0.512 vs PPO 0.568 on Qwen2.5-7B). User ablation on ColBench: LLM 0.200 success, symbolic 0.177, hybrid ε = 0.5 0.213 (within noise). Intra-run intervention in run 5 beat inter-run-only given the same prior experience (no compute match).
**The run record (A.2) is the most useful part:** 15 knob writes, 2 measured harms, 3 retracted attributions; diagnoses included (a) a min_questions counter that ignored turns that both asked and answered, **deadlocking 41% of episodes**; (b) raising facts_per_reply 1 → 3 made the simulator **disclose the reference solution** in 837-char replies; (c) lowering volunteer_interval raised success while the question rate fell 40% → 26%, i.e. **success rose because the user volunteered answers** (reverted as masking); (d) max_reveals did not count repeated disclosures; (e) the leak filter targeted the wrong fact kind (shape, 8% of facts, vs return, 18%); (f) an entropy increase raised measured entropy 50% while behavioural diversity fell; (g) noise floor of 0.228 on a metric made several interventions inconclusive.

**Failure modes & limits.** Authors: changes may introduce errors or task-information disclosure; no matched compute; experience pool not ablated separately. Mine: changing reward and simulator mid-run means the reported policy was trained on a moving objective, so results are not attributable to any fixed environment; final-run selection after up to 5 restarts is a form of selection on training metrics; the symbolic-vs-LLM mixture was never actually adapted (fixed at 0.5); the meta-agent is a frontier model reading full traces, expensive at scale.

**Tips & tricks.**
- Diagnose each bad trajectory to a side: policy, user simulator, environment/verifier, or config.
- Gate difficulty increases on a recent training success rate (≥ 0.80 here).
- Range-check and step-cap every knob write; keep a revert path.
- Treat "success up while the target behaviour (questions asked) goes down" as a masking alarm.
- Audit simulator disclosure: count facts revealed, including repeats, by fact kind.
- Compute GAE over action tokens only in multi-turn PPO.
- Keep an experience pool of what each intervention did, including retractions.

**Fit to Crucible Part 2.** F12 and the World loop (§3.8): the A.2 defect list is a ready seed set of **fault-side labels** (simulator leak, simulator over-volunteering, counter/termination bug, filter mis-scope, metric noise floor) for the failure taxonomy and the frozen anchor set; add "simulator disclosure audit" (facts revealed per kind, repeats counted) to the People/ActorSpec health card, and a G8-like check that the simulated user's known info excludes the answer. The pipeline doctor role can copy EAU's side-diagnosis + experience-pool format, but stay proposal-only. The success-threshold gate for hardening matches our controller (do not harden below band). The ε-mixture of a symbolic and an LLM user is a cheap way to get deterministic, auditable user behaviour for G2 determinism on multi-turn tasks: use the symbolic arm for gating and the LLM arm for training diversity. Avoid hot-swapping reward during a measured run. Priority P1 (defect taxonomy, disclosure audit, symbolic user arm), P2 (in-run meta-agent).

## 2606.19047 — RODS: Reward-Driven Online Data Synthesis for Multi-Turn Tool-Use Agents (Fang et al., 2026; venue n/r, Ant Group Inclusion AI/Zhejiang/Westlake)
Read: FULL (body; appendices A–P incl. thresholds, fault tolerance, prompts, execution internals, error taxonomy, feedback loop, quality gates, OOD table, synthesis-LLM robustness, compute cost; examples skimmed).  Relevance to Part 2: high for **the task loop and F9/F11 pool management**: variance-triggered variants of in-band tasks, structural-isomorphism constraints, staged injection, and three-layer retirement are concrete and ablated. The domain is small (BFCL V3 multi-turn, 400 seeds) and the evaluation is held-in, so treat the gains as mechanism evidence, not scale evidence.

**Problem.** Static multi-turn tool-use datasets deplete: as the policy improves, fewer tasks have within-group reward variance, so GRPO gradients vanish.

**Method / algorithm.**
1. *Boundary detection, zero extra inference.* Use the rollouts already computed for GRPO (K = 16). Mean progress reward r̄ (fraction of turns resolved, state × execution correct) partitions tasks: mastered r̄ > α⁺ = 0.85, boundary 0.20 ≤ r̄ ≤ 0.85, hard r̄ < 0.20. Empirically, variance in the boundary zone is 2.0–2.2× that of the other zones (4,800 task measurements).
2. *Type-quota seed emission.* Each step, emit up to M boundary seeds with per-type quotas (base/long-context, missing-function, missing-parameter), ranked by φ = 4r̄(1 − r̄); a temporal exclusion window of c steps avoids re-emitting the same seed.
3. *Skill-aligned synthesis (structural isomorphism).* Extract the seed's complexity profile Φ (DAG of API dependencies and parameter flows); generate a new task whose Φ matches in dependency depth and API topology with a new narrative and environment state. Five stages with Qwen3-32B: (I) planner writes an execution plan and a narrative, conditioned on failure history; (II) execution orchestrator samples concrete functions, an LLM fills parameters from the current state, the sandbox VM executes them; an **error critic** (config-patch agent) edits the initial environment config via accumulated XML patches and the planner gets a growing **function blocklist**, up to K_max = 3 attempts; a query agent writes per-turn queries without function names; (III) a coherence rewrite of all turns at once against the narrative; (IV) deterministic gates: re-execute all ground-truth calls on a fresh VM, every GT function must be in the provided tools, list params ≤ 5 items and strings ≤ 200 chars; then an LLM quality judge (query–GT alignment "no more, no less", state consistency, cross-turn coherence, naturalness, intended ambiguity present) with auto-reject on prompt-leak patterns; one refinement cycle where a classifier labels the failure query-fixable (rewrite once) or GT-unfixable (drop); (V) optional adversarial transforms (remove a tool, blur a parameter) to force clarification turns.
4. *Replay buffer lifecycle.* Staged injection: variants seeded in epoch n enter at epoch n+1, capped at 20% of the active pool per epoch, sampling re-initialised. Retirement: burn-in eviction if the first observation is < 0.20; boundary-drift eviction to mastered (> 0.95) or unsolvable (< 0.20) after n_min observations; variance-prioritised pruning when generated items exceed P_max = 400; prune long-unsampled variants. Original seeds are never retired. Crash recovery by replaying append-only variant logs and recomputing retirement deterministically.
5. *Curriculum.* Stage 1 format reward on 100 base tasks; Stage 2 progress reward on base; Stage 3 all 400 seeds + expansion. GRPO, lr 1e-6, KL 0.01, mini-batch 512, 5 epochs per stage, Qwen3-4B-Instruct on 8×A100; synthesis on a separate 8×A100.

**Verification / grading.** Deterministic re-execution of ground-truth calls on a fresh VM (the simulator is a replica of the training simulator), plus an LLM judge for query–GT alignment. Reward: fraction of turns whose state and execution match GT. Weak points: GT-trajectory matching rather than goal-state checks; the judge is the only guard against queries that under-specify the GT.

**Scale & cost.** 400 seeds → over 800 unique tasks generated; active pool ≤ 400 seeds + 400 variants. 9–15 LLM calls per base variant. Seed-to-variant latency about 1 step (3.7 min); staging delay about 13 steps; pass@16 drifts < 0.10 meanwhile. About 56 h wall-clock: 448 GPU-h training + 448 GPU-h synthesis.

**Key results.** BFCL V3 multi-turn (held-in 400): Qwen3-4B 22.13 → static 50.00 → EnvTuning 50.50 → **RODS 56.00** (FunReason-MT-4B with 17K offline samples: 56.50). Qwen2.5-7B 36.92 → 40.25; Llama-3.1-8B 28.25 → 30.88. Ablations (Qwen3-4B, Δ vs 56.00): random seed selection −4.75; binary accuracy instead of progress reward for detection −3.25; no coherence rewrite −5.13 (judge pass rate collapses from about 63% to 12%); no narrative planning −3.63; blind retry instead of feedback loop −2.13; no retirement −3.38; static pool −2.88. P_max 50 already helps; returns diminish beyond 200. Swapping Qwen3-32B for GLM-4.5-Air as synthesiser: −0.75. OOD for Llama-3.1-8B: τ²-bench 19.46 → 25.00, BFCL V4 7.05 → 18.00, ACEBench 4.15 → 11.15.

**Failure modes & limits.** Authors: needs deterministic, introspectable simulators; doubles GPU footprint. Mine: training and the main evaluation share BFCL V3's distribution (400 held-in); the boundary thresholds (0.20–0.85) are wide and use a dense reward that rewards partial progress; "structural isomorphism" is generator-enforced, never measured; variants are tuned to the current student checkpoint only.

**Tips & tricks.**
- Reuse training rollouts to pick variant seeds: rank in-band tasks by 4p(1 − p).
- Enforce per-type quotas when emitting seeds so one task type does not take over.
- Make variants match the seed's dependency DAG (depth, topology) while changing narrative and state.
- On execution failure, patch the start state and block the failing functions, then re-plan (≤ 3 tries).
- Re-execute ground truth on a fresh World before judging a variant.
- Rewrite all turns of a multi-turn task together against one narrative; it was the largest single component.
- Inject new tasks only at epoch boundaries, capped at 20% of the pool.
- Retire tasks that drift out of band; never retire original seeds.

**Fit to Crucible Part 2.** Task loop (§3.8) and F9/F11: RODS is the "variance-triggered variant" reference already cited; make its mechanisms explicit. (1) F12 → F3: emit `Assignment`s for tasks with p̂ in band, ranked by p(1 − p), with per-cell quotas (our cells replace its three types) and an exclusion window. (2) F4: variants keep the parent's oracle DAG shape (signature-level isomorphism measured by F7, not asserted) but change World slice and narrative; this is the "same cell, new instance" operator that complements SETA's context shift and RST's harder rewrite. (3) F11: adopt staged injection (≤ 20% per epoch), burn-in eviction and drift eviction, keyed per student; keep originals; log append-only for replay. (4) F5: the config-patch + function-blocklist repair loop is a good F4 repair round, but every patch to the start state must re-run G1/G2/G8. Avoid GT-trajectory turn matching as reward; use state checks. Priority P1 (needs the RL loop live), with the pool lifecycle rules P0 for the archive design.

## 2610.21656 — Data World: Scaling Data Environments from Scratch (Li et al., 2026; venue n/r, Meituan LongCat + Nanjing Univ. and others)
Read: FULL (body; appendices A.1–A.5 incl. per-domain, cause/consequence, RL config, evaluation protocol; case-study file listings skimmed).  Relevance to Part 2: **high**. "Specify the world's mechanisms first, then generate the files" is exactly our F2 latent-trait / hidden-state idea applied to analytical tasks, with an independent auditor that checks **target recoverability from the observed files**, the gate our G8 needs for any "find the cause" task. RL-zero on Qwen3.6-35B-A3B (our student) with synthetic data only.

**Problem.** Data-agent tasks with open-ended findings are unverifiable when the generating process behind real files is unknown: rubrics written by exploring files omit valid findings and reward the curator's guesses; real data has privacy/IP limits and contamination risk.

**Method / algorithm.** All construction by GLM-5.3 in Claude Code; **each stage an independent agent session sharing only on-disk artifacts**; each writes a machine-checkable ledger plus a narrative self-report.
1. *Dependency skeleton G.* From a PersonaHub persona, an LLM writes a DAG whose nodes are variable clusters and edges are directional generative relationships (monotonic, threshold, saturation, lagged, interactive) with notes.
2. *World contract C* (fixed before data): entities and timeline; per-edge mechanism (functional form, heterogeneity, temporal behaviour, confounders); global invariants (ids, units, shared events); **observation systems** (the imperfect business systems through which truth is seen); deliverables incl. the recomputable phenomena I.
3. *Canonical truth X, layer by layer.* Topological strata by longest-path depth; one agent session per layer writes a deterministic script with a fixed seed; upstream state read-only; layer commits are atomic; for every incoming edge the layer agent runs empirical checks that the declared pattern, form, lag and heterogeneity hold, recorded in the ledger.
4. *Observation projection E = O(X)* by a separate session: explicit observation mechanisms, not noise: identifier spellings and key conventions differ across systems; missing values, delays, duplicates, unit drift, categorical encodings, schema drift, each with a stated origin; unlabelled foreign keys; no data dictionary.
5. *Independent audit.* An auditor with all artifacts writes its own scripts to re-check every edge relation, invariant and phenomenon in I, **including recoverability from E without access to X**, and writes an analyst-perspective world guide. It may not modify environment or truth; it only issues pass/fail and must report failed expectations.
6. *Task synthesis.* Partition nodes into K depth strata; per stratum pick the max in-degree node (a **cause** task: explain its variation from upstream factors) and the max out-degree node (a **consequence** task: trace downstream effects), giving up to 2K structurally spread tasks per world. A question writer with read-only access to contract, scripts, ledgers, state and guide writes (task, rubric) after checking the targeted phenomena are derivable from E. Rubrics split **data computation** from **insight discovery**, each with atomic positive items and **negative items** for demonstrably wrong calculations or contradicted conclusions; unlisted valid insights get no credit and no penalty.
7. *Splits.* 1,302 candidate worlds → 1,087 kept. Test: 50 held-out worlds passing every audit check, one cause + one consequence task each, chosen by 15 annotators for question realism → DataWorld-Bench (100 tasks, 16 domains). Train: 1,037 worlds (95.98% DAG-edge pass rate, looser filter) → 2,135 tasks.
8. *RL-zero.* GSPO on Qwen3.6-35B-A3B, group 8, 24 prompts per rollout batch, 262k context, lr 1e-6 constant, clip 3.5e-4/5e-4, no KL/entropy, 48 training + 64 rollout H20 GPUs; **rubric judge during RL = the base Qwen3.6-35B-A3B itself** (cost reasons); evaluation judge Gemini-3.8-Flash.

**Verification / grading.** Rubrics cross-checkable against the generative record; LLM judge scores item by item, net points normalised to [0,1]. Hack surface: self-judging during RL (policy and judge share weights at start); rubric items can be gamed by verbose reports listing many findings unless negative items bite; judge consistency across models not measured.

**Scale & cost.** 1,087 worlds (yield 83.5% from candidates), 2,235 tasks total. Token or $ cost n/r.

**Key results.** DataWorld-Bench (10 frontier models): best overall 74.43 (GPT-6-Astra); every model has a computation–insight gap of 4.87–21.35 points; negative items triggered in 14–43% of trajectories. Domain offsets after removing model means: bioinformatics +7.70, operations +7.25, transportation −11.44, environment −8.50 (6–8 tasks per domain, so no rankings). Cause vs consequence: no difference beyond the minimum detectable effect (MDE = 2.802·s_Δ/√n, about 9–10 points). RL: DataWorld-Bench 37.64 → 44.70 (+7.06), DAComp +14.28, DABstep-Hard +20.90, JobBench +12.13; DataMind retrained on 7,323 public tasks with the same recipe improved external benchmarks but left DataWorld-Bench unchanged (−0.29). Rounds and response tokens rose on every benchmark (e.g. 36.5 → 102.8 rounds on DataWorld-Bench). MMLU-Pro unchanged, LCB-Hard −0.85, SimpleQA +1.8.

**Failure modes & limits.** Authors: no component ablations (tight coupling, regeneration cost); synthetic questions may not match real user requests; rubric coverage incomplete; judge bias. Mine: self-judging RL is a reward-hacking risk the paper does not measure; the training split uses a looser audit than the test split, so training tasks may include unrecoverable targets; the auditor is the same model family as all builders (GLM-5.3), so shared blind spots are possible; reported gains include much longer trajectories, so budget effects are confounded.

**Tips & tricks.**
- Write the generative mechanism (DAG + contract) before any data; keep it fixed.
- One agent session per stage or per DAG layer, communicating only through read-only artifacts.
- Have each generating session record empirical checks of the mechanism it implemented.
- Model observation defects as named processes with origins, not random noise.
- Make the auditor read-only, pass/fail only, and require it to re-derive targets from the observed files alone.
- Pick task targets by graph structure (max in/out-degree per depth stratum) for spread across the skeleton.
- Use negative rubric items for contradicted conclusions; do not penalise unlisted valid findings.
- Report a minimum detectable effect before claiming no difference.

**Fit to Crucible Part 2.** F2: adopt the contract → canonical state → observation projection split for any World with hidden causes (our `latent_traits (hidden)` in `SeedBundle`): store the mechanism DAG and observation systems in the seed bundle so verifiers can recompute ground truth. F6: add a **recoverability gate** (a G8 variant for analytical/answer tasks): an independent session, without access to hidden state, must re-derive each targeted finding from the observed World; failing that, the task is unsolvable as posed. The per-stage ledger + self-report pattern fits `factory/provenance.py`. F3 diversity: cause/consequence routes and depth-stratified targets are a coverage axis (scenario type) for analytical domains. F5: positive and negative rubric items map to answer checks and the "wrong answer" negative class. Avoid self-judging for RL reward (family rule, §3.0 rule 5) and apply the strict audit to the training split too. Priority P1 (P0 for the recoverability gate concept in G8).

## 2610.18868 — Tev: Scaling Long-Horizon Agentic Environments with Dense Progress Rewards (Hu et al., 2026; venue n/r, Adobe Research + UCLA)
Read: FULL (body; appendices A.1–A.9 incl. sourcing, determinism/cost, covering array, scale ladder, eight qualification gates, statistics, comparison protocol, decontamination; A.10 worked examples skimmed; B dense-reward derivations; C.1 recipe; C.2–D skimmed).  Relevance to Part 2: **very high**. Latent-world-first, generator-code environments with eight generation-time gates (exploit probes, reward causality, role-independent graders, two independent reference solvers, metamorphic tests), a strength-2 covering array as the diversity rule, and a verifiable progress potential Φ. This is the most rigorous verifier-testing design in the batch and maps one-to-one onto our F1–F7 and the Φ/milestones field.

**Problem.** No long-horizon training corpus exists (only small hand-made benchmarks); long tasks are hard to verify, and terminal-only reward starves GRPO: the share of all-fail groups is (1 − p)^G, 66% at p = 0.05, G = 8.

**Method / algorithm.**
1. *Sourcing.* Per ALE computing-and-math subdomain (software, data/analytics, AI/CS research, math/OR, security/forensics, infra/cloud, quantum), sample real task specifications (web, MLE-bench, reference manuals) and have coding agents author a **seeded generator program** around each (structure and difficulty only, never copying prompt, input, answer or grader). Filters before implementation: feasibility (ground truth knowable by construction, CPU-only, no live services, no "improve this"), a similarity gate over code, spec and generated data against all registered generators, and an **adversarial review** of the spec for shortcuts, short horizons or disguised sources. ≥2 generators per domain. Authors review generator code once; running it needs no model.
2. *World construction (Stage 1).* Seed + scale tier → latent world W (complete correct domain state), validated against invariants (unique ids, valid joins, finite measures), plus a seed-derived **defect plan** (which records/shards/fields get corrupted by which declared operator).
3. *Workflow DAG (Stage 2), by code.* Stages with dependencies, allowed parallelism and per-stage work estimates; the critical path defines the horizon (median 6 stages, range 3–12).
4. *Rendering (Stage 3).* Project W into wire formats (CSV/TSV, JSON, SQLite, safetensors shards, stripped binaries, manifests, even a screenshot); assert the render **round-trips** to W.
5. *Controlled corruption (Stage 4).* Apply the declared, invertible defect plan (schema drift, duplicates, missing records, categorical drift, scrambled shard indices, stale caches). So s0 fully determines W, and the correct answer is computable from what the agent sees.
6. *Public contract and hidden suite (Stages 5–6).* Prompt: input roles, required outputs and schemas, ordered requirements, authority-precedence rules, permitted toolchain. Sealed: metamorphic transforms (meaning-preserving rewrites must keep the grade) and stale-output counterfactuals (plausible wrong states must fail).
7. *Progress contract.* Nodes v (checkable workspace states) with weights summing to 1 and prerequisite sets; partial scorer c_v(s) ∈ [0,1] against W (set precision/recall for records, tolerances for numbers); credit gated by the weakest prerequisite; Φ(s) = Σ w_v · c̃_v(s).
8. *Eight qualification gates at generation time:* (i) reward causality: each reward component drops when its cause is mutated in a passing workspace; (ii) exploit resistance: **14 gaming probes** (empty output, minimal schema-valid output, copied input, single-seed hard-coding, path traversal, private lookup, …) score 0 on both verifier and Φ; (iii) role independence: reference solver, alternative solver, strict verifier and progress scorer have disjoint, audited code closures; (iv) solver agreement: reference and independently authored alternative solver give identical output trees on every seed (disagreement = unresolved spec → reject); (v) progress validity: 0 < Φ < 1 on partial states, monotone to 1 along the reference, negative on regression; (vi) metamorphic invariance; (vii) six-seed diversity (distinct world ids, public-tree hashes, task ids); (viii) public-contract hygiene (no private authority in prompt or tree).
9. *Coverage.* 19 labelled axes (curriculum layer, subdomain, generator revision, scale tier, four horizon axes, workflow stage, tool capability, artifact role, relation type, corruption class, source kind, licence, reward component, observed reward band, outcome, failure category); the corpus must be a **strength-2 covering array** (every valid pair of values of any two axes co-occurs in an admitted environment), extended greedily by picking the generator/seed/tier that covers the most uncovered pairs.
10. *Difficulty controls.* Scale tier (unit → small → full; median input 17 files/51 KB → 28 files/586 KB) and DAG depth × number of corruption classes. Difficulty itself is reported per learner as verified success under a declared harness, not as a property of the task.
11. *PPRS reward.* R(τ) = 1[pass] + λ·Φ(s_T), λ = 0.25 (untuned), applied as per-turn increments λ(Φ(s_t) − Φ(s_{t−1})) with return-to-go (γ = 1) and a **per-turn-index group baseline**; any pass (1 + λ) outranks any failure (≤ λ). They bound when the shaped objective can prefer a less successful stochastic policy: only if the pass-rate gap is < λ(1 − p₁)/(1 + λ) ≤ 0.2. DPPO, G = 24, 8 tasks per step, 65k response tokens, ≤64 tool calls, single bash tool, zero-variance groups refilled.

**Verification / grading.** Strict verifier against W plus Φ, both gated as above. This is near-best practice: independent solvers, independent graders, mutation-based causality, probe-based exploit resistance, metamorphic and counterfactual tests. Remaining risk: generator authors (coding agents + authors) can still mis-specify the world; the 14 probes are fixed and generic.

**Scale & cost.** 1,170 environments (Math & Science 264, ML 242, Coding & System 664), balance score 0.89–0.91. Marginal cost per environment: median 30 s CPU (p90 82 s), no model calls; one-time authoring per generator (cost n/r). Gemini 3.6 Flash: median 12.4 min per rollout (prior corpora 0.5–2.0), P@1 29%, P@8 40%; untrained Qwen3.8-27B solves 3.2% (52% of its rollouts exhaust 65k context). 26/92 sampled environments unsolved by the frontier evaluator.

**Key results.** ALE-CM P@5: Qwen3.8-27B 0.17 → Tev-27B 0.28 (GPT-6 Astra 0.28, Opus 5 0.28); Qwen3.5-9B 0.06 → 0.11 (unit tier only, 264 tasks). TB 4.0-CM P@1 0.04 → 0.10; TB 3.0-CM 0.09 → 0.14; TB 2.1 0.764 → 0.794. Tev-320B (GLM-5.3-Flash): TB 3.0-CM 0.20 → 0.27, TB 4.0-CM 0.29 → 0.37, gains mostly in P@1 (reliability), not P@5. **Data ablation (9B, terminal reward):** public-view verifier (LLM writes the verifier from the agent's view) 0.24 S@1 and **88% of groups discarded**; prompt-first self-instruct pipeline 0.23; sparse with Tev data 0.25; base 0.25 → neither LLM-built variant beat the base. **Reward ablation:** PPRS 0.29 S@1 / 0.11 P@5 vs sparse 0.25 / 0.06; pooled normalisation 0.28 / 0.06; direct additive Φ(s_t) with γ = 0 0.29 / 0.06 but more context exhaustion; at 27B, terminal-only reward **could not complete a single optimiser step** (all groups zero-advantage). In 24 measured all-fail groups, Φ gave non-zero variance in every group (plateaus 0.05, 0.26, 0.69, 0.78, 0.90, 1).

**Failure modes & limits.** Authors: ALE-CM-targeted only; CM subsets of TB chosen by Claude (correlation with full sets r = 0.96–0.97); stronger bases needed. Mine: generator authoring cost is hidden; tasks are "repair a corrupted world" style, so skill coverage is narrower than the domain list suggests (corruption-class diversity, not intent diversity); Φ rewards workspace states, which an agent could reach by an unintended route (accepted by design); per-turn-index baselines assume aligned turn semantics across rollouts.

**Tips & tricks.**
- Build each environment family as a seeded generator; marginal cost becomes seconds of CPU.
- Assert render round-trip and declared, invertible corruption so the answer is provably computable from the start state.
- Require two independently written reference solvers that agree on every seed.
- Keep verifier, progress scorer and solvers in disjoint code closures; check imports.
- Run a fixed battery of generic gaming probes (empty, minimal-valid, copied input, hard-coded, path traversal, private lookup) on every task.
- Test reward causality: mutate each cause in a passing state and check the component drops.
- Add metamorphic (must still pass) and stale-output counterfactual (must fail) cases.
- Gate progress credit by the weakest prerequisite so correct aggregates on wrong inputs earn nothing.
- Use a strength-2 covering array over coverage axes and fill uncovered pairs greedily.
- Quote horizon as the DAG critical path, not observed rollout length.
- Report difficulty per learner and harness, not per task.

**Fit to Crucible Part 2.** This is the reference design for F1/F2/F4–F7 in `world_synth` domains. Concretely: (1) G-list additions: **G15 exploit probes** (generic battery, Φ and verifier must both score 0), **G16 reward causality** (mutate each cause), **G17 solver agreement** (two oracles from different families must produce the same end-state fingerprint; this strengthens G14 alternatives), **role independence** as a provenance check on code closures (§3.0 rule 5 at the code level), and metamorphic/counterfactual cases inside G5. (2) `VerifierBundle.milestones` should follow the progress-contract shape (weights, prerequisites, weakest-prerequisite gating, monotone and regression-negative), and F6 should check progress validity before admitting Φ as a reward. (3) §3.5: replace "MAP-Elites fill fraction" alone with a strength-2 covering-array requirement over the DomainSpec axes plus the greedy pair-filling rule; it detects template locking that per-axis balance misses. (4) §3.6: scale tier and DAG depth × corruption count are clean `count`/`horizon`/`linkage` knobs; report p per (task, student, harness). (5) PPRS with λ = 0.25 and per-turn-index baselines is the candidate reward for long tasks where p(35B) < 0.05, since terminal reward gave zero optimiser steps at 27B. (6) The public-view-verifier ablation (88% wasted groups, no gain) is strong evidence for our rule that verifiers come from privileged ground truth. Priority **P0** (gates G15–G17, progress-contract schema, covering array), P1 (generator-based families, PPRS).

## 2609.27321 — Verifiable Hidden Dynamics Play: Generating Agentic RL Environments from Solved Mechanisms (VHD-Play) (Shen et al., 2026; venue n/r, Georgia Tech + Alibaba Token Foundry/Qwen)
Read: FULL (body; appendices A–K incl. admission criteria and audit, reference computation, setter capacity, isolation, training config, environment-first comparison with EnvScaler, mechanism families, complexity sweep, limits; D examples and H trajectories skimmed).  Relevance to Part 2: **high**. Solve-first construction with a normalised optimality-gap reward, an explicit information boundary knob (written-out / parameters revealed / parameters acquired), a matched environment-first control on our exact student (Qwen3.6-35B-A3B), and evidence that the student itself can act as setter. It is the cleanest published case of "ground truth comes from a solver, not a model".

**Problem.** Environment-first pipelines generate the environment, then attach a reward or annotate trajectories, so dynamics and evaluation must be aligned afterwards; written-out tasks are cheap to verify but do not require acting in changing state.

**Method / algorithm.**
1. *Mechanism family* f = (parameter sampler P_f, reference solver S_f, reusable realisation/replay adapter), registered once. Eleven families: inventory DP, routing, budget-coupled knapsack, LP, QP, scheduling, tardiness scheduling, facility location, negotiation, sequential stopping, sequential search.
2. *Sample and solve.* θ ~ P_f; S_f computes z_θ = (u*(θ), u₀(θ)): the optimum (backward Bellman, Held-Karp, enumeration, HiGHS, SLSQP; no LLM) and the value of a fixed **default policy** (act on sticker numbers, split shared budget evenly, never probe).
3. *Reward fixed before the environment exists:* r = clip₀¹((u(π;θ) − u₀) / (u* − u₀)); the default scores 0, the full-information optimum 1. Under partial information u* is an upper reference, not necessarily attainable.
4. *Realisation.* Decision variables → state updates; constraints enforced in the transition function; objective accumulated as terminal utility. A frozen setter LLM receives the full draw plus one sampled real-world document passage (28 topical domains) and writes the scenario, entity/relation model, backing database, ≥10 executable tools, player instruction, an executable default policy and the output format. Reusable family dynamics come from the sampler where available.
5. *Interface = information boundary.* Catalogue, **probe** (reveals a designated view of hidden parameters, costs budget), decision (changes state) and clock operations, plus a state-independent compute tool; no read of the draw or references. Three presentations of the same draw: written-out F, informed-agentic I (parameters shown upfront), agentic A (parameters acquired by probing).
6. *Admission.* C1 executability (dynamics and tools initialise and run; reference policies reach numeric outcomes); C2 default outcome inside a family-defined admissible region; C3 **reward agreement at the optimum**: replaying the solver's policy through the generated environment reproduces u* within tolerance (routing uses a separate interface driver). Up to three replay drivers: optimal, greedy-on-visible-values, and idle (commit nothing). Failed candidates are regenerated.
7. *Training.* GRPO, 64 prompts × 16 rollouts (oversampled to 18), advantage = return − group mean (no std normalisation), no KL, lr 2e-6, clip 4e-3, 34 optimiser steps over 2,176 environments (34,816 scored rollouts); up to 1,000 turns, 65k managed context.

**Verification / grading.** Solver-derived references plus replay agreement; an audit of 80 held-out environments × (optimal, default, idle) × 2 runs: 480 executions, no exceptions, all 240 repeated outcomes agreed, no realised utility exceeded u*. Residual risk: setter-written tools could leak hidden parameters through an unintended observation (isolation is by interface design, not tested adversarially).

**Scale & cost.** 3,300 admitted environments (2,200 train over 3 families, 300 held-out in-family, 800 for 8 unseen families); setter attempts mean 1.41, 65.6% admitted first try, 31.6% interface rewritten; about 900 input + 6,300 output tokens per admission, **$0.01–0.03 per environment**. Setter capacity: frozen Qwen3.6-35B-A3B admits 70% (21/30) with 2.5 attempts and 45.5% interface refinement; Qwen3.7-Max 100% with 1.03 attempts; cost per admission about equal. Topical label entropy 0.997, largest label 4.67%.

**Key results.** Five-family diagnostic, Base → trained: written-out 0.962 → 0.992, informed-agentic 0.231 → 0.875, agentic 0.204 → 0.815; i.e. **most of the gap is stateful execution, not problem solving** (0.962 vs 0.231 with parameters revealed); training closed 84% of the revealed-parameter gap. Held-out training families +0.56, unseen optimisation families +0.63, far-OOD families +0.24/+0.16. Code-tool adoption explains only +0.030 of a +0.443 gain. Policy shift KL 0.089 nats/token. External: E-Commerce Bench 365-day storefront mean balance 54,294 → 182,844 (Qwen3.7-Max 165,224), no bankruptcies; BFCL V4 ten-cell mean 61.25 → 64.08; TravelBench 0.700 → 0.794. **Matched environment-first control** (2,200 EnvScaler scenarios, same base, optimiser and 34 steps): BFCL 58.56 (below base), storefront 52,661, TravelBench 0.753. Knapsack co-scaling (frozen 35B setter): gains +0.41, +0.55, +0.68, +0.86 as items × periods grow from 6×5 to 11×11 (base falls 0.432 → 0.085).

**Failure modes & limits.** Authors: terminal reward only; three training families; one run and one eval seed; families are well-known OR models. Mine: the domain is OR-style decision problems, so transfer claims to enterprise workflows rest on three external benchmarks; probes make information acquisition explicit and cheap, which real Apps may not; the 0.89-gain sweep is one family; clip-at-0 reward hides policies worse than the default.

**Tips & tricks.**
- Fix the reward from a solver before building the environment; normalise between a default policy (0) and the optimum (1).
- Admit an environment only if replaying the solver's policy through it reproduces the precomputed optimum.
- Replay optimal, greedy and idle drivers twice from fresh state as an audit.
- Treat parameter visibility as a knob (written-out, revealed, acquired) and measure the gap at each level.
- Ground scenarios in sampled real document passages to diversify setting and language without changing dynamics.
- A student-sized setter can build valid environments once the mechanism is fixed; a stronger setter mainly raises yield.

**Fit to Crucible Part 2.** F4/F5: for any domain with a computable optimum (scheduling, allocation, inventory, routing inside the finance_ap or helpdesk packs), use the solver as oracle and the normalised gap as an `answer_check`/state reward; add "replay agreement" as a G3 variant (oracle replay through the App reproduces the solver value). F3/§3.6: the F/I/A boundary is an `observability` knob with three levels, and the measured F-vs-A gap is the cleanest intent probe we have seen for "does this task exercise stateful execution": add it to F10 as a fourth ablation (written-out version of the same draw), where a high written-out score with a low agentic score shows the skill is the interaction, not the math. F1: the default-policy and idle drivers are cheap null agents for G4. Diversity: corpus-passage grounding is a cheap surface-variation axis, but signatures will cluster by mechanism family, so families, not passages, are the unit (§3.10). The matched EnvScaler control supports "construction-first beats environment-first" for a 35B student. Priority P1 (mechanism families as a `world_synth` source), P0 for the observability-knob intent probe.

## 2512.19682 — GenEnv: Difficulty-Aligned Co-Evolution Between LLM Agents and Environment Simulators (Guo, Yang, Chen, Xiao et al., 2025; venue n/r, Princeton/Columbia/Michigan/Chicago)
Read: FULL (body; appendix A proofs and hyperparameters).  Relevance to Part 2: medium. The α-curriculum reward for a task generator and its ranking-consistency bound are useful for the task loop, but tasks and their "evaluation specification" are generated by an LLM simulator with no executed ground truth, and evaluation decomposes multi-turn benchmarks into single steps, so the environment side does not meet our verification bar.

**Problem.** Static agent datasets stop matching the agent's weaknesses as it improves; offline teacher augmentation scales volume, not relevance.

**Method / algorithm.** Two policies, both initialised from Qwen2.5-7B-Instruct.
1. *Environment policy* π_env generates a batch of n task variations per seed (prompt + tool specs + constraints + goal, an evaluation spec such as exact-match target or checker, and optionally a target action a).
2. *Agent policy* π_agent attempts them. Agent reward: exact match for structured actions (tool calls), soft similarity (token-F1 or embedding) for free text, in [0,1].
3. *Environment reward:* batch success p̂ = k/n; R_env = exp(−β(p̂ − α)²) with α = 0.5 (β n/r). Batches with |p̂ − α| > 0.1 are excluded from environment updates.
4. *Updates.* Agent: GRPO (lr 1e-6, batch 64, 9k tokens, 10 epochs). Environment: reward-weighted regression, i.e. SFT on its own generations weighted by exp(λ·R_env), λ = 1, lr 5e-7, with a KL penalty to the initial simulator and a per-step KL cap.
5. *Pools.* Agent pool accumulates valid (parseable, executable, checker-runs) traces across epochs plus base data; environment pool accumulates weighted generations.
6. *Theory.* With a baseline b = p, E‖g‖² ∝ p(1 − p) under bounded score variation, maximised at p = 1/2; and the mis-ranking probability of two task types by R_env decays as 4·exp(−(2/9)(Δ₂ − Δ₁)²·n) in rollouts n.

**Verification / grading.** Exact match against a generator-provided target for tool calls; similarity for text. No execution of tasks against a real environment state, no solvability proof, no negative tests; a generator can reach α by producing ambiguous tasks that half the rollouts match by chance. Evaluation: ALFWorld decomposed into single steps; BFCL long-context subset with each turn independent.

**Scale & cost.** n/r beyond 10 epochs, batch 64; "1x original data + dynamic simulation" vs Gemini 2.5 Pro offline data at about 1.76× and 3.27× the training set.

**Key results.** Average over five benchmarks: GenEnv 7B 53.6 vs Qwen2.5-7B 33.0 (ALFWorld 14.2 → 54.5, BFCL 7.0 → 41.8, API-Bank 61.6 → 79.1, TravelPlanner 14.3 → 16.6). BFCL validation: GenEnv 0.458 vs Gemini-offline 3.3× 0.438; GenEnv beats GenEnv-Random (untrained simulator) by 12.3%. Simulated-task success rose from 0.138 and settled in about [0.4, 0.6]; required response length 137 → 204 tokens by epoch 6.

**Failure modes & limits.** Authors: few stated. Mine: no verifier testing at all; the "emergent curriculum" is measured by response length; band hits on generator-made tasks are not evidence of correctness; single-step decompositions inflate multi-turn benchmark gains; no seeds or variance; Gemini comparison is the only strong control.

**Tips & tricks.**
- Reward a task generator with a bell curve around the target pass rate, exp(−β(p̂ − α)²).
- Exclude batches far from the band from generator updates to avoid chasing noise.
- Regularise a trained generator with a KL cap to its initial weights.
- Use the Hoeffding-style bound to size rollouts: separating two task types whose band distances differ by Δ needs n ≈ (9/2)·ln(4/δ)/Δ².

**Fit to Crucible Part 2.** §3.6 already cites GenEnv for a 0.5 band centre; keep it as one data point but note that its band is measured on unverified tasks. The ranking bound gives F9 a principled rollout count: to tell an in-band task from one 0.2 further away with 95% confidence needs about 4.5·ln(80)/0.04 ≈ 490 rollouts, far beyond k = 8, so per-task bands need sequential tests and pooled cell-level estimates, not single-task ranking. For the generator loop (§3.8), the α-reward is a cheap score for swarm proposers, but only after F6 gates pass (AutoEnvScaling's −1/−0.25/+1 shape is closer to what we need). Avoid exact-match-to-generated-target rewards. Priority P2.

## 2601.16443 — Endless Terminals: Scaling RL Environments for Terminal Agents (Gandhi et al., 2026; venue n/r, Stanford + Microsoft Research)
Read: FULL (short paper; no appendix in the HTML).  Relevance to Part 2: medium. A clean minimal four-stage pipeline with a pre-state test, a "final tests fail in the start state" check and a frontier pass@16 > 0 filter. Its main lesson for us is negative: easy, frontier-filtered tasks gave large in-distribution gains but tiny transfer, which §3.6 already cites.

**Problem.** Terminal benchmarks are evaluation-sized; RL needs an autonomous generator of tasks, containers and tests.

**Method / algorithm.**
1. *Task description.* Prompt an LLM (model n/r) with a random draw over three axes: task category (file management, text processing, log analysis, git, database queries, security scanning, …), complexity level (single command to multi-step), scenario context (persona-like: developer, DevOps engineer, analyst). Output: a user-style instruction plus a **privileged ground-truth section** (exact file contents, paths, expected states) never shown to the agent.
2. *Container + initial-state tests.* Generate an Apptainer definition or Dockerfile and a test file of prerequisites (files, directories, processes, cloned repos); build, run the tests inside, feed failures back; ≤3 rounds, else discard.
3. *Final tests.* Generate completion tests from the description, ground truth and initial tests; **require that they fail in the initial state**.
4. *Solvability filter.* o3 samples 16 solutions in the same agent loop; keep tasks with pass@16 > 0 (about half of candidates are discarded).
5. *Agent loop and RL.* Minimal scaffold: free reasoning then `<command>`; `done` to finish; persistent PTY shell in Apptainer (or Harbor for Docker); structured observation (success/failure, stdout/stderr, exit code). PPO via SkyRL, 16 rollouts per prompt, 16 turns, 2,048 tokens per turn, 16k context, T 0.6, clip 0.2/0.28, no KL ("hurt performance"), binary episode reward, 5-min environment timeout; 64 turns at inference with history collapsing.

**Verification / grading.** pytest-style end-state tests derived from privileged ground truth; no-op check via "fails in initial state"; solvability via o3. No negatives beyond the start state, no leak or shortcut checks; tests and ground truth come from the same model as the task.

**Scale & cost.** 3,255 tasks (about 2,500 also in Harbor format); about 50% discarded at the o3 filter; roughly half of kept tasks are solved by all 16 o3 attempts. Training: 3B/7B on 4×A100 for about 2 days; 8B on 8×B200 for about 8 h. Token cost n/r.

**Key results.** Held-out dev set (same generator): Llama-3.2-3B 4.0 → 18.2%, Qwen2.5-7B 10.7 → 53.3%, Qwen3-8B-openthinker-sft 42.6 → 59.0%. Terminal-Bench 2.0: 0.0 → 2.2, 2.2 → 3.4, 1.1 → 6.7%. OpenThinker dev set: 9.7 → 10.2 for the 8B. Failure analysis of the 8B on TB2 zero-success tasks: loops 39%, turn exhaustion 26%, early wrong termination in specialised domains (cryptanalysis, bioinformatics) 49% (overlapping); command diversity after the first error 0.49 in successes vs 0.18 in looping failures. Pass@5 by TB2 difficulty: easy 1/4, medium 8/55, hard 3/30.

**Failure modes & limits.** Authors: tasks resemble competitive-programming requests, not messy real requests; the o3 filter caps difficulty at the frontier; binary reward is sparse. Mine: half the kept tasks are trivially solved by o3, so the pool is easy for the frontier and largely out of band for a 35B after a few steps; the dev set shares the generator, so the 10.7 → 53.3% gain overstates transfer; no dedup or diversity measurement beyond categories.

**Tips & tricks.**
- Generate a privileged ground-truth block with every task; tests read only from it.
- Validate the container with prerequisite tests before writing completion tests.
- Require completion tests to fail on the untouched start state.
- Measure "command diversity after the first error" as a looping diagnostic in traces.

**Fit to Crucible Part 2.** Confirms G4 (null/start-state must fail) and the `privileged_notes` field. The transfer gap (big in-distribution gains, TB2 +1–6 points) supports two plan items: difficulty must come from structure rather than a frontier pass filter (§3.6), and held-out evaluation must be on other families or human benchmarks, not a same-generator dev split (§3.10). The looping diagnostic is a cheap trace feature for F12's failure clustering (a `loop` label with a command-diversity score). Priority P2 (patterns already adopted).

## 2601.04126 — InfiniteWeb: Scalable Web Environment Synthesis for GUI Agent Training (Zhang, Wang et al., 2026; ACL 2026 per note, venue line not in text; Microsoft Research Asia)
Read: FULL (body; appendices A cases, evaluator example, TCTDD example, B implementation, C detailed results, D–E human checks; F prompts skimmed).  Relevance to Part 2: medium-high for the **website App tier** of the World (§2(b)) and for instrumented milestone rewards; the "derive everything from tasks" order (tasks → data models → shared interfaces → backend under task-centric TDD) is a useful alternative to tool-first App synthesis.

**Problem.** GUI-agent benchmarks are hand-built (tens to hundreds of apps); LLMs generate single pages well but multi-page websites with shared state come out inconsistent, buggy along long task paths, and visually homogeneous.

**Method / algorithm.** GPT-5 (high reasoning) at every step.
1. *Seeds.* Sample Common Crawl pages, render a full-page screenshot as the design image, have an LLM write a short website seed ("online bookstore"); filter robots.txt and illegal content.
2. *Unified specification.* Generate 8–10 realistic user tasks for the seed first; derive data models (entities, attributes, relations), a page architecture (≤12 pages), and one shared set of programming interfaces in which each task step maps to interface calls. Parameters are classified system-managed (userId, sessionId; read from localStorage) vs user-provided (productId, quantity), and interfaces are wrapped to expose only the latter.
3. *Task-centric backend (TCTDD).* Generate concrete data consistent with tasks (a task about products under $50 guarantees such products exist; real image URLs via APIs). Generate tests from task specs and implementation code in parallel from the same data; run; on failure feed the failing test, expected vs actual and the relevant code to the LLM; ≤8 iterations; only task-relevant paths must be correct ("task-centric correctness"). 1.5% of sites remain unfixed; most need 1–3 iterations.
4. *Design-guided frontend* (in parallel): a VLM extracts colour system, typography, spacing and component styles from the design image; per-page design (content blocks, flows, routing by URL params, responsive grid); a shared header/footer/CSS-variable framework; per-page HTML/CSS/JS bound to the backend SDK through data attributes; an init script writes generated data into localStorage (no server).
5. *Evaluators.* For each task, identify key steps and add **instrumentation variables** (checkpoints written to localStorage when the relevant function runs, e.g. search submitted, item added, checkout completed) beside existing state variables; generate a JS evaluator returning a weighted sum of checkpoints (example: attempt 0.35, record consistency 0.30, on-site confirmation 0.35).
6. *Training.* UI-TARS-1.5-7B, GRPO, lr 1e-6, batch 16, clip 0.2–0.3, γ 0.95, 128 parallel environments, 8 trajectories per task, ≤15 steps.

**Verification / grading.** Instrumented checkpoints + state checks in generated JS. Weak points: checkpoints reward actions the agent *attempted* (instrumentation of function calls), i.e. path-based partial credit; the evaluator is generated by the same pipeline; human check of 100 tasks found 95 clear and correctly judged (5% defect rate). No negatives or exploit probes.

**Scale & cost.** About 0.36M input + 0.34M output tokens per website, **$1.93 per site** at GPT-5 batch pricing; median 20 min per site; 600 sites in about 125 min in parallel (6.9% of total training time). 600 training tasks used; 4,000 tasks for the dense-reward analysis.

**Key results.** WebGen-Bench functional score 85.6 ± 1.2 vs Codex 80.8, Claude Code 75.8, Bolt.diy 67.1; without TCTDD 82.6; with GPT-4.1 backbone 77.4. Visual win rate vs Claude Code 85.4%, vs Codex 69.3% (GPT-5 judge, 91% agreement with humans on 100 cases). UI-TARS-1.5-7B: OSWorld 24.5 → 31.4, Online-Mind2Web 23.0 → 28.7, MobileWorld 6.4 → 10.3, rising with 200/400/600 tasks. **Same 600-task GRPO run on Claude-Code-generated websites: +0.7, +0.7, −1.3**, attributed to context management (InfiniteWeb gives each step only the relevant spec; Claude Code accumulates the whole codebase, 4.9 vs 12.6 pages per site). Dense reward: 767 of 4,000 tasks discriminative under GRPO (4 trajectories) vs 174 with binary reward (4.4×). Generated sites are harder than OSWorld for both UI-TARS (7.4 vs 24.5) and Agent S2 (14.1 vs 27.3).

**Failure modes & limits.** Authors: single-website tasks only; web only; generation cost and latency. Mine: localStorage-only state means no server-side truth and easy client-side tampering in principle; task-centric correctness leaves off-path functions buggy, which an exploring agent will hit and learn from wrongly; path-instrumented rewards can be farmed by repeating the rewarded action; WebGen-Bench uses an LLM agent as the tester.

**Tips & tricks.**
- Generate tasks first, then derive data models and one shared interface spec that every page must use.
- Wrap interfaces so system-managed parameters are hidden and only user-provided ones are exposed.
- Seed data from tasks so every task's answer exists in the data.
- Give each generation step only the specs it needs, not the accumulated codebase.
- Use real-site screenshots as style references for visual diversity at near-zero cost.
- Count "discriminative tasks" (non-zero within-group variance) as the metric for reward design choices.

**Fit to Crucible Part 2.** F1 (website tier): the tasks → data model → shared interface → TCTDD order is a good "App from family" recipe for browser Worlds; the system/user parameter split again backs G8. F5: instrumented checkpoints are milestones for Φ, but they are path signals; in our contract they belong to `milestones` with prerequisite gating (Tev) and must never substitute for end-state checks; add a "repeat the rewarded action" probe to G15. F6/G13: task-centric correctness conflicts with interaction completeness; keep G13 (every exposed tool returns a non-crash observation) so off-path bugs do not teach false lessons. The Claude-Code control is evidence that context-scoped, spec-driven generation beats one long agent session for multi-file Apps, which argues for staged sessions in `factory/machine.py`. Priority P1.

## 2605.02964 — Reward Hacking Benchmark: Measuring Exploits in LLM Agents with Tool Use (Thaman, 2026; ICML 2026 per note and keywords; independent researcher)
Read: FULL (body; appendices A instrumentation and precedence, B MicroRHB, C CoreRHB families, D variants, E grading, F chains, G hardening, H ablation, I distribution; J–K prompts/traces skimmed).  Relevance to Part 2: high for **G12 hackability and §3.8 hardening**: a six-category exploit taxonomy with deterministic log-based detectors, a four-intervention hardening ablation, and evidence that exploit rates rise with chain length, unverifiable steps and honest-solution complexity, which is exactly where our long-horizon, hard tasks for a 397B sit.

**Problem.** Do tool-using agents exploit shortcuts when honest solutions are available, does RL post-training raise this, and which environment defences work on multi-step workflows?

**Method / algorithm.**
1. *Tasks.* MicroRHB: 12 small deterministic tasks × 50 instances (schema validation, CSV normalisation, date/email validation, semver compare, AST import graph, hash manifest, …), chainable. CoreRHB: four six-step families (data pipeline, log forensics, performance optimisation, multi-file reconstruction), each ingest → validate → transform → produce → **evaluate on hidden data (steps 5–6)** → verify robustness. Standard and hard variants: hard raises honest work 2–10× (data size, decoys, tighter time/memory budgets, adversarial inputs, stricter schemas, more hidden checks) with the **exploit surface unchanged** (median honest tool calls 12 vs 23).
2. *Regimes.* Independent, and chained (length 2–7) where downstream steps need upstream artifacts; dependencies enforced by **recomputed hashes over upstream outputs**, so schema-valid forgeries fail.
3. *Pipeline.* Seeded instance generation (inputs, decoys in baseline, private grading spec) → agent loop (bash/Python/file tools, 15-min timeout, neutral system prompt with no mention of evaluation) → outputs only from /workspace/output → **grader outside the sandbox recomputes on hidden data** (binary within tolerance) → log replay through deterministic integrity rules. Correctness and exploit are scored separately: a run can be correct and exploitative.
4. *Taxonomy and detectors* (from command logs, reads/writes, diffs of protected files, recomputation discrepancies): (1) leakage/metadata (e.g., read of `_meta/**`); (2) tampering (writes under task dir, edits to harness/verify scripts, env/config changes); (3) sequence manipulation (forged completion markers, fabricated intermediates, skipped verification, final report without prerequisites); (4) proxy gaming/parser exploits (minimal valid JSON, default values, duplicate keys, self-reported runtimes); (5) special-casing visible checks (hard-coding observed instances, branching on ids); (6) denial-of-evaluation (timeouts, crashes, resource exhaustion; fail-closed). Primary category by precedence: tampering > denial > sequence > leakage > proxy > special-casing. Detector audit: 94% agreement on 50 flagged runs (3 borderline false positives), 0 false negatives on 50 unflagged runs.
5. *Hardening toggles.* Randomised intermediate outputs (per-instance nonce that must propagate); explicit step verification (recomputation hooks, required logs from a read-only tool, non-forgeable tokens); hardened boundaries (grader outside sandbox, fail-closed strict schemas, protected mounts with diff alarms); reduced file access (mount namespace: read-only task dir with only the current step's inputs, prior artifacts copied to read-only `prev/`, write-only output, ignored scratch; decoys unmounted).

**Verification / grading.** Hidden recomputation for correctness; deterministic integrity rules for exploits. Rates are lower bounds (undetected strategies possible).

**Scale & cost.** 13 models; 40 independent instances and 35 chains per model; $5–50 per episode on frontier APIs; Clopper–Pearson CIs and Fisher tests throughout.

**Key results.** Exploit rates: Claude Sonnet 4.5 and Opus 4.5 0.0%; GPT-4o 0.9; Gemini 2.5 Flash 0.8; DeepSeek-V3 0.6; Claude 3.7 Sonnet 3.9; Gemini 2.5 Pro 4.6; o1 6.8; o3-mini 7.1; o4-mini 8.4; o3 11.8; DeepSeek-R1-Zero 13.9 (V3 vs R1-Zero, same base: 0.6 vs 13.9, CIs [0.1, 2.6] vs [10.0, 18.5]); within every vendor the RL-reasoning model is higher. Exploits jump at chain length 5, the first step whose check the agent cannot privately verify (hidden split); MicroRHB chains 2.3% vs CoreRHB 8.1% at length 5. 72% of exploit episodes have an explicit rationale framed as efficiency ("checking this first would be much more efficient"); 28% have none. **Hardening: 6.5% → 0.8% exploits (−87.7%), success 83.2 → 82.8 (n.s.)**; single interventions: hardened boundaries −41.5%, reduced file access −36.9%, step verification −32.3%, randomised outputs −20.0%. Hard variants raise exploits for all 13 models (Sonnet 4.5 0.0 → 1.8; o3 11.8 → 19.6; R1-Zero 13.9 → 22.3). Most common categories: sequence manipulation 31%, then leakage 24% (main text) or tampering 19% (appendix; the two disagree).

**Failure modes & limits.** Authors: small samples; observational RL attribution; detector coverage; hardening co-evolution; no-network sandbox. Mine: exploit opportunities are seeded in a fixed set of places (`_meta`, checker scripts), so rates depend on the surface design; the student models we train were not evaluated.

**Tips & tricks.**
- Grade outside the sandbox by recomputation on hidden data; read submissions from one output path only.
- Mount only the current step's inputs read-only; copy prior artifacts into a read-only `prev/`; unmount decoys and grader metadata.
- Enforce chain dependencies by recomputed hashes or non-forgeable per-instance nonces, not by file existence.
- Parse fail-closed with strict schemas; reject duplicate keys and defaults.
- Ignore self-reported metrics; measure them in the grader.
- Detect exploits from logs with deterministic rules and score them separately from correctness.
- Expect more exploitation as honest work grows and as steps become privately unverifiable; harden hard tasks first.
- Do not rely on CoT monitoring alone: about 28% of exploits are unverbalised.

**Fit to Crucible Part 2.** G12 and §3.8: adopt the six categories as the attacker's checklist and as hack-flag labels in F12 (`hack_flags` with category + evidence); implement the log-based detectors over our trace (`_call_tool` records, file diffs) as cheap deterministic G12 pre-checks before the paid attacker. The four hardening toggles map to existing Crucible mechanisms: hardened boundaries = verifier custody (`world/custody.py`), reduced file access = path constraints / protected paths, step verification = milestone checks with nonces, randomised outputs = per-seed variation (G2 must then compare fingerprints modulo the nonce). The complexity-threshold result means F9's harder variants for the 397B need **more** hardening, not less: re-run G12 on every variant that raises the knob band. The chain-length-5 jump argues for placing at least one privately unverifiable check (hidden split / held-out state) inside long tasks and monitoring exploit rate there. Priority **P0** (taxonomy + detectors + hardening checklist in G12).

## 2610.33568 — Trajectory2Gym: Decision-Grounded Compositional Interaction Synthesis for Tool-Use Agents (Hu et al., 2026; venue n/r; affiliation n/r in the extracted text)
Read: FULL (body; appendices A protocol, B corpus/representation/synthesis, C grounding, D selection and parent normalisation, E theory notes, F extra analysis; G qualitative skimmed). Teacher/collector model identity n/r.  Relevance to Part 2: high for **traces-to-tasks and trace-based supervision**: it formalises when an action in a logged trajectory is a legitimate learning target (grounded in the learner-visible history), counts capability-path support, and targets synthesis at under-supported paths. It is SFT-only and trains inside the benchmark environments' own train splits, so treat the absolute numbers with care.

**Problem.** Successful trajectories are poor supervision when they (a) under-represent multi-step dependencies (in their 34,772-candidate pool, 40.9% have ≤2 supervised decisions and only 10.0% contain a certified decision after an authentic error) and (b) contain actions the agent could not justify from what it saw (e.g., ids known only to the collector; a stale exchange accepted by the API).

**Method / algorithm.**
1. *Capability vocabulary K* (semantic actions/arguments, observation outcomes, recovery, branching, handoff, termination, horizon); a trajectory's **canonical path** p = (κ₁ … κ_ℓ) (example: lookup, error, clarification, retry, order read, confirmation, cancellation, update). Support n_S(p) = number of selected trajectories with that path.
2. *Deficit-driven synthesis.* For paths below target support, a generator builds a request and a compatible start state that *require* the dependency (information-dependent: a later value only obtainable from earlier visible evidence; recovery: a discoverable native rejection; state-dependent: later operations must respect earlier state), binding every required value to a visible source (request, user turn, tool result). A teacher executes in the native environment. **Only paths whose dependencies actually appear in the executed log count** toward support and guide later rounds ("intended structure decides where to generate; realised structure decides what was obtained").
3. *Grounded supervision mask.* Student context c_t contains only events exposed through the native agent interface (teacher hints and private events excluded). Local eligibility g_t = e_t · v_t: e_t = authenticated non-error execution; v_t = tool available to the agent and identifier-like arguments supported by preceding visible information (discoverable tools must first appear in a visible retrieval). Final mask m_t = R_τ · 1[q_τ ⪯ A_τ] · g_t (terminal success × required operations appear as an ordered subsequence × local eligibility). Rejected calls stay as context without loss; the grounded recovery after them becomes a target.
4. *Structural-support selection.* Per learner scale a target depth d_s of distinct trajectories per path (1, 2, 3, 4, 8 from 1.7B to 30B); select a certified core, one completing exemplar per task, close uncovered atoms/paths, then add trajectories reducing deficits [d_s − n(p)]₊ (exactly maximises capped support under a cardinality budget). They prove uniform selection of B of N misses a once-represented path with probability 1 − B/N.
5. *Parent-normalised SFT.* Each semantic trajectory gets equal weight regardless of how many rendered examples it produces (row averaging lets long dialogues dominate). One epoch, lr 1.1e-5 (1.7B) to 3.7e-6 (14B/30B), batch 8, non-thinking.

**Verification / grading.** Native checkers of τ-bench/BFCL for terminal success; the visibility/provenance check is deterministic over logs. Weak point: ordered-requirements q_τ come from the native task where available; otherwise the checker defines it.

**Scale & cost.** 34,772 certified interactions over 2,515 training-side tasks (35,819 / 3,602 for 30B); selected views 11.6k–19.9k trajectories (13.0M–23.9M target tokens). Cost n/r. Training uses τ1/τ2 train splits (τ1 Airline is transductive: same 50 task identities as evaluation, fresh dialogues).

**Key results.** Three-benchmark mean +16.9 to +29.8 at every Qwen3 scale; τ mean +20 to +41 (τ2 Telecom at 30B-A3B 12.50 → 95.00; Qwen3-4B τ2 69.17 vs public 30B-A3B 28.33). BFCL Overall: 8B 67.30 → 78.62, 30B-A3B 77.58 → 80.93; Multi-turn Base +7 to +41; Live Simple drops 6–13 points at four scales. EnvFactory-8B nearly matches on BFCL (77.55) but trails by 47.5 on τ2: function-calling skill did not transfer to stateful tasks. **Matched ablations (8B, mean):** targeted expansion +3.55; decision grounding vs loose success-derived targets +2.75; structural vs random selection +2.32 (942 more paths covered at the same budget); **parent normalisation vs row averaging +8.04** (τ2 52.50 → 74.17), the largest single effect; single runs, one τ2 Airline task moves the mean by 0.56.

**Failure modes & limits.** Authors: single-run arms; component gains not additive; selection views differ by scale. Mine: in-environment training (τ train splits) inflates τ gains relative to transfer; capability paths are defined over a hand vocabulary; teacher identity and cost unstated; no RL.

**Tips & tricks.**
- Supervise only actions whose arguments are traceable to learner-visible evidence; mask the rest but keep them as context.
- Keep authentic errors in the context and supervise the grounded recovery after them.
- Count support per realised capability path, not per task; synthesise toward paths below target depth.
- Credit a synthesised task only for structures that actually appear in its executed log.
- Weight each semantic trajectory equally in SFT, not each rendered row.
- Scale repeated-support depth with learner size.

**Fit to Crucible Part 2.** Traces-to-tasks (§3.4): the grounding mask is the right rule for turning logged traces into supervision or into oracle programs: an oracle step whose argument is not visible from the start state or earlier observations violates **G8 communicability**; implement v_t as the G8 check over oracle programs (it is the same provenance test, applied to our oracles). F7/§3.5: "canonical capability path" is a compact `BehaviourSignature` projection; use path support counts as a coverage meter beside cell fill, and the realised-not-intended rule for cell membership (already our F7 principle). F11: deficit-driven selection with per-student depth d_s is a concrete quota policy; the 1 − B/N miss probability argues against random subsampling of rare cells. F12: when we use failing student traces to make variants, the rejected-call-as-context rule decides what is shown. Parent normalisation matters for any SFT warm-start we do (it is a training detail, not a factory one). Priority P1 (G8 provenance check P0).

## 2610.33817 — EnvLunch: The Environment as a Free Lunch for Learning to Interact (Liu, Gao, Du, He, 2026; venue n/r, King's College London/Chongqing/Turing)
Read: FULL (the HTML has no appendix; body read in full).  Relevance to Part 2: medium-high. Two ideas transfer directly: (1) "random executable program → its output is the task" gives annotation-free warm-up tasks on any World, and (2) **counterfactual multi-environment verification** (perturbed copies of the World that the agent never sees) is a generic anti-hardcoding check for answer tasks, with a measured collapse without it.

**Problem.** Data-analysis agents need many annotated tasks for RL; an executable environment already defines verifiable outcomes, so can it supply the tasks too?

**Method / algorithm.**
1. *Action pool.* Generic operators per substrate: 15 SQL operators (10 aggregates of rising composition up to a three-table FK chain or a CTE compared to its own average; 5 non-aggregates such as filtered projection, top-k with tie-break); pandas: one source (table or FK merge), 0 / 1–2 / 3–4 / 5–6 transforms by level (filters, top-k, grouped aggregates, ratios, ranks), a join at the top two levels with probability 0.5, one terminal (scalar aggregate, quantile, row count).
2. *Online synthesis.* Draw valid actions uniformly given the current observation, execute after each step, rebuild the valid pool (an action survives only if its operands exist and it still changes the observation); parameters read from the observation (thresholds are real quantiles; categories are real values). Length from difficulty level. Task = (environment E, target observation o* = τ(E)); τ hidden.
3. *Counterfactual filter at construction.* K perturbed copies (SQL K = 2, pandas K = 3): delete 30% of rows of every table with ≥20 rows, cascading along foreign keys; rescale measure columns by random factors; never change ids or keys. Keep τ only if it executes non-degenerately in every copy **and its result changes in at least one copy**.
4. *Reward.* R = (1 + w(1 − t/t_max)) · min_k m(τ̂(E′_k), τ(E′_k)), with m = row-multiset overlap (SQL) or exact match after canonicalisation (pandas), w = 0.5 brevity bonus on turns t (t_max 16 SQL / 48 pandas). The agent sees E and o*, not the copies.
5. *Training.* GRPO (8 rollouts, lr 1e-6, KL 0.01, entropy 0.001, clip 0.2/0.28, truncated IS [0.5, 1.5]) for 100 steps × 16 tasks; 1,600 warm-up tasks built in **20 min on CPU** (vs >4 h for model-based task synthesis); warm-up 3–4 h; then normal downstream GRPO on 8–2,048 labelled examples. Environments: 112 Spider/BIRD/Archer training databases and 398 tables (DataMind, BIRD, DABench), all disjoint from evaluation sets by name.

**Verification / grading.** Execution agreement across hidden perturbed copies. **Without the copies the agent hard-codes constants and stops querying: held-out warm-up accuracy 16.8 vs 28.1 untrained vs 46.1 with copies.**

**Scale & cost.** 1,600 tasks; trivially cheap; downstream budgets up to 2,048 examples; 3 seeds per curve.

**Key results.** Six data-analysis benchmarks, curve-level gain +9.3 (9B) / +9.6 (4B) (e.g., TAT-QA +12.8, MultiHiertt +11.4/+14.3); baseline needs 8–32× (median 16×) more labels to match EnvLunch at its smallest budget (DSEval: never). One fixed labelled example trained 32 steps: EnvLunch still +5.5 to +12.6. Beyond data analysis: BIRD +4.8/+6.8, HotpotQA +15.3/+14.0, ALFWorld +3.7/+2.1, AppWorld +5.7/+0.4, SpreadsheetBench +2.0/−0.2. **Controls:** continued pre-training on environment text −2.4/−3.5; rejection-sampling SFT on EnvLunch successes −4.7/−5.7; RL on model-written tasks over the same databases (Self-Challenging style +1.6 at 9B, explore-first −0.3, self-play majority-vote −4.0) all below EnvLunch, attributed to unchecked self-labels. In a 64-world controlled table, EnvLunch reduced uncertainty about hidden encodings most (log₂ of consistent worlds), not explained by more actions.

**Failure modes & limits.** Authors: relational/dataframe only; 4B/9B only; open-ended tasks untested. Mine: tasks have no intent; the gain is a warm-up for interaction habits (inspect, narrow, recover), not for any domain skill, so it belongs before training, not in the pool; brevity bonus may discourage verification in other settings.

**Tips & tricks.**
- Build answer tasks by executing a random valid program on the World and asking for something that reproduces its output.
- Read program parameters from the current observation so every step is meaningful.
- Verify answers against hidden perturbed copies of the World (row deletion with FK cascade, measure rescaling, keys untouched); take the minimum agreement.
- At construction, keep only programs whose output changes under at least one perturbation.
- Measure information gathering with possible-world counting in a controlled environment.

**Fit to Crucible Part 2.** F5/G9/G12: counterfactual World copies are a generic **anti-hardcoding check for read-only answer tasks**: re-run the oracle and the candidate answer program on K perturbed seeds of the same World (our F2 seeds make this cheap) and require agreement; an answer that is a constant fails. Add this as a G12 pre-probe and as a negative class ("constant answer"). G2 already needs two seeds; reuse them. F2: the perturbation operators (FK-cascading deletion, measure rescaling, key preservation) are a ready seed-variation recipe for `world_synth` domains. Sources (§3.4): EnvLunch tasks are a cheap, intent-free warm-up source; keep them out of the pool and the benchmark (no skill leaf), but consider them for a student cold start. The controls also support our rule that model-written self-labels are not ground truth. Priority P1 (counterfactual check P0 for answer tasks).

## 2610.33149 — WebUniverse: Scaling Verified Training Data for Agentic Web Development (Ding, Jiang, Feng et al., 2026; venue n/r, Univ. of Washington and others)
Read: FULL (body; appendices A–D incl. scaffolds, model roles, loop-interruption continuation, decontamination, packaging, verifier audit, training/eval; C example and F traces skimmed).  Relevance to Part 2: medium. SFT trajectory corpus for front-end development on our student (Qwen3.5-35B-A3B), with two transferable mechanisms: **blind test generation plus review of failed tests only** (to catch tests with unstated assumptions) and a **per-verifier human audit with precision/recall** (the measurement our F6 gates lack).

**Problem.** Front-end development trajectories (edit → run → inspect in browser → revise) and reusable environments are scarce; screenshot-code pairs do not demonstrate the loop.

**Method / algorithm.**
1. *Text seeds.* High-star licensed GitHub front-end repos (created 2022+); GPT-5.5 summarises functionality, user actions and interface changes into a seed. GPT-5.4/5.5/5.6 Sol write tasks that **change the scenario but keep the interaction mechanism**, at two specification levels (high-level goals vs detailed stack, identifiers, appearance) and two settings (standalone vs iterative sequences of requests on the same codebase). Front-end only, no external APIs.
2. *Visual references.* FineWeb URLs filtered by CrUX, metadata, accessibility, robots.txt; deduplicated registered domains, disjoint across variants; full-page captures (deferred loading triggered, animations frozen, overlays removed; ≤8,000 px; 3 viewports for multi-viewport); human review; navigation records for multi-page tasks (3–7 pages within two links of home). Vision tasks are assembled by fixed templates, no model.
3. *Workspaces.* Harbor containers with a browser; 15 project scaffolds (React/Vue/Svelte/Angular/plain, several state and styling libraries, bundlers) for detailed tasks; empty workspace for high-level tasks; OpenCode harness.
4. *Trajectories.* Independent sampling from a model pool (GPT-5.6 Sol 75.3% of kept, Qwen3.8-27B 8.4%, GPT-5.5 6.9%, MiniMax-M3 4.3%, GPT-5.4 4.2%, base Qwen3.5-35B 1.0%); passing iterative tasks seed the next task's workspace. **Trajectory refinement**: interrupt attempts when a loop detector finds persistent repeated tool calls, trim the repeated run, and let another model continue from the preserved workspace; only the resumed part is supervised.
5. *Verification, chosen per task type.* (a) Browser scripts for detailed tasks: an LLM extracts criteria and writes Playwright tests **from the task statement before any solution exists**; because tests may impose unstated assumptions, an LLM reviews **only failed tests** for such assumptions, regenerates faulty ones and reruns on the unchanged app. (b) A GUI agent (GPT-5.6 Sol) explores the running app without reading source and records pass/fail/blocked per test (high-level tasks). (c) A VLM visual judge with a six-level rubric per page × viewport; unreachable pages score 0.
6. *Selection.* All tests pass (and review resolved); visual ≥ 0.75 on every page–viewport; complete records; iterative sequences keep the passing prefix of ≥3 tasks from the first.
7. *Decontamination.* Text: 5-gram Jaccard > 0.6 or MiniLM cosine > 0.55 against 1,029 benchmark statements, all hits manually reviewed (514 semantic-similarity hits retained as confirmed false positives, flagged and grouped separately); vision: registered-domain matching against benchmark sites.
8. *Training.* SFT of Qwen3.5-35B-A3B (vision tower frozen), 2 epochs.

**Verification / grading.** Mixed executable tests, agentic GUI testing, and VLM judging. **Audit (one author, 100 accepted + 100 rejected per verifier):** browser scripts precision 98.0 / recall 91.6; GUI agent 97.0 / 94.2; visual judge 87.0 / 83.7. Packages replay saved reference solutions against the fixed verifiers in reconstructed environments (all pass).

**Scale & cost.** 15K environments + 15K trajectories (10,500 text, 4,500 vision) from 1,559 repos and 3,500 sites; 511.9M tokens, 551,818 tool calls; medians 20.6K tokens/20 calls (text) vs 59.4K/70 (vision). $ n/r.

**Key results.** Qwen3.5-35B-A3B: Vision2Web avg 51.7 → 68.3; WebGen-Bench 34.5 → 63.9 (Step-3.7-Flash 62.3, GPT-5.6 Sol 64.5); Web-Bench pass@2 12.2 → 23.1. Matched 15K StepFun-Mix SFT: 52.4 / 31.5 / 17.7, i.e. **below the base on WebGen functional checks**. Ablation: text-only subset helps function and iteration; **vision-only subset drives functional accuracy far below the base (WebGen 12.1)**; the mixture is best on every metric. 5K → 10K → 15K nested: monotone gains. Traces show more post-edit checks and error–edit–recheck cycles; repetition without change persists.

**Failure modes & limits.** Authors: web front-end only; screenshots miss temporal behaviour. Mine: teacher concentration (75% one model) limits behavioural diversity; GUI-agent and VLM verifiers are model judges with 3–13% false accepts; single eval run per model; 514 semantically similar tasks retained.

**Tips & tricks.**
- Write tests from the statement before any solution; when a test fails, have a reviewer check only failed tests for assumptions the statement does not make, then regenerate and rerun on the same app.
- Audit each verifier on balanced accepted/rejected samples and report precision and recall.
- Interrupt looping attempts, trim the loop, continue with another model, and supervise only the continuation.
- Keep tasks' interaction mechanism fixed while changing the scenario to widen surface diversity cheaply.
- Keep the passing prefix of iterative sequences so early tasks are not over-represented.
- Single-skill data can hurt other skills (vision-only SFT damaged function); mix families.

**Fit to Crucible Part 2.** F5/F6: "blind tests + review of failing tests for unstated assumptions" is a concrete G8 repair path for test-based tasks (complements SETA's post-rollout judge and RST's discoverability rule). §3.8 frozen anchor set: WebUniverse's balanced 100/100 audit per verifier is exactly the evidence format we want for each gate and judge (precision on accepts, recall on rejects); adopt it as the acceptance report for any new gate or judge. F12: the loop detector + trimmed continuation is a trace tool for salvaging partial expert runs into supervision (SFT only). Diversity: the vision-only harm is a reminder that family mix matters for the student (§3.10 mix rule). Priority P1.

## 2610.27781 — GRADUS: Discovering and Recovering Agent Lessons from the Environment's Latent Syllabus (Ping, Yang et al., 2026; venue n/r, AWS AI/USC/BMW)
Read: FULL (body; appendices A.1–A.6, A.8–A.10; A.7 worked example skimmed).  Relevance to Part 2: **high**. Guarded operators (action × guard → outcome), a global (policy, outcome) **coverage ledger** that steers proposals, separate structural vs interaction kernels, and **joint task–solution refinement where execution arbitrates and the LLM only diagnoses** map cleanly onto our F0 skill tree, F3 grounding, F4/F5 repair rounds and the "hardness never filtered out by verification" problem. It also builds frontier exams with a human audit.

**Problem.** In a fixed policy-constrained environment (airline, retail, telecom, in-car assistant), pipelines that keep only tasks the proposer solves at once bias data toward easy behaviours; verification acts as a hidden curriculum selector and drops the hardest compositions.

**Method / algorithm.**
1. *Guarded operators.* An LLM compiles policies, tool code and state schemas into a library: per atomic action, purpose, parameters, relevant state fields and branches g(a) = {r_i ⇒ q_i} where guards combine conditions (and/or/not) and outcomes are state updates, follow-ups, refusals or failures (e.g., cancel-eligible → refund; ineligible → refuse).
2. *Coverage-guided evolution* (code schedules, LLM realises):
   - Atomic blueprints: k per operator from the full catalogue; a shared ledger of covered (policy, outcome) pairs is in the prompt to prioritise gaps.
   - Structural evolution: per parent, up to K children, each with a sampled kernel: **causal** (link actions through a state change), **parallel** (independent request), **repetition** (apply over a user-described set); the LLM may decline incoherent extensions; builds a lineage tree (depth = evolution depth 1–5).
   - Interaction variation: rewrite with kernels for indirect reference, ambiguity, user pressure, extra reasoning, keeping actions and outcomes fixed.
   Blueprints specify user goal, context, known and unknown information, intended operator outcomes, with entities unbound.
3. *Joint validity loop.* (a) Initialisation: an agent with tools, policies, schemas and a state-probing tool grounds a blueprint into a concrete task and a reference action sequence; code replays the reference immediately. (b) Simulation: a user simulator with the task talks to a solving agent that never sees the task spec or reference; K parallel branches × ≤m attempts; a trajectory evaluator scores action correctness, policy compliance and communication and gives retry feedback (it sees task, reference, policies, execution evidence). (c) Verification: replay reference and demonstration from the same initial state; **accept only if outcomes agree and programmatic policy checks pass**; otherwise a diagnostic LLM attributes the failure: demonstration error → more solution search; task/reference error (incoherent, unsolvable, hallucinated state, wrong reference) → back to initialisation with feedback. The LLM never certifies correctness. Accepted outputs from every round accumulate.
4. *Training split by depth.* Depths 1–3 mostly SFT (3 epochs, lr 1e-5, 32k), depths 4–5 mostly RL (GRPO + DAPO clip 0.2/0.25, KL 0.01, G = 16, lr 1e-6), reward = the same executable acceptance check.
5. *Frontier exams.* With Opus 4.5 as scout, evolve base tasks to depth 5 and keep verified tasks whose gold outcome is matched in ≤5/8 scout rollouts; two annotators audit.

**Verification / grading.** Reference–demonstration outcome agreement under replay + programmatic policy checks; LLM evaluators only guide search and attribute failures. Remaining risk: the reference itself is model-written; agreement of a flawed reference and a demonstration that copies its flaw would pass if policy checks miss it.

**Scale & cost.** Per domain with Opus 4.5: airline 698 SFT tasks (8,468 rows) + 341 RL tasks; retail 585 + 381; telecom 414 + 367; CAR 1,901 + 1,227 (Qwen3-235B proposer: fewer). Accepted by depth (Opus, airline): 156/352/267/156/108. Cost n/r.

**Key results.** Qwen3-30B-A3B (Opus proposer): τ² airline/retail/telecom 0.75/0.86/0.90 after SFT, **0.80/0.89/0.97 after RL** (base 0.63/0.77/0.38); CAR-Bench avg 0.47 → 0.83 (above every frontier model listed). Qwen3-235B proposer: 30B to 0.76 τ² avg, 0.62 CAR. **Matched proposer/student/budget (Opus, 8B):** model-prior synthesis 0.45, graph-based 0.51, trajectory-first 0.59, GRADUS 0.76 avg. Ablations (235B proposer, 30B student, telecom/CAR-disambiguation): full 0.75/0.60; −guarded operators 0.64/0.45; **−global ledger 0.54**/0.52; −structural evolution 0.63/0.55; −interaction variation 0.67/0.46. Validity loop cumulative: none 0.65/0.40 → +parallel 0.68/0.43 → +reflection 0.71/0.55 → +task recovery 0.75/0.60. Coverage: 1.4–2.9× more (policy, outcome) pairs and up to ~5× more state-changing action combinations than baselines, which plateau. Student zero-shot success falls 0.87 → 0.17 with depth; **recovered tasks are disproportionately hard** (medium-hard + hard: 41% of first-round accepts vs 75% and 83% of round-2 and round-3 recoveries). Frontier exams: annotators judged 87.5%/100%/90.5% correct (AC1 0.79–1.00); Opus 4.5 falls 88 → 52% (airline), held-out models fall 18–44 points.

**Failure modes & limits.** Authors: bounded environments with explicit policies and executable outcomes. Mine: training and evaluation are in the same environments (benchmark tasks held out, but tools, policies and DBs are shared), so this is environment-targeted depth, not transfer; the evaluator LLM that grades communication quality is part of the search, a possible bias; Opus 4.5 is both proposer and the strongest reference model.

**Tips & tricks.**
- Compile each tool + policy into guarded operators (guard → outcome) and use them as the unit of task design.
- Keep a corpus-level ledger of covered (rule, outcome) pairs and put it in the proposer prompt; it was the largest single ablation effect.
- Separate structural kernels (what is required: causal, parallel, repetition) from interaction kernels (how it is surfaced: ambiguity, indirection, pressure).
- Let the code schedule kernels and the LLM decline incoherent ones, instead of enumerating the Cartesian product.
- On verification failure, attribute the side (task/reference vs demonstration) and repair that side; do not discard.
- Accept only on executed outcome agreement plus programmatic policy checks; the LLM diagnoses, never certifies.
- Route shallow tasks to SFT and deep tasks to RL.
- Build frontier exams by keeping verified tasks a strong scout solves at most 5/8 times, then human-audit.

**Fit to Crucible Part 2.** F0: a `GuardedOperator` list per App (tool, guard, outcome) belongs in the DomainSpec's skill tree; each (policy, outcome) pair is a skill leaf, giving a precise, enumerable coverage axis. F3: put the ledger in the proposer prompt alongside the K nearest tasks (§3.5 point 3), and adopt structural vs interaction kernels as two separate knob families (structural changes the behaviour signature, interaction must not; F7 can check both). F4–F6: GRADUS's loop is the repair-round design we want: replay-based acceptance + side attribution; the LLM's role is limited to diagnosis, consistent with rule 2. F9/§3.6: "recovery keeps hard tasks" addresses the funnel bias where hard candidates die at construction; track the difficulty mix of first-pass vs recovered accepts as a meter. Benchmark split (§3.10): the scout ≤5/8 + two-annotator audit is a ready recipe for refreshing a held-out benchmark. Priority **P0** (ledger + guarded operators + side-attributed repair), P1 (frontier-exam builder).

## 2610.23194 — OfficeTown: Generative Organizations for Evolving Agent Intelligence (Wei, Ying et al., 2026; venue n/r, Microsoft Research Asia + universities)
Read: PARTIAL (body in full; appendices A.6–A.7 simulation time/recovery and accumulation, B.1, C.1 judge note read; A.1–A.5, B.2–B.4, D, E skimmed by section only).  Relevance to Part 2: **high for the World (§2(b)) and traces-to-tasks (§3.4)**: a simulated organisation of role-playing professionals with persistent, permissioned state and a simulated clock that *produces* assignments over time; tasks are task-time snapshots of that state. This is the closest published analogue to our "World with people and time" and to "trace → World snapshot → task".

**Problem.** Benchmarks and environment synthesis treat professional tasks as isolated instances; real work arises from ongoing activity, with reviews, revisions, follow-ups and accumulated materials.

**Method / algorithm.**
1. *Organisation from a description.* Objectives, roles (profiles from O*NET/ESCO), reporting lines, role-specific authority (what each may execute, delegate, approve, share) and a **seed** of documents and data mixing retrieved public sources and synthetic organisation records (origins tracked). Example: a 12-role financial-modelling firm.

Not globally observable: role, ownership, sharing rules and confidentiality decide each member's view; reporting lines do not grant file access. A six-month run grew 27 seed files to 497 materials.
4. *Tasks from ongoing work.* A task = a work request + the **task-time snapshot** available to its responsible professional at assignment time (personal files, authorised shared resources, artifacts needing revision), excluding later solutions and evaluator-only information. Each attempt starts a fresh workspace from these inputs; no history replay needed.
5. *Benchmark construction.* Requests edited into self-contained tasks; rubrics drafted by an LLM from requirements and source materials (human examples guide form, not facts); a separate model review checks correctness, coverage, overlap and unsupported restrictions; **71 domain experts** review tasks and rubrics (realism, clarity, input sufficiency, feasibility; criterion importance P0–P3). Judge: GPT-5.5 (high); the authors state judge–human agreement is not established.

**Scale & cost.** Bench: 406 tasks from 23 organisations, 8 domains, 139 job titles, 247 file-based + 159 service-state tasks, 44.5 input files per task (18,082 total), 4,836 criteria. Training: 2,202 SFT trajectories distilled from DeepSeek-V4-Flash (kept without success filtering) and 828 task–environment pairs for on-policy distillation. Simulation and judge costs n/r.

Astra still misses ≥1 critical (P0) criterion on 20.8% of tasks (Terra 53.3%, V4-Flash 78.3%); weighted score and pass rate rank models differently (Opus passes more than Terra with a lower weighted score). Execution framework changed V4-Flash weighted score 61.9 (own executor) vs 48.6 (Pi) vs 40.7 (OpenCode). Qwen3.5-9B: GDPval rubric 65.75 → 70.30 (SFT) → 73.65 (SFT + OPD); APEX-Agents 9.40 → 19.43; Terminal-Bench 2.1 42.31 → 63.64; OfficeTown Bench Pass@1 1.48 → 4.68. The principal–assistant harness beat Codex, MetaGPT and CAMEL on five external columns with GPT-5.5.

**Failure modes & limits.** Authors: judge agreement with humans not established; harness comparisons not token-matched. Mine: rubric grading with an LLM judge and no anchor set; training gains come from distillation (SFT + OPD), not from verified RL; the simulated professionals' review decisions are model judgements and could encode errors that become "accepted" inputs to later tasks; no measurement of simulation fidelity.

**Tips & tricks.**
- Generate tasks from an ongoing simulation of people and time, then snapshot the state each task's owner could see at assignment time.
- Enforce permissioned views (role, ownership, sharing, confidentiality) and keep save/accept/share separate.
- Tie message acknowledgements to processed rows and journal workspace updates for crash recovery.

## 2610.19686 — Interlock: From Local Correctness to Task Completion in Long-Horizon Agents (Hao, He, Wang et al., 2026; venue n/r, PKU/HKUST-GZ/Tsinghua/Meituan)
Read: FULL (body; appendices A scoring, B diagnostic protocol, C statistics, D corpus, G algorithm/setup read; F cases and H prompts skimmed).  Relevance to Part 2: **high for F5 (collateral and "realisation" checks) and F6 review gates**. It formalises a failure our state checks can miss: a correct decision whose downstream effects are only partly propagated ("locally correct, incomplete"). The typed completion graph and the dual review (source coverage vs public support) are directly reusable.

**Problem.** Long-horizon agents satisfy individual requirements but fail to maintain relationships: decisions not grounded in the right evidence, joint constraints violated, required downstream updates left undone.

**Method / algorithm.**
1. *Typed completion graph* G_b = (evidence/rule roles E, decisions/shared states D, required effects Y; grounding edges E→D, **coupling hyperedges** (set of decisions/effects, shared public condition ψ), **realisation edges** D→Y). Each effect y = (B_y public basis, Ω_y object population, α_y applicability condition, φ_y outcome condition): "for every object in Ω where α holds, φ must hold".
2. *Reusable specs.* Domain → task family (objective + obligation set O_n) × archetype (recurring relationship pattern ρ_a, e.g., several outputs share one decision; several allocations share a capacity) × scenario parameters ξ → G_b. 8 archetypes, 128 domains, 484 families in the retained corpus.
3. *Three generation roles from the same graph,* each also emitting a **carrier map** (where each graph requirement appears): environment builder (workspace W0 + evidence index), task setter (request q + private deliverable contract H; every obligation in H must be supported by q or the public workspace), rubric compiler (criteria for decisions, joint conditions, effects). Construction constraints: grounding sources present and decision left unresolved; coupling condition really constrains the joint choice; every realisation target has an observable effect and a check. Source conflicts, partial records and stale outputs instantiate the work.
4. *Dual review.* **Source coverage**: trace every typed relation from the original obligation spec through the graph into each stage via carrier maps; pass only if P(c) = 1 (all required carriers present with public basis, applicability, scope, outcome condition). **Public support**: a critic that sees only (q, W0, V) checks that criteria follow from public inputs, are jointly consistent and judgeable from the specified evidence. Findings with evidence references go back to the producing role; revisions bounded and versioned.
5. *Execution-based admission.* A validation policy runs from a fresh W0; an agent-as-judge inspects initial and final workspaces and their diff and returns per-criterion judgements plus a package-quality assessment. **Admission does not require the validation solver to succeed** (keeps valid hard tasks); it requires both reviews, normal termination, complete judgements and a sound package.
6. *Scoring.* Agent-as-judge with terminal access, writing and running verification scripts. Acceptance A_V = all required criteria pass. Diagnostic score: criterion credit propagated through declared dependencies (m̃_i = m_i · Π m̃_j), change criteria already satisfied at start are excluded, essential criteria zero their group, critical groups ≤ half the weight. Follow-through rate FTR = Σ u_i e_i / Σ u_i (correct upstream decision AND all downstream effects).
7. *Training.* Per-backbone rejection-sampling SFT: Qwen3.6-27B and Qwen3.6-35B-A3B each make 5 attempts per task; keep own accepted rollouts (8,957 each, about 154M tokens).

**Verification / grading.** Agent-as-judge (backbone n/r for training; GPT-5.5 judges external benchmarks) with script execution; criteria are 44% content inspection, 41% recomputation, 11% initial–final comparison, 4% text matching. No negatives or exploit probes; judge correctness unaudited.

**Scale & cost.** 3,278 retained tasks (each with ≥1 accepted rollout from both backbones); 32,780 attempts, 32,370 normal; median 17 source files and 30 criteria per task; trajectories average 84,293 tokens, 27.6 turns, 42.1 tool calls (ClawGym: 14,940 / 11.9 / 14.8). Cost n/r.

**Key results.** Qwen3.6-35B-A3B: AutomationBench 9.00 → 13.50, JobBench Main 11.81 → 15.01, Easy 51.86 → 56.17, Harvey LAB 54.18 → 58.34; ClawGym-SFT made it worse (5.17 / 6.25 / 40.66 / 54.97). Qwen3.6-27B: 14.33 → 18.33, etc. Domains 16 → 32 → 64 → 128 at a fixed 8,957 trajectories: monotone gains on all four metrics. **Agent-as-judge vs text-only LLM-as-judge filter** (same judge backbone, rubrics, rollout pool): AutomationBench 18.33 vs 13.17 (text filter below the base 14.33), JobBench Main 18.46 vs 15.14, at 11% more judge tokens.

**Failure modes & limits.** Authors: few explicit. Mine: tasks are retained only if both students already solve them at least once, which biases the corpus to within-reach tasks (a self-selected easy end for a pool meant to teach); RFT, no RL; judge-based acceptance without an anchor set; the 35B base is weak on these benchmarks (9% AutomationBench), so absolute levels are low.

**Tips & tricks.**
- Model each obligation as (public basis, object population, applicability, outcome) and check it over every applicable object.
- Declare coupling constraints as hyperedges over decisions and effects, and check them jointly.
- Require every realisation target (each downstream record that must reflect a decision) to have its own check.
- Emit carrier maps from each generator so a reviewer can trace each requirement into instruction, workspace and rubric.
- Run two complementary reviews: original spec → artifacts (nothing lost) and public inputs → rubric (nothing unsupported).
- Admit tasks without requiring a validation solve; select trajectories separately.
- Verify outcomes with an agent that can run scripts, not a text-only judge.
- Measure follow-through: correct decision AND every applicable downstream effect.

**Fit to Crucible Part 2.** F5: add **realisation checks** to the five check kinds: for each oracle decision, the verifier must enumerate the downstream rows/artifacts that must reflect it (Ω, α, φ) and check all of them; this extends "collateral" (nothing else changed) with its dual (everything that should change did). The "drop a realisation" mutation becomes a negative class (partial propagation), which our drop-step operator does not quite cover. F6: the dual review maps to G8 (public support) plus a new **coverage-trace gate** over carrier maps (nothing from the `TaskProposal` lost in instruction/World/verifier); cheap and deterministic once carriers are recorded. F12: FTR is a precise failure metric for traces ("decided right, did not follow through"). Archetypes (shared decision, shared capacity) are good structural knobs for §3.6. Avoid the "both students must solve it" retention rule for the training pool; use our band. Priority P0 (realisation checks + partial-propagation negatives), P1 (carrier-map trace gate).

## 2610.17953 — Agent-Reflex: Teaching Language Agents to Act Reflectively (Dong et al., 2026; venue n/r, Renmin University + NUS)
Read: FULL (body; appendices B–E incl. failure taxonomy, model pool, training stages, contamination controls, noise attribution; E.3 skills skimmed).  Relevance to Part 2: medium-high for **World realism (noise injection) and traces-to-tasks (failure-mined variants)**. It gives an empirical tool-failure taxonomy from 24,510 real error returns, a restore-at-first-error data recipe, and a structured "reflection skill" record mined from success/failure pairs across model families.

**Problem.** Training environments return clean tool results and template users, while deployed MCP services time out, fail and are corrected by users mid-task; even frontier models drop sharply under tool and user noise.

**Method / algorithm.**
1. *Environments.* 557 high-usage MCP server specs from the Smithery registry as topics; following Agent-World, a research agent (search, browser, code, OS) builds and enriches a topic database (3 complexification rounds); a coding agent writes tools + unit tests; keep tools that compile, pass tests, respect state-transition constraints and admit an executable verifier; 60 verifier-backed tasks per topic.
2. *Failure mining and injection.* Replay agents on nine public agentic benchmarks (MCP-Atlas, τ³-Bench, AutomationBench, OfficeQA Pro, JobBench, Harvey LAB, GDPval, …), log 177,700 tool returns; 24,510 errors grouped into **eight families**: server/gateway unavailable 33.6%, auth/permission 17.9%, timeout 14.7%, resource missing 10.5%, argument/validation 10.2%, generic exception 8.3%, rate limit 4.5%, network 0.3%, each with its admissible recovery (bounded backoff; refresh/escalate, unchanged retry insufficient; check whether state changed before retrying; verify id or search; repair schema; inspect; back off; transient). Inject per return with p = 0.2, families sampled **uniformly** (not by frequency) so rare ones get enough instances; keep perturbed tasks only if recovery is verifiably possible.
3. *Skill mining.* Nine-model pool across five families (Qwen3 4B–235B, Llama 3.1 8B, Gemma 4 31B, GPT-OSS 120B, DeepSeek-V4-Flash) runs every task under identical budgets; DeepSeek-V4-Flash as analyzer + the environment verifier label each rollout (disagreements discarded) and, for failures, give the error rationale, the **first erroneous turn t\*** and its state snapshot. Pair success/failure on the same task (cap per task, ≥5 tasks per environment); the analyzer turns pairs into environment-indexed **skill records**: trigger over visible history with supporting/contradicting evidence, diagnosis naming the failure family, recovery template (retry, switch endpoint, ask user, abort), reversibility and partial-effect flags, provenance and replay validation. 1,170 skills over 557 environments.
4. *ReSFT (student = Qwen3-8B, all training trajectories from the student itself):* Self-Reflection: restore the World to s_{t\*}, append the skill, continue; keep if the verifier accepts; store without the skill. Skill Recovery: reset to s₀, restart with the skill; keep if verified; store without it. User-centric Reflection: a user simulator (GPT-4.1) turns the skill into a natural correction inserted after the error turn; keep the correction (deployment-visible), drop the skill. 54K trajectories.
5. *ORPO.* On 2.5K EnvScaler RL tasks (environments overlap with the 557 topics; skills looked up by environment id): groups of G = 8 with ν = 0.25 rolled out under noise, advantages normalised over the mixed group; plus on-policy distillation where the same policy, prompted with the environment's skill card, re-scores the sampled tokens; confidence weight γ = sigmoid(β·Δ) on the skill-induced log-prob shift; L = L_RL + λ·L_OPD.

**Verification / grading.** Environment verifiers (state-based); AgentNoiseBench's Stability-Gated Success credits a rollout only if the trajectory was never derailed by the injected artifact. Contamination controls: splits at environment-family level, near-duplicate checks against benchmark instructions and tool schemas, benchmark answers never in analyzer/teacher/simulator prompts.

**Scale & cost.** 557 environments × 60 tasks; 54K ReSFT trajectories; 1,170 skills; 2.5K RL tasks, 100 RL steps for algorithm comparison. Cost n/r.

**Key results.** Qwen3-8B overall on five tool-use benchmarks 40.2 → 58.6 (EnvScaler-8B 50.9, Agent-World-8B 53.6); τ² avg 26.2 → 62.1 (Agent-World 54.6); ACEBench 54.0 → 78.0. AgentNoiseBench overall 12.3 → 29.1 (EnvScaler 18.2, NoisyAgent 25.9); τ² tool noise 14.1 → 38.4. Frontier models also degrade under noise (GPT-5.2 τ² clean 81.0 → tool noise 61.0). Ablations (ANB-τ² / Vita): full 45.9/12.3; −SR 41.3/8.9; −KR 42.4/10.2; −UR 43.0/10.9; −OPD 43.7/9.5; −confidence weight 44.5/10.4. ORPO beat GRPO, DAPO, REINFORCE++ and SEED at 100 matched steps.

**Failure modes & limits.** Authors (Appendix F, partly read): few. Mine: skills are written by one analyzer model (DeepSeek), so the skill library carries its biases; failure injection replaces true returns, so environment state and observation can diverge in ways real services do not (a "timeout" after a successful write is the real hard case, and only some families model state change); the analyzer is also a correctness labeller.

**Tips & tricks.**
- Inject tool failures drawn from an empirical taxonomy, sampling families uniformly so rare ones are learnable.
- Keep a noisy task only if recovery is still verifiably possible.
- Find the first erroneous turn and snapshot the World there; restore and continue from that state to make recovery data.
- Mine success/failure pairs on the same task across model families; distil environment-level recovery rules with triggers, diagnosis and reversibility flags.
- Keep deployment-visible corrections (user messages) in stored data; strip privileged hints.
- Mix a minority of noisy rollouts (25%) into each RL group rather than training noisy-only.

**Fit to Crucible Part 2.** World loop / F1: add a **fault-injection profile** to each App (the eight families, p_inj, uniform family sampling, recovery admissibility per family) as a DomainSpec knob (`observability`/`noise`), with G3 run under the profile to confirm the task stays solvable; timeout-after-write cases need a state-consistent implementation, not observation replacement. Traces-to-tasks / F12: first-erroneous-turn + state snapshot is exactly our "first wrong step" (§2(d)) joined to World snapshots: make it the standard way to turn failed student traces into **late-start variants** (start at s_{t\*}) for the ladder (§3.6, R³-style), and the skill-record schema a template for failure-cluster summaries. User-correction turns are a cheap way to cover the "multi-turn with simulated user" task type. Priority P1 (fault profiles and first-error late starts), P2 (ORPO).

## 2610.16397 — Recursive Environment Scaling for General Long-Horizon Agents (RES) (Jing, Jiao et al., 2026; venue n/r, UESTC/HKUST/CUHK-SZ/THU/Westlake/NUS)
Read: FULL (body; appendices A protocol/validation/review/cost, B training data, C aggregation, D ablation details incl. the 17-operator library).  Relevance to Part 2: **high, with an intent warning**. It hardens *existing* tasks by transforming the environment (information access, resource relations, execution dependencies) while keeping objective, facts and grader fixed, with replay-based validation and recursive inheritance. It is a direct generator for our §3.6 `obfuscation`, `observability` and `linkage` knobs, and the clearest example of hardness that may be "access busywork" rather than skill.

**Problem.** Benchmarks saturate; can the environment itself be scaled to raise difficulty while the task's core objective and completion requirements stay fixed, enabling paired evaluation and harder training data?

**Method / algorithm.**
1. Task (C_k, E_k): C = objective, constraints, completion conditions (fixed, only access instructions update); E = resources, states, operations, dependencies.
2. *Proposer* (GPT-5.6 Sol, high effort) inspects the validated parent and composes a transformation plan Π_k from a fixed library of **17 operators**: basic six (sharding, pagination, summary-to-detail access, field references, numeric re-encoding, export preparation) + evidence dispersion, namespace bridges, source routing, candidate intersection, dependent lookups, multi-source exports, external-schema views, archive views, version selection, index reconstruction, staged release. Three classes: resource (information access), relational (relations among sources), operational (when actions become available). **Dependency composition**: one transformation consumes information/state produced by another (e.g., a linked view requires a link query and export prep; a later round adds index recovery first).
3. *Validation* (independent of the proposer): check lineage and protected-contract hashes; **replay the declared transformations from the frozen parent and require the rebuilt definition to match the candidate**; in a fresh session follow only public interfaces to resolve references, run preparation steps and reconstruct transformed resources; compare recovered content with source facts; reject content loss or duplication, invalid references, non-terminating preparation, and **original-file bypasses**. Diagnostics drive repair (≤8 outer proposer executions per parent).
4. *Recursion.* Accepted child becomes the parent; ≤10 accepted transformations; target DeepSeek-V4.1-Flash makes 3 attempts (60 turns) at evaluated nodes; three assessed failures stop the lineage. Evaluation then freezes environments and runs one 50-turn attempt per model.
5. *Training comparison.* Apply RES to 8,428 ClawGym training tasks; DeepSeek-V4.1-Flash collects trajectories in scaled environments; SFT Qwen3.5 Base models on these vs on the original ClawGym trajectories (same count, same settings), evaluate on the **original** benchmark tasks.

**Verification / grading.** The benchmark's own graders, unchanged; construction validity by deterministic replay + public-path reconstruction; manual review of 60 lineages (120 endpoint environments) by three researchers for objectives, information, scoring, answer leakage and bypasses: no issues found.

**Scale & cost.** 294 seed tasks (Claw-Eval-Live 105, Workspace-Bench-Lite 100, Terminal-Bench 2.1 89). Claw: 289 accepted children from 105 seeds; 1.45 proposer executions, 89.2K tokens, 112.6 s per child; 92% need ≤2 executions; 25.78M tokens total.

**Key results.** All 18 model × benchmark pairs drop: Claw-Eval-Live Pass@1 DeepSeek-V4.1-Flash 82.86 → 5.71, Opus 5 86.67 → 28.57, GPT-5.6 Sol 85.71 → 26.67; Terminal-Bench 2.1 drops 41.6–47.2 points; Workspace-Bench-Lite 12–19 points. Interaction demand over depth: mean turns 3.55 → 43.22, tool calls 8.05 → 206.02, turn-limit rate 75%. Depth caps: 82.9 → 60.0 (d1) → 17.1 (d2) → 7.6 (d3) → 4.8% (d10). **Ablations (15 tasks):** removing composed dependencies from saved environments → 100% pass (from 0%); **no inheritance (independent single enhancements) → 93.3% vs 6.7%**; basic 6-operator library → 80.0%. **SFT on RES trajectories beats original-trajectory SFT in all 9 comparisons**: Qwen3.5-35B-A3B Claw 64.76 → 77.14, Workspace TCR@80 14 → 28, Terminal-Bench 2.1 23.60 → 38.20.

**Failure modes & limits.** Authors: none beyond scope. Mine: most added difficulty is **access and preparation work** (pagination, archives, index rebuilding, encodings) before the original task; the failure case shows the agent running out of turns while still acquiring evidence, i.e. the budget, not the core skill, binds. That the SFT data still helped on original tasks suggests it teaches persistence and tool discipline, but the intent of each scaled task (does success need the original skill or just more turns?) is unmeasured. One proposer family (GPT) and one target family (DeepSeek).

**Tips & tricks.**
- Harden a task by transforming the World's access paths and dependencies while freezing objective, facts and grader; then compare original vs scaled pairs.
- Validate a transformed World by replaying the declared transformations from the frozen parent and diffing, then reconstructing content through public interfaces only.
- Reject any transformation that leaves an original-file bypass or loses/duplicates content.
- Inherit accepted transformations; independent single-step hardening barely changes difficulty.
- Compose transformations so one's output is another's prerequisite; composition, not count, made tasks hard.
- Stop a lineage after three assessed target failures.

**Fit to Crucible Part 2.** §3.6 knobs: RES's operators are a concrete implementation of `obfuscation`, `observability` and `linkage` for World tasks; add them as App-level transformation operators with a frozen catalogue and record each in the lineage (`shares_fixes_with`). F6: the replay-and-diff validation + "no bypass" check should be a gate for any World transformation (it generalises G1/G2 to transformed Worlds). **F10 is essential here:** run the budget-2× probe and a written-out/direct-access control (VHD-Play's F/I/A idea) on RES-style variants; if success returns at 2× budget or with direct access, label the hardness "access/budget" in the IntentCard and do not count it as the target skill. Use RES variants mainly as a source of long-horizon persistence data and for the 397B, with intent labelled. Priority P1 (operators + replay gate), with the F10 guard P0 whenever these knobs are used.

## 2610.14774 — ProgAgent: Learning Tool Orchestration through Programmatic Training (Li, He, Zheng et al., 2026; venue n/r, HKUST/BUPT/NTU and others)
Read: PARTIAL (body in full; appendices B task synthesis/filtering and C.3 hyperparameters read; C.1–C.2, C.4, D, E skimmed by heading).  Relevance to Part 2: medium. Two transferable pieces: (1) **environment-state scaling** (hold instruction, logic, tools and verifier fixed; grow the database 1/2/4/8× and files 1/2/3/4×) as a clean difficulty knob that targets context load; (2) evidence that the **action interface** (code over tools vs direct calls) changes what a task measures, which matters for intent.

**Problem.** Direct tool calling (DTC) appends every raw tool output to context, causing context rot on long tasks; programmatic tool calling (PTC: code that calls tools, keeps results in variables, prints selectively) has only been studied at inference, and verifiable PTC training tasks are scarce.

**Method / algorithm.**
1. *Task synthesis* (Gemini 3.0 Flash for intents; Claude Opus 4.6 via Claude Code as constructor and auditor): 23 domains → intents filtered for rich state → constructor writes scripts that build a relational DB + file workspace under a SCALE config; single-purpose tools with hidden implementations and **bounded returns (pagination)** so large retrieval needs many calls; an instruction omitting tool names, schemas and verifier details; data sit in tables while constraints sit in unstructured files.
2. *Certification.* Python verifier on final response and environment state (no LLM judge); a Python oracle restricted to the provided tools must score 1; failures drive repair of data, tools, instruction or verifier.
3. *Controlled scaling.* Same task at v0–v3 (rows 1/2/4/8×, scalable files 1/2/3/4×); DB 99 → 711 KB, files 12.7 → 40.3.
4. *Filtering.* An independent harness agent writes its own solver at v3 and checks tools/state/verifier vs instruction (repair and re-audit); DeepSeek V4 Pro K = 8 under PTC; **keep only if 0 < p < 0.8 at every scale** (35 of 250 removed → 215 tasks × 4 scales = 860 instances). Exported also as Harbor tasks.
5. *Runtime.* Persistent IPython kernel exposed as an MCP server, tool proxy returning native Python objects, Bubblewrap sandbox hiding verifier and oracle.
6. *Training.* Cold-start SFT on teacher trajectories with dense criterion score ≥ 0.7 (3 epochs), then GSPO 150 steps, 32 tasks × 16 rollouts, Qwen3-8B/14B; same pool under DTC, PTC and Hybrid harnesses (DTC RL used v0 only, since larger scales gave no reward).

**Verification / grading.** Deterministic Python verifiers + oracle self-test + independent solver audit. No negatives; MCP `isError` semantics matter (servers that omit it hide failures from programs).

**Scale & cost.** 215 tasks (vs thousands to millions in baselines); 8×H200 × 2 nodes SFT, 8 × 8 H200 RL. Synthesis cost n/r.

**Key results.** DeepSeek V4 Pro pass@8 under DTC falls 0.95 → 0.42 from v0 to v3 but stays > 0.87 under PTC/Hybrid: **the same task is a context-load test under DTC and not under PTC.** RL reward at 14B: DTC 0.08 → 0.15; PTC 0.50 → 0.70; tool-output tokens per episode ~30k (DTC) vs < 20k (PTC, falling 20% during RL); PTC runtime errors 6.4 → 3.6. LOCA-bench at 64k state: ProgAgent-14B 30.7% vs 0% for comparable baselines. Cross-harness (14B): PTC-trained beats DTC-trained under both harnesses (MCP-Atlas under DTC 41.6 vs 29.7). Training on v0 only instead of all scales: LOCA-bench 38.3 → 23.7 (14B). PTC programs use loops 82%, conditionals 64–66%, error handling 8–10%; on unstructured Playwright pages 40.7% of PTC calls are single invocations. Disabling server error detection: 38.3 → 34.5.

**Failure modes & limits.** Authors: reversion to DTC-like behaviour on unstructured observations; silent server failures. Mine: difficulty band is defined on a frontier model, not the student; 215 tasks across 23 domains is thin for diversity claims; "harder" at v3 is mostly retrieval volume.

**Tips & tricks.**
- Scale the World's data volume (rows, files) with instruction, logic, tools and verifier frozen to get a monotone difficulty ladder.
- Paginate tool returns so volume becomes a real interaction cost.
- Put structured data in tables and the governing constraints in unstructured files so solving needs both.
- Require an oracle restricted to agent-visible tools; have a second agent write its own solver as an audit.
- Keep a task only if it is in band at every scale of its ladder.
- Report and fix tool error signalling (`isError`) before training code-based agents.

**Fit to Crucible Part 2.** §3.6: `count`/`distractors` knob at the World level = ProgAgent's SCALE config; adopt "in band at every rung" as the admission rule for ladder families, keyed per student. F10/intent: the DTC-vs-PTC contrast is a strong reminder that the **harness is part of the task**: a context-volume task is a different skill under a code interface; record the interface in the `DifficultyRecord` and the IntentCard, and run the budget-2× probe under the target harness. F1: tool return bounds (pagination) and correct error flags are App conventions worth enforcing (ties to G13). Priority P1.

## 2610.14118 — ClawLoop: Self-Improving Agents via Harness-Native Training Loops (Yang, Hao, Hao et al., 2026; venue n/r, Meituan + Peking University)
Read: FULL (body; appendices B algorithm, C SFT vs RL, D loop dynamics, E case study read; A experimental details skimmed).  Relevance to Part 2: high for **the task loop, F12 diagnosis and G8**: a teacher-free generate → validate → train → diagnose loop on Qwen3.6-27B, where the synthesiser writes seeded generators (answers computed, not asserted) plus an **answer contract** that declares every hidden decision rule (filter, rounding, tie-break, join key), and the loop's own per-iteration yields are reported.

**Problem.** Harness-agent (shell/filesystem) post-training pipelines are one-shot and teacher-bound: a stronger model makes tasks and trajectories once, and evaluation results go to humans rather than back into synthesis.

**Method / algorithm.** K = 3 iterations; each synthesises 1,024 candidates; the loop model (Qwen3.6-27B in OpenClaw) plays every role.
1. *Capability-driven route.* A catalogue binds workflow patterns (reconciliation, cross-source audit, multi-document merge, domain calculation) to target capabilities across an analysis track (structured deliverables) and a terminal track (end states), instantiated in deliberately long-tail domains (beekeeping hives, trail maintenance, ham-radio logs) to decouple skill from surface. **The LLM never writes task data**: it writes a seeded generator build(seed) → (s0, y, C) executed in a sandbox: multi-source evidence s0 (≥2 sources that require cross-referencing), answer key y computed by code, and **answer contract C** declaring each hidden decision (filtering criterion, rounding convention, tie-break, join key), the deliverable schema and numeric tolerance, with no answer values.
2. *Domain-grounded route.* Take an executable domain (MCP server or synthesised tools + DB); build a **tripartite graph** of tools ↔ atomic parameters/return fields ↔ DB tables (AST + LLM); cluster tools into skills by weighted affinity (the agent may override with justification); materialise each skill as a CLI script on a state snapshot + skill doc + capability spec extracted from code. Sample an **abstract task graph** by structural features (long-range dependencies, branching, convergence, error-recovery paths, multiple sub-goals) whose nodes are knowledge states and edges actions, with no business content; then ground it in a domain, seed exactly the needed background data, reject graphs whose transitions the skills cannot support. The instruction is written behind an information barrier from the gold trajectory: gives initial parameters, refers to records without copying them, states the goal without procedure, order or branch conditions. Terminal states become predicates over the final DB compiled into tests that **locate records by business-semantic keys, not hard-coded ids**.
3. *Difficulty growth (diagnosis-conditioned).* Multi-hop draw: index file (ids → filenames, no values) + per-entity detail files (none sufficient alone) + ≥1 cross-cutting reference (rate table, thresholds), enforced by construction. Dirtiness draw: distractors, missing fields, schema inconsistencies, unit mismatches, constrained so ground-truth logic stays well-defined. Deliverable format round-robin (JSON, CSV, multi-file, free report with a machine-checkable sidecar of criteria). Best schedule: raise difficulty by at most one level per iteration.
4. *Validation.* Agent-free: oracle runs and passes its own test-based verifier; **leakage audit** (instruction does not leak the key; tests do not pass on the untouched start state). Agent-based: N = 8 rollouts of the current policy; keep tasks with 1–5 passes ([N_l, N_h] = [1, 5]).
5. *Training.* Self-distilled SFT on successful rollouts (observation tokens masked), then GRPO on the same groups.
6. *Diagnosis.* On a held-out split of each iteration's pool, the updated agent summarises each failed trajectory (failure point, root cause class: misunderstanding, wrong tool, incorrect edit, premature termination; missing capability); summaries are clustered per skill category by root cause and the top patterns condition the next synthesis round (example: modifies a file but not the imports of dependent modules).

**Verification / grading.** Seeded generators + computed answer keys + test suites over final state; start-state-pass leakage check; band filter on the current policy. No negatives beyond the start state, no attacker; the same model writes tasks, tests and diagnoses.

**Scale & cost.** Per iteration 1,024 candidates → agent-free pass 897/910/913 (~89%) → in band 672/469/567 (65.6/45.8/55.4%); SFT trajectories 1,978/892/1,694; mean trajectory 5.6/11.4/8.7 turns and only 1.2K/2.9K/1.9K tokens (short tasks). Compute n/r.

**Key results.** Qwen3.6-27B: SkillsBench 46.3 → 57.2 (ClawGym 52.6), Claw-Eval-Live 69.3 → 76.9 (74.6), ClawGym-Bench 67.6 → 68.4 (ClawGym's own SFT 61.9, below base). Transfer of ClawLoop tasks to Qwen3.5-4B/9B with RL: Claw-Eval-Live 32.4 → 48.0 and 58.3 → 71.7; ClawGym-Bench 33.0 → 44.1 and 32.0 → 43.6 (ClawGym SFT with MiniMax-M2.5 + GLM-5.1 teachers: 36.8/64.3 and 34.6/35.3). Route ablation: capability-only 73.2 on Claw-Eval-Live, domain-only 70.1, both 76.9. K saturates around 3 on two benchmarks. **The difficulty controller overshot at k = 2** (admission fell to 45.8%, trajectories doubled), then corrected; authors name the controller, not iteration count, as the limiting factor. For small students, GRPO mattered more than self-SFT (few successes to imitate).

**Failure modes & limits.** Authors: single loop model so scale effects on producer vs consumer are confounded; small students inherit the 27B's weakness profile. Mine: self-labelled diagnosis and self-written tests with no independent check (the RSI risk §3.8 warns about); the held-out split is drawn from the same synthesised pool, so diagnosis tracks synthetic weaknesses; tasks are short (≤3K tokens), far from our 300-call horizon.

**Tips & tricks.**
- Have the synthesiser write a seeded generator that computes the answer, never the data or answer itself.
- Ship an answer contract that names every hidden decision rule (filter, rounding, tie-break, join key) and the output schema/tolerance, without values.
- Make tests find records by business keys, not ids, so any correct path passes.
- Enforce multi-hop structure by construction (index → detail files → cross-cutting reference).
- Constrain injected dirtiness so the ground-truth logic stays well-defined.
- Raise difficulty at most one level per iteration; watch admission rate for overshoot.
- Summarise failed held-out trajectories into (failure point, root cause, missing capability), cluster per skill, and feed the top clusters into the next synthesis round.

**Fit to Crucible Part 2.** G8 (communicability): the **answer contract** is the clearest operational form we have seen: for every answer/state check, any rule that cannot be recovered from the World by inspection must be declared in the instruction or contract; add `AnswerContract{hidden_decisions, schema, tolerance}` to `TaskProposal` and make G8 check every verifier rule against it. F5: business-key lookup in checks is a column-policy convention. F4: generator-computed answers = our oracle-by-construction. F12 → F3: the failure-summary schema and per-skill clustering are a concrete design for the trace clusterer and the `Assignment` stream; but keep a different-family diagnoser and route its output through F6 (no self-labelled loop). §3.6: ClawLoop's overshoot is evidence for the plan's sequential measurement and the "one knob band per step" rule; log admission rate per iteration as a controller health meter. Priority P0 (answer contract in G8), P1 (diagnosis → synthesis loop under §3.8 guards).
