**Batch summary.** 29 papers (the note-04 enterprise and web environment set). Read FULL: 26; PARTIAL: 3 (2408.06327 VisualAgentBench, 2401.13649 VisualWebArena, 2404.07972 OSWorld: bodies in full, long per-app appendices skimmed); ABSTRACT-ONLY: 0. In a few FULL papers the prompt figures are images and were not in the HTML; each card says where.

**Five cross-paper takeaways for Part 2.**
1. **Generated and inherited checks are wrong far more often than assumed, and judges are worse.** VeriEnv's SDK-validated judges were correct only 76% of the time (top cause: reset not reproducing the seeded data); WebArena-Lite had to fix 30–39 of 165 sampled WebArena checks; on τ-bench 70.6% of reward-0 runs were judged successful by the real user; LLM/VLM judges overestimate (GUI-Genesis 71.8% judge vs 49.0% state check). Executed state checks with mandatory negatives (G5), seed-exact reset (G2), and family separation are not optional. Cheap negative devices to adopt: WorkBench's side-effect metric, VisualWebArena's must_exclude, ClawsBench's one-way-door [−1,1] scoring, WebForge's deceptive same-format outcome codes per mistake class, EnterpriseOps-Gym's four check classes (goal, integrity, permission/process, collateral).
2. **Build the World first, but measure diversity on behaviour, not text.** AgentMercury (World → seeded tasks, 10 per World; invariants checked after the episode, not enforced by transitions) and CRMArena (latent traits that cause the records) validate the F1/F2-before-F3 order. But AgentMercury's own analysis shows a template lattice: 8.3% near-twin tasks, mostly across Worlds, task shape set by one variable. WebGym shows domain breadth and distinct-task count drive OOD gains, and hard-biased resampling from a narrow pool overfits. F8/F11 should dedup and set quotas on tool-set/behaviour signatures and on template, not on instruction text.
3. **Difficulty works as a declared knob vector with measured, monotone effects.** WebForge's seven dimensions × 3 levels with compositional level rules were monotone for every model; horizon (EnterpriseOps-Gym, EntWorld), observability (WorkArena++ explicit vs ticket+policy), number of Apps (OfficeBench), fault type (OccuBench: implicit truncation hardest) and hint/plan scaffolds (human plans +14–35 points; Qwen3-4B with plans ≈ large models) are the strongest levers. WebGym's check-subset decomposition makes strictly easier, still well-posed siblings for small students; TRUSTEE's dead-band controller with within-level re-sampling is a simple online band keeper. Per-student bands (35B now, 397B later) should be set on these knobs.
4. **Simulated people and simulated tools make tasks easier and less faithful.** 451 real users vs 31 simulators: simulators front-load identifiers, cooperate, and raise agent success to 77.8% vs 63.6% with humans; persona prompting did not fix it. OccuBench's simulators fabricate state, drop entities and invent rules; TRUSTEE's fully simulated environments train well only for stateless tools. Keep people behind an information-release schedule with deterministic fidelity checks (front-load ratio, IDs per turn), implement faults and error modes in App code (REAL-style config flags), and keep LLM-simulated components out of the reward.
5. **Traces are a source of both tasks and Worlds, and the factory's own construction traces are training data.** EnterpriseClawBench's gated session miner (5,291 → 852; fixture-resolvable, unique-match redaction recovery, no external dependency, self-contained, preflight) is a ready design for the trace source; GUI-Genesis and VeriEnv rebuild Apps from traces/screenshots with a golden-path test and a privileged SDK; SWE-Lancer re-injects the same bug a different way for contamination-proof variants; AgentMercury lifted Qwen3.5-35B-A3B (our student class) from 3.3% to 83.3% on World authoring by SFT on construction traces including validator-guided repair. Crucible should log F1/F5 repair rounds as training data for its own builders.

## 2604.17739 — Democratizing Tool Learning with Environments Fully Simulated by a Free 8B Language Model (Tang et al., 2026; NeurIPS-format preprint, v3 Oct 2026)
Read: FULL (body, Alg. 1, all four prompt templates, App. C–F).  Relevance to Part 2: medium. It is the strongest published case for a *fully LLM-simulated* environment (task, user, tool and verifier all one 8B model) with an online difficulty controller. Its controller and its ablations are reusable; its verifier is the opposite of Crucible's "execution decides" rule.
**Problem.** Agentic RL for tool calling needs online environments; executable synthesis (AWM, EnvScaler) costs proprietary-model tokens and freezes difficulty at creation time. Can one open 8B model play every environment role and still train a good tool agent?
**Method / algorithm.** TRUSTEE. Inputs: a tool repository (ToolBench RapidAPI specs, names and parameters only, not executable; filtered KEEP/DISCARD by Qwen3-Next-80B on name, description and parameter quality) and one backbone LM Φ = Qwen3-8B (vLLM, YaRN 4× to 131k context, frequency penalty 0.1). Per training iteration n:
1. *Task generation.* Sample tool subset f from the repository, size set by difficulty D_n (1–10 tools; tools drawn from one category until it is exhausted, so the set is coherent). Φ is prompted with f plus four settings (expected distinct calls 1–3, persona expert/beginner/novice, first-query ambiguity clear/somewhat/highly, expected turns) and returns JSON: expected tool list c, user intent g (the hidden ground truth, richer than the first message), persona p, first query q (natural, must not name tools). The agent system prompt h is chosen from four specificity levels (detailed how-to, concise notes, one sentence, "helpful assistant").
2. *Simulated interaction.* M = 8 rollouts per task. A tool call goes to Φ with (history, call, tools, intent g): it first validates (parseable, tool exists, required args, types, plausible values) and returns an error string if invalid, else realistic concrete output (no placeholders), and also a per-step reward in {-1,0,1}. A text reply goes to Φ as the user with (q, g, p, tools, history): reveal info only when asked, end with an empty string on success or clear failure. Turn caps 1–3 user, 1–3 tool, 1–6 agent.
3. *Reward.* Φ as verifier sees (q, c, g, p, tools, full trajectory) and a criteria list; +1 if all criteria met, 0 if most, −1 otherwise or if no tool was called (an extra format check also forces −1 when no tool is called). Criteria are cumulative with difficulty: intent met → expected tools used correctly → no hallucination → no redundant or wrong trials → concise and efficient.
4. *Optimisation.* Multi-turn GRPO, token-level loss (DAPO style), final-reward group-normalised advantage, KL 0.001, clip 0.2, lr 1e-6, 200 steps, 16 tasks × 8 rollouts per step (batch kept small so the local simulator is not overloaded).
5. *Curriculum.* One scalar D in [1,100]; after each step, if mean batch reward > η_high = 0.5 then D += δ (=3); if < η_low = 0.0 then D −= δ. Every knob is a floor-scaled function of D (e.g. persona level = ⌊0.02·D⌋). "Soft curriculum": with ε = 0.5 per task, the tool count, expected calls, turns, persona and ambiguity are each re-sampled uniformly *within* the current level, so knobs do not move in lock-step.
The authors frame the gain as information asymmetry: the environment sees {τ, g, p, c, D}; the agent sees only τ.
**Verification / grading.** Entirely an LLM judge (the 8B backbone). Checked against ToolRL's rule-scored test split (410 trajectories: gold, perturbed gold, model outputs): Spearman 0.70, accuracy 0.87, precision 0.72, recall 0.93, AUC 0.89. Hand audit of 20 rule-scored failures found 10 actually correct (7 exact-match too strict, 3 malformed gold). Hackable in obvious ways: the tool simulator invents outputs, so there is no state to check; precision 0.72 means many false positives; the judge sees the expected-tool list, so the reward partly scores tool-name matching; one family plays policy and judge (for the Qwen3-8B run they are the same weights).
**Scale & cost.** 8×H20, 4 for training and 4 for the simulator. Training wall time ~30–43 h vs ~150–170 h for EnvScaler on the same node. About 1e8 backbone tokens per run. τ²-bench eval ~$30 per run (GPT-4.1 user).
**Key results.** Qwen3-8B (self-simulated): BFCL Non-Live 87.8→89.7, Live 80.3→82.2, Multi-Turn 39.9→46.4; τ²-Retail 43.0→45.6, Telecom 15.8→17.5, Airline 24→26 (CIs overlap on post-trained models). Qwen3-8B-Base: BFCL Multi-Turn 0→7.9, Non-Live 8.4→83.9. Ablations on Qwen3-8B BFCL Multi-Turn (46.4 default): no curriculum (fixed at hardest) 41.5; no soft curriculum 44.5; fixing tool count at max 27.4; fixing user at hardest 32.8; hiding intent 43.0, persona 43.1, expected calls 44.4 from the environment. Step size δ=10 → 38.8. A 397B backbone was not better (Multi-Turn 41.3 for Qwen3-8B). Turn-level rewards from the user/tool simulators did not help (35.6 → 33.0). Stateful tools (EnvScaler's) trained less well than stateless (Multi-Turn 7.9 → 1.0 on the base model).
**Failure modes & limits.** Authors: simulator capability caps task complexity (many tools, long horizons); many hyper-parameters; Qwen-only. Mine: gains on post-trained models are within CIs; benchmarks are mostly single-call BFCL; the stateful result is the warning sign, since Crucible's domains are stateful; "fidelity" is scored by another LLM (DeepSeek-V4-Pro, 1–5 scale), not by execution; no hack-rate measurement.
**Tips & tricks.**
- Drive all knobs from one scalar difficulty with a dead band (raise above 0.5 mean reward, lower below 0); step size matters (3 of 100 worked, 10 hurt).
- Re-sample knobs independently within a level (ε=0.5) so the curriculum does not collapse onto one pattern.
- Make persona and ambiguity orthogonal axes ("an expert can ask vaguely").
- Tighten grading criteria as a difficulty knob: first outcome, then efficiency and no redundant calls.
- Decrease system-prompt specificity across training so the policy works under a generic prompt.
- Sample tool subsets within one category first, so the tool set reads as one App.
- Hiding the hidden intent from the simulator hurts; the user simulator needs intent plus persona.
**Fit to Crucible Part 2.** F9 (per-student difficulty) and F11/F12 curriculum: adopt the dead-band controller and the soft within-level re-sampling as the online band keeper over DomainSpec knobs (count, horizon, tools, hints, observability), with "system-prompt specificity" and "user expertise × ambiguity" added as knobs. F3: persona × ambiguity as orthogonal diversity axes; the task-proposal JSON (intent richer than first message, hidden from solver) matches `TaskProposal.user_intent` + `privileged_notes`. Avoid: LLM tool simulation and LLM-only reward for stateful Apps (their own stateful ablation is weak; G3–G5 require executed checks). Use an LLM-simulated tool only as a cheap pre-warm or for stateless lookup tools. Interface: `DifficultyController(scalar D, η_low, η_high, δ, ε) → knob_vector`. Priority P1.

## 2603.11245 — Mind the Sim2Real Gap in User Simulation for Agentic Tasks (Zhou, Sun et al., 2026; CMU, preprint v2 Jul 2026)
Read: FULL (body and appendix A.1–A.12).  Relevance to Part 2: high for every task with a simulated person (F2 people, F3 user_known_info, G8 communicable, F10 intent). It is the only large paired human-vs-simulator study on an agentic, tool-using, DB-graded benchmark, and it quantifies how a simulated user makes tasks easier.
**Problem.** LLM user simulators play two roles in agent benchmarks: they drive the user turns and they judge the result. Nobody had checked either role against real people on a full tool-agent benchmark.
**Method / algorithm.** 165 τ-bench tasks (airline + retail), agent fixed to GPT-5.2. 451 Prolific participants role-play the customer from the same task instruction in a chat UI, ending with `/stop`, then fill a 10-question survey: 5-way success (No-policy issue correctly explained / No-failed / Partial / Yes / Fully), efficiency, number of clarifying questions, answer effort, human-likeness, smoothness, overall 1–5, reuse intent, free text. Three independent annotator batches per task give a human-human ceiling. Human-trace quality control: a GPT-5 judge scores role-play fidelity and survey honesty 0–100 (80 to pass); validated on 51 author-labelled traces, κ=0.6, precision 0.94. Then 31 simulators (18 proprietary, 9 open, 4 user-sim fine-tunes) run the same 165 tasks ×3 and answer the same survey.
Metrics. Behaviour D1–D4 from lexicon (LIWC, NRC emotion) and regex features on user turns: D1 style (words per turn, ≤3-word turns, politeness, dash use, ack-only turns, verbosity CV, repeated trigrams, identity confusion), D2 information pattern (share of words in first two turns, identifier-like tokens per turn, opening length), D3 clarification (hedges, certainty markers, pushback, clarification and info questions, in regex priority order), D4 error reaction (emotion, accusation, pivot). Per metric, Dice = 2·min(M,H)/(M+H)·100; dimension = mean. Outcome calibration: tasks binned into 5 difficulty bins by mean success across all simulators; ECE = Σ_b |S_b|/N · |p̂_sim(b) − p̂_human(b)|. Evaluation: MAE between simulator and human survey answers mapped to [0,1]; Eval = (1−MAE)·100. USI = mean(D1, D2, D3, D4, (1−ECE)·100, Eval).
**Verification / grading.** The object under study is τ-bench's DB-state binary reward: 70.6% of reward-0 runs were judged successful by the human user, 33% of reward-1 runs judged unsuccessful or partial, and 81% of policy-constrained correct refusals got reward 1. Cramér's V between human success and reward is 0.168; quality ratings are indistinguishable between the two reward groups. (Authors note τ-bench v1 has known task/reward bugs, but comparisons are paired.)
**Scale & cost.** 451 people, 495 human sessions (165×3), 31 simulators × 165 × 3 batches. No $ given.
**Key results.** Human ceiling USI 92.7; best simulator DeepSeek-V3.1 76.0, Gemini-2.0-Flash 74.7, GPT-5.1 73.5; Claude-Opus-4 59.2; user-sim fine-tunes 47–67. Capability (Arena Elo) does not predict fidelity except within the GPT line. Concrete gaps: GPT-4o has 1% short turns vs 29% for humans and 49% polite turns vs 15%; UserLM-8B gives 4.8 identifiers per turn vs 2.6; GPT-4o hedges in 14.6% of turns vs 7.3%; simulators pivot 16–19% vs 8.4% and rarely accuse. Effect: most general simulators raise agent success above the human 63.6%, up to 77.8% ("easy mode"); weak specialised simulators fall below because they fail to follow the role. As evaluators, GPT-5.1 rates human-likeness +1.11 and reuse +0.83 higher than humans but task success −0.15 lower. A findings-informed persona prompt (reveal gradually, vary tone, push back) for GPT-5-mini *lowered* USI 70.9→64.6 and worsened ECE 0.18→0.29: fixing some features overshoots others. Simulator rankings held with a different agent (Gemini-3.1-Pro).
**Failure modes & limits.** Authors: lexical and regex proxies; D4 not tied to actual error turns; US English role-players, not genuine needs; one agent; 3 sessions per task. Mine: the study is customer-service only; the human-success label is itself a role-player's opinion, so "reward is orthogonal to success" mixes real reward bugs with users not knowing the policy; no attempt to train a better simulator.
**Tips & tricks.**
- Front-loading is the biggest easy-mode lever: measure identifiers per turn and share of words in the first two turns.
- Report simulator behaviour, outcome and ratings separately; USI is a summary only.
- Use ECE over difficulty bins as a cheap check that a simulator does not shift pass rates.
- Calibrate on a small human set that spans easy and hard tasks per domain, and check that agent rankings hold.
- Do not trust an LLM user's satisfaction rating as reward; it is lenient on experience.
- Do not fix fidelity by prompt rules alone; test the change with the same metric.
- Keep the binary state reward, but add a separate outcome class for "correct policy refusal".
**Fit to Crucible Part 2.** F2/F3 people and simulated users: Crucible's simulated users will run easy mode unless information release is constrained. Adopt (a) a `UserSimSpec` with a hard information-release schedule (user_known_info revealed only when asked, as identifiers in fragments), checked by deterministic D2 metrics on the oracle and frontier traces; (b) an F6 gate "user-sim fidelity": front-load ratio and IDs/turn within a band of a small human or customer-trace reference; (c) an F9 measurement that pass rate with the simulator is not above the rate with a stricter or human-derived user on a sample (ECE-style); (d) the answer-kind `policy_refusal` as its own verdict class in the VerifierBundle (DomainSpec.infeasible_share). Avoid LLM-user ratings as reward. Traces-to-tasks: real customer conversations are the reference distribution for D1–D4. Priority P1 (P0 for any domain whose skill is clarification or elicitation).

## 2510.19286 — TheMCPCompany: Creating General-purpose Agents with Task-specific Tools (Esfandiarpoor et al., 2025; Brown/Microsoft, preprint)
Read: FULL (body, App. A–B prompts).  Relevance to Part 2: medium. Not a synthesis method; it is evidence about tool-surface design (one MCP tool per REST endpoint, retrieval over 18.5k tools) and about real-cloud tasks with Terraform setup. Useful for F1 (curated tools vs full API surface) and the "tools" difficulty knob.
**Problem.** General agents mostly act through browsers and shells. What happens when every operation of every company service is exposed as a task-specific tool, at the scale of tens of thousands?
**Method / algorithm.** Extends TheAgentCompany (self-hosted Plane, GitLab, RocketChat, ownCloud with pre-populated data and LLM-played coworker NPCs; per-task checkpoint scripts). (1) Adds real Microsoft Azure. (2) Builds MCP servers that map each REST endpoint to one tool, with descriptions from the OpenAPI spec (GitLab 1,085 tools; Azure 16,837; RocketChat 520 with GPT-4.1-rewritten descriptions because its spec docs are poor; official Plane server patched with missing tools; ownCloud as an 11-tool file server). Total 18,505 tools, mean 5.53 args, up to 39 args; 21.5% have array/object args; many near-duplicates and name-alike tools. (3) Adapts 175 TheAgentCompany tasks and their checkers to tool use, hand-checks each is feasible with the tools, and hand-annotates a small sufficient ("oracle") tool set per task. (4) Adds 10 primitive Azure tasks (one action on one named resource) and 7 composite ones (fix a broken multi-service app, apply a security policy, add a feature) with a description, an evaluation script, a proof-of-concept solution script using the MCP tools, and a Terraform script that creates and destroys the resources. (5) MCPAgent: OpenHands CodeAct minus the browser plus a gateway server with two tools, `find_tools(query)` (text-embedding-3-large cosine over each tool's JSON spec, top-k) and `call_tool(name,args)`; the prompt tells the agent to try 3–4 alternative tool paths before giving up.
**Verification / grading.** TAC tasks: 50% checkpoint credit + 50% only on full success. Azure: success only (many valid paths, so no partial credit), checked on end state plus "the app works". Hackability not discussed; a real cloud admits irreversible collateral (GPT-5 deleted a VM by mistake).
**Scale & cost.** 175 + 17 tasks; Azure on free tier, <$1 total during development. Inference per TAC task: browser $0.41–14.58, oracle tools $0.17–7.17.
**Key results.** Over 6 models, oracle tool set beats the browser by +13.8 points on average and costs $2.29 less per task (Opus 4.1 −$7.41); MCPAgent with retrieval +5.4 points and −$2.06. GPT-5: browser 50.2, retrieval 52.3, oracle 54.5. GPT-5-mini with retrieval (32.1) is worse than with the browser (33.4); retrieval recall 33% vs 59–70% for frontier models. Azure primitive: 9/10 for GPT-5, Sonnet 4, Opus 4.1; 2/10 GPT-5-mini. Composite: at most 1/7 for any model. Failures: no alternative path after a quota error, fixating on IAM as the cause, not checking that the app works, declaring victory after part of the task.
**Failure modes & limits.** Authors: only 17 Azure tasks; real-cloud risk. Mine: oracle tool sets are hand-picked; 18k tools come mostly from one vendor; descriptions mirror the spec, so retrieval is the main skill tested; no training.
**Tips & tricks.**
- Generate one tool per REST endpoint from OpenAPI; rewrite poor descriptions with an LLM that can read the docs.
- Give a gateway with search + call instead of listing all tools; agents find what they need in about 20 retrieved tools.
- Annotate a sufficient tool set per task to separate tool selection from tool use.
- Ship a solution script and a create/destroy script (infrastructure as code) with every task on a stateful external service.
- Composite tasks with a "the system must work" end check expose premature victory.
**Fit to Crucible Part 2.** F1: confirms that a full generated CRUD surface plus a curated tool list is a real difficulty axis; adopt "tool exposure" as a DomainSpec knob with three values (oracle subset, curated App tools, full surface behind `find_tools`), and record the oracle's tools as the task's sufficient set (Oracle.tools_used already does this). F4: the proof-of-concept script is our Oracle; Terraform is the analogue of SeedBundle + teardown. F5/G6-style: composite tasks should carry a functional "system works" check besides state checks. For small students (35B MoE) retrieval over a large surface may make tasks unlearnable (GPT-5-mini did worse than with a browser), so F9 should treat surface size as a band knob. Priority P2.

## 2403.07718 — WorkArena: How Capable are Web Agents at Solving Common Knowledge Work Tasks? (Drouin et al., 2024; ICML 2024)
Read: FULL (body, App. A–B).  Relevance to Part 2: medium. A hand-built benchmark, but its task contract (setup / teardown / validate / cheat) and its template-instance expansion are the cleanest early form of Crucible's Oracle + Verifier pairing, and its knowledge-base generation pipeline is a small, reusable verified-QA generator.
**Problem.** No benchmark measured web agents on everyday enterprise software (ServiceNow), whose UIs are dynamic, non-standard and huge.
**Method / algorithm.** 33 task templates in 6 categories on free ServiceNow Personal Developer Instances, expanded to 19,912 instances by filling human-designed goal templates with pre-defined values; combinatorial categories are capped at 1,000 random instances. Lists (12: filter with 1–5 conditions, sort by up to 3 columns; 6,900 instances), Forms (5: 1–26 fields, tabs, autocomplete; 5,000), Knowledge base (1; 1,000), Service catalog (9; 3,550), Dashboards (4: read chart values, min/max; 1,862), Menus (2: navigate, impersonate; 1,600). Goals are explicit and complete by design. Each task ships a validation function (also gives live feedback, from unfilled mandatory field to invalid DB write) and a hand-coded Playwright oracle (`cheat()`), used for feasibility, as ground truth for learners, and to detect breakage after platform upgrades. BrowserGym is the Gym wrapper: a new task is four functions, `setup()` (create DB rows, navigate, log in), `teardown()`, `validate()` (returns reward, optional user chat message, done) and optional `cheat()`. Observations: chat, open tabs, last error, DOM, AXTree, screenshot, each element with id, box, visible and clickable flags. Actions: id-based primitives, coordinate primitives, or raw Python with Playwright.
Knowledge-base generator: 100 (item, value) facts → GPT-4 writes an HTML article that must contain the exact sentence stating the fact → GPT-4 writes 10 paraphrased questions plus format instructions → GPT-3.5 must answer each correctly from the article; failures are sent back to GPT-4 to rewrite (a weaker solver is used so the writer cannot cater to itself) → GPT-4 lists 10 acceptable answer formats, checked by hand.
**Verification / grading.** DB queries for created records and orders, client-side checks of the resulting list, answer-in-acceptable-set for retrieval, URL or logged-in-user for menus. Hackability not analysed; validators check only the target record, so collateral writes elsewhere would pass.
**Scale & cost.** 19,912 instances; 10 seeds per task in evaluation; Llama3-70B served on 4 A100s. No $.
**Key results.** GPT-4o 42.7%, GPT-4o+vision 41.8%, Llama3-70B 17.9%, GPT-3.5 6.1%. List-filter 0% for every model (non-standard widget); service catalog 77.8% for GPT-4o. Same agent on WebArena 23.5% (vs 14.4% in the original paper). Ablations: removing chain-of-thought costs ~10 points for Llama3; extra prompt features hurt weaker models (prompt bloat and truncation); thought history makes agents stick to early wrong decisions.
**Failure modes & limits.** Authors: some tasks need more than the 15-step cap; only atomic tasks (addressed in WorkArena++). Mine: instances of a template differ only in values, so 19,912 overstates diversity; explicit goals mean no clarification skill.
**Tips & tricks.**
- Define a task as setup / teardown / validate / cheat; the cheat run is the feasibility gate and the upgrade canary.
- Let validate() return a user chat message as well as a reward, so a checker can talk.
- When an LLM writes Q&A, check it with a *weaker* solver from the article so questions are not self-serving.
- Make the writer embed the fact as an exact string, so the source of truth is checkable.
- Generate acceptable answer variants once at build time, not with a judge at grade time.
- Cap combinatorial instances per template and sample randomly.
**Fit to Crucible Part 2.** F4/F5/F6 contract: matches Oracle (cheat) + VerifierBundle (validate) + SeedBundle (setup) + teardown; nothing new to adopt, but it is evidence that a scripted oracle per template keeps a benchmark alive across App upgrades (re-run G3 after any App change). F3/F5 answer tasks: adopt the fact-embedding + weaker-solver check + precomputed answer variants as the generator for `answer_kind=lookup` tasks over seeded documents. Diversity warning for F8: template-instance counts are not diversity; dedup should count templates (behaviour signatures), not instances. Priority P2.

## 2407.05291 — WorkArena++: Towards Compositional Planning and Reasoning-based Common Knowledge Work Tasks (Boisvert, Thakkar et al., 2024; NeurIPS 2024 Datasets & Benchmarks)
Read: FULL (body; App. A human study, C task families, D curriculum algorithm, E traces and composition, G discussion; error-analysis examples in App. F skimmed).  Relevance to Part 2: high on two mechanisms: (1) composition of atomic (setup, oracle, validator) units into workflow tasks with oracles composed for free, and (2) the same workflow presented at two observability levels (explicit steps vs ticket + knowledge-base policy), which is exactly a Crucible difficulty knob.
**Problem.** WorkArena L1 tasks are atomic and explicit. Real knowledge work needs planning, arithmetic and logical decisions, memory across pages, retrieval of procedures, and recognising impossible requests.
**Method / algorithm.**
1. *Atomic building blocks*: L1 tasks plus new atomics (e.g., edit an existing record), each = setup, teardown, oracle (Playwright), validator.
2. *Composition*: a workflow chains atomics (onboard user = create user → order laptop → assign laptop). The composite oracle calls the atomic oracles in order; validation is either sequential per sub-task or one global DB query. New tasks come from appending steps (e.g., also create a first task for the user).
3. *341 workflows × 2 presentation levels = 682 tasks*. L2: the chat gives the exact steps (not how to drive the UI). L3: the chat says only "please complete the following task"; a ticket assigned to the agent carries the key values and points to a knowledge-base protocol article; success requires reading the ticket, finding and applying the protocol, and closing the ticket.
4. *Five skill families*: planning and problem solving (66: workload balancing, expertise-based assignment, 48 scheduling variants under time window/overlap/impact/risk constraints, priority-aware deduplication); information retrieval (39: values from charts or lists then a follow-up action); data-driven decisions (156: hierarchical-rule expense deduplication, 57 knapsack-style investment selection with different answer modes, 87 chart statistics such as median followed by actions); memorisation (28–29: navigate + do, on/offboarding); infeasible (52: non-existent field, invalid configuration; declare infeasible, optionally with a justification naming the cause, via a `report_infeasible(reason)` action).
5. *Instances*: each task has a seed that draws its parameters (e.g., budget). *Curriculum*: skills → buckets of tasks needing the same ability (ordering an iPad ≈ ordering a MacBook) with weights; one meta-seed m draws num_seeds per category, and per seed samples tasks from each bucket without replacement (Alg. 1) → 235 instances per level. Meta-seeds 0–9 reserved for evaluation, others for tuning.
6. *Robustness*: an installer pins instance config (system params, themes, KB, list/form layouts); every task runs as a fresh user created at start and deleted at end, which allows parallel runs and lets agents change UI preferences safely; 10 fictitious company brands with themes sampled per task for visual diversity.
7. *Traces*: running the oracle under BrowserGym records AXTree, screenshot, DOM and the Playwright action per step, giving unlimited demonstrations.
**Verification / grading.** Validators query the DB through REST plus front-end JS state; binary. Composite tasks validate each step or the global end state. Infeasible tasks check the declaration and, in one variant, the named reason. Hacks not studied; a global DB check of the target rows does not see collateral changes elsewhere.
**Scale & cost.** 682 tasks, thousands of configurations each; 50-step cap. Human study: 15 volunteers, 98 instances.
**Key results.** Humans 93.9% on both L2 and L3. GPT-4o: L2 3.0%, L3 0.0% (human subset 2.1%); GPT-4o-v L2 3.8%; Llama3-70B, Mixtral, GPT-3.5 all 0%. Only memorisation (14.6%) and a few chart retrievals were ever solved. ## 2411.02305 — CRMArena: Understanding the Capacity of LLM Agents to Perform Professional CRM Tasks in Realistic Environments (Huang et al., 2024; NAACL 2025)
Read: FULL (body, App. A–G).  Relevance to Part 2: high for F2 (state seeding). Its data generator is the clearest published recipe for a schema-anchored, densely linked World with *latent variables* that cause the data and are hidden from the agent but used to compute ground truth.
**Problem.** Work benchmarks have few objects and few foreign keys, and their tasks are toy UI chores. CRM work needs reasoning over a dense, interlinked record graph.
**Method / algorithm.**
1. *Inputs*: company name and description (a fictional shoe company), a real schema (Salesforce Service Cloud data model, 16 objects), and target scale per object (mid-size firm, 4 years).
2. *Generation order*: each object is generated conditioned on the objects it depends on (a DAG; e.g., Account/Contact → Order → OrderItem; User skills → Case → EmailMessage/LiveChatTranscript/CaseHistory). Latent variables sit in this DAG as hidden nodes: `ShoppingHabit` per customer (when and what they buy, seasonal), `Skill` per agent (whether the agent can solve a case or must transfer it), and policy-deviation flags that cause violations in transcripts. Without the Skill latent, no transfers exist, so the transfer task could not exist.
3. *Batching and dedup*: JSON entries generated by GPT-4o in mini-batches of 10; all previously generated entries of that object go into the prompt with an instruction not to repeat; after generation, exact-string dedup on task-critical fields (e.g., user email).
4. *Verification*: a format verifier rejects and regenerates any batch with a missing required field; a task-specific content verifier, e.g., for entity disambiguation an LLM must pick the right product from the customer's purchase list given the paraphrased name; entries it fails are discarded (so the paraphrase is neither too far from the original nor too close to another product).
5. *Upload* to a clean Salesforce Simple Demo Org *without* the latent variables; generated IDs mapped to Org IDs.
6. *Queries*: KQA from LLM-generated QA per knowledge article. Other 8 tasks: 14 hand-written seed templates with slots ([YEAR], [EXTREMA], [NCASES], [PRODUCT], [TODAY]...) → slots filled → ground truth computed by code on the generated DB *with* latents (e.g., which policy was violated is only knowable there) → ID mapping → LLM paraphrase of the query. 30% of queries in five tasks are false-presupposition non-answerable ones (expected answer "None"). 130 instances per task, 1,170 total.
7. *Tools*: raw SOQL/SOSL (`execute`, `submit`) or 27 hand-written Python wrappers (query vs calculation, independent vs dependent).
**Verification / grading.** Exact match on returned object IDs (or "None"); token F1 for KQA. The policies needed (case routing tie-breaks, quarter/season boundaries, "significantly more than other months") are stated in the system prompt, which removes ambiguity. Hack risk: answer-only grading, guessable when the candidate set is small (e.g., ~100 agents); no path checks.
**Scale & cost.** 100 users, 196 contacts, 500 products, 22,000 price-book entries, 2,071 orders, 7,100 order items, 977 cases, 3,234 emails, 387 chats, 45 articles. Agent cost $0.13–0.37 per query. Generation cost not given. 10 Salesforce-daily experts in a 60-min study.
**Key results.** Best: o1 57.7% (ReAct) and 64.3% (function calling); GPT-4o 38.2% ReAct, 54.4% FC. Weak models get worse with hand tools (gpt-4o-mini 28.3 → 19.5; claude-3-sonnet; deepseek-r1 FC 9.0). Removing calculation+dependent tools costs GPT-4o −26.7 points but *helps* weaker models. pass^k falls equally fast for Act, ReAct and FC. Non-answerable queries are often easier than answerable ones. 90% of experts rated the Org realistic or very realistic; the main complaint was empty, "not worked in" records.
**Failure modes & limits.** Authors: service personas only; each case simplified to one issue and one product so analysis is feasible. Mine: tasks are aggregate lookups with one answer, not state changes; ground truth leans on latents that the agent cannot see, so some answers may be undeterminable from visible data unless checked (no G8-style check reported).
**Tips & tricks.**
- Anchor the World on a real vendor schema and generate objects in FK-dependency order.
- Put hidden latent traits in the generation DAG to create the behaviours a task family needs (no Skill latent, no transfers).
- Strip latents before loading the World the agent sees; compute ground truth with them.
- Show all prior entries in each mini-batch prompt and exact-dedup key fields afterwards.
- Gate content with a task-specific solvability check by an LLM on the visible data.
- Add 30% false-presupposition queries with expected answer None.
- Write the business policy (tie-break rules, period definitions) into the task context so the answer is unique.
- Hand-made helper tools help strong models and hurt weak ones; treat tool helpfulness as a per-student knob.
**Fit to Crucible Part 2.** F2 SeedBundle: adopt CRMArena's recipe directly; `latent_traits (hidden)` already exists in the contract, and this paper shows how latents should *cause* records (skill → transfer, habit → order timing) so task families become possible. Add a G8 variant: every answer computed from latents must also be derivable from visible state (the oracle must reach it with policy-visible tools). F3: seed templates with typed slots + code-computed ground truth + paraphrase is a cheap proposer for analytics cells; diversity comes from slot values and paraphrase, so F8 must dedup on templates. F5: `answer_kind=None/false_presupposition` share. F9: tool-helper exposure as a knob (helps 397B-class, may hurt 35B). Expert realism study as an F2 fidelity check sample. Priority P0 for F2 latent-driven seeding.

## 2509.26506 — SCUBA: Salesforce Computer Use Benchmark (Dai et al., 2025; Salesforce, preprint, updated Aug 2026)
Read: FULL (body, App. A–G).  Relevance to Part 2: medium. Hand-built from user interviews, but three mechanisms are directly reusable: (1) snapshot → diff → revert-only-what-changed reset for a World that cannot be cheaply recreated, (2) rule-based milestone scores with rubrics (process reward), (3) human trajectories distilled into plans as retrieved demonstrations.
**Problem.** Enterprise computer-use benchmarks either cover only service tasks (WorkArena) or only read-only queries (CRMArena). SCUBA adds admin, sales and service workflows that change data and settings in a real Salesforce org.
**Method / algorithm.** Environment: a free Salesforce developer sandbox org (UI identical to production). Reset: recreating an org is too expensive, so the initial org configuration is snapshotted as a set of config files; after a run the current config is diffed against the snapshot and only changed files are reverted (task-level reset, since the task says which configs it should touch). Parallelism through many headless browsers or Docker desktops reverted to an initial snapshot. Tasks: workflows from interviews with solution engineers, admins, SDRs/BDRs and account executives; each workflow → one template with slots, linked to one Trailhead knowledge article and tagged easy/medium/hard by UI-action complexity and distinct abilities. Each template → 5 instances whose slot values are *chosen to vary difficulty* (extra scrolling, alphabetical search, more checkboxes to track), paraphrased by ChatGPT, checked and rewritten by two authors. 60 templates × 5 = 300 instances over 5 abilities (UI navigation, retrieval from transcripts, data/metadata manipulation with permissions, workflow build such as approval actions, troubleshooting Q&A grounded in org settings). Each instance has a config with initialization (synthetic records uploaded, settings enabled), evaluator inputs, and pre/post hooks. Evaluators are hand-written against the Metadata and Tooling APIs and return success plus milestone scores with rubrics naming which part failed. Internal annotators (after onboarding tests) solved every instance with the agents' action space, which validates feasibility and checks evaluators against human expectation; rejected trajectories go to a different annotator. Demonstrations: GPT-5 summarises each human trajectory into a short plan; two demos per template; 2 of 5 instances see their exact demo among candidates, 3 see only similar ones.
**Verification / grading.** Rule-based through platform APIs: binary success + milestone fraction. Strong because it reads the config/metadata state, not the screen. Not stated: whether evaluators check for collateral config changes (the diff-based reset would have that information).
**Scale & cost.** 300 instances; full evaluation <90 min for self-served models (8 vLLM replicas, round-robin). Per-task cost $0.24–1.44; 50-step and 90-min caps.
**Key results.** Zero-shot browser-use: GPT-5 51.3% (milestone 0.73), o3 45.7%, Claude-4-sonnet 34.7%, Gemini-2.5-Pro 31.0%. Computer-use: Agent-S2.5 39%, Claude-4-sonnet 27%, OpenAI-CUA 16%, UI-TARS-1.5-7B 2.7%, OpenCUA-7B 0.7% (large drop from their OSWorld scores). With demonstrations: Gemini-2.5-Pro 31→46%, Claude computer 27→47.7%, UI-TARS 2.7→9.2%; time and cost usually fall. Even *similar* (not exact) demos help. Budget caps of $0.5/$1 per task cut success modestly. Browser-agent success depended on heavy DOM-parser customisation. Failures: grounding errors, history that records a failed click as done, human demos that are correct but not shortest.
**Failure modes & limits.** Authors: grounding, history handling. Mine: 300 instances from 60 templates is small; evaluators hand-written per instance do not scale; difficulty labels are author judgments.
**Tips & tricks.**
- Reset expensive Worlds by snapshot + diff + revert of changed artefacts only; the same diff is a free collateral-damage check.
- Choose slot values to vary difficulty inside one template (extra search, more state to track).
- Score milestones with a rubric that names the failed sub-goal; use it as process reward and for failure analysis.
- Validate every instance with a human or oracle run on the agent's exact action space.
- Distil successful trajectories into short plans and retrieve similar ones as hints; this is also a "hints" difficulty knob.
- Report cost and latency next to success; test under per-task budget caps.
**Fit to Crucible Part 2.** F2/F6: the diff-and-revert reset maps onto `StateAdapter.diff`; adopt the diff as the collateral check in G5 (side-effect negatives) and as a cheap integrity gate between episodes. F5: milestone rubrics = VerifierBundle.milestones for Φ; emit per-milestone verdicts into F12 failure clusters. F3: "slot values chosen to vary difficulty" is a within-template knob (search depth, items to track) to declare as monotone knobs in DomainSpec. F9: retrieved plan-demos as a `hints` knob; similar-demo condition gives a graded hint level for the 35B student. Traces-to-tasks: plan distillation from trajectories is the summariser step that turns traces into reusable procedure docs (KB articles) in the World. Priority P1.

## 2405.00823 — WorkBench: a Benchmark Dataset for Agents in a Realistic Workplace Setting (Styles, Miller et al., 2024; COLM 2024)
Read: FULL (body, App. A data samples, template variation, no-action analysis, full tool docstrings).  Relevance to Part 2: medium. Small and early, but it is the clean origin of three Crucible rules: outcome-centric grading against the full end state of *all* databases, the side-effect metric, and template + outcome-function task generation. Its conditional tasks ("if X, do A, else B") and no-action tasks are also cheap anti-shortcut devices.
**Problem.** Tool benchmarks either grade retrieval only or compare function-call sequences, which punishes valid recovery and cannot see side effects.
**Method / algorithm.** Five small sandbox tables for one user (Sam) at a fictitious company: calendar (300 events), email (500), web analytics (500 visits), CRM (200 customers), project management (300 tasks); plus a company directory. 26 tools with full docstrings (description, params, returns, example, *limits*, e.g., `search_events` returns at most 5 so the agent must page by time window). Tasks: 69 hand-written templates (single-domain 48, multi-domain 21), each paired with an *outcome function* that computes the expected change to the databases from the template slots and the current data; 10 instances per template (690 tasks); each template has three phrasings for linguistic variation. Multi-domain templates are often conditional ("if page views fell >10% last week, schedule X at the earliest free slot tomorrow; otherwise email Y"). 122/690 (18%) need no action (condition false or nothing to cancel); up to 12 actions.
**Verification / grading.** Accuracy = all five databases after the run equal the ground-truth end state exactly. Side effect = any database differs from ground truth *and* from the start (wrong action taken); failing without changing anything is not a side effect. Any path is accepted. Weakness: exact string equality for written text fields (email body) means wording must be specified in the task.
**Scale & cost.** 690 tasks; no $ given.
**Key results.** GPT-4 ReAct 43% with all 26 tools, 49% with only the needed toolkit (redundant tools hurt); Claude-2 26%, Mixtral 16%, GPT-3.5 and Llama2-70B ~0% (context too short for all tools). GPT-4 by domain: Calendar 65%, CRM 23%; multi-domain 40%. Side effects: Analytics 54% (plots for the wrong period), multi-domain 29%. Resampling on format errors (up to 5 retries at T=0.5) 43%→49%. GPT-4: 0-action tasks 75%, ≥1 action 36%, ≥2 actions 18%. Per-template pass rates mostly 10–90% (only 15/69 templates at 0% or 100%), so instances within a template differ in difficulty. Errors: hallucinated email addresses instead of directory lookup, searching the past for "next meeting", ignoring result limits.
**Failure modes & limits.** Authors: small, clean inboxes overstate ability; single-turn; no retrieval-only tasks. Mine: everything belongs to one user and one week, so the World is thin; no-action tasks are an exploitable prior unless balanced.
**Tips & tricks.**
- Write each template with an outcome function that computes the expected end state from slots and data.
- Grade the whole World's end state, and count side effects separately from failures.
- Add tool result limits (pagination) to force iteration; document the limit.
- Include conditional tasks whose branch depends on data, and a share of no-action instances, to stop "always act" policies.
- Check that templates are not all-or-nothing (pass rate spread within a template).
- Measure redundant-tool cost by comparing needed-toolkit vs all-tools prompts.
**Fit to Crucible Part 2.** F5/G5: WorkBench's side-effect definition is the collateral check; adopt "diff outside the gold diff = side effect" as a separate verdict reported to F12. F4: "outcome function" = Oracle kind `end_state` computed from slots; for template families it is cheaper than an action program. F3/F8: conditional branch tasks and a no-action share (≈15–20%) as DomainSpec defaults; check the policy cannot score by always acting or never acting (extends G4 null agents with an "act on the else-branch" null). F1: tool result limits as a knob. F9: per-template pass-rate spread as a within-template difficulty signal. Priority P1.

**Key results.** Best Lite score 0.663 (Codex/GPT-5.5). - Use "the original agent had to ask for clarification" as a non-self-contained signal.
- Rewrite multi-turn sessions into one prompt that names inputs and the exact deliverable.
- Run a full preflight (upload, run, download, judge routing) before admitting a task.
- Put cheap deterministic hard rules (file exists, opens, no placeholders, no traceback) before any judge.

Priority P0 for the trace miner design.

## 2608.20634 — AgentMercury: Your Agent Can Synthesize Verifiable Environments for Business Scenarios at scale (Jeong & Yoon, 2026; Meridian Intelligence / UMass, preprint v1 Aug 2026)
Read: FULL (body, App. A corpus and diversity analysis, B hyper-parameters, C benchmarks, D training logs, E authoring).  Relevance to Part 2: high (core). It is the closest published system to Crucible's F1/F2/F3 order: a *World first* (company, service graph, schema, seeded state, cross-service invariants), tasks sampled from the World afterwards, deterministic SQL-style checks, RL on a 35B-A3B MoE (the same student class as ours), and supervised learning of the World-authoring step itself. Its own diversity analysis is the most useful negative evidence in the batch.
**Problem.** Training environments are built around predefined tasks, so more tasks do not mean more diverse Worlds; can a persistent World be synthesised from a business scenario and tasks emerge from it?
**Method / algorithm.**
1. *Roles.* "Planet" constructs the World; a Task generator poses objectives; the policy acts; a grader scores. Pipeline σ → Planet → w → Task → (u, ρ) → π → τ → Grade → r.
2. *World* w = ⟨S, A, Ω, T, O, s₀, R⟩. Planet factorises as p(C|σ) company identity → p(G|C) service graph → p(Σ|G,C) state schema → p(s₀|Σ) seeded state → p(R|G,Σ,s₀) world-level invariants. Key design: invariants R are **not enforced by T**. E.g., "a downstream record must exist after an upstream event" is checked after the episode, and the World does not create the record for the agent, so the agent must do the cross-service follow-up. R has two views of the same rules: R_vis (surfaced as in-World documents or policies the agent must discover) and R_hid (executable checks).
3. *Tasks.* (Δs₀, u, ρ) ~ Task(s₀, R): a task-specific state seed applied before the episode, an instruction, and a task rubric of programmatic assertions derived from the World structure plus Δs₀. Ten task seeds per World. Assertions are of three forms only: record exists, field equals, field differs (2–10 per task, mean 5.4). Up to six "hard requirement" flags (precise scoping, reconciliation, cross-system correction); 25,991/43,300 tasks flagged with cross-system action risk. Tasks are "investigation" tasks with one of six persona roles (account manager, coordinator, sales manager, ops coordinator, support lead, analytics owner).
4. *Grading.* r = Grade(s_H, τ; ρ, R_hid) ∈ [0,1], fraction of assertions met; deterministic replay possible from seed + action sequence. In practice the RL reward also uses a "behaviour penalty" (repetition, post-answer continuation, truncation) and a DeepSeek-V4-Flash judge at T=0 (App. B), so the training reward is not purely state-based.
5. *Tooling.* MCP environments run in-process; a fixed core of 10 tools (employee search/list/get/update, email search/list/send, Slack list-channels/list-messages/post) plus 4 tools (search/list/get/update) per extra resource, so tool counts take only the values {10,14,18,22,26}.
6. *RL.* Qwen3.5-4B and Qwen3.5-35B-A3B; GRPO with 8 samples per prompt, decoupled-PPO clip 0.2/0.28 (Dr.GRPO style), no std normalisation, no entropy term, zero-variance groups dropped, lr 1e-6 constant, global batch 128, rollout batch 16, ≤20 tool turns, 16k response tokens; fully async (2 actor + 6 rollout GPUs on one node, staleness ≤4, fresh-token ratio ≥0.75, partial rollouts). Also SAO (single-rollout async), which failed at 4B.
7. *Learning to author.* SFT of Qwen3.5-35B-A3B on 29,823 samples from construction traces of four kinds: brief→World, completion of a partly built World, validator-guided repair of a corrupted World, intent→diff on an existing World. Evaluated on 30 held-out briefs with 12 structural validators (all must pass).
**Verification / grading.** Deterministic assertion checks on final DB state + hidden invariants; replayable. Weak points: only existence/equality/inequality assertions (no collateral or path checks are described); judge and behaviour penalty mixed into reward; no hack analysis; the 12 validators are not listed.
**Scale & cost.** Claimed 4,783 Worlds (14 industries, 50 countries); the RL corpus has 43,300 tasks from 4,326 Worlds, 2,287 industry descriptions, 842 tools, 222 state-table types, 148 service combinations, 10–26 tools per World, 1–5 services per task (mean 2.9). One RL run used 3,200 tasks (7.4%) over 200 steps, which still touched 2,313 Worlds (53.5%) and 75.8% of tools. No $ or token cost for construction is given.
**Key results.** EnterpriseOps-Gym (held-out, not used for construction): Qwen3.5-4B 12.3→15.7 (GRPO); Qwen3.5-35B-A3B 24.8→28.1 (GRPO) / 28.3 (SAO), gains in all 8 domains at 35B (CSM fell at 4B, 9.2→5.6). Out of domain at 4B: AIME26 45.9→56.0, HMMT 28.5→35.4, LiveCodeBench 36.6→44.0, τ³-Airline 48.8→58.7; at 35B: BFCL 31.1→42.5 and much lower run-to-run variance on τ³ (Telecom 49.1±49.8 → 68.9±20.5). Training reward ~0.4→0.55–0.60 (35B GRPO), truncation 0.35→~0. Authoring: frontier API models pass all validators zero-shot on 67–87% of briefs; recipe prompt (invariant digest + exemplar) gives no systematic gain (McNemar p≥0.375); base Qwen3.5-35B-A3B 3.3% → 83.3% after trace SFT (Fisher p=1.2e−10; 11.5/12 validators on average); but the fine-tuned model *with* the recipe drops to 10% (27/30 fail the cross-service check). Dominant authoring failure: collapsing a cross-service invariant into one service (GPT-5.4 on 10/30).
**Diversity analysis (App. A, important).** TF-IDF t-SNE of task text shows blobs that do not correspond to domain, persona or shape; tool-set vectors do separate CRM, billing, project management and support. Mean pairwise text similarity 0.13 but median nearest-neighbour similarity 0.83, and 8.3% of tasks have a near-twin (cos >0.99); only 17% of near-twins are sibling seeds of the same World, so the redundancy comes from shared templates across Worlds. Task shape is a lattice set by one variable (number of extra resources). CRM ≈53–61% and "Account Manager" ≈53–63% of every cluster.
**Failure modes & limits.** Authors: no closed loop yet (no generator steered by policy failures); SAO weak at small scale. Mine: (a) the "World diversity" is largely a template lattice (same core tools, CRUD-per-resource, one persona dominating); (b) out-of-domain math/code gains at 4B from business tool tasks are surprising and unablated (no control run with the same RL budget on non-World data, so a general "RL on anything" effect cannot be excluded); (c) count inconsistencies (4,783 vs 4,326 Worlds; "five" API models but four rows; 80.7% vs 78.3% mean); (d) invariants not enforced by T is a good idea but also means many tasks are pure "did you also update service B" checks.
**Tips & tricks.**
- Build the World before tasks; sample many seeded tasks per World (10) and spread RL sampling across Worlds.
- Keep cross-service invariants out of the transition function, check them after the episode, and surface them as in-World policy docs (visible view) with a hidden executable view.
- Express task success as record-exists / field-equals / field-differs assertions over the end state.
- Drop zero-variance GRPO groups; keep truncated samples during cold start so the truncation penalty is learned.
- Train the authoring model on four trace types (forward, partial completion, validator-guided repair, intent→diff); repair data is cheap to make by corrupting valid Worlds.
- Do not add long recipe prompts to a fine-tuned author; they broke the cross-service structure.
- Measure diversity on tool-set and behaviour vectors, not task text; report near-twin rate and whether twins share a World.
**Fit to Crucible Part 2.** F1/F2: validates the AppBundle/SeedBundle-before-proposal order; adopt `invariants: [Invariant{trigger_service, target_service, check_sql, visible_doc_ref}]` as a first-class AppBundle field, with R_vis rendered into the World's policy docs and R_hid into VerifierBundle.state_checks; add a G-gate "cross-service invariant is really cross-service" (their top authoring failure). F3: tasks = (Δs₀, u, ρ) per World with ≥10 seeds; F11 quota: cap tasks per World and per template. F8/diversity: their analysis is a direct warning for Crucible's MAP-Elites grid: measure tool-set/behaviour-signature distance and near-twin rates across Worlds; break the CRUD lattice by varying the tool surface beyond search/list/get/update. Self-improvement loop (§3.8): their authoring SFT (3.3%→83.3% for the same 35B-A3B we use) is evidence that the swarm's World-building can be distilled into the student family itself; add "validator-guided repair" traces from F1 repair rounds as training data. F9: their 35B student gained ~3 points on EnterpriseOps-Gym; set expectations accordingly. Avoid: mixing an LLM judge into the reward; their unablated OOD claims should not be cited as evidence without a control. Priority P0.

## 2601.17722 — EntWorld: A Holistic Environment and Benchmark for Verifiable Enterprise GUI Agents (Mo et al., 2026; Zhongguancun Lab / Tsinghua, preprint)
Read: FULL (body, App. A–C).  Relevance to Part 2: medium-high for F1/F3. A schema-driven generator over *real open-source enterprise apps* (EspoCRM, ZenTao, OpenProject, Veops CMDB, Snipe-IT, iTOP): it reverse-engineers the schema graph, verifies inferred joins by probe SQL, and validates generated task SQL inside a rolled-back transaction. Weakness: despite the abstract, all 1,756 tasks are SELECT retrieval; numbers in the text contradict each other.
**Problem.** Consumer web benchmarks lack enterprise logic; enterprise trajectories are private and costly; LLM/visual judges cannot verify committed DB state.
**Method / algorithm.** (1) *Infrastructure*: each app in its own Docker image with data baked in; hierarchical (Hydra) configs; a DatabaseAdapter abstracts the engine. (2) *Workflow discovery*: list non-empty tables → LLM writes a SchemaJSON per table (purpose, key fields) from names and contents → relation inference: explicit FKs parsed; implicit links proposed by an LLM from column-name and type similarity; every inferred link is tested with a probe JOIN and kept only if it returns rows → LLM abstracts workflows (core tables, key relations, business description); results cached by MD5 of the core-table list. (3) *Task generation*: LLM writes bilingual templates (prompt + SQL logic + placeholders) constrained by the verified graph → slots filled from real DB rows via cross-table queries; for CUD tasks an LLM proposes realistic data variants from existing records → *execution check*: run the SQL in a transaction, require executability and non-empty result, for CUD inspect affected rows, then ROLLBACK so the seed DB stays clean. (4) *Packaging*: WebArena format, semantic dedup of instructions, illegal answers removed, `require_reset` tag for state-modifying tasks. (5) *Difficulty*: D_task = Σ wᵢdᵢ over table count, relation count, operation type (SELECT < INSERT/UPDATE/DELETE), result size, SQL complexity (JOINs, WHERE, subqueries, aggregates), weights predefined. (6) *EntAgent*: Qwen2.5-VL-32B SFT on successful template-driven trajectories, then GRPO (8 rollouts/task, 64 parallel envs, 1 epoch, lr 1e-6, clip 0.2/0.3) with reward = w₁·success + w₂·step-level executability (penalty for failed actions, averaged) + w₃·format; an *experience replay buffer* swaps a stored success into any all-zero GRPO group.
**Verification / grading.** Ground-truth SQL per task; answer compared with executed SQL result (retrieval). Robust for the answer, but it checks returned values, not navigation; no collateral checks needed since tasks are read-only.
**Scale & cost.** 1,756 tasks over 6 apps (97–397 each); 11,572 logged agent actions (74.5% clicks); GPT-4.1 $0.16/task.
**Key results.** GPT-4.1 47.61% (text also says 37.39%, garbled), Claude 3.5 Sonnet 28.8% (partial), UI-TARS-72B 34.5%, Qwen2.5-VL-32B 24.0%, EntAgent-SFT 50.6%, EntAgent-RL 56.9%; human 85% (estimated). By horizon: GPT-4.1 34.0% (<5 steps) → 2.7% (>15). Screenshot + a11y tree beats either alone (EntAgent-RL 53.7% vs 35.2% tree, 15.6% screenshot); a11y trees are often incomplete in legacy apps.
**Failure modes & limits.** Authors: write operations left to future work. Mine: claims of long-horizon CUD workflows are not borne out by the released task mix; the SFT/RL train/test split is drawn from the same templates and apps, so the RL gain is in-distribution; "human 85%" is estimated, not measured.
**Tips & tricks.**
- Infer implicit relations with an LLM but keep only those a probe JOIN confirms.
- Validate generated state-changing SQL inside a transaction and roll back; check affected rows.
- Fill templates from real rows via cross-table queries so answers exist.
- Cache schema analysis by a hash of the core-table set.
- Use a structural difficulty score (tables, joins, operation type, result size) as a prior.
- In GRPO, inject a cached success into all-fail groups to avoid zero-signal batches (watch for off-policy bias).
**Fit to Crucible Part 2.** F1 (App synthesis from real OSS apps): adopt "LLM proposes relation → probe query confirms" as the schema-integrity gate when ingesting an existing App or customer DB (§2 enterprise ingest), and the transaction-rollback check as the cheap G3 pre-check for SQL-expressed oracles. F9: their D_task features are a ready baseline for the difficulty predictor (rank before frontier audit). F12/trainer: the success-replay trick is a cheap fix for all-zero groups on hard cells, but it is off-policy; record it as an option, not default. Priority P1 (F1 gate ideas), P2 (rest).

## 2307.13854 — WebArena: A Realistic Web Environment for Building Autonomous Agents (Zhou, Xu et al., 2023; CMU, ICLR 2024)
Read: FULL (body, App. A.1–A.10).  Relevance to Part 2: medium. The reference design for self-hosted, data-filled real OSS apps with programmatic functional checks; it is the substrate many later RL papers train and evaluate on (see 2408.06327, 2510.16252). Its evaluator vocabulary and unachievable tasks recur in Crucible's verifier design; its keyword checks are a known weakness.
**Problem.** Agent environments are simplified or static, and grading compares action sequences instead of functional outcomes.
**Method / algorithm.** Site choice from ~200 segments of the authors' own browsing histories → 4 categories: e-commerce (Magento, ~90k products, 300+ categories from WebShop data), forum (Postmill: 95 subreddits, 127,390 posts, 661,781 users), GitLab (300 repos sampled 80% from top-decile by stars and 20% from bottom decile, >1,000 accounts), shop-admin CMS (Magento admin); tools (OpenStreetMap for the US north-east, calculator, scratchpad); knowledge (offline Wikipedia via Kiwix, GitLab and Adobe Commerce manuals). One Docker image per site with data baked in; reset by restarting from the image (seconds to a minute). Unachievable tasks expect "N/A". Answers double-annotated, third annotator breaks ties. Hackable: must_include on bodies rewards keyword stuffing; locators look at "latest post" so collateral posts are invisible.
**Scale & cost.** 812 tasks; humans 78.24% (5 CS grad students on 170 tasks, 110 s avg).
**Key results.** GPT-4 CoT 11.7% with the "unachievable hint", 14.41% without it; the hint made GPT-4 call 54.9% of feasible tasks impossible. Per-template success: GPT-4 is 100% on only 4 of 61 templates with any success; instances of one template differ in difficulty ("fork metaseq" vs "fork all repos from Facebook"). Errors: latching on the first plausible information (homepage best-sellers instead of the 2022 report), repeating a typed query, ignoring previous action.
**Failure modes & limits.** Authors: human baseline from CS students. Mine: author-written tasks; 3.3 instances per template; string-inclusion checks; reset is container restart (slow at RL scale, fixed later by WebServ/WebGym).
**Tips & tricks.**
- Choose App categories from real usage logs.
- Seed one persistent persona per App with long history so personal queries are possible.
- Separate locator (where to read state) from matcher (what must hold) in every check.
- Keep an unachievable class with expected "N/A", and test that the "you may give up" instruction does not cause false give-ups.
- Mix popular and long-tail entities when sampling seed data (80/20 by stars).
- Halt runs on 3 repeated actions on the same observation or 3 invalid actions.
**Fit to Crucible Part 2.** F5: locator + matcher is the shape of state_checks; replace keyword `must_include` with structured field predicates wherever the App has a DB, and add collateral checks (WebArena has none). F3/G4: the UA-hint result is a direct warning for infeasible tasks: measure false-infeasible rate on feasible tasks as a G4-style null-agent ("always say infeasible") check. F2: persona with history and 80/20 popular/long-tail sampling as SeedBundle defaults. F8: template ≠ difficulty class; per-template pass spread is informative. Priority P2.

## 2510.16252 — WebServ: A Full-Stack and RL-Ready Web Environment for Training Web Agents at Scale (Lu, Wang et al., 2025; Northeastern/Amazon, preprint v2 May 2026)
Read: FULL (body, App. A–C).  Relevance to Part 2: medium (infrastructure). Not task synthesis; it is the reset/isolation and observation layer that makes on-policy RL on stateful web Apps affordable. Directly relevant to how Crucible snapshots and restores Apps per rollout.

## 2601.02439 — WebGym: Scaling Training Environments for Visual Web Agents with Realistic Tasks (Bai, Taymanov et al., 2026; Microsoft/UIUC/CMU, preprint v6)

A 292k-task RL corpus built by *rubric-derived decomposition* (each task's rubric is split into fact groups; proper subsets with a large group become strictly easier, still well-posed tasks), with a measured, controlled ablation of breadth, size, difficulty mix and horizon on held-out *websites*. Grading is an LLM judge over live sites, which Crucible should not copy, but the difficulty and curriculum findings transfer.
**Problem.** RL for web agents needs many diverse, graded tasks and fast rollouts; existing sets are small, narrow, or lack evaluation criteria.
**Method / algorithm.** (1) *Seed*: 10 public task sets (InSTA-v3 146k tasks on 146k sites; PAE-WebVoyager 128k on 13 sites; AgentSynth, BrowseComp, TravelPlanner, Mind2Web-Live, Online-Mind2Web, DeepShop, Mind2Web-2, GAIA-Web). GPT-4o infers a website when missing. (2) *Rubric*: GPT-4o writes an evaluation rubric as *fact groups* (each group 1+ facts); difficulty = total facts (easy 1–3, medium 4–6, hard 7+). (3) *Decomposition* (Alg. 1): if ≥2 groups and ≥1 group has ≥3 facts ("large"), every proper subset of groups that contains a large group becomes a new task (GPT-4o rewrites the instruction) with that subset as its rubric; e.g., a 9-fact task with groups of 2/3/4 yields 5 sub-tasks of difficulty 3–7. Sub-tasks are strictly easier and well-defined if the parent is; no rollouts needed. (4) *Split*: 1,167 OOD test tasks, each from a distinct website; every training task on those websites removed. (5) *Grading*: GPT-4o selects evidence-bearing "keypoint" screenshots (high recall), then judges each fact (criterion A) and checks the final answer against screenshots for hallucination (criterion B); reward 1 only if all pass; benchmark reference answers override the judge when present. A GPT-4o blocking detector puts anti-bot sites on a dynamic blocklist. (6) *Rollout system*: CPU-only browser server (master/worker) + GPU client; fully asynchronous process pool, no step or episode barriers; per-operation local queues (navigate, screenshot, execute) instead of one FIFO; 1,800 trajectories × 13.2 steps in ~30 min on 128 CPUs + 24 H100 (4–5× faster than synchronous; 48.6 vs 264 min at 64 CPUs). (7) *RL*: REINFORCE with binary reward and no baseline, i.e., online filtered BC on successes; a "memory" field the model rewrites each step; *repetition penalty*: drop any step whose next screenshot is identical (even inside successful trajectories); per-difficulty step caps.
**Verification / grading.** LLM judge with rubric; validated on 80 human-labelled trajectories: rubric raises accuracy and precision for all judges (GPT-4o, Qwen3-VL-8B, Gemma3-27B) at some recall cost (stricter). Live sites drift, so labels are not reproducible; hackable by answer hallucination (criterion B mitigates).
**Scale & cost.** 292,092 train tasks over 127,645 sites (top-20 sites ≈ half of tasks, mostly PAE); ~80% easy. Runs collect ~36–42k training trajectories. Effective batch 3×4×8×2.
**Key results.** Qwen3-VL-8B-Instruct 26.2% → 42.9% on OOD sites (GPT-4o 27.1%, GPT-5-Thinking 29.8%). Hard-biased sampling overfits after ~36k trajectories (repeated hard tasks from few domains); "only easy" beats "only medium" overall; memory prompt and repetition penalty each add ~2–3.5 points. Steps rise with difficulty (7.8 / 9.9 / 11.9 mean). Thinking variant starts higher but Instruct overtakes it.
**Failure modes & limits.** Authors: over-strict generated rubrics. Mine: live websites → non-reproducible rewards and contamination risk; LLM-judged reward for training; positive-only REINFORCE avoids negative gradients, so failure information is unused; "difficulty = fact count" measures answer breadth, not reasoning depth.
**Tips & tricks.**
- Decompose a verified task into strictly easier sub-tasks by taking proper subsets of its checks; difficulty = number of checks; keep only subsets with a sizeable group.
- Split train/test by *source* (website/App), not by benchmark; remove all training tasks that share a source with test.
- Do not over-sample hard tasks from a narrow pool; effective distinct-task count matters more; uniform over a large pool won.
- Cap steps per difficulty tier and tighten caps: it raised success, including on hard tasks.
- Drop steps that produce no state change from the gradient (no-op penalty).
- Make rollouts fully asynchronous with per-operation queues; CPU sim server and GPU policy client separate.
- Keep a blocklist of sources that fail for infrastructure reasons, detected automatically, so they do not pollute reward.
**Fit to Crucible Part 2.** F3/F9: adopt "check-subset decomposition" as a difficulty *down-shifter*: for any task whose VerifierBundle has grouped checks (milestones), proper subsets with ≥1 large group become easier sibling tasks with the same World and oracle prefix; this directly serves per-student bands (35B gets sub-tasks, 397B the parent) and is a cheap way to fill low-difficulty cells. **Method / algorithm.** Real OS in VMs (Ubuntu, plus 43 Windows tasks), snapshot reset, parallel VMs, headless. Each task is a config file: VM snapshot; *setup* (download files from cloud, open apps, resize windows, set intermediate states such as "document half edited" or "after a crash"); *post-processing* after the episode (activate windows, save files); *getters* that fetch evidence (files from VM or cloud, Chrome cookies via remote debugging, VS Code via an extension, the a11y tree, even decrypted Thunderbird account data); *evaluator* function + parameters (e.g., `is_cookie_deleted`, `compare_table(rules)`, `check_a11y_tree(selectors)`); dynamic getters (crawler at evaluation time) for live facts. Actions: raw pyautogui code (any mouse/keyboard, loops) plus WAIT, FAIL (declare infeasible), DONE. Tasks: 369 from tutorials, how-to videos, WikiHow, forums (Reddit, StackOverflow, Superuser), courses and blogs, chosen by popularity, plus author-designed multi-app workflows (101, 27.4%), 30 infeasible tasks (deprecated or hallucinated features raised by real users), and 84 adapted from other benchmarks. Each task cross-checked by two other authors for feasibility, ambiguity and alignment, then attempted by two non-authors; four rounds of fixes during experiments.
**Verification / grading.** 134 distinct execution-based evaluator functions (vs ≤7 in earlier web benchmarks); reward 1 or partial, or 1 for correctly predicting FAIL on infeasible tasks. Authors note residual false positives/negatives and say red teaming would reduce them. Hackable: FAIL on infeasible tasks gives free reward to agents that give up (Gemini-Pro screenshot setting did exactly this).
**Scale & cost.** 369 tasks; 302 distinct initial states; ~1,800 person-hours (650 single-app, 750 workflow, 400 double-checking), ~1 h setup and ~2 h evaluator per task; humans (CS students new to the apps) 72.36%, median 111.9 s per task (WebArena 35.4 s).
**Key results.** Best baseline 12.24% (a11y tree, GPT-4); screenshot-only 5.26–5.80%; workflow tasks ≤6.57%; LibreOffice Calc often 0%. Human success by time: easy 84.9%, medium 81.1%, hard (>180 s) 49.6%; agents near 0 on hard. SoM hurt GPT-4V in dense OS UIs; more text history helps, image history does not; resolution matters non-monotonically. Errors: click coordinate inaccuracy, not dismissing pop-ups/cookies, repetitive actions, weak app knowledge.
**Failure modes & limits.** Authors: annotation cost; residual check errors. Mine: 369 tasks, nearly one evaluator per task, so not a scaling recipe; the infeasible class rewards giving up unless balanced.
**Tips & tricks.**
- Specify each task as config: snapshot + setup + post-process + getter + evaluator, so new tasks reuse a function library.
- Start tasks from intermediate states (work in progress), not fresh apps.
- Source scenarios from tutorials and Q&A forums ranked by views and votes; infeasible tasks from real users' requests for deprecated or hallucinated features.
- Have non-authors attempt every task before release.
- Keep a FAIL action and infeasible tasks, but measure false FAIL on feasible ones.
- Log annotation hours per stage.
**Fit to Crucible Part 2.** CUA/Harbor lane: the getter/evaluator split is the generic VerifierBundle shape for real-app Worlds (getter = StateAdapter read, evaluator = predicate); keep a shared evaluator library so per-task code shrinks.
