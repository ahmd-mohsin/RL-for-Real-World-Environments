**The five most important cross-paper takeaways for Part 2**

1. **Diversity must be forced by structure and measured on behaviour.** A model-family mix or reworded text does not produce it.
   - Artificial Hivemind: cross-family output similarity is 0.71–0.82, and paraphrasing the prompt barely helps.
   - NoveltyBench: bigger models give fewer distinct outputs.
   - Prismatic Synthesis: embedding diversity and persona variety rank datasets *backwards*, while gradient-space diversity predicts OOD transfer (ρ ≈ 0.9).
   - OpenThoughts-Agent: the number of distinct task descriptions is the scaling bottleneck, and the tail of task sources hurts.
   - What to build: Vendi on `BehaviourSignature`s at a fixed n, with a check that it predicts held-out-family transfer. Add sparse-cell acceptance and in-context regeneration (K nearest tasks plus the batch's own earlier proposals). Use VS-Multi in F3, and a cross-family "top-N nearest" homogeneity meter.

2. **Hardness must be built in a way that keeps the task solvable. Text-level hardening fails.**
   - What fails: Evol-Instruct-style rewrites; OpenThoughts' "harden / add constraints" augmentations, which never beat untouched tasks; asking a generator for a hard task directly, which only lets easy tasks survive (AgentSynth's asymmetry ablation: 11% generation success, and evaluation stays flat).
   - What works:
     - composing verified subtasks (AgentSynth: 62% → 14% across six levels);
     - layer-wise leaf-constant expansion with no target-adjacent constants (WebShaper);
     - removal or history-reversion bugs with inverse mutation (SSR);
     - bugs that arise as side effects of feature work (BugPilot: Claude solves 41% vs 66% for SWE-smith bugs);
     - tool-only oracles that are updated on every hardening step (DeepSeek-V3.2).
   - Every obfuscation needs an executed uniqueness check, because WebSailor admits non-unique answers.

3. **Difficulty is a property of the student, so select by learning potential, edit at the frontier, and predict before paying.**
   - Score tasks by regret: reference pass minus student pass (PAIRED).
   - Sample the pool PLR-style, with rank prioritisation and staleness; the score for GRPO students is p̂(1−p̂).
   - Grow the frontier by editing it (ACCEL). Keep lineage, and add a per-cell cap because ACCEL has no diversity control.
   - Warm-start a goal-conditioned competence predictor (MAGELLAN) to rank candidates before F9.
   - Use the ZPD sandwich (AgentFrontier): escalate until a weak reference fails, keep if a strong reference passes, send all-fail items to humans. It costs about $0.78 per kept item.
   - SSR's optimum target is a solve rate of ≈ 0.2 at G = 8. Its tunnel-vision result means the controller needs a knob-entropy monitor.

4. **Ladders for too-hard tasks work, but they must be removed, and they must share the parent's verifier.**
   - QuestA: partial solutions, cut from 50% to 25%. A hint's effect is steep and non-linear: 25% looks like no hint at all.
   - R³: late start states, mixed in training rather than staged, with an equal reward for every start.
   - Terminal-Gym: hint removal, with one test suite grading every hint level.
   - What to build: variants share the parent's `VerifierBundle` and record `hint_level` or `start_offset`. The unscaffolded p̂ stays the real metric. F10 labels the skills that a scaffold removes.

5. **Any model-judged step carries limited information, so anchor the loops to execution.**
   - Mind the Gap: the generation–verification gap saturates in 2–3 rounds and erodes diversity, unless the verifier is exact.
   - Artificial Hivemind: judges and reward models are least calibrated among equally valid alternatives.
   - AgentSynth's LLM verifier accepts 12% of near-miss states.
   - DeepSeek's synthesis agent edits the solution and the verifier until they agree.
   - SSR shows the solver its full oracle tests.
   - What to build: hidden checks; verifiers written by a different family from the solution; judges stronger than the generator, combined in AND-ensembles; a GV-gap test for every judge on the frozen anchor set; near-miss negatives in G5; a cap on unanchored self-improvement rounds.

## 2212.10560 — Self-Instruct: Aligning Language Models with Self-Generated Instructions (Wang et al., 2022; ACL 2023)
Read: FULL (body, App. A.1–A.4 prompts and hyperparameters).  Relevance to Part 2: medium. It is the ancestor of every seed-pool-and-filter task generator; its diversity filter (ROUGE-L < 0.7) and seed-mixing rule are the baseline F3/F8 must beat, but it has no execution check, so its 54% all-fields-valid rate is the warning for Crucible.
**Problem.** Human instruction data is costly and narrow (skewed to classic NLP tasks); can a vanilla LM bootstrap its own diverse instruction-tuning data?
**Method / algorithm.** Iterative bootstrap over a task pool.
1. Seed pool: 175 hand-written tasks (25 classification, 150 not), each 1 instruction + 1 instance; written without reference to test sets (mean ROUGE-L to SuperNI test instructions 0.21).
2. Instruction generation: sample 8 in-context instructions per call, **6 from the human seeds and 2 from earlier model generations** (the mix promotes diversity while anchoring quality); the LM continues "Task 9..." until it stops or hits "Task 16". GPT-3 davinci, T=0.7, top_p=0.5, presence penalty 2.
3. Classification identification: few-shot (12 classification + 19 non-classification seed instructions), T=0, 3 tokens.
4. Instance generation, two orders: **input-first** for open tasks (invent input fields, then output); **output-first** for classification tasks (enumerate the labels, then write an input conditioned on each label). Output-first exists because input-first collapses onto one label (e.g. grammar-error detection mostly yields grammatical inputs).
5. Filtering: add an instruction only if its ROUGE-L with every pool instruction is < 0.7; drop keywords the LM cannot serve (image, picture, graph); drop duplicate instances and same-input/different-output instances; heuristic drops (too long/short, output repeats input).
6. Survivors return to the pool; loop until ~52K instructions.
7. Fine-tune the same GPT-3 on (instruction + input → output), with randomised templates (with/without "Task:", "Input:" prefixes, varied line breaks) for format robustness; prompt loss weight 0, 2 epochs.
**Verification / grading.** None automatic beyond the heuristics. Quality was audited by one author on 200 samples: instruction valid 92%, input appropriate 79%, output correct 58%, all fields valid 54%. Eval: SuperNI ROUGE-L (119 unseen tasks) and a 252-instruction user-oriented set rated A–D by the instruction authors (κ = 0.57). Nothing checks outputs, so incorrect labels train in freely.
**Scale & cost.** 52,445 instructions (11,584 classification), 82,439 instances (35,878 with empty input). Whole dataset about $600 of davinci calls at $0.02/1K tokens.
**Key results.** SuperNI zero-shot ROUGE-L: GPT-3 6.8 → 39.9 with Self-Instruct (InstructGPT-001 40.8; T0 33.1; GPT-3+T0 data 37.9). Combined with SuperNI training data 49.5 → 51.6. Human eval: within 5% of InstructGPT-001 counting A+B. Data-size ablation: gains plateau after about 16K instructions on the user set, and after only hundreds on SuperNI. Quality ablation: regenerating outputs with InstructGPT-003 gave +10% on human eval, so output quality, not instruction count, was the binding constraint.
**Failure modes & limits.** Authors: gains skew to head-of-distribution tasks; works best with large models; amplifies LM biases; label imbalance. My critique: 46% of samples had a defect, which is fine for SFT format learning but would poison an RL reward; ROUGE-L dedup is purely lexical, so paraphrased duplicates survive; the 2-of-8 model-generated examples can drift the pool over iterations with no measure of it; the seed set defines the reachable space (coding seeds beget coding tasks).
**Tips & tricks.**
- Mix fixed human seeds with recent generated items in each prompt (6:2) to anchor quality and still move.
- Generate the label first, then the input, when an answer space is small, to avoid label collapse.
- Filter by similarity to the whole pool, not just to seeds.
- Blocklist task kinds the solver cannot serve (modalities, tools) at generation time.
- Measure a quality rate per field (instruction / input / output) on a sample; the weakest field is the one to fix.
- Data size plateaus early; spend on correctness of answers instead.
**Fit to Crucible Part 2.** F3 (proposal) and F8 (dedup). Adopt: the seed+recent mix as a template for F3's "K nearest tasks" context, and the output-first trick generalised as answer-first / end-state-first construction (already §3.0 rule 3: solution by construction). Avoid: lexical-only dedup (F8 must add embedding and behaviour-signature layers) and any unverified outputs (F4/F5 executed oracle replaces it). Interface: `TaskProposal` should carry the ids of the in-context exemplars used, so F11 can measure pool drift per iteration. Priority P2 (historic baseline; nothing new to build beyond what §3.5 already has).

## 2304.12244 — WizardLM: Empowering Large Pre-Trained Language Models to Follow Complex Instructions (Xu et al., 2023; ICLR 2024)
Read: FULL (body, App. A–F prompts).  Relevance to Part 2: medium. Evol-Instruct is the canonical "rewrite operator" approach to difficulty and breadth; its operator taxonomy maps onto Crucible knobs, but its hardness is textual, which §3.6 explicitly rejects unless the behaviour signature changes.
**Problem.** Human-written instructions skew easy/moderate (ShareGPT's difficulty distribution); how to mass-produce harder, more diverse open-domain instructions automatically?
**Method / algorithm.**
1. Start pool D⁰ = Alpaca's 52K (Self-Instruct-made) instructions.
2. Each epoch (M = 4), for every instruction pick one of six operators uniformly at random:
   - **In-depth** (5): add one constraint; deepen (widen the inquiry); concretize (general → specific concepts); increase reasoning steps (ask explicitly for multi-step); complicate input (add structured data — XML, SQL table, Python, HTML, shell, JSON — via in-context demos). Each prompt asks for a version "a bit harder" for ChatGPT/GPT-4 that a human can still understand, and caps growth at **10–20 added words** so difficulty climbs gradually.
   - **In-breadth** (1): mutation — create a new prompt in the same domain but "more rare", with similar length and difficulty.
3. Response generation: the same LLM (gpt-3.5-turbo, T=1, top-p 0.9, 2048 tokens) answers the evolved instruction.
4. **Elimination evolving** — the evolution failed if: (a) an LLM equality judge says the new instruction has no information gain (same constraints and same depth/breadth); (b) the response contains "sorry" and is < 80 words; (c) the response is only punctuation/stop words; (d) the instruction copies template words ("given prompt", "#Rewritten Prompt#"). Failed items go back to the pool unchanged and are retried next epoch.
5. Merge D⁰…D⁴ (≈250K), shuffle, and sample 70K (to match Vicuna's size) for SFT of LLaMA-13B (3 epochs, 8×V100, 140 h).
Difficulty is measured by a 1–10 LLM difficulty judge (App. E), cross-checked against GPT-4 and humans (agreement reported as good in App. I).
**Verification / grading.** No answer verification; the response is whatever ChatGPT writes. Quality control is only the four elimination rules. An operator can produce an instruction that is unanswerable or ill-posed and still pass (the "sorry" heuristic is the only solvability probe).
**Scale & cost.** 52K × 4 epochs × 3 calls = 624K API calls → 250K instructions. Cost not stated in $.
**Key results.** WizardLM-13B avg 58.96 over 9 benchmarks vs Vicuna-13B 54.60, Alpaca-13B 43.44; HumanEval 24.0 vs 12.5 (Vicuna); GSM8k 37.15 vs 24.34; WizardEval (218 real instructions, 29 skills) 89.1% of ChatGPT. Human blind ranking: WizardLM beats Alpaca and Vicuna (κ > 0.6). Ablations: per-epoch data (C0→C4, ~52K each) — average benchmark score rises with evolution round, tracking judged difficulty; ShareGPT seed > Alpaca seed (61.87 avg) except GSM8k (ShareGPT has 4.3% math vs Alpaca 11.8%: the seed's skill mix propagates); LLaMA-2-70B-Chat as evolver works nearly as well (56.27); all 250K > 70K (60.30); 70K of SuperNI-style closed tasks is far worse (37.73). In-breadth: k-means (20 clusters) on BERT embeddings shows wider spread than ShareGPT/Alpaca (qualitative t-SNE only).
**Failure modes & limits.** Authors: evaluation via GPT-4 judges and small human sets is limited. My critique: "harder" is judged by an LLM rating text complexity, not by any solver failing; constraints added by rewording may not change what the solver must do; no correctness check on responses; the uniform operator choice ignores which operator actually helps; the seed's domain mix is inherited (math share), so evolution does not fix coverage gaps; difficulty creep is limited only by the word cap.
**Tips & tricks.**
- Name the hardness operators explicitly (constraint, deepen, concretize, more steps, richer input, mutate-to-rarer) and sample them; it gives an auditable knob vector.
- Cap each mutation's size (10–20 words) so difficulty rises in small steps.
- Keep failed evolutions in the pool for a retry instead of discarding them.
- Use an "equal/not equal" judge for no-information-gain mutations — a cheap semantic no-op detector.
- Train on all rounds mixed, so the pool spans difficulty levels.
- The seed's skill mix propagates; fix coverage at the seed, not by evolving.
**Fit to Crucible Part 2.** F3 (proposal), F9/§3.6 knobs, §3.8 task loop (variants). Adapt the operator set into `DomainSpec.knobs` — add constraint → collateral/path constraint; concretize → specific World entities; more steps → horizon/composition; complicate input → distractors/observability; mutate-to-rarer → move to an empty grid cell. Adopt the no-information-gain check, but make it behavioural: a variant is rejected unless its `BehaviourSignature` differs from the parent's on the knob changed (already the §3.8 task-loop acceptance rule; Evol-Instruct shows why the rule is needed). Avoid: LLM-rated difficulty as a band signal (F9 must use student p̂). Interface: each variant records `parent_id`, `operator`, `knob_delta`. Priority P1 (the operator→knob mapping is cheap and directly usable in the difficulty controller).

## 2406.08464 — Magpie: Alignment Data Synthesis from Scratch by Prompting Aligned LLMs with Nothing (Xu et al., 2024; ICLR 2025)
Read: FULL (body; App. C filters, D.3 decoding/system-prompt ablations, D.4 annotator, E.1 configs, F.2–F.5 ablations).  Relevance to Part 2: low–medium. It is a seed-free way to sample the user-intent prior of an aligned model; useful as a persona/intent sampler for F3 and the simulated user, not as a task generator (no verifiable ground truth).
**Problem.** Seed-based synthesis (Self-Instruct, Evol) is bounded by its seeds and prompt engineering; can user queries be drawn directly from an aligned model's learned distribution?
**Method / algorithm.**
1. **Instruction step.** Feed an open-weight aligned model only its pre-query chat template (e.g. Llama-3's user header) and let it complete; it writes a plausible user query, stopping at end-of-turn. Repeat N times.
2. **Response step.** Wrap the query in the full template and generate the answer (greedy decoding, on the reasoning that top tokens reflect the training distribution).
3. **Control by system prompt** for domain/language (e.g. "you are a math assistant" → math queries; Chinese prompt → Chinese queries); or use a specialist model (coder, math model) as the source. Multi-turn: append the pre-query template after each turn, with a system prompt reminding the model it is the user (8B models forget the role).
4. **Annotate** every instance with Llama-3-8B-Instruct: task category, input quality (5 levels), input difficulty (5 levels); embed with all-mpnet-base-v2 and compute min-neighbour distance via FAISS (removes repetitions); reward r* from a reward model (FsfairX-LLaMA3-RM) and reward difference r* − r_base, where r_base scores a URIAL-prompted base-model response.
5. **Filter** (App. C): e.g. Pro-Filter = quality ≥ average, min-neighbour distance > 0, reward > −12, then keep the 300K longest responses. Air-Filter adds difficulty ≥ medium and reward difference > 0.
6. **DPO extension:** sample k=5 responses at T=0.8, RM picks best/worst as chosen/rejected.
Decoding sweep (D.3): raising temperature (1.0→1.25) and lowering top-p (1→0.99) slightly lowers judged quality but raises judged difficulty and markedly raises min-neighbour distance (diversity); adding a generic system prompt lowered quality and made queries easier, so they recommend none.
**Verification / grading.** None of correctness: responses are model outputs ranked by a reward model and LLM ratings. Quality/difficulty ratings are self-annotation by the same family (D.4 re-rated with Qwen2-7B and found ratings no lower).
**Scale & cost.** Magpie-Air: 3M from Llama-3-8B-Instruct (1.55 h instructions + 50 h responses on 4×A100); Magpie-Pro: 1M from Llama-3-70B-Instruct (3.5 h + 150 h). 206 and 614 GPU-hours; about $0.12 and $1.1 per 1K instances. Instruction step is ~3% of compute.
**Key results.** Llama-3-8B base SFT on 300K Magpie-Pro-Filtered: AlpacaEval 2 LC 25.08 (vs WildChat 652K 14.62, Evol 8.52, Self-Instruct-Llama-3 100K 7.21, official Llama-3-8B-Instruct with >10M data 22.92); Arena-Hard 18.9 vs 20.6 official. +DPO: LC 50.10, above GPT-4-Turbo-1106. Same-model comparison, 100K each: Magpie 20.17 LC vs Self-Instruct 7.21 — seeds constrain format diversity. Filtered 300K beats 4M raw (25.08 vs 24.45). No single filter wins all benchmarks. Response generator swap to Qwen2-7B costs ~7 LC points. Weakness: math/reasoning (GSM8K 47.9 vs 71.7 official) — the prior over-represents information seeking (>50% of Pro); a 150K booster set fixed part of it.
**Failure modes & limits.** Authors: weak on reasoning; <1% harmful content. My critique: the sampled prior reproduces the model's own head distribution (information seeking dominates) — "diversity from the prior" is diversity in the region the aligned model has mass; it cannot reach skills absent from alignment data; possible regurgitation of alignment-set prompts (contamination with chat benchmarks is not checked); judge-rated difficulty only.
**Tips & tricks.**
- Template-prefix sampling is a near-free intent sampler (instruction step ~3% of cost).
- Temperature/top-p trade quality for diversity and difficulty; sweep them and mix slices instead of picking one.
- Avoid generic system prompts when you want hard, varied queries; use targeted ones only for domain control.
- Filter by min-neighbour embedding distance plus a response reward floor; filtered small beats raw large.
- Check the category histogram of anything sampled from a model's prior; expect information-seeking dominance and add boosters for missing skills.
**Fit to Crucible Part 2.** Peripheral. Possible use in F3 persona/intent sampling and in the simulated user's opening turn: sample "what a user of this App would ask" from an aligned model's prefix to seed realistic intents, then ground it in a cell and a World slice (§3.5 item 3). Also a cheap source of distractor requests. Avoid as a task source: no executed ground truth, and its prior collapses toward common intents (consistent with Artificial Hivemind). Lesson for the diversity meters: the decoding-parameter sweep is a measurable diversity knob for the swarm proposer. Priority P2.

## 2308.07074 — #InsTag: Instruction Tagging for Analyzing Supervised Fine-tuning of Large Language Models (Lu et al., 2023; ICLR 2024)
Read: FULL (body, Alg. 1, App. E and I).  Relevance to Part 2: medium. It is the clearest recipe for building an open-set intent/skill ontology from data, and for selection by coverage first; that is what F0 skill trees and F12 trace clustering need, but the tags are LLM-assigned text labels, not behaviour.
**Problem.** Diversity and complexity of SFT data are claimed as key but never quantified; can fine-grained intent tags define and measure them, and drive selection?
**Method / algorithm.**
1. **Open-set tagging:** ChatGPT tags each query (each turn separately) with fine-grained intention tags plus a one-line explanation per tag, as JSON, with few-shot format examples; no ontology given. >100K raw unique tags (12K+ in an earlier pass).
2. **Normalisation** (the reusable part):
   - frequency filter: drop tags seen < α = 20 times → 8,541;
   - rule aggregation: lowercase, special chars → spaces, NLTK stemming → 7,157;
   - semantic aggregation: PhraseBERT embeddings + DBSCAN at a similarity threshold (0.05 as stated) → 6,587;
   - association aggregation: FP-Growth rules (min support 40, min confidence 99%) merge always-co-occurring tags into atomic tags (1,772 rules; e.g. "math problem" + "mathematics" → one).
3. **Quality check:** GPT-4 rated 2,000 precision cases (all tags of a query correct) and 2,000 consistency cases (a tag's meaning stable across queries): 96.1% / 86.6%; 3 humans on 1% (40 cases): majority 100%/100%, human–GPT κ 0.92 / 0.75; counterfactual (planted wrong tags) cases confirm annotators catch errors.
4. **Metrics:** diversity = fraction of the global tag set covered; complexity = mean tags per query.
5. **Complexity-first diverse sampling (Alg. 1):** sort the pool by tag count descending; sweep, adding a query only if it adds at least one new tag to the current batch's tag set; when the sweep finishes (all tags covered) reset the batch tag set and sweep again; stop at N.
6. Distilled local tagger (InsTagger, LLaMA-2-7B on 773K tagging samples, 1 epoch): tag F1 31.8% exact, 73.4% fuzzy (PhraseBERT cosine > 0.8).
**Verification / grading.** Tag quality by GPT-4 + small human audit. Downstream: MT-Bench (GPT-4 judge, averaged over 3 judgements because of judge noise).
**Scale & cost.** Pool of 4 datasets (WizardLM-Alpaca, WizardLM-ShareGPT, UltraChat, ShareGPT): 306,044 samples, 6,398 tags, mean 4.48 tags/query. Selected 6K with mean 16.56 tags and 100% coverage.
**Key results.** TagLM-13B-v1.0 (LLaMA, 6K samples) MT-Bench 6.44 ± 0.04 vs Vicuna-13B-v1.3 (125K) 6.39, WizardLM-13B (70K) 6.35; v2.0 on LLaMA-2 6.55 vs Llama-2-13b-chat (RLHF) 6.65. Decoupled ablations at fixed 6K: complexity 6.7→16.6 tags/query raises MT-Bench on a coarse scale (all beat random ~4.5), not significantly at fine steps; coverage raises score, with a plateau between 50% and 90%. Dataset analysis: math/code sets are low-diversity, high-complexity; ShareGPT/UltraChat/OpenChat sit top-right and train the best chat models.
**Failure modes & limits.** Authors: MT-Bench only, judge noise, English only. My critique: "complexity = number of tags" rewards verbose multi-intent queries; tags are claims about text, so two queries with different tags can demand the same behaviour; the coverage plateau shows tag counts weight unrelated tags equally (software development vs C++); greedy coverage favours rare, possibly noisy tags; the DBSCAN threshold is under-specified.
**Tips & tricks.**
- Ask the tagger to explain each tag; it improves auditability and was used for quality review.
- Normalise open-set labels in four passes: frequency floor, lexical canonicalisation, embedding clustering, association-rule merging.
- Audit a label ontology on two axes: per-item precision and per-label consistency across items.
- Plant counterfactual wrong labels to verify that the auditor catches errors.
- Select for coverage first (each item must add an uncovered tag), then fill by complexity.
- Distil the tagger to a small local model when volume makes API tagging costly (fuzzy F1 is the honest metric).
**Fit to Crucible Part 2.** F0 (skill tree / axes from data), F12 and traces-to-tasks (Clio-style intent clustering of traces, §3.4 item 5), F11 (selection). Adopt the normalisation pipeline to turn swarm- or trace-derived skill labels into a stable `DomainSpec.skill_tree`, and the precision/consistency audit (with planted wrong labels) as the F0 gate check on any auto-built taxonomy. Adapt Alg. 1 for F11: admit tasks that fill an uncovered grid cell first, then by learnability — but use measured `BehaviourSignature` cells, not text tags (§3.5 item 2). Avoid "tag count = complexity" as a difficulty signal. Interface: `SkillLeaf` needs `aliases`, `merged_from`, and `support` counts from normalisation. Priority P1 (taxonomy building for traces-to-tasks and DomainSpec).

## 2210.02410 — The Vendi Score: A Diversity Evaluation Metric for Machine Learning (Friedman & Dieng, 2022; TMLR 2023)
Read: FULL (body; appendix skimmed for definitions).  Relevance to Part 2: high as a tool. It is the metric §3.5 item 4 names for two of the four batch meters; the card fixes the exact formula, its properties, its cost, and the pitfalls of choosing the kernel.
**Problem.** Diversity metrics in ML need a reference set, a classifier, or discrete features, and average pairwise similarity (IntDiv) saturates and ignores correlated features. A reference-free, kernel-agnostic, interpretable metric is wanted.
**Method / algorithm.**
- Inputs: n items, a positive semidefinite similarity k with k(x,x) = 1. Build K (n×n), K_ij = k(x_i, x_j). Let λ_i be the eigenvalues of K/n (non-negative, sum to 1).
- **VS = exp(−Σ λ_i log λ_i)** = exp of the von Neumann entropy of K/n = effective rank of K.
- With embeddings X ∈ R^{n×d} and cosine/inner-product kernel, the nonzero eigenvalues of K/n equal those of XᵀX/n (d×d), so cost is O(d²n) instead of O(n³). Without embeddings, Nyström column sampling approximates it. The empirical kernel entropy converges at ~1/√n (Bach 2022).
- Weighted variant (App. def. 7.1) for items with explicit probabilities.
- Properties (Thm 3.1): VS ∈ [1, n] (1 if all identical, n if all orthogonal) — read it as "effective number of distinct items"; exact duplicates do not raise it (merging two identical items leaves VS unchanged); for mutually dissimilar groups, VS(union) = exp(H(group shares)) × Π VS(group)^{share} (it decomposes like Shannon entropy); permutation invariant. Averaging two kernels that capture different attributes raises VS, and it rises when attributes are uncorrelated — IntDiv does neither.
- Code: github vertaix/Vendi-Score.
**Verification / grading.** Validated empirically: mixtures of 1–5 Gaussians (VS tracks the number of modes and within-mode variance, IntDiv does not); simulated mode dropping on labelled image/text sets (VS correlates better with the true mode count).
**Scale & cost.** Cheap with embeddings (d² n). 2,500 molecules per model; Inception 2048-d embeddings for images.
**Key results.** Molecules (MOSES, Morgan fingerprints): IntDiv ranks the HMM among the most diverse generators, VS ranks it least diverse because it emits clusters of exact duplicates — the case Crucible's swarm produces. StackedMNIST: two GANs both hit all 1,000 modes (NOM), but VS 746.7 vs 866.6 vs original data 943.7 — coverage counts hide within-mode collapse. Images: no generator reaches its training set's VS; on LSUN the diffusion model with the best precision/recall has lower VS (near-duplicates). Text decoding: VS on an n-gram kernel ranks beam search < diverse beam search (rising with penalty) < human captions; the text interprets beam search as about 3 distinct captions out of 5.
**Failure modes & limits.** Authors: reference-free, so random noise scores high — pair it with a quality metric; the score is only as meaningful as the kernel (too sensitive → everything diverse; too coarse → nothing); cost when no low-d embedding exists. My critique: VS grows with n for any non-degenerate kernel, so comparisons across batches need a fixed n (subsample) or a per-item normalisation (VS/n); embedding kernels on instruction text measure wording, not behaviour; no significance test is provided — bootstrap over subsamples is needed for an alarm threshold.
**Tips & tricks.**
- Read VS as the effective number of distinct items; report VS/n alongside it.
- Compute it with a d×d covariance, not an n×n matrix, whenever embeddings exist.
- Exact duplicates leave VS flat: a falling VS/n in a growing pool flags near-copy production.
- Average kernels for different attributes (e.g. text + behaviour) to get a joint diversity; use separate VS per kernel to see which axis collapsed.
- Always pair it with a quality or validity rate; diversity of broken tasks is worthless.
- Compare batches at a fixed sample size.
**Fit to Crucible Part 2.** §3.5 meters (F8, F11, the generator loop of §3.8). Adopt as specified: VS on instruction embeddings (surface) and VS on `BehaviourSignature` vectors (behavioural), at a fixed n per batch, with bootstrap CIs; report per generator family. ## 2505.20161 — Prismatic Synthesis: Gradient-based Data Diversification Boosts Generalization in LLM Reasoning (Jung et al., 2025; NVIDIA/UW, arXiv)
Read: FULL (body; App. A.1–A.3, C, D).  Relevance to Part 2: high. It is the strongest evidence that *behaviour-relevant* diversity (here, gradients) predicts OOD transfer while surface diversity (embeddings, personas) does not — the justification for §3.5's "behavioural Vendi is the one that matters" — and it gives a sparse-cluster rejection-sampling loop that maps onto F11 quotas.
**Problem.** Which kind of data diversity actually predicts generalization, measured with data scale and quality controlled, and can synthesis be steered toward it?
**Method / algorithm.**
*G-Vendi.* For each sample (x, y), compute the unit-normalised loss gradient −∇log P(y|x; θ) under a small, frozen, instruction-tuned proxy (Qwen2.5-0.5B-Instruct); project to d = 1024 with a Rademacher random matrix (Johnson–Lindenstrauss); stack into G (|D|×d); G-Vendi = Vendi score of GGᵀ/|D|, computed via the d×d matrix GᵀG/|D| (O(d²|D|)). No warm-up training or checkpoint averaging. Motivation: first-order influence — training on z helps z′ in proportion to ∇l(z)·∇l(z′), so spread gradients cover more of the task.
*Evaluating diversity metrics.* Pool of 1.5M synthetic samples per task (Qwen2.5-72B, 5-shot from WANLI or GSM8K+MATH). 300 subsets at fixed sizes (math 10K/50K/100K; NLI 10K/50K), spread across the diversity range with four samplers: random; higher-diversity (k-means, then uniform sampling over clusters); lower-diversity (grow from a seed by adding items with cosine > τ to some member); mixtures. Train Llama-3.2-1B (math) or DeBERTa-v3-large (NLI) per subset (1 H100 each). OOD metric = mean over 7 unseen benchmarks of accuracy relative to the same model trained on the full pool (normalises benchmark difficulty).
*Prismatic Synthesis loop.* (1) k-means on gradient features of the current pool with k = 1% of pool size; (2) generate new problems 5-shot from the pool (Qwen2.5-72B; math solutions by R1-Distill-Qwen-32B up to 16K tokens); (3) keep only generated items that fall in the sparsest k/2 clusters; repeat. Quality filter: majority vote, N = 3 samples with ≥ 2 agreeing (math), N = 2, τ = 2 (NLI). Decontamination: 10-gram match, then embedding nearest-neighbour + LLM paraphrase judge.
**Verification / grading.** No ground-truth answers anywhere; correctness is self-consistency of R1-32B. Eval by math-verify / lighteval, pass@1 (AIME/AMC averaged over 16 runs).
**Scale & cost.** 300+ training runs; PrismMath 1.0M problem–solution pairs, PrismNLI 515K after filtering; up to 16 H100 nodes for generation, 4 for fine-tuning. No $ figure.
**Key results.** Correlation with OOD performance at 100K (Spearman ρ / R²): G-Vendi 0.899 / 0.823 (math), 0.893 / 0.791 (NLI); Embedding Vendi (gte-Qwen-7B, 14× bigger) 0.754 / 0.659 and 0.841; LLM skill-set entropy 0.812; 2-gram entropy 0.736; perplexity −0.631. In-distribution, scale dominates and diversity correlates weakly (only very low diversity hurts). A diverse 10K set often beats a less diverse 100K set OOD. Controlled probe: DiverseReason (10K seeds × 0.1K personas) beats DiversePersona (0.1K seeds × 10K personas) OOD 54.77 vs 38.15 at 10K; G-Vendi ranks them correctly (63.2 vs 51.9), Embedding Vendi ranks them backwards (22.0 vs 24.5). Proxy swap: Llama-3.2-1B-It ρ 0.909, base Qwen2.5-0.5B 0.772 (instruction-tuned proxies better; same-base proxy best). Student swap: up to 25.4% OOD spread on Llama-3.1-8B across 10K subsets ordered by G-Vendi. Scaling: vanilla few-shot and persona-guided generation saturate at 50–100K; Prismatic keeps improving to 1M. PrismMath-7B (from Qwen2.5-Math-7B-It) avg 75.25 vs R1-Distill-7B 72.80 and OpenThinker2-7B 72.36; AIME24 57.08. PrismNLI 74.28 avg OOD vs 66.18 for WANLI+MNLI+SNLI.
**Failure modes & limits.** Authors: correlation only holds with quality controlled — not for comparing datasets from different pipelines; OOD aggregate may hide target-domain effects; they suggest target-conditioned diversity as future work. My critique: gradients of the *answer* likelihood need a reference output — for agentic tasks this means an oracle trace, and the gradient of a 300-call trace on a 0.5B proxy may be dominated by formatting tokens; sparse-cluster acceptance can favour outliers that are broken (self-consistency filter partially guards); the k = 1% rule and "smallest half" are heuristics without ablation; the persona finding is in math only.
**Tips & tricks.**
- Use a small frozen instruction-tuned model's projected gradients as a diversity feature; a proxy sharing the student's base is best.
- Validate any diversity metric by training on many fixed-size subsets that span the metric's range, not by eyeballing.
- Normalise OOD scores per benchmark by a reference model trained on the full pool.
- Build test subsets at known diversity with balanced-cluster (up) and similarity-growth (down) samplers.
- Accept new synthetic items only if they land in under-filled clusters; recluster each round (k grows with the pool).
- Persona conditioning raises surface diversity, not the useful kind; seed-problem variety did more.
- Decontaminate with n-gram first, then embedding-NN + LLM paraphrase check.
**Fit to Crucible Part 2.** §3.5 (meters, quotas), F8/F11, the generator loop (§3.8), and an important caution for F3's persona grounding. Adopt: (a) the validation protocol — before trusting "Vendi on behaviour signatures", show it rank-correlates with held-out-family transfer on small fixed-size task subsets (this is a cheap M-series experiment with a small student); (b) sparse-cell acceptance as the F11 rule (admit into cells below quota; recompute clusters each batch). Adapt: a G-Vendi variant over oracle traces — gradients of the student-family proxy on the oracle action sequence — as a third diversity meter next to signature Vendi; evaluate it before adopting. Avoid: treating persona variety as diversity (§3.5 item 3 should frame personas as realism, with diversity carried by cell and World slice). Interface: `DiversityMeter(kernel="grad:<proxy_id>")`. Priority P1 (P0 for the validation experiment design).

## 2303.09540 — SemDeDup: Data-efficient learning at web-scale through semantic deduplication (Abbas et al., 2023; ICLR 2023 workshop / arXiv)
Read: FULL (body, §6 hyperparameters, §7 cost; appendix algorithm referenced).  Relevance to Part 2: medium. It supplies the scalable algorithm and threshold-tuning recipe for F8's embedding layer; at 500–1000 tasks the scale problem vanishes, but its taxonomy of redundancy and its keep-rule ablations transfer.
**Problem.** Web-scale data is deduplicated only exactly; near-duplicates in meaning waste compute. Can pretrained embeddings find and remove them cheaply without hurting performance?
**Method / algorithm.**
1. Embed each item with a pretrained model (CLIP image encoder for LAION — captions ignored; OPT-125M last-layer last-token embedding for C4 documents).
2. k-means into k clusters (k = 50,000 for LAION-440M; 11,000 for C4) — cost drops from O(n²) to O(n²/k).
3. Within each cluster, all pairwise cosine similarities; a pair with cos ≥ 1 − ε is a semantic duplicate.
4. From each duplicate group keep one item (default: lowest similarity to the centroid) and drop the rest.
5. Tune ε to hit a target dataset size: run on 10% of clusters at two ε values and interpolate (the ε→size relation is near linear).
The paper's four-level redundancy taxonomy: perceptual duplicates (near-identical input), semantic duplicates (same content, different surface — crops, synonym swaps, templated text with one name changed), semantically redundant (different instances of the same concept), misleading data (harmful; not addressed).
**Verification / grading.** Downstream: CLIP ViT-B/16 zero-shot on 30 tasks (24 + 6 ImageNet OOD) and OPT 125M/1.3B perplexity on held-out text and instruction-style prompts; compared with random pruning and NearDup (MinHash).
**Scale & cost.** LAION-440M dedup overhead ≈ 110 GPU-hours at k = 50K, about 0.29 of one training epoch and < 1% of full 32-epoch training (11,541 GPU-h).
**Key results.** LAION-440M: 30% of images have a semantic duplicate at ε = 0.00095, 50% at ε = 0.03; outlier clusters of ~307K EU flags and ~318K "image not found" icons. Removing 37% costs nothing on ImageNet zero-shot; removing 50% costs < 0.5%; average over 24 tasks rises down to 63% kept; OOD average rises at 37% removed and matches at 50%; about 20 of 30 tasks improve. 50% data with 75% of iterations beats the full baseline (IN 69.21 vs 68.74). Random pruning is much worse at equal size. C4: SemDeDup beats random pruning on every validation set and matches NearDup's quality while keeping 80% instead of 96.1%; multi-epoch training on pruned data reaches baseline perplexity with 10–15% less compute. Ablations: k (10K–70K) barely matters; an embedding model trained on different data works equally (66.96 vs 66.90); the keep rule (far from / near centroid / random) is negligible.
**Failure modes & limits.** Authors: does not address misleading data or most semantic redundancy; needs a domain-relevant embedding model; ignores captions; gains smaller on curated text. My critique: ε chosen to hit a size, not a semantic definition — a duplicate threshold should be validated by labelled pairs; for tasks, two items with near-identical instruction embeddings can differ in the one World fact that changes the solution, so embedding dedup can delete legitimate variants.
**Tips & tricks.**
- Cluster first, then compare within clusters; for small pools skip clustering and compare all pairs.
- Tune the threshold on a 10% sample with two probes and linear interpolation.
- Which duplicate you keep barely matters; spend effort on the threshold instead.
- Inspect the largest duplicate clusters; templated "one name swapped" items dominate them.
- Expect the embedding model's training set to matter little for duplicate detection.
**Fit to Crucible Part 2.** F8 layer 2 (embedding similarity) and the herding guard. Adopt the keep-one-per-duplicate-group rule and the redundancy taxonomy as F8's labels (perceptual = MinHash layer; semantic duplicate = embedding layer; semantically redundant = same behaviour signature). Adapt: calibrate the embedding threshold (§3.5 uses AgentFrontier's 0.7 as a start) against a small human-labelled set of task pairs (duplicate / legitimate variant), and never drop on embedding alone when behaviour signatures differ — make the embedding layer a hold-for-review flag, and the signature layer the drop rule. Interface: `DedupDecision{layer, nearest_id, sim, signature_equal, action: drop|hold|keep}`. Priority P1.

## 2504.05228 — NoveltyBench: Evaluating Language Models for Humanlike Diversity (Zhang et al., 2025; COLM 2025)
Read: FULL (body, App. A.1–A.5).  Relevance to Part 2: medium. Not about tasks, but it measures the property that limits every LLM proposer — few functionally distinct outputs per prompt — and supplies the "functional equivalence classes" idea that F8 needs (two tasks are the same if the learner gains nothing from the second).
**Problem.** Benchmarks score the single best generation; they do not measure whether a model can produce multiple distinct, good answers (mode collapse).
**Method / algorithm.**
1. Prompts: NB-Curated (100, authors' own; randomness, underspecified facts, creative writing, subjectivity; 8 human answers each from the authors — a lower bound on human diversity) and NB-WildChat (1,000 from WildChat-1M: Llama Guard filter; dedup by user IP to stop heavy users skewing topics; GPT-4o classifier for "admits many valid answers, English, natural-language output, one clear request"; 85% agreement with 100 human labels).
2. **Functional equivalence:** two generations are equivalent unless a user who saw one would benefit from the other (same plot with new names = equivalent). Authors labelled 1,100 pairs; DeBERTa-v3-large fine-tuned on 1,000 (best ROC-AUC 0.81 vs BLEU/ROUGE/BERTScore and fine-tuned GPT-3.5/4o-mini); held-out accuracy 79% / F1 0.811 in the body (App. A.4 states 71.0% at the chosen threshold — the paper is inconsistent).
3. **Partition:** sequentially assign each new generation to the first class whose random representative it matches; else open a new class. **distinct_k** = number of classes among k samples (k = 10, T = 1).
4. **utility_k** = (1−p)/(1−p^k) · Σ_i p^{i−1} · 1[new class] · u_i, a rank-biased user model with patience p = 0.8; u_i from Skywork-Reward-Gemma-2-27B mapped to 1–10 by matching GPT-4 MT-Bench score distributions. p → 0 recovers single-answer quality.
**Verification / grading.** Classifier vs human pairs; reward model for quality.
**Scale & cost.** 20 models × 1,100 prompts × 10 samples; plus OLMo-2 stage checkpoints and reasoning models.
**Key results.** Distinct out of 10: Claude-3.5 Sonnet 1.76, GPT-4o 2.88, Gemini-2.0-pro 2.25, Llama-3.1-405B 3.20, Llama-3.3-70B 2.49 vs Llama-3.2-1B 6.74, Gemma-2-2B 5.66 (and 9B 3.25 → 27B 3.03). Utility < 4/10 for all closed models. Larger models win at p = 0 but lose utility faster as p rises. Prompting: paraphrasing the prompt and a "produce unique answers" system prompt help only marginally; **in-context regeneration** (keep previous answers in context and ask for a different one) roughly matches the human group's diversity, and GPT-4o / Gemini-2.0-Pro then exceed human utility. OLMo-2: each post-training stage (SFT → DPO → RLVR) lowers diversity, the largest drop at DPO, while utility rises SFT→DPO. OpenAI reasoning models: more reasoning effort → lower diversity and utility.
**Failure modes & limits.** Authors: whether users want diversity is prompt-dependent (car advice vs dice); homogeneous annotators. My critique: the equivalence classifier is trained on creative/chat text and is ~0.8 accurate, so distinct_k has noticeable noise; sequential first-match assignment is order-dependent; reward-model utility is a weak quality proxy; T = 1 is best-case — real swarm runs at lower T will be worse.
**Tips & tricks.**
- Measure diversity as functional equivalence classes (would seeing the second add value?), not lexical distance.
- Use distinct_k at fixed k plus a patience-weighted utility so diversity never trades away quality silently.
- Paraphrasing the request or telling the model to be unique barely helps.
- Put prior outputs in context and ask for a different one — the only prompting fix that reached human-level diversity.
- Expect post-training (especially preference optimisation) and more reasoning effort to shrink diversity.
- When mining real prompts, dedup by user to stop heavy users dominating.
**Fit to Crucible Part 2.** F3 and §3.5 item 3 (grounding), F8 (equivalence), §3.9 (swarm sizing). Adopt in-context regeneration for F3: show the proposer the K nearest existing tasks in the cell *and its own earlier proposals in this batch* and ask for one that differs — the evidence here backs the AZR "dynamic references" point. Adopt functional equivalence as F8's definition: two tasks are duplicates when the learner would gain nothing from the second, operationalised by equal `BehaviourSignature` (not a text classifier). Add a per-generator `distinct_k` meter: sample k proposals for one cell and count signature classes — a cheap mode-collapse probe per swarm model. Caution for role assignment: larger proposers are not more diverse; a smaller model may be the better breadth proposer, with a larger one as verifier. Priority P1.

## 2510.22954 — Artificial Hivemind: The Open-Ended Homogeneity of Language Models (and Beyond) (Jiang et al., 2025; NeurIPS 2025 D&B)
Read: FULL (body; App. A discussion, C.1–C.4 setup and paraphrase study; the long result tables in C and D skimmed).  Relevance to Part 2: high as a constraint. It is the evidence behind §3.5's caveat that mixing model families is not diversity, and that LLM judges and reward models are least reliable exactly where several answers are equally good.
**Problem.** Mode collapse is studied on toy tasks with one model. On real open-ended queries, do single models repeat themselves, do different models converge on the same outputs, and are LMs/RMs/judges calibrated where humans disagree?
**Method / algorithm.**
1. **Infinity-Chat:** 37,426 single-turn English WildChat GPT-4 queries (15–200 chars, non-toxic) → GPT-4o classifies meaningful vs greeting, single vs multiple valid answers; ambiguous ones are rewritten → 26,070 open-ended + 8,817 closed-ended queries. Taxonomy: hand-label ~100, iterate into 6 top-level / 17 sub-categories, then GPT-4o multi-labels all queries and proposes new types (314 novel categories found; human agreement with GPT-4o labels 74.7%). Creative content 58.0%, alternative genres 38.5%, concept explanation 23.6%, skill development 23.5%, brainstorming 15.2%.
2. **Intra-model repetition:** Infinity-Chat100 (human-verified open-ended); 50 samples per query per model (top-p 0.9, T 1.0; and min-p 0.1, T 2.0); mean pairwise cosine of text-embedding-3-small embeddings per query's pool.
3. **Inter-model homogeneity:** mean cross-model similarity; and for each query, the number of distinct source models among the top-N most similar responses (with fully disjoint models, the top-50 would come from one model).
4. **Paraphrase probe:** 30 prompts × 4 GPT-4.1 paraphrases × 20 responses × 42 models.
5. **Calibration:** dense human labels — 25 annotators per item: 18,750 absolute ratings (50 prompts × 15 responses) and 12,500 pairwise labels (50 × 10 pairs). Compare with 56 LMs (perplexity), 6 reward models, 4 LM judges (overall and HHH rubrics) on the full set, on similar-quality subsets (Tukey-fence filtering, k 0.5–3.0; or top-x% judged-similar pairs) and on high-disagreement subsets (top-entropy items; P_disagree = 1 − (max(prefer1, prefer2) + 0.5·tie)/total).
**Verification / grading.** Embedding cosine for similarity (acknowledged as limited); human labels for quality.
**Scale & cost.** 70+ models (25 in main text); 26K queries; 31,250 human annotations.
**Key results.** Intra: in 79% of queries the same model's 50 responses average > 0.8 similarity at T = 1 (random cross-pool pairs sit at 0.1–0.2); min-p at T = 2 still leaves 81% of pairs > 0.7 and 61.2% > 0.8. Inter: cross-model mean similarity 0.71–0.82 (DeepSeek-V3 vs qwen-max 0.82; DeepSeek-V3 vs GPT-4o 0.81); GPT and Qwen API models are similar even to other families; verbatim shared phrases across vendors; identical mottos from two Qwen models; ~8 distinct models in a typical top-50 similarity cluster (some > 10) — inter-model can exceed intra-model similarity. 25 models × 50 metaphors about time form two clusters ("river", "weaver"). Paraphrases barely help: within-prompt 0.821 vs cross-paraphrase 0.781. Calibration: correlations of LM, RM and judge scores with mean human ratings drop markedly on similar-quality and high-disagreement subsets, in both absolute and pairwise setups.
**Failure modes & limits.** Authors: English only; embedding similarity under-expresses creative variation; no causal account (shared data, synthetic contamination, alignment). My critique: open-ended creative prompts are the worst case — task proposals constrained by a World slice may diverge more; but the paraphrase result suggests rewording the generator prompt will not fix convergence; the judge-calibration result is on subjective quality, yet the same mechanism (judges collapse distinctions between equally valid outputs) applies to LLM-judged realism and "interestingness".
**Tips & tricks.**
- Measure diversity inside one model and across models separately; ensembles inherit shared priors.
- Use "distinct sources among the top-N nearest items" as a quick cross-generator homogeneity check.
- High temperature or min-p does not cure collapse; neither does paraphrasing the prompt.
- Do not trust a judge or reward model to rank among equally valid alternatives; check its calibration on high-disagreement items.
- Densely label a few items (25 raters) to see disagreement, instead of sparsely labelling many.
**Fit to Crucible Part 2.** §3.5 (the homogeneity caveat), §3.9 (swarm), F11 interestingness judge, F10/§3.8 judges. Adopt: never count model-family mix as a diversity mechanism; the diversity must come from exogenous structure (sampled cell, World slice, K nearest exemplars, quotas). Add the "distinct generator families among the top-N nearest neighbours" statistic to the per-batch meters to detect cross-family convergence. Caution for F11: the OMNI-EPIC-style interestingness judge is exactly the miscalibrated-judge case; use it only to reject near-copies, never to rank among valid alternatives, and calibrate it on a densely labelled set. Caution for G14 (alternatives): "two alternatives from different families" may be the same solution; check that their action traces differ. Priority P0 (as a design constraint; no build cost).

## 2510.01171 — Verbalized Sampling: How to Mitigate Mode Collapse and Unlock LLM Diversity (Zhang et al., 2025; arXiv, ICML-format)
Read: FULL (body; App. B, C, F.1–F.5, E.7 positive and negative synthetic data, G.2 cost; theory App. D skimmed).  Relevance to Part 2: high (cheap, directly usable in F3 and F5). It is the paper behind §3.5 item 3's "ask for several candidates with stated probabilities"; the card corrects one detail of the plan — the paper samples from or thresholds the verbalized distribution, it does not "keep the least typical valid one".
**Problem.** Aligned models collapse to a few typical outputs. The authors argue a data-level cause — annotators' typicality bias — and seek a training-free fix.
**Method / algorithm.**
*Theory.* Model the reward as r = r_true + α·log π_ref(y|x) + ε. On 6,874 correctness-matched HelpSteer pairs, a logistic fit gives α̂ = 0.57 ± 0.07 (Llama-3.1-405B base) and 0.65 ± 0.07 (GLM-4.5 base), p < 10⁻¹⁴; still significant with length/readability controls. With KL-regularised RLHF the optimum is π* ∝ π_ref^γ exp(r_true/β), γ = 1 + α/β > 1: wherever true utility is flat across valid answers, the policy sharpens toward the base model's mode (temperature-like). Instance prompts collapse to one mode; list prompts ("give 5") collapse to the top-k modes; distribution prompts make "a representative distribution" the modal answer, so diversity returns.
*VS prompting variants* (budget of N total outputs, k per call): **VS-Standard** — "generate k responses with their probabilities"; **VS-CoT** — reason first, then the same; **VS-Multi** — multi-turn, "k more with probabilities". **Tail tuning** — "sample from the tail, each response < p" with p ∈ {1, 0.9, 0.5, 0.2, 0.05, 0.005, 0.001}; lower p → more diversity. In dialogue simulation, the next turn is picked either uniformly from model-decided candidates or probability-weighted from k = 5.
**Verification / grading.** Semantic diversity = 1 − mean pairwise cosine (text-embedding-3-small), lexical = ROUGE-L; quality by Claude-3.7-Sonnet judge with Creative Writing v3 and HumorBench rubrics; human study on Prolific (90 raters); dialogue realism by KS test and L1 on donation amounts; synthetic math by downstream accuracy with Math-Verify.
**Scale & cost.** Creative tasks: 100 prompts, k = 5, N = 30. Cost (poem, 2,000 responses): VS-Standard +12% cost for +86% diversity relative to direct; sequence prompting +11% cost, +56%.
**Key results.** Creative writing: diversity 1.6–2.1× direct; human-rated diversity (1–4) poem 1.90 → 2.39, story 2.74 → 3.06, joke 1.83 → 3.01; quality comparable; VS-CoT and VS-Multi approach the Pareto front. Larger models gain 1.5–2× more diversity from VS than smaller ones, and lose less quality (small models sometimes degrade). Tulu-3-70B stages: direct prompting diversity 20.8% after SFT → 10.8% after DPO; VS stays ≈ 30% and keeps 66.8% of base diversity (direct 23.8%). k from 1 to 20 raises diversity and slightly lowers quality; VS is orthogonal to temperature, top-p (best ≈ 0.95) and min-p. Synthetic math (1K questions from GPT-4.1/Gemini-2.5-Flash, solutions by Qwen3-32B, LIMO-style SFT): average across 3 benchmarks and 3 students — direct 30.6 (below the no-SFT baseline 32.8), sequence 34.3, VS-Standard 36.1, VS-Multi 37.5. Negative data (plausible wrong GSM8K solutions): direct follows the instruction only 34% of the time and collapses to one wrong answer; VS-CoT reaches 0.89 incorrect-rate and 0.57 coverage of distinct wrong answers; offline RL with 1K positive + 1K VS negatives 36.63 vs 34.12 positive-only. Verbalized distributions match a pretraining-corpus proxy with KL 0.12. Factuality and safety unchanged.
**Failure modes & limits.** Authors: more tokens and latency per call; small models gain less and can lose quality. My critique: verbalized probabilities are not calibrated likelihoods — they are a steering device; diversity measured by embeddings (surface); the gains are largest where many answers are equally valid, which is not true of an over-constrained task proposal; the theory assumes flat r_true and a Bradley–Terry reward with KL, not a constrained generator.
**Tips & tricks.**
- Ask for k candidates with probabilities (k ≈ 5) instead of one, or a plain list of k.
- Use "tail" thresholds in the prompt as a diversity dial; no decoding access needed.
- Multi-turn "k more with probabilities" (VS-Multi) gives the best diversity–quality balance on strong models.
- Larger generators benefit more; for small generators check quality.
- VS also generates varied *wrong* answers — a cheap source of diverse negatives.
- Combine with top-p ≈ 0.95; it stacks with decoding knobs.
**Fit to Crucible Part 2.** F3 (proposal), F5 (negatives), the simulated user (People), §3.9 (proposer roles). Adopt VS-Multi for F3: per cell, ask for k = 5 proposals with probabilities, in turns, with the K nearest tasks in context; take candidates in a mix of high- and low-probability (and use tail thresholds when a cell's fill stalls) — then let F7's measured signature, not the stated probability, decide novelty. Correct §3.5 item 3 wording accordingly. Adopt VS for F5's "wrong" and "shortcut" negative classes: ask for k plausible wrong end states or wrong action programs with probabilities, which raises negative coverage (0.57 distinct vs collapse to one). Use probability-weighted VS sampling in the People simulator to avoid identical persona replies across episodes. Interface: `TaskProposal.verbalized_p`, `proposal_batch_id`, `turn`. Priority P0 (prompt-level, near-zero cost).

## 2010.03934 — Prioritized Level Replay (Jiang, Grefenstette & Rocktäschel, 2020; ICML 2021)
Read: FULL (body, Algs. 1–2, Table 1 scoring functions; App. B.3 referenced).  Relevance to Part 2: high for F11/F12. PLR is the template for an in-training sampler over a fixed task pool: score each task by recent learning potential, rank-prioritise, and mix in staleness so stale scores get refreshed.
**Problem.** Procedurally generated levels are sampled uniformly during training, although what a level can teach depends on the current policy. Can sampling by estimated learning potential improve sample efficiency and generalization, with no control over the generator?
**Method / algorithm.** Requirements only: levels share dynamics, have identifiers, and can be replayed by id.
1. Each episode: draw a replay decision d ~ Bernoulli(P_D). With a finite train set, P_D(replay) = |seen|/|train| (anneals toward replay). If d = 0 and unseen levels remain, take a new level uniformly (score 0, timestamp 0); else sample from P_replay.
2. **P_replay = (1−ρ)·P_S + ρ·P_C.**
   - Score S_i after each episode on level i = mean over t of |GAE_t| = mean |Σ_k (γλ)^{k−t} δ_k| (equivalently the L1 value loss under PPO-GAE).
   - **Rank prioritisation:** h(S_i) = 1/rank(S_i), P_S ∝ h(S_i)^{1/β}, β = 0.1. (Proportional and greedy did worse.)
   - **Staleness:** P_C ∝ c − C_i, where c is the global episode count and C_i the last time level i was played. ρ = 0.1 (Procgen), 0.3 (MiniGrid). Gains appear only with 0 < ρ < 1.
3. Unbounded level spaces: keep a rolling buffer of the top-scoring levels (App. B.3).
4. **Value Correction Hypothesis:** with sparse rewards, levels at the edge of ability have non-stationary returns and hence high value error; too-hard levels have stationary failure and low error; so value loss tracks the frontier without any difficulty label. Scores must fall with repeated visits, else the replay distribution collapses onto few levels.
**Verification / grading.** Environment returns; test on 100 unseen levels per game; 10 runs (Procgen), Welch t-test p < 0.05; generalization gap = train − test return.
**Scale & cost.** Procgen: 16 games, 200 training levels, 25M steps, PPO. MiniGrid: ~1,000 levels per difficulty. Negligible overhead (bookkeeping only).
**Key results.** Procgen easy: normalized test return PLR 128.3% of uniform (significant gains on 10/16 games), UCB-DrAC 129.8%, UCB-DrAC + PLR 176.4% (+76% vs PPO, +28% vs previous SOTA); hard setting +35% alone, +83% combined. Alternative scores (policy entropy, min-margin, least confidence, 1-step TD, signed GAE) and TSCL (return slope) are inconsistent across games; TSCL hurts StarPilot. MiniGrid ObstructedMazeGamut-Easy 0.53 → 0.85, Medium 0.65 → 0.73; probability mass moves to harder bins over training (an emergent curriculum); with 6,000 training levels PLR beats uniform sampling over the full ~4-billion-level space.
**Failure modes & limits.** Authors: needs resettable, seed-addressable simulators; slow to find a curriculum early (~4,000 updates on Medium); the best score function may not be value loss. My critique: GRPO-style LLM RL has no value function, so the score must be replaced (group reward variance p̂(1−p̂), or |advantage| mean); PLR only re-weights an existing pool — it creates no new tasks; replaying the same task many times in LLM RL risks memorisation of a specific trace.
**Tips & tricks.**
- Prioritise by rank, not raw score; it is robust to score scale.
- Always mix in staleness (ρ ≈ 0.1–0.3); without it scores drift off-policy and gains vanish.
- Anneal the probability of new-vs-replay by the fraction of the pool seen.
- Use a learning-potential score that falls as a task is mastered, so the sampler does not collapse.
- Track sampled-difficulty mass over time as a curriculum diagnostic.
- For unbounded generators keep a top-k buffer by score.
**Fit to Crucible Part 2.** F11 (pool → curriculum), F12 (feedback), §3.6 (per-student p̂). Adopt PLR as the default sampler over the kept pool during RL: score = discounted group success variance p̂(1−p̂) per (task, student, checkpoint) — matching §3.6's objective — with rank prioritisation β = 0.1 and staleness ρ = 0.1–0.3; new tasks enter with a fresh-task probability that anneals with pool coverage. Feed the sampler's per-task scores back to F12 as `p_hat_updates` and as "drifting cells" (cells whose sampled mass collapses). Interface: `SamplerState{task_id, student_id, score, last_seen_step, visits}`. Avoid reading PLR as a task generator; pair it with ACCEL/PAIRED-style editing (separate cards) for that. Priority P1 (training-side; small build).

## 2012.02096 — Emergent Complexity and Zero-shot Transfer via Unsupervised Environment Design (PAIRED) (Dennis, Jaques et al., 2020; NeurIPS 2020)
Read: FULL (body, App. E alternative regret estimators, F hyperparameters).  Relevance to Part 2: high conceptually. PAIRED is the cleanest statement of *why* a task generator must be scored by regret (a capable reference solves it, the student does not) rather than by student failure alone — the same logic as Crucible's "solvable by construction + frontier audit + student band".
**Problem.** Domain randomization cannot adapt difficulty or produce structure; a minimax adversary that minimises the student's return produces unsolvable environments. Need a generator that makes hard-but-solvable environments tailored to the learner.
**Method / algorithm.**
- **UED formalism.** An underspecified POMDP (UPOMDP) has free parameters Θ; an environment policy Λ: Π → Δ(Θ^T) maps the current agent policy to a distribution over fully specified environments. Decision-theory reading: DR = insufficient reason (uniform), minimax = maximin, PAIRED = minimax regret (Savage). Thm 1: when success and failure rewards are separated, minimax regret picks a policy that succeeds whenever success is possible.
- **PAIRED (Alg. 1)** per batch: the adversary samples θ; protagonist πP and antagonist πA (allied with the adversary) each roll out several episodes; **Regret ≈ max over antagonist episodes U(τA) − mean over protagonist episodes U(τP)**. Adversary and antagonist maximise regret, protagonist minimises it (or just maximises its own reward — App. E.2 found env reward better for complexity, regret-trained agents better for transfer). Thm 2: at a Nash equilibrium where (antagonist, adversary) is a joint best response, the protagonist plays a minimax-regret policy.
- **Why it curricularises.** If unsolvable, both agents fail and regret is 0, so the adversary gains nothing; with an efficiency bonus the antagonist scores more on easier tasks, so the adversary is drawn to the *easiest task the protagonist still fails* — the zone of proximal development; as the protagonist improves, the adversary must build harder ones.
- Navigation implementation: 15×15 grid; adversary sees the full grid, time step and a noise vector z ∈ R^50; places agent, goal, then up to 50 walls (169-way action per step); all trained with PPO. Non-negative regret max(0, R) worked best; protagonist episode length 250.
**Verification / grading.** Environment reward; complexity tracked by blocks, goal distance, shortest passable path, and longest solved path; zero-shot transfer on hand-designed maps (Empty, 50 Blocks, 4 Rooms, 16 Rooms, Labyrinth, Maze), 10 trials × 5 seeds. MuJoCo hopper with adversarial joint torques.
**Scale & cost.** Small (grid, PPO, 30 parallel workers); 5 seeds per method; grid search shared across methods.
**Key results.** Only PAIRED keeps increasing passable and solved path length over training; DR and minimax (including a population-based POET-like variant with 3 adversaries × 3 agents) plateau at similar solved lengths. Transfer: Labyrinth 40% (PAIRED) vs 10% (minimax) vs 0% (DR); Maze 18% vs 0% vs 0%. Hopper: once the adversary's strength cap is removed (after 300 iterations), minimax drives reward to zero; PAIRED stays solvable and is more robust to unseen mass/friction. Ablations: an adversary parameterisation whose random policy mostly makes infeasible maps fails (solved length ≈ 2 vs ≈ 15) — random generators must start feasible. Population/flexible antagonists that break adversary–antagonist coordination did worse.
**Failure modes & limits.** Authors: multi-agent training may not converge; the regret estimate is noisy; UED is unnecessary when the test distribution is known. My critique (and later literature, e.g. ACCEL/PLR⊥): the antagonist must stay stronger than the protagonist or regret collapses; a learned RL adversary is sample-hungry; it maximises regret, not diversity, so it can fixate on one exploit; regret against a weak antagonist under-estimates true regret.
**Tips & tricks.**
- Score a generated task by (best reference return − mean student return), not by student failure; unsolvable tasks then score zero automatically.
- Use max over several reference attempts minus mean over student attempts to cut noise; clip at zero.
- Make sure a random generator already produces mostly feasible instances.
- Keep the reference solver fixed/coordinated with the generator; swapping it each round weakened the curriculum.
- Track structural complexity of generated instances and longest-solved as curriculum diagnostics.
**Fit to Crucible Part 2.** F9 (difficulty), §3.6 too-hard/too-easy routing, §3.8 task loop, self-play source (§3.4). Adopt regret as the *task-value* score: regret(t, student) = (frontier or oracle pass rate) − student p̂ — with the oracle by construction giving the upper term 1 — and route tasks with high regret and p̂ in band to the pool; tasks where the frontier also fails are not "high regret" but suspects (consistent with §3.7's zero-solve rule). Adapt: Crucible's generator is an LLM proposer, not an RL adversary; use regret as the controller's selection signal over knob vectors (bandit over knobs) rather than training a generator by RL. Note for the 35B → 397B shift: the antagonist must be stronger than each student, so for the 397B the regret reference has to be the oracle plus a stronger frontier, or regret saturates. Interface: `DifficultyRecord.regret = ref_pass − student_pass` per student. Priority P1.

## 2203.01302 — Evolving Curricula with Regret-Based Environment Design (ACCEL) (Parker-Holder, Jiang et al., 2022; ICML 2022)
Read: FULL (body; App. B.2–B.3 lineage analysis, C.2 editing, C.3 hyperparameters).  Relevance to Part 2: high. ACCEL is the closest RL-literature analogue of Crucible's "too easy → mutate along a knob, keep the variant only if it is at the frontier" task loop; its lineage results show that small edits of frontier tasks compound into hard, solvable, diverse tasks.
**Problem.** PAIRED's learned teacher is hard to train; PLR only curates random levels and cannot build on structures it has found, which fails in high-dimensional design spaces. POET evolves levels but needs agent populations, domain thresholds and huge compute.
**Method / algorithm (Alg. 1).**
1. Level replay buffer Λ of size K (4,000–10,000); fill K·ρ initially from the generator (or from the simplest base level — "start simple": empty rooms, flat terrain).
2. Each step, replay decision d ~ P_D (replay rate 0.8–0.9):
   - d = 0: sample a new level from the generator; roll out with stop-gradient (no training); score it; insert into Λ if the score clears the buffer threshold (i.e. beats the lowest score).
   - d = 1: sample θ from Λ (PLR rank + staleness), roll out and **train** on it; then **edit** θ → θ′ (a handful of random add/remove-obstacle operations, or a goal move); roll out θ′ with stop-gradient; score both; insert θ′ if its score qualifies. Optionally train the editor on the score (they tried an RL editor maximising positive value loss; random edits were competitive).
3. Score = **positive value loss** (1/T)·Σ_t max(Σ_k (γλ)^{k−t} δ_k, 0), a regret proxy. The student trains only on curated (replayed) levels — a counter-intuitive "train on less data" that inherits PLR's minimax-regret guarantee at equilibrium (Remark 1).
4. Key assumption: regret is smooth in parameter space, so edits of a high-regret level yield batches of high-regret levels. Lineages: a level can be edited up to 40+ times; generations stay at the frontier for the checkpoint that sees them.
**Verification / grading.** Environment reward; zero-shot transfer on human-designed mazes and a 51×51 PerfectMaze (5k-step episodes); BipedalWalker on Stump, PitGap, Stairs, Roughness, Hardcore and POET-threshold "extremely challenging" levels; rliable IQM and optimality gap; 5–10 seeds.
**Scale & cost.** Single GPU. MiniGrid 20k PPO updates ≈ 350M steps; BipedalWalker 30k updates ≈ 2.07B steps, < 0.5% of POET's samples.
**Key results.** Mazes: aggregate IQM solved rate near 100% vs < 80% for Robust PLR (80.2% probability of improvement); PerfectMaze 51×51 53% vs PLR 25%, others 0%. BipedalWalker (8D): ~75% of optimal, ~3× PLR; ALP-GMM collapses in 8D. 5D BipedalWalker at 50k updates — Stump 0.44 vs PLR 0.04; Roughness 0.73 vs 0.23; Hardcore 0.65 vs 0.21; extremely challenging 0.12 vs 0.01 (ALP-GMM 0.02); the buffer fills with "extremely challenging" levels without POET's novelty bonus or stepping stones. Ablation (PLR → PLR+Edit → PLR+Edit+StartSimple): editing helps in both domains; starting simple matters most for BipedalWalker. Edits that keep the optimal path but change observations act as data augmentation; sibling edits of one parent demand different behaviours.
**Failure modes & limits.** Authors: no explicit diversity mechanism — larger design spaces may need one; "start simple" requires a known simplest level. My critique: random edits are cheap in grids; in Crucible an edit is an LLM rewrite plus a full re-gate (F4–F6), so per-edit cost is high and must be paid only for frontier parents; positive value loss requires a critic; the buffer can fill with near-identical descendants of one lineage without a novelty check.
**Tips & tricks.**
- Evaluate edited children before training on them; admit only those that beat the buffer's lowest score.
- Edit only replayed frontier levels; random edits are a strong baseline for a learned editor.
- Start from the simplest instance and let edits compound difficulty.
- Track lineage (parent, generation) and test old checkpoints on late generations to confirm the frontier moved.
- Edits that preserve the solution are free augmentation; edits that change it are new tasks — label them differently.
**Fit to Crucible Part 2.** §3.6 (too-easy mutate, ladders), §3.8 task loop, F11 archive, self-play source. Adopt the ACCEL loop as the task loop's core: parent = in-pool task whose student p̂ has risen above band; edit = a knob change (count, linkage, distractors, horizon, observability, hint removal); child goes through F4–F7 (oracle re-run, verifier regen, gates, signature) and enters the pool only if p̂ for the target student lands in band and its signature differs from the parent's on the changed knob. Keep lineage fields (`parent_id`, `generation`, `edit_ops`) and enforce a lineage cap per cell to stop one family dominating (the missing diversity mechanism). "Start simple" maps to building a family's first instance at knob minimum and climbing. Solution-preserving edits (renames, distractor reorderings) become augmentation variants, not new tasks, and should be deduped as such in F8. Priority P1 (core of the task loop).

## 2502.07709 — MAGELLAN: Metacognitive predictions of learning progress guide autotelic LLM agents in large goal spaces (Gaven et al., 2025; ICML 2025)
Read: FULL (body; App. C.2 hyperparameters, C.4 compute, D.1 architecture ablations).  Relevance to Part 2: high for F9 and F12. It is the method §3.6 cites for "rank candidates by a cheap predictor before any rollout"; it shows a learned, goal-conditioned competence predictor generalises to unseen tasks and tracks learning progress without extra evaluation episodes.
**Problem.** Learning-progress (LP) curricula need per-goal competence estimates; in large discrete language goal spaces, re-evaluating every goal is too costly, online per-goal estimates cannot see transfer between goals, and expert-defined groups are brittle.
**Method / algorithm.**
1. Competence predictor C_θ(g): the goal prompt (same text the policy sees: goal, scene, inventory) → LLM last-token hidden state → 1-layer MLP (128 units, tanh) → success probability. Trained with BCE on a buffer D of the last M = 5,000 (goal, binary outcome) pairs, sampling recent items with weight ∝ position (recency-biased), batch 256, Adam 1e-4, updated every 32 policy updates. **The LLM is fine-tuned too** (its own LoRA adapter, separate from the policy's) — semantically similar goals then share estimates.
2. Keep the last N = 100 snapshots of the predictor's weights; **ALP(g) = |C_θt(g) − C_θ(t−N)(g)|** (absolute LP captures progress and forgetting).
3. Goal selection: multi-armed bandit (Lopes & Oudeyer) sampling goals ∝ ALP with ε-greedy, ε annealed 1 → 0.2 over 320 steps.
4. Baselines: Eval-ALP (periodic evaluation of every goal; accurate but costly), EK-Eval-ALP (evaluation per expert group), Online-ALP (per-goal buffer of the last 2M outcomes; no transfer), EK-Online-ALP (per expert group).
Testbed Little-Zoo: text world with a hidden tech tree (grasp, grow plant, grow herbivore, grow carnivore); ~20M goals, of which 80% are infeasible (feasibility depends on the scene's objects), sampled as 80/16/3.2/0.7/0.1%. Policy: SAC-GLAM fine-tuning Flan-T5-248M.
**Verification / grading.** Deterministic environment success. Competence error vs an EK-Eval reference (2,048 per-group evaluations per 1,000 episodes); held-out goals; goal-space replacement every 50K episodes.
**Scale & cost.** 500K episodes per seed, 8 seeds; 80 H100-hours per seed per method (2 GPUs). Predictor adds no evaluation episodes.
**Key results.** Competence error on par with Eval-ALP at 25K/50K/100K goals with zero evaluation cost; on simulated OpenR1-Math skill acquisition (algebra → geometry → number theory) it tracks true competence, Online-ALP does not. Training: MAGELLAN is the only method without expert groups to reach ≥ 90% SR on all four categories, significantly earlier than Online-ALP (p < 8×10⁻⁴); EK-Online-ALP is faster because its groups discard infeasible goals. Held-out goals: mean |observed − predicted| competence 0.11 (MAGELLAN) vs 0.53 (Online-ALP) vs 0.09 (EK). After training, the embedding space clusters goals by type and separates infeasible goals, even by infeasibility reason; newly learned goals sit near the infeasible boundary. Goal-space swap: when some goals have high ALP, MAGELLAN transfers and keeps training on them, matching EK. Ablations: frozen LLM representation → plateau at "grow plant"; shared adapter with the policy → slower (never masters carnivores); separate adapters best.
**Failure modes & limits.** Authors: small model, controlled testbed; do not generalise to real settings. My critique: needs many binary outcomes (thousands) before estimates are useful — Crucible has 8 rollouts per task; ALP from weight snapshots measures predictor change as well as learner change; the predictor is trained on the learner's own outcomes, so before any rollout it predicts nothing for a new student — it must be warm-started from another student or from task features.
**Tips & tricks.**
- Predict competence with a goal-conditioned model that shares statistical strength across similar tasks; fine-tune its representation.
- Keep it separate from the policy (own adapter/model).
- Use absolute LP (|now − then|) to catch forgetting, sampled ∝ ALP with an annealed ε floor.
- Weight the training buffer toward recent outcomes; snapshot the predictor to compute LP without re-evaluation.
- Expect infeasible tasks to cluster in the predictor's space — a free defect detector.
- Explore over groups (not raw goals) when most of the space is infeasible.
**Fit to Crucible Part 2.** F9 predictor stage, F12 feedback, PLR-style sampler (F11), and a defect signal for F10. Adopt: a per-student competence predictor p̂_pred(task, student) trained on all F9 outcomes (task text + signature features → pass probability), updated continuously; use it (a) to rank candidates before the paid k = 4 sequential measurement (§3.10 lever 2), (b) to generalise p̂ to unmeasured tasks for band planning, (c) to compute ALP per cell during RL for F12's "drifting cells". Adapt for small data: start from the existing advisory predictor (MAE 0.204) features; warm-start the 397B predictor from the 35B's outcomes with a student-id feature. Use "tasks the predictor places in an infeasible cluster" as a hint that a task may be broken (feeds §3.7 zero-solve suspicion). Interface: `DifficultyRecord.predictor_score`, `predictor_version`, and `ALP(cell, window)`. Priority P1.

## 2411.01775 — Eurekaverse: Environment Curriculum Generation via Large Language Models (Liang et al., 2024; CoRL 2024)
Read: FULL (body; App. A.1 algorithm and soft selection, A.4 environment check, A.5–A.6, A.8 ablations).  Relevance to Part 2: medium. It shows an LLM writing environment code as a curriculum, with performance feedback in the evolve prompt; the domain (quadruped parkour) is far from Crucible, but the ablations (no-feedback, diversity-only, initial-only, final-only) isolate what an LLM environment generator needs.
**Problem.** Hand-designing a curriculum of training environments needs domain expertise per task; parameter-only UED cannot express structured terrain. Can an LLM write and evolve environment programs as a curriculum?
**Method / algorithm (Alg. 1).**
1. **Initial generation:** GPT-4o gets a task description and one in-context terrain program (Python: height-field grid + 8 goal coordinates, a function of a difficulty argument); sample N·J programs at non-zero temperature.
2. **Environment check:** executable, and feasibility heuristics (max height < 3 m; height jump between goals < 0.8 m ≈ 2× robot height); > 50% of GPT-4o terrains pass. Common failures: unit mis-scaling, out-of-bounds indexing, missing helpers. Cheap automatic fixes (move out-of-bounds goals, flatten the spawn area, widen too-thin obstacles).
3. **Policy evolution:** train N = 8 PPO agents in parallel, each on its own library of J terrains (each terrain at 10 difficulties with promote/demote: promote at 0.8·8 goals, demote below 0.4·8, stay with p = 0.75); evaluate every agent on the union of all generated terrains so far (proxy set) and pick the best; **soft selection** — next round's agents initialise from the best with p1, the second with p2 < p1, etc.
4. **Environment evolution:** take the terrains that trained π_best; for each, prompt the LLM with that program, environment statistics (e.g. max height difference), policy training statistics (reward terms, success rate) and an in-context evolution example; ask for a variation. 5 iterations × 8 runs × 2,000 steps.
5. (Removed in final version) learning-progress resampling of old terrains — unnecessary once the inner difficulty schedule was tuned for diversity.
**Verification / grading.** 20 held-out simulated parkour tasks × 10 difficulties (not shown to the LLM); real-world Go1 trials (10 per difficulty).
**Scale & cost.** One run ≈ 24 h on 8 A6000s, ≈ $15 of OpenAI API.
**Key results.** Final policy reaches ~2 more goals than one trained on human-designed terrains (which learn fast then plateau) and nearly matches an oracle trained on the test set; random obstacles learn nothing. Ablations all plateau or degrade: **No Feedback** (always "make it harder") improves early then degrades as terrains outrun the policy; **Diversity Only** (sequentially generated to be different, no adaptation) underperforms; **Initial Envs** and **Final Envs** alone underperform (final ones are too hard for a beginner); the in-context example alone underperforms. Real world: jumps up to 75 cm, climbs over 50 cm, 30° ramps, full staircase; the human-designed policy tripped motor protection and damaged hardware on ramps.
**Failure modes & limits.** Authors: needs a moderate number of LLM samples; text-only feedback. My critique: the evaluator is the policy's own proxy set (generated terrains), which the LLM may bias; the feasibility check is two hand thresholds — domain knowledge returns through the checker; with 8 runs × 5 iterations and 3 seeds the evidence is thin; selection of the "best" policy by proxy is itself a curriculum choice.
**Tips & tricks.**
- Put the learner's success rate and per-reward-term stats into the evolve prompt; "make it harder" without feedback overshoots.
- Evolve from the environments that produced the best learner, not from all environments.
- Run a cheap executability + feasibility check and auto-fix common generator errors before any training.
- Parameterise each generated environment by a difficulty argument so one program yields a ladder.
- Neither diversity alone nor hardness alone is enough; the curriculum must track the learner.
- Soft selection (sample among top policies) protects against a noisy proxy.
**Fit to Crucible Part 2.** F1/F3 (LLM writes environment or task code), F6 (cheap checks first), §3.6 (difficulty argument as knob), §3.8 task loop. Adopt: require every generated task or World program to expose a `difficulty`/knob argument so a family yields a ladder (matches `DomainSpec.knobs`); include student p̂ and failure-cluster summaries in the F3 "variant of task T" prompt (the No Feedback ablation is the evidence that the task loop must condition on p̂, not just ask for harder); keep the >50% executability rate as a planning prior for F1/F4 repair rounds. Avoid: proxy-set self-evaluation as the sole selection signal — Crucible's held-out families serve this role. Priority P2 (supports existing design; nothing new to build).

## 2606.24855 — Data Recipes for Agentic Models (OpenThoughts-Agent) (Raoof, Zhuang et al., 2026; arXiv)

The largest controlled ablation of agentic task *sources* to date, plus an RL data-source study; its stage-by-stage ablation protocol is what §3.8's generator loop should copy, and several of its findings (augmentation fails at small scale, source tail hurts, longer traces help, LLM-verified RL tasks compact rather than explore) bear directly on Crucible.

- **Six-stage SFT pipeline, each stage ablated independently** at a fixed 10K-trajectory budget: (1) task sourcing (95 strategies), (2) mixing, (3) task augmentation, (4) task filtering, (5) teacher, (6) rollout filtering. - Mixing: Top-N strategies, 10K/N tasks each, random shuffle or round-robin.
- Augmentation tried: LLM combination of tasks, adding constraints, hardening, etc.

- Rollout filters: drop timeouts, subagent traces, < 5 turns.
- Scaling to 100K: (1) more rollouts per task; (2) more tasks from the same sources; (3) synthetic augmentation; (4) more sources.

**Scale & cost.** > 100 ablations; 95 task strategies; final 100K traces; 160 GPU-h per 10K ablation.

- Do not assume rewriting/hardening improves tasks; test it.
- Frontier token spend on a task is a cheap difficulty/value proxy (+3 pp).
- Choose the teacher by downstream student results, not leaderboard rank.
- Prefer longer multi-turn traces; control for tokens when claiming it.
- When rollouts-per-task plateau, add distinct task descriptions, not more samples.

## 2506.14205 — AgentSynth: Scalable Task Generation for Generalist Computer-Use Agents (Xie et al., 2025; Berkeley, arXiv / ICLR submission)
Read: FULL (body incl. verifier calibration and stress test, asymmetry and generator ablations; App. C task-property table, E cost, F web transfer).  Relevance to Part 2: high. It is the clean demonstration of **hardness from composition of verified subtasks** (§3.6) with a built-in difficulty ladder, a solvability-by-construction trajectory, and a measured asymmetry ablation — plus a cautionary LLM-judge verifier.
**Problem.** Computer-use datasets need humans for tasks and demonstrations; LLM agents cannot reliably produce trajectories for genuinely hard tasks, and simple generation repeats itself.
**Method / algorithm.** Six GPT-4.1-based roles in OSWorld (Ubuntu VM, 1920×1080 screenshots, pyautogui actions):
1. **Task proposer:** persona from PersonaHub + initial screenshot → a clear, simple task doable in a few atomic actions; no logins, no sending email.
2. **Executor:** ReAct planner GPT-4.1 (natural-language next action) + computer-use-preview for pixel grounding; ≤ 10 steps per subtask.
3. **Verifier:** WebJudge-style — extract key requirements, pick key screenshots, judge success (binary) + completion %; screenshots downsampled; GPT-4.1-mini.
4. **Reviser:** if partial, rewrite the subtask description to match what was actually achieved (hindsight relabelling).
5. **Follow-up proposer:** sees all prior subtasks + current screenshot and earlier failed proposals; proposes the next simple subtask building on current state.
6. **Summariser:** merges the first k of n completed subtasks into one high-level task; k = 1…6 gives six difficulty levels from one chain.
Core idea (information asymmetry): forward step-by-step generation is easy; the composed instruction hides the step decomposition, so solving it is hard.
**Verification / grading.** LLM verifier for both data generation and evaluation. Human audit (100 tasks, ~16 per level): feasibility/realism 91%, subtask coherence 90%, persona relevance 94%, verifier agreement 88% (inter-rater κ 0.74); verifier completion score monotone with human completion. **Adversarial stress test:** near-miss states (almost-right filename, similar wrong folder) accepted as success 12% of the time; benign UI perturbations accepted 94%.
**Scale & cost.** > 6,000 tasks. ≈ $0.011 per step, ≈ 50 steps per 6-subtask chain → ≈ $0.60 per trajectory, ≈ $0.10 per task (six levels per chain). Human-curated comparisons: OSWorld 4.4 h/task, TheAgentCompany 17 h/task.
**Key results.** Bare agents: o4-mini 18% at level 1 → 4% at levels 5–6; GPT-4.1 fails beyond level 3; humans 70% at level 6. With Agent S3 scaffold, GPT-5.1 62% → 14% (levels 1 → 6). Task properties rise with level: horizon 5 → 45 steps, apps 1.2 → 3.3, app switches 0.5 → 4.3, memory span (max distance between reading info and using it) 2 → 18 steps; fine-grained-perception share flat ~40% (so difficulty is not from perception). **Asymmetry ablation:** asking the generator for long tasks directly yields generation success 64% / 33% / 11% (easy / medium / hard) and evaluation success flat 60/51/48% — the survivors are easy; AgentSynth keeps generation success 65/57/52% while evaluation falls 62 → 14%. Generator swap (GPT-4.1, GPT-5-mini, GPT-5, GPT-5.1): similar curves; stronger generators make slightly harder tasks. > 60% of level-6 tasks use ≥ 2 apps, > 40% ≥ 3. Transfers to a web environment (InSTA).
**Failure modes & limits.** Authors: generator-model effects open. My critique: the verifier is an LLM judge, so the 12% near-miss acceptance is a direct reward-hacking surface for RL (a policy that saves "report_final2.docx" may be paid); the "ground truth" is a trajectory plus a judge, not a state check; the summariser can drop a subtask's constraint, creating instruction–trajectory mismatch (90% coherence leaves 10%); composed difficulty is mostly horizon and memory span, so a budget-2× probe (§3.7) is essential; failures are dominated by GUI grounding, which may not be the intended skill.
**Tips & tricks.**
- Build long tasks by chaining verified short subtasks from the current state; summarise k of n to get a free difficulty ladder per chain.
- Relabel partial successes to what was actually done instead of discarding them.
- Feed failed proposals back so the follow-up proposer goes simpler.
- Measure difficulty with structural stats (horizon, memory span, app switches), not just success.
- Stress-test any judge with near-miss and benign perturbations; report both rates.
- Compare against "ask the generator for a hard task directly": its survivors are easy.
**Fit to Crucible Part 2.** F3–F5 (proposal, oracle, verifier), §3.6 hardness from structure and the composition knob, F7 signature, traces-to-tasks. Adopt: the chain-and-summarise construction as a `world_synth` family generator — oracle = concatenated subtask action programs executed in the World (solution by construction, G3), verifier = the state diff after k subtasks (not an LLM judge), and the six-level ladder as the `count` knob; memory span and app switches go into `BehaviourSignature` (cross_app_flows, horizon). Adopt the near-miss/benign stress test as part of G5 (negatives must include near-miss end states). Check with G8/G9 that the summarised instruction still communicates every value the oracle used. Avoid: LLM-judge verification for reward. Priority P0 (direct template for composed `world_synth` tasks).

## 2507.15061 — WebShaper: Agentically Data Synthesizing via Information-Seeking Formalization (Tao et al., 2025; Tongyi Lab, arXiv)
Read: FULL (body; App. A–C).  Relevance to Part 2: high for the method, medium for the domain. Its formal task representation (a graph of relation triplets with variables and constants) and **layer-wise expansion** that removes redundancy and reasoning shortcuts is a general recipe for controllable, shortcut-free compositional tasks — directly applicable to multi-entity World tasks; §3.6 cites it for hop depth and width.
**Problem.** Information-driven synthesis (crawl first, then ask an LLM to pose questions) produces reasoning structures inconsistent with the information, wrong answers, and homogeneous structures.
**Method / algorithm.**
1. **Formalisation.** A knowledge projection R(V) = {u | ∃v ∈ V, (u,v) ∈ R or (v,u) ∈ R}. Operations: R-union (R(S1) ∪ R(S2) = R(S1 ∪ S2), so a union becomes a merged constant like {90s}) and intersection across relations. A task is ?T with T = ∩_i R_i(·), recursively nesting target sets. **KP representation:** a list of triplets [X, r, S], X a variable (V@), S a variable or a constant (C@); recursion flattens into intersections over variables. The task is a graph: nodes = variables and constants, edges = relations.
2. **Seeds:** random walks over an offline Wikipedia hyperlink graph; an LLM writes QA grounded only in the walked articles; filter by 5 WebDancer/QwQ rollouts, keep if ≥ 1 correct → 18K seeds.
3. **Layer-wise expansion** (n steps, answer fixed): find all leaf constants of the current graph; for each, the Expander turns the constant into a variable defined by a new sub-question whose answer is that constant, and merges it. Contrast: *random* expansion adds constants attached to constants (**redundancy**, no extra reasoning); *sequential* chains leave a constant directly attached to the target (**reasoning shortcut** — solvers can guess from the near constant). Number of layers l controls difficulty.
4. **Expander agent** (ReAct, QwQ): Search (Google, with year filter), Summarize (visit several URLs and build union constant sets), Validate — two QwQ calls: (a) is the constant's *type* consistent with the sub-question; (b) **can an LLM answer the sub-question without tools? If its answer equals the constant, reject** (too easy / memorised).
5. **Trajectories:** QwQ ReAct agent with Search + Visit, 5 rollouts per question; keep only judge-verified correct ones with no tool errors; drop hallucinated observations and heavy repetition → 5,000 trajectories.
6. Training: SFT (observation tokens masked), then GRPO (group 8, T = 1.0, lr 1e-6).
**Verification / grading.** Answer correctness via LLM judge against the constructed answer set; validation of sub-questions by LLM; evaluation GAIA and WebWalkerQA with LLM-as-judge pass@1.
**Scale & cost.** 18K seeds; 5,000 kept trajectories; no $ figures.
**Key results.** GAIA avg: WebShaper on Qwen2.5-72B 60.1, QwQ-32B 53.3, Qwen2.5-32B 52.4 (WebDancer 40.7 on 32B); WebWalkerQA 52.2 (72B). Same-size SFT data comparison (5K each): WebShaper beats WebWalkerQA, E2HQA, MHQA on all three backbones (QwQ 53.3 vs 45.6/45.6/41.7). RL after SFT: +7.8 (32B) and +13.5 (72B) on GAIA. Ablations: formal-language expansion beats natural-language expansion on all backbones; layer-wise beats sequential on all backbones (figures only). Trajectories need > 3 searches 3–4× more often than E2HQA/MHQA; non-zero mass up to 30 tool calls.
**Failure modes & limits.** Authors: none substantive beyond scope. My critique: the open web is non-stationary (answers drift; Google results change); answer sets rely on LLM summarisation for unions (an error source); judge-based correctness; GAIA has only ~100 IS items, so per-level differences (16.6 on Level 3) are one or two questions; the "LLM can answer without tools" check uses one model (QwQ) — memorisation by the *student* is not tested.
**Tips & tricks.**
- Represent each task as a graph of (variable, relation, constant) triplets; reason about structure, not wording.
- Expand only by replacing leaf constants with variables defined by new sub-questions; this blocks redundant facts and target-adjacent shortcuts.
- Keep the answer fixed through expansion; difficulty = number of layers.
- Reject any sub-question a no-tool model answers correctly (closed-book probe).
- Ground seeds in a fixed offline corpus snapshot; filter seeds by "at least one of k rollouts solves".
**Fit to Crucible Part 2.** §3.6 (hop depth/width knobs; hardness from structure), G9 (no shortcut), F3–F5, F7. Adopt: for `world_synth` lookup/reasoning tasks, represent the task as a relation graph over World entities (the World's DB is the exact, stationary analogue of WebShaper's web — no drift, exact answers by SQL, no judge); expand layer-wise from leaf constants; difficulty knob = layers (depth) and intersections (width). Add two structural gate checks to G9: **no constant node attached directly to the target**, and **no constant–constant edges** (redundancy) — both computable from the oracle's query plan/trace. Adopt the closed-book probe as part of F10's instruction-only ablation, run on the *student family* as well as a frontier model. Interface: `TaskProposal.formal_graph` (triplets) stored privately; F7 compares the oracle's actually-traversed edges with the graph. Priority P0 (cheap, generic, directly fixes shortcut tasks).

## 2507.02592 — WebSailor: Navigating Super-human Reasoning for Web Agent (Li et al., 2025; Tongyi Lab, arXiv)
Read: FULL (body; App. A.1–A.5).  Relevance to Part 2: medium–high. Two reusable ideas — **information obfuscation** as a difficulty knob, and **DUPO**'s variance-based batch filling — plus the honest admission that obfuscated tasks often have non-unique answers, which is the failure Crucible's G14 (alternatives) and exact-state verifiers must guard against.
**Problem.** Open web agents score near zero on BrowseComp; training data covers only "Level 1" (low uncertainty) and "Level 2" (multi-hop with a clear path) tasks, not "Level 3" (high uncertainty, hard to reduce, no predefined path).
**Method / algorithm.**
1. **Graph construction (SailorFog-QA):** start from a *rare* entity from Wikidata SPARQL; gather its features by simulated browsing; extract related entities and relations; iteratively, with some probability, expand a new node or return to a previous node (to avoid linear chains), until an edge budget is reached → dense, overlapping relational graphs.
2. **Subgraph sampling** with diverse topologies → an LLM writes question + answer from the subgraph.
3. **Information obfuscation:** exact dates → vague periods ("early 2010s"), names partially masked ("initial F"), quantities → qualitative ("market share below 1%"). Raises initial uncertainty.
4. **Trajectories:** QwQ-32B / expert LRMs solve with Search + Visit (≤ 30 tool calls); keep only successful action–observation sequences; **discard the expert's own thoughts** and have a separate instruction model write a short, action-oriented thought for each step given history, action and observation (avoids stylistic contamination and context overflow).
5. **RFT cold start:** keep correct trajectories, ≤ 32K tokens, **> 5 tool calls**; ~2K examples; observation tokens masked.
6. **DUPO RL:** before training drop tasks with 8/8 correct; during training drop zero-variance groups and fill batch slots by **duplicating other same-batch groups with non-zero variance** (2–3× faster than DAPO's resampling); token-level loss, clip-higher; reward = 0.1·format + 0.9·answer (LLM judge).
**Verification / grading.** Answer correctness by LLM judge; format by rules.
**Scale & cost.** ~2K cold-start trajectories; RL only 50 steps (synchronous framework bottleneck). No $ data.
**Key results.** BrowseComp-en / zh / Xbench-DeepSearch / GAIA: WebSailor-72B 12.0 / 30.1 / 55.0 / 55.4; 32B 10.5 / 25.5 / 53.3 / 53.2; 7B 6.7 on BrowseComp-en vs WebDancer-32B 2.5 (DeepResearch 51.5). Difficulty of SailorFog-QA before filtering: o4-mini 47.3% (WebDancer-QA 90.2%, BrowseComp-en 26.3%); DeepSeek-R1 38.9% (84.4%, 9.5%). Training-data tool-call distribution is long-tailed like BrowseComp's (WebDancer's: > 50% need only 2 calls). RFT cold start: direct RL rises faster but converges lower and uses fewer tool calls; gap largest on BrowseComp-en. RL raises pass@1 much more than pass@3. Strong on SimpleQA too (downward compatible).
**Failure modes & limits.** Authors: **answers are not always unique** — obfuscation can yield several entities satisfying all conditions (they guarantee only that the given answer satisfies them); 32K cap; over-thinking on simple questions; 50 RL steps. My critique: with an LLM-judged single answer, a correct alternative is marked wrong — a false-negative reward; obfuscation is a text transform, so it raises search cost without necessarily changing reasoning structure (a budget-2× probe should be run); rare-entity seeding biases toward trivia.
**Tips & tricks.**
- Seed graphs from rare entities and expand non-linearly (revisit old nodes) to avoid chain-shaped tasks.
- Obfuscate dates, names and quantities to raise uncertainty — but then check answer uniqueness.
- Rebuild short thoughts for expert action traces rather than imitating verbose reasoning.
- Keep only trajectories with > 5 tool calls for agentic cold starts.
- Drop all-correct tasks before RL; fill zero-variance slots by duplicating informative groups in the same batch.
**Fit to Crucible Part 2.** §3.6 (the `obfuscation` knob already in `DomainSpec.knobs`), G14 alternatives, G9, F9 batch construction, §2(a) RL. Adopt: obfuscation operators over World facts in F3 (exact value → range, name → initial or role, number → qualitative band) **paired with a uniqueness check by execution**: after obfuscation, query the World for all entities satisfying the stated constraints; reject (or make the verifier accept the full set) unless exactly one remains — the World makes this exact, unlike the web. Adopt DUPO-style variance filling in the trainer (Part 1) as a cheap efficiency lever. Note the RFT-before-RL evidence for students with near-zero initial pass rates. Priority P1.

Forge: agent side / gateway + data pool / train-inference side; white-box vs black-box agents; windowed FIFO (W = 0.3N) to avoid easy-first distribution shift; prefix-tree merging (up to 40× training speedup).

**Scale & cost.** 229.9B total / 9.8B active; no counts or costs for any data pipeline.
**Key results.** M2.7: SWE-bench Pro 56.2, Multilingual 76.5, Terminal-Bench 2.0 57.0, BrowseComp 77.8, GDPval-AA 50.0, Toolathlon 46.3, MLE Bench Lite 66.6% medal rate (3 × 24 h). Self-evolution evidence is internal and qualitative.
**Tips & tricks.**
- Route mined tasks by type and give each type its own reward definition (F2P+P2P, new tests, perf P2P).
- Invert a fix into a test-writing task for a second, verifiable skill from the same source.
- Remove hints from task text and grade all hint levels with one shared test suite.
- Rank difficulty by a reference solver's pass rate and by how many repairs the environment needed.
- Accept search answers only when grounded in retrieved evidence.
- Reverse-derive tasks from executed tool traces or state walks: grounding by construction.
- Sample training trajectories under perturbed scaffolds; mix domains in every RL stage; schedule with a FIFO window to avoid easy-first batches.
**Fit to Crucible Part 2.** §3.6 hint knob, §3.3 contract (task types), traces-to-tasks (§3.4), F5/G5, §3.8 pipeline doctor. Adopt: (a) hint levels as a knob where **one verifier grades every variant** (G-rule: variants of a family share the `VerifierBundle`; only the instruction changes) — this guarantees a variant's difficulty change is not a grading change; (b) type routing in the debug lane's contract (bug fix vs feature vs test-writing inversion as separate families); (c) workbook/state walk = World random-walk synthesis for `world_synth` (atomic App operations from a seed state, recycle intermediate states, derive answer from the end state) — the same pattern as traces-to-tasks; (d) env-repair iteration count as an F9 predictor feature; (e) windowed FIFO for the Part 1 trainer. Self-evolution is in the §3.8 spirit (agent proposes, human steers) and supports keeping the human-review gate. Priority P1.

## 2510.24695 — Scaling Agents via Zone of Proximal Development Data Synthesis (AgentFrontier) (Qiao et al., 2025; Tongyi Lab, arXiv)
Read: FULL (body, Alg. 1, App. A.1–A.3 hyperparameters and cost; tool details skimmed).  Relevance to Part 2: high. A complete, costed loop for "escalate along named axes until the no-tool model fails, keep if a tool-using expert can solve it, send all-fail items to humans" — a two-model difficulty sandwich that maps directly onto F9's predictor + frontier audit, with explicit $ per kept item. Its 0.7 reranker dedup threshold is the source of §3.5 item 5's starting threshold.
**Problem.** Synthetic data either stays within the generator's ceiling or stacks constraints heuristically; difficulty is not calibrated to the learner's frontier. Knowledge-fusion (multi-document) tasks are scarce.
**Method / algorithm (Alg. 1).**
1. **Seeds for knowledge fusion:** 1M public documents → Qwen3-235B condenses into information-dense chunks → vector index; for each chunk, k_nn = 10 neighbours; find triplets with pairwise similarity > τ_theme = 0.8; a generator writes a QA pair from each coherent triplet.
2. **Agentic escalation** (refinement agent with search, scholar, browser, code): operator Ψ applies one of four moves per iteration — knowledge expansion (weave in retrieved background), conceptual abstraction (higher-level principles, subtle relations), factual grounding (multi-source cross-validation), computational formulation (turn it into a calculation or simulation verified with Python). **Stop when the LKP (base model, no tools) can no longer solve it**, or at K_max = 30 (mean 7.81 iterations).
3. **ZPD calibration:** LKP solves (GPT-4o judge) → goes to the continued-pre-training pool; else **MKO** (tool-augmented strong agent) gets N = 3 attempts: ≥ 1 correct → post-training set; 0/3 → **human review** (flawed or too hard).
4. **Diversity:** drop a new item if its reranker similarity to any kept question ≥ ε = 0.7.
5. **ZPD Exam:** same engine on 30K disjoint 2023–2025 papers; keep items the baseline fails 3/3 without tools and solves 3/3 with tools; 1,024 public questions + a private set; regenerate as models improve ("living benchmark").
6. Training: RFT on 12,000 trajectories (iterative tool-call + summarised "reasoning report" rounds), loss only on report tokens; optional CPT on 50B tokens (1M chunks + 20M knowledge QA pairs).
**Verification / grading.** Single short answers judged by an LLM (o3-mini with the HLE strict prompt; GPT-4o inside the engine). No execution check except computational items' Python.
**Scale & cost.** Refinement ≈ $0.24 per candidate; MKO verification ≈ $0.18 per candidate with a 33% pass rate → ≈ $0.54 amortised; **≈ $0.78 per kept item** (DeepSeek API pricing).
**Key results.** HLE text-only (2,154 q): Qwen3-30B-A3B RFT on AgentFrontier 25.67 vs TaskCraft 19.87, MegaScience 20.15, MiroVerse 19.64 (equal 12K trajectories, normalised to 25,600 rounds); with CPT 28.6 (above OpenAI DeepResearch 26.6). 8B: 18.80 vs ≤ 15.00; 32B: 23.82 vs ≤ 19.92. ZPD Exam-v1: 93.4 (CPT+RFT); base Qwen3-30B 4.9 without tools, 47.2 with. Held-out 300-item validation: pass@1 21.7% → pass@8 40.7% (room for RL). Balanced tool use (search 0.32, scholar 0.66, browser 0.82, code 0.52 calls per trajectory) vs skewed baselines; conditional tool accuracy on HLE 26.3% vs ~21%. ZPD Exam stratifies agents into intrinsic (< 20), bottleneck (20–60), mastery (> 60) zones.
**Failure modes & limits.** Authors: binary scaffolding (full MKO solution), imitation only, static tools. My critique: "ZPD" is defined against a no-tool base model, so most of the gap is *tool access*, not skill — a task becomes "hard" simply by needing retrieval; GPT-4o judging both sides admits judge errors into the calibration; the MKO ≥ 1/3 rule keeps lucky solves (a 1/3 item may be ambiguous); the 33% MKO pass means two-thirds of refinement spend lands in the human-review or discard bin; ZPD Exam is calibrated to one baseline and saturates (93.4) fast.
**Tips & tricks.**
- Name the escalation moves and stop escalating at the first iteration the weak reference fails; this avoids overshooting.
- Sandwich difficulty: weak reference must fail, strong reference must succeed at least once in N.
- Route all-fail items to human review rather than discarding — they hold both broken and frontier tasks.
- Build multi-source tasks from mutually similar triplets found via k-NN, not combinatorial search.
- Cost each stage per candidate and amortise by downstream yield.
- Regenerate an eval set against the current model to avoid saturation (keep it disjoint from training sources).
**Fit to Crucible Part 2.** F9 (difficulty), §3.6 too-easy/too-hard routing, §3.7 zero-solve rule, §3.10 cost model, F8 threshold. Adopt the sandwich, per student: escalate a family's knobs until the *student-proxy* (cheap predictor or a small same-family model) fails, then require the oracle (by construction) plus a frontier audit on a sample; all-frontier-fail items go to the INCONCLUSIVE/human queue as §3.7 already says — AgentFrontier's 0/3 → human routing is the same rule. Use its cost accounting (refine + amortised verify) in §3.10's formula. Calibrate the 0.7 reranker threshold on Crucible task pairs before relying on it. Caution: "fails without tools" is not evidence of the intended skill (§3.7 — hardness is not intent). For the 397B, the weak reference must be re-chosen (the 35B itself is a natural LKP for the 397B's ZPD). Priority P1.

## 2512.18552 — Toward Training Superintelligent Software Agents through Self-Play SWE-RL (SSR) (Wei et al., 2025; Meta FAIR / UIUC, arXiv, ICML-format)
Read: FULL (body; App. A game analysis, B incentives, C training details, E limitations and unsuccessful attempts; D prompts skimmed).  Relevance to Part 2: very high. It is the strongest existing self-play task source for code, and the source of three items in Crucible's plan: G6 inverse mutation, the ~0.2 optimal solve rate at G = 8, higher-order bugs from failed attempts, and the "tunnel-vision challenger" warning behind §3.6's knob-entropy penalty.
**Problem.** SWE agents train on human-curated issues and tests, which do not scale and can be unreliable. Can one model, given only sandboxed repos (Docker images with dependencies, no tests, test commands, parsers or issues), improve by injecting and repairing its own bugs?
**Method / algorithm.**
*One policy, two roles* (CWM-sft 32B, Bash + editor), trained jointly with RL.
1. **Bug injector** explores the repo, discovers how to run tests, and emits a **bug artifact**: `test_script.sh`; `test_files.txt` (oracle test files, always restored before grading); `test_parser.py` (test output → JSON id→pass/fail); `bug_inject.diff`; `test_weaken.diff` (removes or weakens tests to hide the bug — its reversal is the solver's specification). Injection strategies: (a) direct prompting; (b) **remove code hunks or files** with compatibility fixes so the project still runs (a semantic, not syntax, bug); (c) **revert selected historical changes** from git log. Control parameters: min changed files, min passing tests, min failing tests.
2. **Consistency validation** (all must pass): test files exist and cover the weakening patch's files; parser produces valid JSON; test script on the original passes ≥ min_passing_tests; bug touches ≥ min_changed_files; ≥ min_failing_tests previously-passing tests fail after the bug; some buggy-state failures pass after weakening; **inverse mutation testing** — for each file in the bug patch, revert only that file in the buggy state and run the non-weakened tests; at least one failing test must pass, else the file is unnecessary and the artifact fails. Valid artifacts become SWE-bench-style F2P/P2P instances.
3. **Solver** sees the buggy repo (bug applied, tests weakened, **.git removed and re-initialised** to block history leakage) and the **reversed test-weakening patch** as its only spec; no natural-language issue. Grading: apply the prediction patch, restore oracle test files from the original tag, run the script and parser; reward +1 if all pass, −1 otherwise.
4. **Higher-order bugs:** a failed solver attempt's resulting state becomes a new buggy starting state (bug + weaken + failed patch) for another solve attempt; capped at second order to avoid overlap.
5. **Injector reward** (from Absolute Zero): −1 if consistency fails; −α if solve rate s ∈ {0, 1}; 1 − (1+α)s if 0 < s < 1; α = 0.8; s over G = 8 solver attempts. Opposing incentives: the solver wants high s, the injector low-but-non-zero s.
*Game analysis (App. A):* with s estimated from G = 8 binomial samples, the expected reward R(p) has a unique optimum at a target solve rate **p\* ≈ 0.2**; a Beta reward s^a(1−s)^b has optimum ≈ a/(a+b). A sufficiently capable challenger has **dominant strategies**: tests that pass pseudo-randomly by hash of the code, or obfuscating the codebase so nothing can be fixed; and a **tunnel-vision** strategy — tune one parameter (operand length, obfuscation level, chain length) to hold s at p\* without diversity, after which learning stops. Mitigations: ground the challenger in large, diverse real data; keep it close to its initial instruction-based strategy (shallow self-play); do not self-play natural language.
**Verification / grading.** Execution of the agent's own test script with oracle-file restoration; no LLM judge.
**Scale & cost.** 512 H100s per run (64 train / 448 rollout); 131K context; 16M-token global batch; group size 8; rollouts > 8 off-policy steps discarded; 150 steps ≈ 2.5B tokens; lr 3e-6. Same environment images as CWM's RL.
**Key results.** Over the training trajectory SSR beats the "human-data" RL baseline (same images and hyperparameters, but with real issues and tests) on both benchmarks; net self-improvement +10.4 (SWE-bench Verified) and +7.8 (SWE-Bench Pro) for one attempt per task, T = 1.0 — despite never seeing a natural-language issue. Ablations (averaged over 1,231 tasks): **self-play > repair-only** (training only on deduplicated valid bugs from earlier self-play runs) **> injection-only** (degrades) — the online, evolving task distribution matters. Injection strategy: direct prompting collapses to trivial one-line edits (worst); removal-only is stronger; **removal + history reversion is best**. Reward ablation: solver-feedback reward is only slightly better than a consistency-only ±1 reward (solve-rate feedback is weak and noisy at G = 8; the expected reward is smoothed). Eval noise ≈ 2% paired SE on Verified.
**Failure modes & limits.** Authors: the full oracle tests are visible to the solver (no hidden tests) — hacking risk; unit tests only; one model for both roles; **natural-language issue generation failed** (copied test patches, incoherent, collapsed to identical patterns); training on 23 benchmark-repo images did not beat more diverse repos; training instability (gibberish) at scale; no control of injection location → duplicates and distribution bias (seeding suggested). My critique: "removal" bugs teach reconstruction, a narrower skill than diagnosing wrong behaviour; s from 8 samples is coarse; the injector's own test script is both the spec and the judge — a weak script is a weak verifier, guarded only by the consistency rules.
**Tips & tricks.**
- Specify a self-generated bug formally (tests, parser, inject patch, weaken patch); use the reversed weakening patch as the spec.
- Always restore oracle test files before grading; delete and re-init .git.
- Inverse mutation: every changed file must be necessary (reverting it alone must flip a test).
- Prefer removal and history-reversion injections over free-form "add a bug".
- Recycle failed solver states as higher-order bugs; cap the order.
- Target solve rate ≈ 0.2 at G = 8 with the asymmetric reward; penalise degenerate s by −α, not −1, to keep gradient.
- Keep self-play shallow and grounded; watch for single-knob tunnel vision.
- Seed injection locations to control duplicates.
**Fit to Crucible Part 2.** Self-play source (§3.4), G6, F5 negatives, §3.6 band centre and "too-easy → failed attempts become higher-order variants", §3.8 guards, F11 diversity. Adopt as written in the plan, and add: (1) **hidden oracle split** — Crucible's F5 must keep held-out tests/checks the solver never sees (SSR's own stated gap); (2) **injection-location seeding from the coverage grid** — the injector receives a sampled file/function cell, fixing SSR's duplicate problem with §3.5's grounding; (3) **knob-entropy monitor** on the injector's operators (fraction of removal vs history vs other, files touched) as the tunnel-vision alarm; (4) treat solve-rate feedback as weak — rely on consistency gates plus F9 measurement rather than optimising the injector on s; (5) for `world_synth`, the analogue of "remove hunk" is "remove or corrupt a World record/rule that the oracle path depends on", and inverse mutation becomes "restoring any single corrupted record flips a check" (G6 generalised). Natural-language task text must come from F3 with grounding, not from self-play (SSR's failed attempt). Priority P0 for G6 + hidden checks + seeding; P2 for in-training self-play.

- Categorise bugs by hierarchical LLM summarisation over the pooled datasets, then classify; compare category histograms across sources.
- Choose teachers whose trajectories carry reasoning text between tool calls.
- Use realistic-origin bugs as a small high-value slice on top of a cheap base mix.

## 2512.02556 — DeepSeek-V3.2: Pushing the Frontier of Open Large Language Models (DeepSeek-AI, 2025; tech report, arXiv)

## 2507.13266 — QuestA: Expanding Reasoning Capacity in LLMs via Question Augmentation (Li, Lin et al., 2025; Tsinghua / Amazon, arXiv v4 2026)
Read: FULL (body, theory §4, App. B.5–B.6 data and p choice, D.1 no-hint ablation; proofs skimmed).  Relevance to Part 2: high for §3.6 ladders. QuestA is the cleanest evidence that **partial-solution scaffolds make too-hard tasks learnable without hurting unscaffolded performance**, with a removal schedule and the empirical observation that a mid-size hint can be indistinguishable from none.
**Problem.** RLVR on easy prompts lowers pass@k (entropy collapse, overconfidence); RLVR on hard prompts stalls because all-fail groups give no gradient; final pass rates become bimodal (a task is either learned or never). How to train on hard tasks efficiently?

1. **Hard pool:** OpenR1-Math-220K → DeepSeek-R1-Distill-1.5B, 8 samples each; keep items with 0–1 correct → 26K.
2. **Augment:** for a problem with solution y = (y_1…y_n), prepend the first p% (by tokens) of the *final solution block* (not the chain of thought) as "Hint: Partial Solution".
3. **Second screen on augmented prompts:** the current training model samples 8; keep items with **0–4 correct** (includes the max-variance point 4/8) → ≤ 10K.
4. **Curriculum:** RL on Partial-50 until saturation (≈ 100 steps; entropy starts falling after that), then re-filter and RL on Partial-25 (1,900 steps). Partial-25 → Partial-0 gave no gains.
5. RL: GRPO without KL in AReaL; DAPO dynamic filtering of all-correct/all-wrong groups; 16 samples per prompt; 24K generation; T = 1.0; clip 0.2/0.2; lr 2e-5 (high), batch 128; 8 H800 nodes. **Hints are never shown at evaluation.**
*Theory:* if every question's model capacity set misses its solution set, RL with TB = Θ(1/δ) samples has constant probability of no update (Thm 4.4); if a hint of probability ≥ δ′ = δ^{1/2−ε} exists after which a solution has probability δ′, the sampling budget falls to O(1/δ′) — roughly the square root (Thm 4.6).
**Verification / grading.** Exact-answer math checking; pass@1 over 32 samples (T 0.7, top-p 0.95).
**Scale & cost.** 26K → ≤ 10K augmented prompts; 2,000 RL steps; 8 × H800 nodes.
**Key results.** Nemotron-1.5B (avg over 5 benchmarks) 53.14 → **63.26** (AIME24 61.77 → 72.50; AIME25 49.50 → 62.29; HMMT25 31.56 → 41.67) — above DeepSeek-R1-Distill-32B (58.08). DeepScaleR-1.5B +6.50 avg. Ablations: **same data without hints** 60.44 (hints add +2.82 and reach the no-hint run's score in about half the steps); Partial-50 only for 2,000 steps 60.26 vs curriculum 63.26; OpenMathReasoning data (60K items at 0 or 1/32) gives similar first-stage gains (58.11). pass@k: RL on easy prompts degrades pass@k at large k; QuestA keeps or lifts the whole curve; unsolved AIME items at pass@32 fall 5 → 2 (AIME24) and 6 → 3 (AIME25). On training prompts without hints, mass moves out of the 0/8–1/8 bins. Entropy rises during training (no collapse). **Hint calibration table:** on the filtered pool, Partial-50 makes most items easy (17,741 at 8/8), while Partial-25 and Partial-10 look almost like no hint (0/8: 3,155 / 3,589 / 3,812 for 25 / 10 / 0%) — the useful hint range is steep and narrow.
**Failure modes & limits.** Authors: math only; extension to coding/agentic tasks left open. My critique: requires a reference solution whose prefix is a meaningful partial solution — in agentic tasks the analogue (oracle's first k actions, or a mid-trajectory start state) can leak the plan; hint percentage by tokens is crude (25% may cover the key insight or nothing); high-variance selection (0–4 of 8) is computed on the hinted version only; one model family, small models.
**Tips & tricks.**
- Scaffold only items the student fails; never scaffold at evaluation.
- Use the solution, not the reasoning trace, as the hint source.
- Re-screen after scaffolding and keep items at 0–4/8 (around max variance).
- Start with a large hint, then cut it; switch when entropy starts falling.
- Measure the pass-rate histogram per hint level first; hint effect is non-linear.
- Expect hint-trained models to keep pass@k, unlike RL on easy prompts.
**Fit to Crucible Part 2.** §3.6 ladders for too-hard tasks, F9 sequential measurement (0/4 → ladder), §3.8 task loop, F11 curriculum. Adopt: the ladder as a knob `hint_level ∈ {oracle prefix 50%, 25%, 0}` for agentic tasks implemented two ways — (a) **checkpoint start** (start state after the oracle's first k actions — Crucible's `difficulty.py:237-296` checkpoint-start variants), (b) **plan hint** (summarise the oracle's first steps in text); calibrate per family with a pass-rate histogram per level before use; schedule removal by entropy/p̂, and always evaluate the unscaffolded parent. Interface: the variant shares the parent's `VerifierBundle` and records `hint_level`, `parent_id`; F12 tracks the parent's unscaffolded p̂ as the real learning signal. Note the conflict with intent: a scaffolded variant may not exercise the skill the parent targets (e.g. localisation) — F10 must label scaffold variants with the reduced skill set. Priority P1.

## 2402.05808 — Training Large Language Models for Reasoning through Reverse Curriculum Reinforcement Learning (R³) (Xi et al., 2024; Fudan / ByteDance, ICML 2024)
Read: FULL (body, ablations §5, App. A algorithm referenced).  Relevance to Part 2: medium–high for §3.6 ladders. R³ is the "late start state" ladder: begin rollouts from intermediate states of a correct demonstration and slide the start back to the beginning; crucially, **mixing start positions beats staged progression**, and difficulty-weighted rewards hurt.
**Problem.** Outcome-only rewards are sparse on long reasoning chains; process rewards need costly step annotation. Can outcome supervision give step-level signal?
**Method / algorithm.**
1. Given a correct demonstration τ = (s_0, a_1, …, s_T), sample M intermediate start states (at line breaks, else uniformly), M = 5–6.
2. The policy continues from s_k: π(a_{k+1:T} | s_k); outcome reward on the final answer supervises only the generated suffix.
3. **Vanilla staged RL:** stages from the start state nearest the goal back to s_0.
4. **R³ (final):** **mix all start positions in training** (multi-task view) — staged RL overfits early stages and drops sharply at stage switches.
5. PPO with GAE; KL to the SFT init (β = 0.05 math CoT, 0.3 other, 0.01 program-CoT); partial reward ε (0.1 SVAMP, 0.2 GSM8K) when an answer is numeric but wrong; SFT warm-up first. Dynamic-programming intuition: learning time becomes linear rather than exponential in chain length.
**Verification / grading.** Gold answers (exact match; program execution for P-CoT).
**Scale & cost.** Llama2-7B, Galactica-6.7B, CodeLlama-7B; 8 × A100; 50 RL epochs on math.
**Key results.** Llama2-7B CoT average over 8 tasks: SFT 60.19, RL 61.48, staged RL 62.81, **R³ 65.62** (+4.1 over RL); GSM8K 41.55 / 44.67 / 47.69 / 50.49. Program-CoT GSM8K: CodeLlama-7B RL 70.7 → R³ 74.2; Llama2 63.1 → 68.9; Galactica 66.1 → 69.3; on Tora-code 72.6 → 76.3 using only original data. Accuracy rises as the start moves toward the goal (Fig. 2) on train and test. Ablations: β = 0 still works (46.6 vs 50.5 default; normal RL tends to collapse without KL), β = 0.1 hurts (44.1); partial reward too small or large hurts (best 0.2); M saturates at 5–6; **difficulty-scaled rewards** (linear, square, sqrt, discount on start distance) **all lower performance** (avg 63.8 → 58.7–60.0) — treat start states equally; removing the hardest-start data hurts most, removing easiest barely matters; R³ training reward is far more stable than RL's.
**Failure modes & limits.** Authors: 7B models, limited scale. My critique: needs a correct demonstration per task; a late start leaks most of the solution, so pass rates from late starts measure completion, not the full skill; for agentic tasks, an intermediate *state* (environment after k oracle actions) differs from a text prefix — the environment must be restored to that state, and the student must not be able to read the oracle's earlier actions unless intended.
**Tips & tricks.**
- Start rollouts from a few (5–6) intermediate states of a demonstration; outcome reward then acts like step supervision.
- Mix start positions in every batch; do not run sequential stages.
- Do not scale reward by how late the start was.
- Keep the hardest (earliest) starts in the mix — they carry most of the value.
- A small partial-credit reward for well-formed wrong answers can help; too large invites gaming.
**Fit to Crucible Part 2.** §3.6 ladders (late start states), F11/F12 curriculum, PLR sampler. Adopt: Crucible's checkpoint-start variants as an R³ ladder for too-hard tasks — start states = World/repo snapshot after the oracle's first k actions (k at 5–6 evenly spaced points), **trained mixed with the full-start task, not staged**, equal reward. Each start is a variant sharing the parent verifier (`shares_fixes_with`), with `start_offset` as the knob; F12 reports the full-start p̂ as the true metric. Make sure the snapshot hides the oracle's action log (instruction-only access as in §3.0 rule 5). Avoid difficulty-scaled rewards. Combine with QuestA's text hints when snapshots are impossible. Priority P1.

## 2412.02674 — Mind the Gap: Examining the Self-Improvement Capabilities of Large Language Models (Song et al., 2024; Harvard / Amazon, ICLR 2025)
Read: FULL (body; App. B ablations incl. fixed and gold verifiers, verifier variance; per-model tables in C skimmed).  Relevance to Part 2: medium–high for §3.8. It formalises *when* a model-in-the-loop improvement step can help: only to the extent the verifier adds information over the generator (the generation–verification gap), which saturates in 2–3 rounds and erodes diversity unless the verifier is exact. That is the quantitative reason Crucible's loops must be anchored to executed checks and frozen anchors, not to model judgment.
**Problem.** Self-improvement (generate → self-verify → filter/reweight → distill) is widely used but poorly understood and confounded (format fixes, length changes). When does it work, and how does it scale?
**Method / algorithm.**
- Framework: generator f; proxy utility û_g from verifier g; reweighted distribution f[w(û_g)](y|x) ∝ f(y|x)·w(û_g(x,y)); update projects f_{t+1} onto it (rejection sampling w = 1[û ≥ τ], or KL-regularised RL w = exp(û/β)).
- Three conditions: improvable generation (variance across samples), **informative verification**, high-fidelity update. J(f_{t+1}) − J(f_t) ≥ gap(f_t, g) − ε_update.
- **GV-gap** gap(f, g) = J(f[w(û_g)]) − J(f); **relative gap** = E_x[(J_reweighted − J)/(U_max − J)] (normalises by headroom).
- Measurement: base models only (Qwen-1.5/2/2.5, Llama-2/3/3.1, Yi-1.5; also Pythia, OPT), lm-eval-harness, 4-shot, T 0.7, top-p 0.9; 128 generations per prompt and one verification each. Verifiers: multiple choice (P("Correct")), CoT-Score (1–10 with reasoning), CoT-Binary, tournament (pairwise single elimination).
**Verification / grading.** Ground truth for computing the gap: GSM8K, MATH exact answers; Natural Questions; 4×4 Sudoku (288 puzzles).
**Scale & cost.** Dozens of base models; 128 samples per prompt.
**Key results.** Small models (Qwen 0.5B, Llama-2-7B) have non-positive gaps — they cannot self-improve. CoT verification is more stable than MC (MC is non-positive even for some 14–32B models). **Relative gap with CoT-Score grows roughly linearly in log pre-training FLOPs** (absolute gap does not). Cross-verification: gap rises with verifier capacity and falls with generator capacity (stronger generators' errors are subtler). Natural Questions: gap < 1% for all sizes (factual recall: verification ≈ generation). Sudoku: only ~70B models get a gap, and then large (Qwen-2-72B 8.82% → +16.99, relative 20.81). **Iterative self-improvement saturates to ≈ 0 gap in 2–3 rounds, at a rate independent of model size**; pass@k at large k falls across rounds (effective diversity lost, converging on wrong answers the verifier accepts); with a **gold verifier there is no diversity loss**; with a stronger but imperfect verifier (Qwen-1.5-72B) the loss persists. MC verification saturates after one round. Accuracy gains in round 1 partly come from answer-format adherence (a confounder the gap metric isolates). Verifiers disagree (low correlation between methods); gap does not correlate with generation accuracy; **AND-ensembles of verifiers raise the gap** (e.g. Qwen-2-1.5B: MC 5.27, CoT-S 2.78, MC+CoT-S 7.68). Optimal thresholds transfer across model sizes within a method; CoT-Score has a self-bias (mode = 10).
**Failure modes & limits.** Authors: observational scaling; one verification sample per generation; base models only (instruct models noisy). My critique: tasks are short-answer; for agentic tasks with executable verifiers the gap is defined by the executor, not a model — the paper's warnings apply to every *model-judged* component (intent auditor, realism reviewer, interestingness judge, LLM verifiers in hard-to-execute domains).
**Tips & tricks.**
- Measure a verifier's value as the accuracy gain from filtering by it (the GV-gap), on held-out ground truth, before trusting it.
- Report relative gap (normalised by headroom) when comparing generators of different strength.
- Expect self-filtering loops to saturate in 2–3 rounds; stop or add new information.
- Track pass@k at large k across rounds; falling large-k pass is the diversity-collapse alarm.
- Ensemble different verifier types with AND; their errors do not overlap.
- Use a stronger verifier than the generator; weak-to-strong verification is not guaranteed positive.
- Tune thresholds on a small model and transfer within a verification method.
**Fit to Crucible Part 2.** §3.8 loops and guards, F10 judges, F5/G5, the anchor set, self-play caution. Adopt: (1) a **GV-gap test for every model-judged component** in F6/F10/F11 — on the frozen anchor set, filtering by the judge must raise precision against human labels; report the relative gap per judge version (this operationalises "agreement with the frozen anchor set holds or improves"); (2) cap automatic improvement loops that rely on model verification at ~2–3 rounds unless new executed information enters (new negatives, new traces); (3) monitor pass@k at large k (and signature diversity) across loop rounds as the collapse alarm; (4) prefer AND-ensembles of different-family, different-method judges for INVALID/VALID intent verdicts; (5) the judge's family/size must exceed the generator's for the check to be informative — relevant when the swarm's judges audit DeepSeek/GLM-built tasks and when the 397B becomes the student. Priority P1.
