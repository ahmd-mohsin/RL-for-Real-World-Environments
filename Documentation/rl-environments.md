Frontier labs and startups in San Francisco make proprietary RL environments to make models better at specified tasks. The procedure is as follows. Domain experts use their knowledge to find tasks where LLMs fail. Then they make RL environments that train models on these tasks. After post-training, they make evaluations and benchmarks and show the performance increase of the models on these benchmarks. Then they sell the RL environments, or the data, to the labs.

This method has two problems. First, you cannot increase expert-made RL environments to a large scale. There are not sufficient experts, the work is difficult, and the labs now approach a limit. Second, the startups make RL environments for vertical workflows, because these are easier. A vertical workflow stays in one domain. For example, a startup can make code repositories as RL environments for coding agents only. This method is easier, but it also has a limit. The real agentic workflows occur inside enterprises, and they stay inside enterprises. These workflows are horizontal, because many departments do work on one output. For example, finance, HR, sales, and engineering can all do work on one report. It is very difficult to make these dense horizontal workflows, and it is also difficult to make benchmarks that evaluate them. Each enterprise has thousands of these workflows.
There is one more bottleneck. Data and workflows are different in each enterprise, and this data and these workflows never go out of the enterprise. Thus, RL environment startups such as Patronus AI, Snorkel, Fleet AI, Core Automation, and Prime Intellect can only make workflows that do not copy the real workflows. They can sell these environments to frontier labs, but these environments do not improve the workflow experience inside the enterprise.

To make real workflows inside an enterprise, you must do tests in many domains, and you must have strong horizontal and vertical integration. One solution is that enterprises make their own RL environments. But this is difficult, and it needs many domain experts. Also, the workflows occur inside the enterprise. Thus, we need rubrics that score these workflows. We also need agentic traces from these workflows. Then we can make RL environments that are grounded on these traces.

But this gives a "chicken and egg" problem. We want to give enterprises a "black box" solution. We use the term "black box" because we do not know yet what is inside it. The black box gives an RL environment as output, and the enterprise uses this environment to train its open models to be better at a specified workflow. This solution looks good, but it has caveats. It is not difficult to make an RL environment that is grounded on an agentic workflow in an organization. The real difficulty is to copy the expert signal. This signal must have high quality, so that the model continues to improve itself over many samples. This makes the problem a recursive self-improvement (RSI) problem. We assume that the black box is an LLM with a harness and orchestration around it. The black box must get very useful signals from an agentic workflow in the enterprise. Then it must give an RL environment that improves a model. Thus, a model improves a model, and this is recursive self-improvement.

There are also other factors. Data is the most important factor when we want to improve LLM performance. Frontier labs now put less work into post-training methods, because nothing can replace good data. Thus, there is a risk that we train models on low-quality, AI-generated data ("AI slop"). To decrease this risk, we assume that the black box makes RL rubrics with strong signals. These signals must push the policy to the correct behavior, so that the policy performs well on the benchmark for that specified workflow. If possible, the same black box must also make the evaluation benchmarks.
